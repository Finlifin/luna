# Flurry 演进手记 (119)：连接两段代码的管道工——上下文替换 `~[ a = b ] <expr>` 与变量重绑定

> **阅读指南**：在上一回（第 118 回）中，我们掌握了 `'(...)` 与 `~<...>` 的阶段切换与单洞规则。当我们在编译期把许多独立生成的代码片段组装成一个完整的状态机时，最核心的工作就是**“接水管”**——把一段代码期望的输入端口，连接到当前作用域里的真实运行时变量上。结合 `docs/cmtt/contexts-and-substitution.md`，本篇我们将彻底讲透 CMTT 的 **上下文替换（Context Substitution）**：
> 1. 构造时映射 `'[port = a](...)` 与接入时映射 `~[port = b]<...>` 的方向口诀是什么？
> 2. 为什么 `~[left = right, right = left]<code>` 能够完美交换两个输入，而不会发生顺序覆盖？
> 3. 默认对应（Default Correspondence）、卫生性（Hygiene）与资源所有权检查在替换后是如何协同工作的？

---

## 一、 问题背景：当两段代码的“变量名”对不上，或者撞名了怎么办？

设想我们在写一个网络协议状态机。
- 负责生成“帧头校验”的子模块写了一段开放代码，它期望上下文里有一个名叫 `input` 的字节变量：`< input: u8 |- bool >`；
- 但在我们主状态机循环的函数体里，当前读进来的字节变量名叫 `packet_byte: u8`；
- 更棘手的是，有时候主函数里碰巧也有一个毫不相干的局部变量叫 `input: bool`（表示“是否开启输入流”）。

### 靠“文本同名自动粘合”引发的问题

在传统的非卫生宏或简单的模板替换里，代码拼接完全靠“名字长的一样就自动粘在一起”：

```flurry
-- 如果代码拼接只看变量名字符串
-- 问题 1：子模块叫 input: u8，主函数叫 packet_byte: u8，名字不一样就接不上。
-- 问题 2：主函数里恰好有个同名的 let input: bool = true;
--         结果子模块期望的 input: u8 一头撞上了主函数的 input: bool，当场类型爆炸。
-- 问题 3：如果你想把两个参数 (left, right) 倒过来传给代码片段，
--         按顺序文本替换先把 left 改成 right，再把 right 改成 left，结果两边全重名了。
```

**核心问题**：
我们需要一套像硬件跳线帽（Jumper）一样精确的**上下文替换协议**：既能在关系明确时享受省心的**默认对应**，又能在需要改名、重定向或交换端口时，通过显式替换表 `[ 接口名 = 当前绑定名 ]` 做**同时替换（Simultaneous Substitution）**，而且绝不允许替换操作破坏原有的绑定身份与内存安全。

## 二、 核心机制：一张表看懂四种替换方向与“同时替换”法则

在 Flurry 的 CMTT 语法中（见 `docs/cmtt/contexts-and-substitution.md`），方括号替换表 `[ id = id, ... ]` 可以出现在 **Quote（构造代码）** 和 **Splice（接入代码）** 两个时机，且同时适用于**表达式代码**和我们下一回将要学习的**模式代码**。

怎么一眼分清等号 `=` 左边和右边谁是谁？请牢记这句黄金口诀：

> **💡 核心心智模型：等号左边永远是“代码接口名（对外端口）”，等号右边永远是“当前现场的名字（对内源码绑定 / 外部供应变量）”。**

下面通过对照表，把四种位置的接线方向看得一清二楚：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                 CMTT 上下文替换表 `[ 左侧 = 右侧 ]` 方向全解                 │
│           口诀：【左侧】永远是代码的公开接口端口名，【右侧】永远是当前现场名 │
├────────────────────────┬─────────────────────────┬───────────────────────────┤
│ 1. 表达式 Quote (构造) │  '[port = a](a + b)     │ 把源码内部的绑定 `a`      │
│                        │   ▲       ▲             │ 包装暴露为对外接口 `port` │
│                        │  接口名  源码内绑定     │ (b 仍保持原固定绑定身份)  │
├────────────────────────┼─────────────────────────┼───────────────────────────┤
│ 2. 表达式 Splice (接入)│  ~[port = w]<code>      │ 用当前作用域的变量 `w`    │
│                        │   ▲       ▲             │ 供应给代码的接口端口`port`│
│                        │  接口名  当前供应变量   │                           │
├────────────────────────┼─────────────────────────┼───────────────────────────┤
│ 3. 模式 Quote (构造)   │  '[out = inner]<inner>  │ 把模式内部捕获的 `inner`  │
│                        │   ▲      ▲              │ 包装暴露为导出接口 `out`  │
├────────────────────────┼─────────────────────────┼───────────────────────────┤
│ 4. 模式 Splice (接入)  │  ~[out = found]<pat>    │ 匹配成功时，将模式导出的  │
│                        │   ▲      ▲              │ 接口 `out` 绑定为新变量   │
│                        │  接口名  新引入的变量名 │ `found`                   │
└────────────────────────┴─────────────────────────┴───────────────────────────┘
```

### 端口重定向与无覆盖的“同时交换（Simultaneous Swap）”

更棒的是，替换表 `[ left = right, right = left ]` 中的所有映射是**同时发生（Simultaneous）**的。编译器会一次性解析所有右侧标识符在当前作用域中的真实绑定身份，然后再统一赋给左侧的接口端口，绝不会按从左到右的文本顺序互相覆盖。

让我们通过一段真实的 Flurry 代码，验证端口暴露、重定向与同时交换：

```flurry
use std.prelude.*;

-- 场景 1：构造时用 '[port = a] 暴露端口，接入时用 ~[port = replacement] 重定向
fn redirected(a: i32, b: i32, replacement: i32) -> i32 {
    -- 将表达式中的 a 暴露为可替换接口端口 port，而 b 保持对形参 b 的固定引用
    const code = '[port = a](a + b);

    -- 用 replacement (40) 供应端口 port，加上原有的 b (2)，得到 42。
    ~[port = replacement]<code>
}

-- 场景 2：同时交换两个上下文端口，绝不发生顺序覆盖。
fn swapped(left: i32, right: i32) -> i32 {
    const code: < left: i32, right: i32 |- i32 > = '(left - right);

    -- ✅ 同时替换：接口的 left 拿到外层的 right (10)，
    --              接口的 right 拿到外层的 left (3)，
    --              计算出 10 - 3 == 7。
    ~[left = right, right = left]<code>
}

test {
    println("redirected: {}", redirected(1i32, 2i32, 40i32));
    println("swapped: {}", swapped(3i32, 10i32));
}
```

## 三、 默认对应、模板授权与三大安全防线

你可能会问：“难道每次写 `~<code>`，我都得手写一长串 `[a = a, b = b]` 吗？”
当然不用。只要上下文对应关系是**早已确立且无歧义的**，你直接写 `~<code>` 就能享受丝滑的 **默认对应（Default Correspondence）**。

哪些情况下编译器会自动建立合法的默认对应？
1. **引用时保留的原绑定**：比如在 `fn read_original(value: i32)` 里直接写 `const code = '(value + 1i32);`，`code` 已经记住了形参 `value` 的身份，直接 `~<code>` 即可（哪怕中间又声明了一个同名的 `let value = 100i32;` 也不会篡改它。）；
2. **模板（`template fn`）明确授予的接口绑定**：当模板通过 `quote lambda body: < adjusted: i32 |- i32 >` 向调用者的代码块授予了 `adjusted` 绑定时，模板内部建立了 `let adjusted = ...` 后，直接写 `~<body>` 就能自动对上号。

### 用 `template fn` 体验零样板的默认对应

```flurry
use std.prelude.*;

-- 模板函数：接收一个在 < adjusted: i32 |- i32 > 上下文下编写的代码块 body
template fn with_adjusted(
    value: i32,
    quote lambda body: < adjusted: i32 |- i32 >,
) -> i32 {
    let adjusted = value + 1i32;
    -- ✅ 模板接口已经明确授予了 adjusted，因此无需手写 ~[adjusted = adjusted]<body>。
    ~<body>
}

-- 使用模板实例化出普通函数 doubled：在大括号里直接使用模板授予的 adjusted。
fn doubled use with_adjusted {
    adjusted * 2i32
}

test {
    -- (20 + 1) * 2 == 42
    println("doubled: {}", doubled(20i32));
}
```

与此同时，为了防止上下文替换沦为绕过类型与内存安全的后门，编译器在接线时严格把守着 **三条安全红线**（见 `docs/cmtt/contexts-and-substitution.md`）：

1. **红线 1：替换表右侧只能写标识符（绑定名），不能塞入任意有副作用的表达式。**
   为什么？因为如果允许写 `~[x = produce_side_effect()]<code>`，而 `x` 在 `code` 里出现了三次（比如 `x + x + x`），你是希望 `produce_side_effect()` 执行一次还是三次？为了彻底杜绝这种C宏式的重复求值歧义，CMTT 规定**替换表右侧只能是已经存在的绑定标识符**。如果要先计算表达式，请先老老实实用 `let tmp = produce_side_effect();` 建立运行时绑定，再写 `~[x = tmp]<code>`。
2. **红线 2：凭空捏造的虚拟端口不会仅仅因为外面有个“同名变量”就盲目粘合（除非经由模板授权或显式映射）**，缺失供应或存在歧义时直接拒绝。
3. **红线 3：替换成同一个对象时，必须通过真实的别名与仿射资源检查。**
   你可以把两个输入端口映射到同一个变量 `~[a = x, b = x]<code>`，但如果 `code` 内部先后两次按值移动（Move）并消费了 `a` 和 `b`，接入后的资源检查器会立刻发现同一个 `x` 被消费了两次，直接报错拦截。

让我们看看违反这些红线时的编译期拒绝例：

```flurry
fn produce_number() -> i32 {
    42i32
}

fn broken_substitutions() -> i32 {
    const code: < x: i32 |- i32 > = '(x + x);

    -- 负例 1：企图在替换表右侧直接写函数调用表达式
    -- ❌ 编译期直接拒绝。
    -- 替换表 [id = id] 右侧只能是绑定标识符，不接收任意表达式。
    -- 应先写 let val = produce_number(); 再写 ~[x = val]<code>
    ~[x = produce_number()]<code>
}
```

## 本篇小结

| 替换机制 / 规则 | 语法形式 | 核心语义保证 |
| :--- | :--- | :--- |
| **构造时暴露端口** | `'[port = a](a + b)` | 将内部绑定 `a` 暴露为可替换接口 `port`，其余绑定保持原身份 |
| **接入时同时替换** | `~[left = right, right = left]<code>` | 所有映射同时生效，绝不发生按文本顺序的覆盖污染 |
| **默认对应与模板授权** | `~<code>` / `fn f use tmpl { ... }` | 已锁定的原绑定身份与模板授予的上下文自动对接，免疫同名遮蔽 |
| **右侧仅限标识符 + 资源重检** | `substitution -> id = id` | 杜绝宏参数重复求值副作用；接入后按真实对象身份重跑别名与移动检查 |

### 下一篇预告

到这里，我们已经把 CMTT 的第一类代码值——**表达式代码 `< Ψ |- T >`** 玩得炉火纯青了：它站在上下文 $\Psi$ 的肩膀上，向右计算出结果 $T$。

但是，在写协议解析器或状态机时，光能拼接“表达式”还远远不够。想一想，在 `match` 语句里，箭头 `=>` 左边的 **模式（Pattern）** 才是重头戏：
- 有时候我们要匹配一个区间 `(20u32..100u32) as number`；
- 有时候我们要解构一个元组 `(left, right)` 或枚举变体 `.add(number)`；
- 此外：**模式本身不仅要检查输入值，它还会在匹配成功时“无中生有”地生产出一批新的局部变量（如 `number`、`left`、`right`），交给箭头 `=>` 右边的表达式代码去使用。**

如果我们要在编译期动态拼装模式，该怎么在类型系统里精确描述**“一个模式接收什么主语类型，并在匹配成功后导出哪些新绑定”**？
