# Flurry 演进手记 (178)：Anar 构建调度与编译期脚本——声明式依赖、宏准备与确定性构建缓存

在[上一篇（第 177 篇）](./177-packages-umbrellas-and-architecture-boundaries.md)中，我们理清了 `package`、构建目标、构建实例与 `umbrella` 四层组织边界，以及 `Package(p)` / `Descendants(m)` / `All` 三层可见性体系。

现在，我们要让这座多包工程真正运转起来。
在 Flurry 工具链中，有两个核心角色协同工作：
- **`anar`（包与构建调度器）**：负责解析 `package.fl` 与工作区清单、构建跨包依赖有向无环图（DAG）、按需调度编译期脚本与宏准备任务、管理增量指纹与产物缓存，并向编译器交付版本化的工程输入。
- **`luna`（Flurry 编译器）**：接收 `anar` 准备好的构建实例输入、已注册源码与已就绪的宏接口，执行语言前端检查、编译期求值与后端降码。

今天，我们就来解决大型项目构建中最容易踩坑的三大问题：
1. **配置与代码的职责边界**：`package.fl` 里的配置计算，和业务代码里的 `build` 上下文，到底是谁决定谁？交叉编译时，构建脚本跑在哪个平台上？
2. **按需调度与三阶段分离**：如果一个 `umbrella` 里有 20 个构建脚本，我只编译其中一个小工具目标，`anar` 会把 20 个脚本全跑一遍吗？
3. **宏准备与源码生成的拓扑序**：为什么普通模块之间可以“互相递归引用（Mutual Recursion）”，但宏准备任务与它的消费方解析之间却严格禁止形成循环？

## 一、 传统的构建难题：脚本乱跑、宿主与目标平台混淆、增量缓存失灵

在很多传统构建系统中，开发者经常遭受以下折磨：
- **配置语言与编程语言割裂**：项目配置用一套残缺的 DSL（或者不受控的外部 Shell/Python 脚本）编写，既没法享受静态类型检查，也没法优雅地表达编译期逻辑。
- **发现即执行（Discovery = Execution）**：只要构建系统扫描目录看到了构建脚本，无论当前选定的目标用无须得着，先一股脑全编译、全执行一遍，导致哪怕跑个最小的单元测试也要等半天。
- **交叉编译时的平台前后存在分歧**：在 `x86_64` 开发机上交叉编译 `aarch64` 固件时，构建脚本自己明明需要在宿主机（Host，`x86_64`）上运行，却错误地读取或污染了目标机（Target，`aarch64`）的配置。

## 二、 升级：同构的 Flurry 配置程序与“宿主 vs 目标”双轨分离

在 Flurry 中，无论是包配置文件（`package.fl`）还是构建脚本，写的全都是原汁原味的 Flurry 代码。
例如，在配置层中，我们可以直接用 `pure comptime fn` 表达带静态类型保障的配置逻辑（源自 `docs/code-organization/configuration-and-scripts.md`）：

```flurry
pure comptime fn buffer_limit(debug: bool) -> u32 {
    if debug { 64 } else { 1024 }
}
```

同时，`anar` 严格划清了**两个不同视角的配置接口**以及**两条独立的环境轨道**：

```text
  ┌─────────────────────────────────────────────────────────────────────┐
  │ 1. 配置与调度层 (`package.fl` / `anar` 构建图组装阶段)              │
  │    - 运行在宿主机 (Host Environment)                                │
  │    - 计算依赖版本、特性开关、元数据，为每个目标组装 Build Instance  │
  └──────────────────────────────────┬──────────────────────────────────┘
                                     │ 冻结并交付构建实例配置
                                     ▼
  ┌─────────────────────────────────────────────────────────────────────┐
  │ 2. 受检源码层 (业务 `.fl` 模块，由 `luna` 编译)                     │
  │    - 通过只读的 `build` 上下文观察当前绑定的那一个 Build Instance   │
  │    - 如 `build.target.arch`、`build.package_metadata("cuda")`      │
  └─────────────────────────────────────────────────────────────────────┘
```

> **💡 核心心智模型：切勿混淆“脚本的执行环境（Host）”与“产物的目标平台（Target）”。**
> 当你在 `x86_64` Linux 主机上，为一个 `aarch64` 嵌入式目标运行代码生成脚本或过程宏时：
> - **脚本/宏本身的编译与执行**发生在 **Host（`x86_64`）** 上；
> - **脚本读取的目标参数与它生成的源码将要被编译到的地方**是 **Target（`aarch64`）**。
> `anar` 为这两条轨道分别维护独立的编译任务与指纹，禁止把宿主机架构误当成目标机架构注入给业务代码。

## 三、 拓扑调度：`schedule(selected_targets)` 与三阶段严格分离

当你在命令行要求构建某个具体目标（例如 `selected_targets = [app_cli]`）时，`anar` 的调度器 `schedule(selected_targets)` 遵守两条黄金准则：

### 准则 1：“发现脚本”、“编译脚本”与“执行脚本”三阶段严格分离
`anar` 扫描工程目录树发现某个脚本文件时，**仅仅是在任务图里登记了一个潜在节点**，不会当场编译或执行它。
只有当 `selected_targets` 的反向依赖闭包真正需要某个脚本的产出时，`anar` 才会按拓扑序依次触发：
1. **Discover（发现与声明解析）**；
2. **Compile Script（在 Host 环境编译该脚本及其工具依赖）**；
3. **Execute Script（在受控沙箱中执行脚本，登记生成的源码或产出宏接口）**。

如果 `umbrella` 里的另一个兄弟包 `heavy_gpu_bench` 带有耗时的构建脚本，而你今天只构建 `app_cli`，那么 `heavy_gpu_bench` 的脚本连编译都免于发生。

### 准则 2：宏准备（Macro Preparation）与源码生成的合法拓扑链

让我们看看当一个包使用了**编译期宏**或**源码生成脚本**时，`anar` 与 `luna` 是如何接力调度的：

```text
  [ 链路 A：宏脚本准备链路 ]
  ┌──────────────┐    ┌──────────────┐    ┌───────────────┐    ┌──────────────┐    ┌──────────────┐
  │ 1. 工具依赖包 │───▶│ 2. 编译宏脚本 │───▶│ 3. 交付宏接口  │───▶│ 4. 消费方语法 │───▶│ 5. 消费方语义 │
  │  (Tool Dep)  │    │ (Host Target)│    │(Macro Surface)│    │ 解析 (Parse) │    │ 检查 (Check) │
  └──────────────┘    └──────────────┘    └───────────────┘    └──────────────┘    └──────────────┘

  [ 链路 B：源码生成任务链路 ]
  ┌──────────────────┐    ┌──────────────────────┐    ┌──────────────┐    ┌──────────────┐
  │ 1. 执行生成脚本   │───▶│ 2. 显式登记生成的源码 │───▶│ 3. 统一纳入  │───▶│ 4. 统一进入  │
  │(Generation Task) │    │ (Registered Source)  │    │ 模块树 Parse │    │ Elaboration  │
  └──────────────────┘    └──────────────────────┘    └──────────────┘    └──────────────┘
```

请注意链路 B 中的关键细节：**生成脚本产出的 `.fl` 源文件，必须通过构建接口显式登记（Registered Source），然后和手写源文件一样，走完全相同的语法解析与类型检查流程。** 禁止生成脚本绕过模块树直接往编译器后端塞未受检的私有结构。

## 四、 反例警告：为什么“模块互相调用”合法，而“宏准备循环依赖”直接报错？

很多初学者会问：在 Flurry 的同一个包里，模块 `a` 调用模块 `b` 的函数，模块 `b` 调用模块 `a` 的函数（静态模块互递归），是完全合法的。
那如果模块 `consumer` 的语法解析依赖宏脚本 `macro_gen`，而编译 `macro_gen` 又反过来依赖 `consumer` 解析完成后的结果，行不行？

**不行。这在拓扑调度上是一个不可解的死锁环（Unresolvable Execution Cycle）。**

```flurry
-- ❌ 编译期 / 构建调度期直接报错。
-- 试图构造“先有鸡还是先有蛋”的跨阶段执行环：
--
--   consumer 模块 Parse ──(需要展开宏)──▶ macro_script 编译与准备
--          ▲                                      │
--          └────────(依赖 consumer 的定义)────────┘
--
-- 构建调度器 (anar) 直接报错（Cyclic Task Dependency Error）：
-- 静态声明之间的互递归之所以合法，是因为两边的语法树都已经存在，可以同时收集签名；
-- 但 `consumer parse -> macro script prep -> same consumer parse` 是跨阶段的执行依赖环：
-- 不准备好 macro_script 就无法完成 consumer 的解析展开，而不完成 consumer 的解析就无法编译 macro_script。
```

## 五、 确定性构建缓存：什么会让增量指纹（Fingerprint）失效？

为了做到“改一处，只重编最小受影响子图，且不漏编”，`anar` 为每个构建任务计算确定性的缓存指纹。以下任何一个维度的变化，都会精准触发对应任务的缓存失效与重算：
1. **源码与配置输入**：源文件文本内容、`package.fl` 配置求值结果、绑定的 `build` 实例参数；
2. **目录与模块布局**：影响模块发现或脚本登记的文件增删与重命名；
3. **宏与生成接口指纹**：上游宏包导出的宏签名/实现变更，或源码生成脚本产出的文件内容变更；
4. **Host / Target 环境元数据**：编译器版本、宿主机工具链标识、目标平台架构（`arch`）、指令集特性（`features`）与包级元数据（`package_metadata`）。

只有当上述所有指纹严丝合缝，且落盘产物经校验完好无损时，`anar` 才会直接复用缓存结果。

## 本篇小结

| 协作与调度维度 | `anar` 与 `luna` 的机制设计 | 解决的工程问题 |
| :--- | :--- | :--- |
| **职责分工** | `anar` 管包、依赖图、任务调度与缓存；`luna` 管语法、类型、编译期求值与降码 | 构建调度与语言语义解耦，通过版本化输入/输出/错误契约清晰交接 |
| **Host vs Target 双轨** | 脚本/宏在 Host 环境编译运行；生成的源码与业务目标按 Target 实例编译 | 解决交叉编译时“把宿主机配置误当成目标机配置”的平台错乱 |
| **三阶段分离与按需调度** | `schedule(selected_targets)` 仅调度可达任务；区分发现、编译与执行脚本 | 避免一上来把工作区里无关子包的构建脚本全部编译运行一遍 |
| **宏准备与生成链路** | 宏接口就绪后才进入消费方 Parse；生成源码登记后走正规前端流水线 | 避免未登记幽灵文件与跨阶段循环死锁（`consumer parse <-> macro prep`） |
| **多维确定性指纹** | 覆盖源码、配置、目录布局、宏接口与 Host/Target 元数据 | 增量构建既快又稳，不因为改了 `package.fl` 或目标特性而漏编 |
