# Flurry 演进手记 (182)：函数调用中的双向类型推导——兄弟参数约束、外层期望类型与求值顺序保证

在[上一篇（第 181 篇）](./181-why-all-flurry-irs-dump-as-lisp-s-expressions.md)中，我们学习了如何利用 `'type` 视图与布局查询在编译期自检类型结构。

在日常编写高阶函数与泛型代码时，我们经常写出下面这样自然简洁的调用：

```flurry
fn apply_first(step: fn(T) -> R, value: T) -> R
where
    T: Type,
    R: Type
{
    step(value)
}

const RESULT: i32 = apply_first(|item| item + 1, 41i32);
```

仔细观察 `apply_first(|item| item + 1, 41i32)` 这一行代码：
- 第一个实参是一个没有标注参数类型的匿名函数 `|item| item + 1`；
- 第二个实参是一个类型明确的整数字面量 `41i32`。

在阅读这行代码时，我们很容易理解：既然第二个形参 `value: T` 传入了 `41i32`，那么泛型参数 `T` 就是 `i32`；既然 `T` 是 `i32`，第一个形参 `step: fn(T) -> R` 接收的 `item` 自然也是 `i32`，因此 `item + 1` 合法且返回 `i32`。

这背后蕴含着 Flurry 函数调用的两条重要语义契约：
1. **编译期双向与兄弟参数联合推导**：同一调用中的外层期望类型、被调用函数签名与所有兄弟实参共同参与类型推导，不受“必须把参数顺序反过来写”的限制；
2. **运行时严格保持从左到右求值**：编译期跨参数传递类型信息，绝不会改变运行时的实参求值顺序。

---

## 一、 双向类型流与兄弟参数联合约束

在 Flurry 中，当检查一次函数调用时，三股类型信息会汇合到一起：
1. **被调用者签名（Callee Signature）**：声明形参之间的关联关系（如 `step: fn(T) -> R` 与 `value: T` 共享同一个类型参数 `T`）；
2. **外层期望类型（Expected Type）**：例如 `const RESULT: i32 = ...` 从外向内限定返回类型 `R == i32`；
3. **兄弟实参（Sibling Arguments）**：第二个实参 `41i32` 确定了 `T == i32`，这一约束直接流入第一个实参 `|item| item + 1`，使 `item` 获得具体类型 `i32`。

```text
                     外层期望类型: i32
                          │
                          ▼ (限定返回类型 R = i32)
               ┌──────────────────────┐
               │  apply_first 调用契约 │
               │  T = i32, R = i32    │
               └──────────────────────┘
                /                    \
   (流入输入类型 T = i32)         (由实参确定 T = i32)
              ▼                        \
   实参 1: |item| item + 1            实参 2: 41i32
   在 item: i32 下检查 item + 1
```

因此，无论你把闭包放在第一个参数 `apply_first(|item| item + 1, 41i32)`，还是放在最后一个参数，都不需要冗余地手写 `|item: i32| item + 1`。

## 二、 编译期类型信息流不改变运行时求值顺序

有人可能会问：**“既然编译期先利用了第二个实参 `41i32` 的类型来检查第一个实参，那么在程序运行时，会不会先求值第二个实参、再求值第一个实参？”**

**绝不会。** 在 Flurry（见 `docs/functions/calls-and-returns.md`）中，编译期类型推导方向与运行时求值顺序是完全解耦的：

```flurry
fn produce_arg() -> i32 {
    41i32
}

fn demo() -> i32 {
    -- 编译期：两边共同确定 T = i32, R = i32
    -- 运行时：严格按源码从左到右的顺序，先构造第 1 个实参，再调用第 2 个实参 produce_arg()。
    apply_first(|item| item + 1, produce_arg())
}
```

运行时调用始终遵守以下四条确定性求值规则：
1. **显式实参按源码从左到右求值**：左边的实参表达式必定在右边的实参表达式之前完成求值，且每个显式实参在运行时精确求值一次；
2. **前向依赖的默认参数按序补齐**：未显式传入的可选参数，在它所依赖的前序参数绑定完成后求值；
3. **中途失败立即按逆序清理已求值实参**：如果第 2 个实参通过 `!Err` 短路返回错误，第 1 个已经求值完成的仿射实参会立即按逆序执行 `Drop` 析构。

## 三、 调用点类型推导 vs 定义点刚性泛型参数

理解了调用点的类型推导后，需要注意区分**调用点推导（Call-Site Inference）**与**定义点泛型契约（Definition-Site Generic Contract）**：

```text
  [ 调用点 (Call Site) ]                         [ 定义点 (Definition Site) ]
  apply_first(|item| item + 1, 41i32)           fn invalid_increment(value: T) -> T
                                                where T: Type {
                                                    value + 1
                                                }
  职责：为本次具体调用找到满足签名的 T             职责：证明对【任意合法的 T】函数体都成立。
  由实参 41i32 推导出 T = i32 -> ✅ 合法         不能因为函数体写了 + 1 就把 T 缩窄为 i32 -> ❌ 拒绝。
```

当你在函数定义头写下 `fn invalid_increment(value: T) -> T where T: Type` 时，你声明的是：**“对于调用者传入的任意类型 `T`，函数体都必须成立。”**
在没有声明算术 Trait 约束的情况下，随意的类型 `T`（比如一个结构体或布尔值）并不支持 `+ 1` 运算。因此类型检查器绝不会在定义点自作主张把泛型参数 `T` 猜成 `i32`。

## 四、 拒绝例：缺少约束的泛型定义与无法唯一确定的调用

让我们通过两个拒绝例，看看违反上述边界时的编译期诊断行为。

### 拒绝例 1：在无约束的泛型参数上直接执行算术运算

```flurry
fn invalid_increment(value: T) -> T
where
    T: Type
{
    -- ❌ 编译期拒绝：T 是未加算术约束的泛型类型参数，不能对其直接执行 + 1
    value + 1
}
```

### 拒绝例 2：调用点既无实参约束、也无外层期望类型导致类型未决

如果一个泛型函数的返回类型参数 `R` 既不出现在任何输入实参中，调用点也没有通过变量类型注解或外层上下文指明 `R`，类型检查器会报告类型未决错误，而不会随意猜测默认类型：

```flurry
fn default_value() -> R
where
    R: Type
{
    ...
}

fn ambiguous_caller() {
    -- ❌ 编译期拒绝：既无输入实参决定 R，也无外层类型注解约束 R，类型推导无法唯一确定 R
    let _ = default_value();
}
```

只需补充显式类型注解（如 `let x: i32 = default_value();`），即可提供明确的外层期望类型。

## 五、 本篇小结

| 维度 | 核心规则 | 对开发者的意义 |
| :--- | :--- | :--- |
| **兄弟参数联合推导** | 同一调用中的具体实参（如 `41i32`）可为同调用中的闭包实参（`\|item\| ...`）提供类型 | 闭包与高阶函数调用无需冗余标注参数类型，参数顺序设计更自由 |
| **外层期望类型传导** | 变量注解、返回类型与结构体字段类型从外向内约束调用结果类型 | 字面量、枚举变体 `.variant` 与泛型返回值可自然适配上下文 |
| **源码顺序求值保证** | 编译期跨参数推导绝不重排运行时的从左到右实参求值顺序 | 有副作用的实参调用与错误回滚边界始终可预测 |
| **定义点泛型刚性** | 定义点的 `where T: Type` 必须凭显式约束使用，不能靠函数体反向缩小 `T` | 保证泛型函数在定义时即完成完整的契约验证 |
