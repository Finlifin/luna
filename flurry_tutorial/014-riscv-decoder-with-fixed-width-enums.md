# Flurry 演进手记 (014)：手写 RISC-V 指令解码器——32 位定宽 `enum` 的互斥性与覆盖性证明

在 [上一篇 (013)](./013-enum-grouped-variants-and-tag-names.md) 的结尾，我们接到了一个极具系统编程魅力的任务：为传感器板载的 **32 位 RISC-V 协处理器**编写算术指令（以 `ADD` 和 `SUB` 为例）的编码与反汇编解码器。

翻开《RISC-V 非特权指令集架构手册》，32 位 R-Type 整数算术指令的二进制格式是这样规定的（从最高有效位 Bit 31 到最低有效位 Bit 0）：

```text
   31         25 24     20 19     15 14   12 11      7 6           0
  +-------------+---------+---------+-------+---------+-------------+
  |   funct7    |   rs2   |   rs1   |funct3 |   rd    |   opcode    |
  |  (7 bits)   | (5 bits)| (5 bits)|(3bits)| (5 bits)|  (7 bits)   |
  +-------------+---------+---------+-------+---------+-------------+
  |   0000000   |   rs2   |   rs1   |  000  |   rd    |   0110011   | ──► ADD rd, rs1, rs2
  |   0100000   |   rs2   |   rs1   |  000  |   rd    |   0110011   | ──► SUB rd, rs1, rs2
  +-------------+---------+---------+-------+---------+-------------+
     ▲                                  ▲                    ▲
     └────────────── 判别位被三个 5 位寄存器载荷切得七零八落！ ──┘
```

仔细看这张硬件编码表，它的设计对硬件译码器极其友好（寄存器 `rs1`、`rs2`、`rd` 永远固定在相同的比特位置上），但对传统软件程序员来说却有三个头疼点：
1. **判别位碎片化**：决定一条指令是不是 `ADD` 或 `SUB` 的固定比特，分散在 `31..25`（7 位）、`14..12`（3 位）和 `6..0`（7 位）三个不连续的区间里，中间隔着 `rs2`、`rs1` 和 `rd`。
2. **字段顺序与汇编语法倒挂**：在二进制机器码里，三个寄存器的从高到低顺序是 **`rs2`、`rs1`、`rd`**；但在人类阅读的汇编语言 `ADD x1, x2, x3`（代表 `x1 = x2 + x3`）里，打印顺序却是 **`rd`、`rs1`、`rs2`**！
3. **零额外内存开销要求**：如果我们要在模拟器或即时编译器（JIT）里用 `enum ArithmeticInstruction` 表示一条指令，它的大小**必须严格等于 `u32`（4 字节）**，绝不能像普通枚举那样多塞一个 tag 字节变成 8 字节！

让我们看看在 Flurry 中，如何把这张 PDF 手册里的表格原封不动地变成受编译器数学证明保护的代码。

## 第一版：传统移位与掩码的苦力活（v0）

如果我们沿用 C 语言或传统系统语言的套路，手写掩码（Mask）和移位（Shift）或者手动切 `BitVec` 下标，写出来的 `v0` 解码器大概是这样的：

```flurry
use std.prelude.*;

-- v0：手动按 LSB 下标切分各个位段并逐一比对
fn describe_instruction_v0(word: u32) {
    let bits = word'bitvec;
    let opcode = bits[0..7];
    let rd     = bits[7..12];
    let funct3 = bits[12..15];
    let rs1    = bits[15..20];
    let rs2    = bits[20..25];
    let funct7 = bits[25..32];

    if opcode == 0b0110011 and funct3 == 0b000 {
        if funct7 == 0b0000000 {
            println("ADD x{}, x{}, x{}", rd.as(u32), rs1.as(u32), rs2.as(u32));
        } else if funct7 == 0b0100000 {
            println("SUB x{}, x{}, x{}", rd.as(u32), rs1.as(u32), rs2.as(u32));
        } else {
            println("not an ADD/SUB encoding");
        }
    } else {
        println("not an ADD/SUB encoding");
    }
}
```

看看 `v0` 里的六行切片：`bits[0..7]`、`bits[7..12]`、`bits[12..15]`、`bits[15..20]`、`bits[20..25]`、`bits[25..32]`。
- 不仅方向跟手册表格从左到右（`31..0`）完全相反；
- 万一你在写 `rs1` 和 `rs2` 时把 `15..20` 和 `20..25` 搞反了，编译器根本不可能替你发现——因为它们都是 5 比特宽，类型一模一样！
- 更糟的是，这只是一段命令式 `if-else`，你依然没有得到一个 4 字节大小的类型 `ArithmeticInstruction`。

## 第二版：把 RISC-V 手册直接抄成定宽 `enum`（v1）

现在，让我们请出 Flurry 的定宽模式枚举（详见 `docs/type/user-defined-types/fixed-width-enum-example.md`）。

在 Flurry 中，当你在 `enum` 内部配置了 **`.base_type u32`** 和 **`.discrete_tag true`** 后，每个变体都可以直接用一个 32 位的位向量模式来定义！
而且，那三个 5 比特宽的寄存器编号，可以直接用 5 位无符号整数类型 **`u5`**（或在早期仅接入位向量的环境中使用等价宽度的 `BitVec<5>`）作为命名载荷段 `(rs2: u5)`、`(rs1: u5)`、`(rd: u5)` 嵌在模式中间！

来看看 `v1` 的定义有多么震撼：

```flurry
use std.prelude.*;

enum ArithmeticInstruction {
    .base_type u32,
    .discrete_tag true,

    -- 直接从最高位 (Bit 31) 到最低位 (Bit 0) 照抄 RISC-V 手册表格！
    -- 宽度自动核验：7 + 5 + 5 + 3 + 5 + 7 = 32 bits！
    add: 0b0000000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011,
    sub: 0b0100000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011,
}

-- 用编译期契约断言验证：整个 enum 的物理大小严格等于一个 u32（4 字节）！
comptime {
    assumes Type.size_of(ArithmeticInstruction) == Type.size_of(u32);
}
```

让我们画一张 **Code Cartoon**，把 RISC-V 指令格式与 Flurry 的 `enum ArithmeticInstruction` 放在一起对照：

```text
  RISC-V 手册表格:   | funct7(7) |  rs2(5)   |  rs1(5)   |f3(3)|   rd(5)   |opcode(7)|
                    ├───────────┼───────────┼───────────┼─────┼───────────┼─────────┤
  Flurry 模式声明:   0b 0000000   (rs2: u5)   (rs1: u5)   000   (rd: u5)    0110011
                       └─┬───┘   └───┬───┘   └───┬───┘   └─┬─┘  └───┬───┘   └──┬────┘
                     固定判别段   载荷字段1   载荷字段2  固定段  载荷字段3  固定判别段
                     (7 bits)    (5 bits)    (5 bits)   (3b)    (5 bits)   (7 bits)
                    ◄─────────────────── 合计严格等于 32 bits (u32) ────────────────►
```

> **🔍 语法小贴士：同一个 `0b` 前缀管辖整条位向量模式！**
> 仔细看 `0b0000000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011`：
> 你只需要在最开头写**一个 `0b`**！后面的 `000` 和 `0110011` 虽然中间被 `(rs2: u5)` 等绑定段隔开了，但因为它们同属一条 `bit_vec_bin_pattern`（语法产生式为 `0b segment+`），编译器在分析阶段会自动溯源回源码字形，把中间的 `000`（3 位二进制）和末尾的 `0110011`（7 位二进制）统统按 `0b` 二进制精确解释，绝不会把 `0110011` 误当成十进制的十一万零一十一！

### 在原始 `u32` 指令字上直接匹配并重排寄存器

接下来，我们要写一个接收任意原始 32 位机器字 `word: u32` 的反汇编打印函数 `describe_instruction(word: u32)`。

请注意一个极其重要的语义区分：
- 在 `enum ArithmeticInstruction` **声明内部**，因为配置了 `.base_type u32`，变体模式享有 base type 豁免，直接作用于 32 位表示；
- 但在**普通函数里**，参数 `word` 只是一个普通的 `u32` 整数！对普通整数做位向量模式匹配时，**必须显式通过 `'bitvec` 取得它的位视图 `word'bitvec`**，并且因为任意 `u32` 可能是 `0x00000000` 等非 `ADD`/`SUB` 指令，必须保留 `_` 兜底分支！

```flurry
fn describe_instruction(word: u32) {
    word'bitvec match {
        0b0000000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011 => {
            -- 编码里从高到低是 rs2, rs1, rd；
            -- 打印时靠绑定名字直接按 rd, rs1, rs2 顺序输出，零心智负担！
            println("ADD x{}, x{}, x{}",
                rd.as(u32), rs1.as(u32), rs2.as(u32));
        },
        0b0100000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011 => {
            println("SUB x{}, x{}, x{}",
                rd.as(u32), rs1.as(u32), rs2.as(u32));
        },
        _ => println("not an ADD/SUB encoding"),
    }
}

test {
    -- 0x003100b3 正是 ADD x1, x2, x3 的机器码！
    describe_instruction(0x003100b3);
    -- 0x403100b3 正是 SUB x1, x2, x3 的机器码（Bit 30 为 1）！
    describe_instruction(0x403100b3);
    -- 0x00000000 是全零非法指令，落入兜底分支！
    describe_instruction(0x00000000);
}
```

运行结果干净漂亮：

```text
ADD x1, x2, x3
SUB x1, x2, x3
not an ADD/SUB encoding
```

## 第三版：钻进编译器内部——不用遍历 $2^{32}$ 个数，如何一秒证明互斥？（v2）

现在，让我们揭开本篇最硬核的悬念：
当你在 `enum ArithmeticInstruction` 里写下 `add` 和 `sub` 两个 32 位模式时，Flurry 编译器必须强制验证两件事：
1. **宽度合法性**：每一段宽度之和是否恰好等于 `u32` 的 32 位？
2. **变体互斥性（Disjointness）**：由于 `.discrete_tag true` 没有额外分配 tag，编译器必须 100% 确认——**宇宙中绝对不存在任何一个 32 位整数，既能匹配 `add`，又能匹配 `sub`！**

如果让你写一个检查器去证明两个 32 位模式不相交，甚至以后面对 64 位、128 位指令时不相交，难道要写个循环从 `0` 跑到 `4294967295`（$2^{32}-1$）去暴力穷举吗？

当然不！Flurry 编译器内部使用了一套极其优雅的**位向量掩码代数（BitVec Mask Algebra）**。
让我们画一张 **Code Cartoon**，看看编译器是如何把 `add` 和 `sub` 编译成掩码四元组的：

```text
  对于每一个定宽位模式，编译器提取两个 32 位常数：
  1. 掩码 M (Mask)：固定字面段的位置填 1，载荷变量段 (rs2, rs1, rd) 的位置填 0。
  2. 目标值 V (Value)：固定字面段填模式要求的 0/1 值，载荷位置填 0。

  Bit:     31..25 (7b)   24..20   19..15  14..12  11..7    6..0 (7b)
          ┌───────────┬─────────┬─────────┬─────┬─────────┬───────────┐
  M_ADD : │  1111111  │  00000  │  00000  │ 111 │  00000  │  1111111  │ = 0xfe00707f
  M_SUB : │  1111111  │  00000  │  00000  │ 111 │  00000  │  1111111  │ = 0xfe00707f
          ├───────────┼─────────┼─────────┼─────┼─────────┼───────────┤
  V_ADD : │  0000000  │  00000  │  00000  │ 000 │  00000  │  0110011  │ = 0x00000033
  V_SUB : │  0100000  │  00000  │  00000  │ 000 │  00000  │  0110011  │ = 0x40000033
          └─────▲─────┴─────────┴─────────┴─────┴─────────┴───────────┘
                │
         注意 Bit 30：V_ADD 要求为 0，V_SUB 要求为 1！
```

有了 $(M_1, V_1)$ 和 $(M_2, V_2)$，一个 32 位机器字 `word` 匹配 `add` 的充要条件就是：
$$(word \text{ AND } M_{\text{ADD}}) == V_{\text{ADD}}$$

那么，`add` 和 `sub` 两个变体要想**互斥（不可能同时匹配同一个 `word`）**，充要条件是什么？
那就是：**在两个变体都规定了固定比特的共同关切位（$M_{\text{ADD}} \text{ AND } M_{\text{SUB}}$）上，至少存在一个比特位，使得 $V_{\text{ADD}}$ 和 $V_{\text{SUB}}$ 的要求截然相反（即 `XOR` 不为 0）！**

于是，编译器只需要算一次极其轻量级的位运算公式：

```text
  互斥证明公式：
  Conflict = (V_ADD XOR V_SUB) AND (M_ADD AND M_SUB)
           = (0x00000033 XOR 0x40000033) AND 0xfe00707f
           = 0x40000000  (≠ 0，在 Bit 30 上发生确定性冲突！)
```

因为结果 `0x40000000 != 0`，编译器连一次循环都不用跑，在纳秒级时间内就完成了数学铁证：**`add` 与 `sub` 在 Bit 30 上绝对互斥！**

### 试试挑战编译器的底线：宽度错误与编码冲突

如果我们故意在定义 `ArithmeticInstruction` 时犯两个硬件开发中常见的手滑错误，会发生什么？

```flurry
-- ❌ 编译期直接拒绝 1：宽度不匹配（33 bits != 32 bits）
enum BadWidthInstruction {
    .base_type u32,
    .discrete_tag true,
    -- 手滑把 rd 的类型写成了 u6（6 比特），总宽度变成 7+5+5+3+6+7 = 33 位！
    add: 0b0000000 (rs2: u5) (rs1: u5) 000 (rd: u6) 0110011,
}

-- ❌ 编译期直接拒绝 2：变体编码重叠（Conflict == 0，不互斥！）
enum OverlappingInstruction {
    .base_type u32,
    .discrete_tag true,
    add: 0b0000000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011,
    -- 复制粘贴 sub 时忘了把开头的 0000000 改成 0100000！
    sub: 0b0000000 (rs2: u5) (rs1: u5) 000 (rd: u5) 0110011,
}
```

在第二个错误例子里，编译器算出 `(V_ADD XOR V_SUB) AND (M_ADD AND M_SUB) == 0`，当场抓出像 `0x003100b3` 这样的机器码会同时命中 `add` 和 `sub`，直接拒绝编译！

### 核心心智模型：互斥性（Disjointness） $\neq$ 覆盖性（Exhaustiveness）！

在结束这一篇之前，请务必分清定宽模式验证中两个截然不同的概念（详见 `docs/type/user-defined-types/fixed-width-enum-example.md`）：

1. **互斥性（Disjointness）**：问的是“有没有任何一个 `u32` 会**同时属于两个变体**？”
   - 定义 `.discrete_tag true` 的 `enum ArithmeticInstruction` 时，要求的是**变体之间必须互斥**。
2. **覆盖性 / 穷尽性（Exhaustiveness / Coverage）**：问的是“是不是**每一个 `u32`** 都至少属于其中一个变体？”
   - `ArithmeticInstruction` 的两个变体只占用了 $2^{15}$ 种编码（三个 5 位寄存器的组合），远远没有覆盖全部 $2^{32}$ 个 `u32`（比如全零 `0x00000000` 就不属于 `ArithmeticInstruction`）。
   - 这也是为什么**不能**把一个未经检验的任意 `u32` 直接强转成 `ArithmeticInstruction`，以及为什么在 `describe_instruction(word: u32)` 里对 `word'bitvec` 做 `match` 时，编译器会找出一目了然的反例见证（如 `0x00000000`），强制要求你写上 `_ => ...` 兜底分支！

## 本篇小结

通过手写一个 32 位 RISC-V 算术指令解码器，我们打通了定宽模式枚举的任督二脉：

| 阶段 / 概念 | 核心做法与机制 | 解决的工程问题 |
| :--- | :--- | :--- |
| **v0 手写切片** | `bits[0..7]`、`bits[7..12]` 等命令式切片 | 下标从 LSB 算起反直觉，无法防止同宽寄存器槽互换，无 4 字节名义类型 |
| **v1 定宽指令 `enum`** | `.base_type u32` + `.discrete_tag true` + 多段 `0b...` 模式 | 从 MSB 到 LSB 直接对应 RISC-V 手册，零额外 tag 空间开销（`size_of == 4`），按绑定名重排 `rd, rs1, rs2` |
| **v2 掩码互斥证明** | `(V1 XOR V2) AND (M1 AND M2) != 0` | 无需枚举 $2^{32}$ 个值即可在编译期秒证变体互斥，并严格区分变体互斥性与 `u32` 全域覆盖性 |

### 留给下一篇的悬念

到现在为止，无论是第 001 篇的 8 位传感器包（`.base_type u8`），还是本篇的 32 位 RISC-V 指令（`.base_type u32`），都有一个共同的前提：**每一个枚举实例的比特总宽度都是固定不变的，且恰好等于单个 `.base_type` 元素的宽度！**

但是，真实世界的通信协议和文本编码并不总是这么整齐划一！
假设现在传感器网关要通过串口发送一段包含多国语言告警文本的 **UTF-8 字节流**（或者一种变长压缩的传感器遥测帧）：
- 英文字符（ASCII）只占 **1 个 `u8` 字节**（以 `0b0` 开头，后跟 7 位载荷）；
- 拉丁扩展字符占 **2 个 `u8` 字节**（第 1 字节以 `0b110` 开头，第 2 字节以 `0b10` 开头）；
- 汉字占 **3 个 `u8` 字节**（`0b1110... 10... 10...`）；
- Emoji 表情占 **4 个 `u8` 字节**（`0b11110... 10... 10... 10...`）！

如果 `.base_type` 是 `u8`（8 比特），而四个变体的宽度分别是 **8 位、16 位、24 位和 32 位**——难道位向量模式在变长协议面前就失效了吗？
