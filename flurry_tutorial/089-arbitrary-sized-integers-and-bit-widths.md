# 089 — 任意位宽整数（Arbitrary-Sized Integers）：从 `u4`、`i24` 到位表示契约

> **阅读指南**：在上一回（第 088 回）结束时，我们提出了一个直击系统编程灵魂的问题：当我们在处理硬件寄存器、4-bit 量化大模型权重、5-bit RGB565 颜色通道或 24-bit 无损音频采样时，为什么传统语言只给我们 `u8`、`u16`、`u32`、`u64` 这几种 2 的幂次字节宽度？在 Flurry 中，当我们写下 `u4`、`u5` 或 `i24` 时，它的**逻辑位表示宽度（Representation Bit-Width）**与**物理内存存储字节数（Storage Byte Size）**之间遵循怎样的契约？为什么一个单独存放的 `u5` 哪怕占了 1 个字节的内存，也绝不会悄悄退化成 `u8`？本篇我们将结合 `primitives.md` 与 `bitvec-algebra.md`，彻底理清任意位宽整数与位向量的表示契约。

---

## 一、 痛点：被 `u8` 绑架的“非整字节”世界

假设我们在编写一个嵌入式图形驱动或二进制协议打包器，需要处理经典的 16 位 **RGB565** 像素格式：
- 红色通道（Red）占 **5 比特**（取值范围 `0..=31`）；
- 绿色通道（Green）占 **6 比特**（取值范围 `0..=63`）；
- 蓝色通道（Blue）占 **5 比特**（取值范围 `0..=31`）。

### 尝试 `v0`：用 `u8` 假装成 5-bit / 6-bit 整数

在只有 `u8`、`u16` 的传统语言里，我们只能拿 `u8` 来凑合表示这三个通道：

```flurry
-- 尝试 v0：全部用 u8 代替 5-bit 和 6-bit 通道
-- 隐患 1：类型签名完全丢失了“红蓝是 5 位、绿是 6 位”的精确信息！
-- 隐患 2：调用者完全可以传一个 red = 200 进来，类型系统毫无察觉！
-- 隐患 3：取 'bitvec 时，u8'bitvec 是 8 位宽，直接拼接会拼出 24 位而不是 16 位！
```

你看，一旦用 `u8` 假装 `u5`：
1. **值域契约失守**：`u5` 的合法无符号值域是 $0 \le x < 2^5$（即 `0..=31`），而 `u8` 允许 `0..=255`。如果调用者传入 `42`，编译器根本拦不住，到了位拼接时就会把多出来的高位脏比特踩进相邻的通道里！
2. **位拼接宽度失真**：在 Flurry 的位向量代数（`BitVec<N>`）中，拼接操作符 `a ++ b` 的结果宽度严格等于两侧位宽之和 `m + n`。如果红、绿、蓝都是 `u8`，它们的 `'bitvec` 视图就都是 `BitVec<8>`，拼起来直接变成了 `BitVec<24>`，你还得手动去切掉高 3 位和高 2 位，既啰嗦又容易切错端点！

## 二、 破局（v1）：精确到每一个比特的位表示宽度

在 Flurry 中，整数与位向量的位宽不必被 8 的倍数绑架。除了常用的 `i8`/`u8`、`i16`/`u16`、`i32`/`u32`、`i64`/`u64`、`i128`/`u128` 和 `isize`/`usize` 外，任意位宽整数（如 `u4`、`u5`、`u6`、`i24`）与定宽位向量 `BitVec<N>` 共享一条最核心的铁律：

> **💡 核心心智模型：位表示宽度（Representation Bit-Width） $\neq$ 物理存储字节数（Storage Byte Size）**
> 正如 `docs/program-synthesis/bitvec-algebra.md` 所明确规定的：
> **“位宽由被观察的位表示决定。例如 `u5` 的位表示是 5 位，不因单独存储可能占用一个字节就变成 8 位。”**

让我们用一张 Code Cartoon 来直观对比“逻辑位表示”与“独立内存存储”的区别：


### 演进到 `v1`：用精确位宽实现零掩码的 RGB565 编解码

有了精确的 5 位与 6 位表示，我们根本不需要手写任何 `<< 11`、`<< 5` 或 `& 0x1F` 掩码，直接用位视图 `'bitvec` 与拼接运算符 `++` 就能写出自文档化、100% 类型安全的 RGB565 打包与解包函数：

```flurry
use std.prelude.*;

-- 演进到 v1：直接用精确位宽组装与拆解 16 位 RGB565 像素
pure fn pack_rgb565(r: BitVec<5>, g: BitVec<6>, b: BitVec<5>) -> u16 {
    -- BitVec<5> ++ BitVec<6> ++ BitVec<5> 的宽度由编译器在 comptime 自动算出：
    -- 5 + 6 + 5 == 16，精确匹配 u16 的 16 位表示！
    (r ++ g ++ b).as(u16)
}

pure fn extract_green(pixel: u16) -> u8 {
    let bits = pixel'bitvec;
    -- 索引 0 是最低有效位（LSB），因此：
    -- [0..5] 是蓝色 (5 bits)
    -- [5..11] 是绿色 (11 - 5 == 6 bits，类型为 BitVec<6>)
    -- [11..16] 是红色 (16 - 11 == 5 bits)
    let green_bits: BitVec<6> = bits[5..11];

    -- 从 6 位向更宽的无符号整数 u8 (8 ≥ 6) 转换是 100% 安全的：
    -- 高端自动补零，按无符号编码交付！
    green_bits.as(u8)
}

test {
    let pixel = pack_rgb565(0b11111, 0b101010, 0b00001);
    let g = extract_green(pixel);
    println("green channel: {}", g);
}
```

> **🔍 语法小贴士：位向量的位序与拼接方向**
> 在 Flurry 的 `BitVec<N>` 中，位序规则非常直观且不随宿主 CPU 的字节序（Endianness）搖摆：
> 1. **索引 `0` 永远是最低有效位（LSB）**，索引增大向高位移动；因此切片 `bits[0..5]` 取的是最低的 5 位。
> 2. **拼接 `a ++ b` 把 `a` 放在高端（High Bits），把 `b` 放在低端（Low Bits）**；这与我们从左到右书写二进制字面量 `0b_RRRRR_GGGGGG_BBBBB` 的阅读顺序完全一致！

## 三、 严格边界：字面量越界、窄化转换与未定义填充（v2）

为了彻底杜绝 C 语言里臭名昭著的“隐式截断（Silent Truncation）”和“读取未初始化内存填充字节（Padding Leak）”，Flurry 为定宽位表示立下了三条不可逾越的红线：

### 红线 1：字面量超出目标位宽，编译期直接拒绝（前导零不改变宽度）

当你把一个整数字面量赋给 `BitVec<5>` 或 `u5` 时，它的数学值必须严格满足 $0 \le \text{value} < 2^5$（即 `0..=31`）。即便你少写了前导零，或者多写了前导零，都不会覆盖目标类型的位宽，更不会授权编译器帮你静默截断高位！

```flurry
fn broken_literal_width() {
    -- ❌ 编译期直接拒绝！
    -- 目标是 BitVec<5>，合法范围是 0..=31。
    -- 32 (0b100000) 需要至少 6 个比特，编译器绝不静默截断成 0！
    let overflow_bits: BitVec<5> = 32;
}
```

### 红线 2：禁止用 `.as(T)` 直接向更窄的位宽转换（必须显式切片！）

在 Flurry 中，从 `BitVec<N>` 向更宽的 `BitVec<M>` 或无符号整数 `uM`（其中 $M \ge N$）执行 `.as(T)`，会自动在高端补零；但是**向更窄的目标直接 `.as(T)` 永远是静态错误**——哪怕当前值在运行期甚至编译期恰好能塞进去也不行！

```flurry
pure fn broken_narrowing_cast(wide: u16) -> u8 {
    let bits: BitVec<16> = wide'bitvec;

    -- ❌ 编译期直接拒绝！
    -- 不能直接把 16 位的 BitVec<16> 通过 .as(u8) 强转成 8 位的 u8！
    -- 编译器不知道你想丢掉高 8 位还是丢掉低 8 位。
    bits.as(u8)
}

-- ✅ 演进到 v2（正确姿势）：必须通过切片显式指明保留哪一段比特！
pure fn explicit_low_byte(wide: u16) -> u8 {
    let bits: BitVec<16> = wide'bitvec;
    -- 显式切出低 8 位 [0..8]，得到 BitVec<8>，再安全转换为 u8
    bits[0..8].as(u8)
}
```

### 红线 3：含有未定义填充（Padding）的聚合体不能直接当成普通 `BitVec` 整体读取

还记得我们在前面图里画的那 3 个 `?` 填充位吗？如果一个结构体字段之间或末尾存在未定义的对齐填充（Padding），它的物理存储字节里就混杂着未初始化的比特。

Flurry 严格规定：**普通 `BitVec<N>` 的每一位都必须是已定义的确定值**。取 `'bitvec` 视图绝不会默默把未定义的填充位补零，因此不能把含未定义填充的对象直接整体读成普通 `BitVec`，而应当观察已经定义的各个字段！

## 本篇小结

| 核心概念 / 操作 | 语义契约 | 编译期安全保证 |
| :--- | :--- | :--- |
| **逻辑位宽 vs. 存储大小** | `u5` 的位表示宽度严格为 5 位（`BitVec<5>`） | 不因独立存储占用 1 字节而退化为 8 位，填充位不混入位表示 |
| **字面量范围检查** | `BitVec<N>` 目标要求 $0 \le \text{val} < 2^N$ | 越界字面量直接报静态错误，绝不静默截断高位 |
| **拓宽转换 `.as(uM)`** | 当 $M \ge N$ 时合法 | 高端自动补零，按无符号编码安全交付 |
| **窄化转换拦截** | 禁止当 $M < N$ 时直接 `.as(T)` | 强制程序员先用切片 `bits[lo..hi]` 显式声明保留哪些位 |

### 留给下一篇的悬念

在这一篇里，我们频繁使用了一个极其顺手的后缀语法：`pixel'bitvec`（取一个值的位向量视图）。回顾前面的章节，我们还见过：
- `value'type`（取一个表达式的类型视图）；
- `Array<'u32, length>`（模式里的具体类型视图）；
- `values'tuple_enumerate`（取元组的带索引枚举视图）；
- 甚至还有契约里的 `x'old`、枚举的 `tag'tag_name`、底层的 `.u8'builtin`……

这个以单引号 `'` 开头的后缀操作 `expr'id`，在 Flurry 中有一个专门的名字：**Take View（取视图机制）**。
