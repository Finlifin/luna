# Flurry 演进手记 (084)：初识命题类型约束（PTC）——定义期符号推理与约束检验

在前面的章节中，我们已经陆续使用过精化类型 `refines { ... }`、编译期谓词 `comptime predicate`、前后置契约 `requires / ensures` 以及类型模式匹配 `T match { ... }`。

在实际工程（例如张量库 `Tensor<T, .dims = s>` 或协议编解码器）中，函数签名往往同时包含多类编译期条件：
- **布尔逻辑组合**：`A and (B or not C)`；
- **编译期算术不等式**：`0 <= index and index + 1 < length`；
- **类型相等与结构分类**：`Type.size_of(T) == 8 and Type.predicates.is_tuple(Itself)`。

为了对这些类型与编译期常量约束进行一致的推理，Flurry 的类型系统采用了一套统一的逻辑约束检验机制——**PTC（Propositional Type Constraints，命题类型约束）**。本篇我们将介绍编译期符号推理与具体常量求值的区别，以及约束检查的四种结果情形。

---

## 一、 问题背景：具体常量求值 vs 定义期符号蕴涵

在编写编译期函数或带约束的泛型接口时，首先需要区分“具体常量求值”和“定义期符号蕴涵证明”这两个概念：

```
  [ 场景 A：具体常量求值 (Concrete Evaluation) ]
  输入已知：index = 2, length = 4
  计算 `0 <= 2 and 2 < 4` ──► 直接归约为布尔常量 `true`。

  [ 场景 B：定义期符号蕴涵证明 (Symbolic Entailment: Γ ⊢ Q) ]
  在函数 `pure comptime fn foo(index: Integer, length: Integer)` 的定义体内：
  `index` 和 `length` 尚未代入具体数值，而是符号参数。
  此时编译器需要验证的是逻辑蕴涵问题：
  “在已知前提集合 Γ 下，能否保证对一切合法输入，目标命题 Q 必然成立？”
```

如果仅依赖调用点代入具体常量后的求值，那么定义端缺失的前提条件（例如函数体用到了 `index + 1 < length`，但签名只写了 `index < length`）就无法在定义阶段被及时发现，也无法从已知条件 `result == index + 1` 和 `index + 1 < length` 自动推导出 `result < length`。

---

## 二、 核心模型：逻辑骨架与领域规则解耦，以及约束检验的四种情形

在 Flurry 中，PTC 专门负责 **`U_1` 编译期与类型层的逻辑命题推理**。它将约束求解分为两层：
1. **外层：命题逻辑层**——处理合取（`and`）、析取（`or`）、否定（`not`）以及从 `where requires`、前置调用 `ensures` 和分支条件中收集到的上下文前提 $\Gamma$。
2. **内层：领域约束规则**——处理特定领域的原子关系，包括线性整数算术、定宽位向量序关系、类型相等性、子类型与 Trait 满足性（我们将在下一篇 `085` 系统梳理这些原子关系）。

当编译器根据当前作用域的已知事实集合 $\Gamma$ 去检验某个目标要求 $Q$（即判断 $\Gamma \vdash Q$）时，结果分为以下四种情形：

```
+-------------------------------------------------------------------------+
|                    逻辑约束检验 (Γ ⊢ Q) 的四种结果情形                    |
+-------------------------------------------------------------------------+
|                                                                         |
|  1. 静态蕴涵成立 (已证明) ──► ✅ 检查通过                                 |
|     • 含义：在前提 Γ 下，目标命题 Q 在逻辑上必然成立。                     |
|                                                                         |
|  2. 存在反例 (前提不足)   ──► ❌ 前提无法保证目标恒成立                    |
|     • 含义：前提 Γ 过弱，存在至少一组满足 Γ 却令 Q 为假的反例。            |
|     • 注意：“存在反例”不等于“证明了 ¬Q 对所有输入都成立”。                |
|                                                                         |
|  3. 暂未决 (超出自动片段) ──► ⚠️ 需显式补充前提或待具体实参代入化简        |
|     • 含义：命题超出了自动线性求解片段（如一般非线性算术）或展开预算。      |
|     • 注意：这是编译器的静态检查状态，不是运行期的第三种布尔真值。          |
|                                                                         |
|  4. 良构性错误 (域错误)   ──► 🚫 命题自身违反了类型域或布局前提            |
|     • 含义：例如对不具备物理内存表示的纯编译期构造查询运行期字节布局。      |
+-------------------------------------------------------------------------+
```

## 三、 实例分析：为什么“存在反例”不等于“对一切输入均错误”？

让我们通过具体代码来理解“静态蕴涵成立”与“存在反例”之间的区别。

在第 080 篇中，当函数入口前提 $\Gamma$ 声明为 `0 <= index and index + 1 < length` 时，内部调用 `checked_index(index + 1, length)` 所需的目标 $Q$（即 `0 <= index + 1 and index + 1 < length`）可以由 $\Gamma$ 直接导出，定义期检查顺利通过。

现在假设在编写 `missing_upper_bound` 时，将入口条件写成了 `0 <= index and index < length`（漏掉了 `+ 1`）：

```flurry
pure comptime fn next_index(index: Integer) -> (result: Integer)
where
    ensures result == index + 1
{
    index + 1
}

pure comptime fn checked_index(index: Integer, length: Integer) -> Integer
where
    requires 0 <= index and index < length
{
    index
}

-- 这里的 requires 只写了 index < length，未保证 index + 1 < length
comptime fn missing_upper_bound(index: Integer, length: Integer) -> Integer
where
    requires 0 <= index and index < length
{
    let step = next_index(index);
    checked_index(step, length)
}
```

分析 `missing_upper_bound` 内部调用 `checked_index(step, length)` 时的约束关系：
- **已知前提 $\Gamma$**：`0 <= index`、`index < length`、`step == index + 1`
- **待证目标 $Q$**：`0 <= step and step < length`（即 `index + 1 < length`）
- **推导分析**：当 `index = 3, length = 4` 时，前提 $\Gamma$（`0 <= 3 and 3 < 4`）成立，但目标 $Q$（`3 + 1 < 4`）为假。因此，仅凭 $\Gamma$ 无法保证 $Q$ 对所有合法输入恒成立（存在边界反例 `index == length - 1`）。

> **说明：“存在反例” $\neq$ 证明了 $\neg Q$**
> $\Gamma \vdash Q$ 存在反例，表示仅凭 $\Gamma$ 不能保证 $Q$ 对**所有**输入都成立；但对于许多具体输入（例如 `index = 2, length = 4`），$Q$ 依然成立。
> - 对于要求定义期完整自洽的函数，定义期检查会直接报告前提不足并给出反例，提示补强 `requires`；
> - 对于阶段化编译期函数 `comptime fn` 的调用，当传入 `missing_upper_bound(2, 4)` 时，代入具体常量后 `2 + 1 < 4` 成立，调用可以通过；而当传入触发边界反例的 `missing_upper_bound(3, 4)` 时，则会在调用点报错拦截。

```flurry
test {
    -- 代入 (2, 4) 时，具体化后的条件 3 < 4 成立，求值结果为 3
    assumes missing_upper_bound(2, 4) == 3;
}
```

而当传入边界反例 `(3, 4)` 时：

```flurry
-- ❌ 编译期拒绝：当 index = 3, length = 4 时，step = 4 违反了 checked_index 的 `step < length`
comptime {
    let boom = missing_upper_bound(3, 4);
}
```

## 四、 非线性约束化简与良构性检查

### 4.1 超出自动线性求解片段的情形

为了保证编译期检查的可终止性与确定性，PTC 的算术推理核心针对的是**线性整数算术**与有界位向量等可判定片段。

如果在符号变量上写出了一般性的**非线性多项式不等式**（例如对未知符号 `value` 和 `limit` 要求证明 `value * value < limit`），在符号阶段无法仅靠线性算术直接消去。需要注意两点：
1. **“暂未决”只是编译期的静态检查状态，不是语言中的第三种布尔值**（Flurry 的 `bool` 类型只有 `true` 和 `false`）。
2. 当调用点传入具体编译期常量时，非线性算术表达式会直接化简为常量比较并完成验证：

```flurry
pure comptime fn checked_square(value: Integer, limit: Integer) -> Integer
where
    requires value * value < limit
{
    value * value
}

test {
    -- 当传入具体常量 (3, 10) 时，3 * 3 < 10 直接化简为常量比较 9 < 10，检查通过
    assumes checked_square(3, 10) == 9;
}
```

### 4.2 约束自身的良构性检查

如果一条约束命题在构造时就违反了被观察对象的良构域（Domain Precondition），例如：
- 将非类型的值传给了只接受 `Type` 的布局查询；
- 对仅存在于编译期、没有运行期物理表示的构造查询目标机器字节布局，

那么在进入真假推理之前，编译器就会直接报告良构性错误。

## 五、 职责边界：PTC 只处理类型与编译期纯值命题

在进入下一篇梳理各类原子约束之前，我们再次明确类型命题与程序状态验证的职责边界：

```
+-------------------------------------------------------------------------+
|                    Flurry 两类静态验证机制的职责边界                      |
+-------------------------------------------------------------------------+
|                                                                         |
|  [ PTC (命题类型约束) ]  <-- 第四卷重点                                   |
|  • 管辖范围：U_1 编译期宇宙、Type 关系、Normal-Form 头、精化类型条件、     |
|              编译期纯算术 (Integer / BitVec)、Trait 与行集合约束。         |
|  • 不涉及：运行期堆内存修改、可变借用状态转移、运行期指针解引用有效性。     |
|                                                                         |
|  ================ [ 编译期类型命题 vs 运行期程序状态验证 ] ================|
|                                                                         |
|  [ 程序验证层 (Program Verification Layer) ] <-- 第三卷重点               |
|  • 管辖范围：U_0 运行期程序状态、内存与资源规格、指针生命周期与分离逻辑。   |
+-------------------------------------------------------------------------+
```

由于 PTC 只处理不可变的编译期项与类型关系，不混入运行期可变内存状态，因此类型检查能够保持确定性与可复用性。

## 六、 本篇小结

| 约束检验结果 | 逻辑含义（针对 $\Gamma \vdash Q$） | 编译器行为与工程应对 |
| :--- | :--- | :--- |
| **静态蕴涵成立** | 从前提 $\Gamma$ 必然推出目标 $Q$ | 检查通过，契约满足 |
| **存在反例** | 存在至少一组满足 $\Gamma$ 但令 $Q$ 为假的反例 | 拒绝不充分的定义期契约（注意：不代表 $\neg Q$ 恒成立） |
| **暂未决** | 超出当前自动可判定片段（如一般非线性算术） | 作为编译期检查状态，要求补充显式前提或在具体化后化简 |
| **良构性错误** | 命题自身违反了类型域或观察前提 | 直接报告良构性错误 |
