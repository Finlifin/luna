## 一、开篇痛点：当子任务遇到未知类型，怎样挂起才不会把整个编译器卡死？

在上一期（第 182 期）中，我们看到 `apply_first(|item| item + 1, 41i32)` 之所以能顺利通过类型检查，是因为第二个实参 `41i32` 确定了 `?T = i32`，并把这个信息传给了第一个实参 `|item| item + 1`。

但是，让我们站在编译器调度器的角度思考一下执行过程：
当编译器开始检查 `apply_first(|item| item + 1, 41i32)` 时，它需要同时推进两个子任务：
- **子任务 A（消费者）**：检查闭包体 `item + 1`，它需要知道 `item` 的类型 `?T` 是什么；
- **子任务 B（生产者）**：检查字面量 `41i32` 并将其与形参类型 `?T` 合一。

当子任务 A 率先启动时，`?T` 还是一个未决的推断变量（Unresolved Inference Cell）。此时子任务 A 走不下去了。

### 初代尝试（`v0`）：粗粒度整树阻塞或忙等待轮询（Busy Polling）

在早期的编译器实现（`v0`）中，处理这种“等待未知变量”通常有两种粗糙的做法：

1. **做法一（整棵父节点阻塞）**：子任务 A 发现 `?T` 未知，直接让整个 `apply_first(...)` 调用进入阻塞状态。结果：因为父节点被挂起了，排在后面的子任务 B（`41i32`）根本连执行的机会都没有！**整个调用直接陷入死锁（Self-Deadlock）！**
2. **做法二（全局忙轮询队列）**：把所有卡住的任务丢进一个大队列里，每走一步就把队列里成百上千个卡住的任务全部拿出来重跑一遍，看看这次能不能跑通。结果：一遇到稍微复杂一点的泛型嵌套，编译时间直接从 $O(N)$ 退化到 $O(N^2)$ 甚至更糟！

更要命的是，如果生产者子任务 B 本身因为编译错误失败了（比如写成了 `apply_first(|item| item + 1, unknown_value)`），消费者子任务 A 如果还在傻傻地等 `?T` 被赋值，就会出现“主因报错之外，挂起队列无法收敛或报出一堆莫名其妙的次生错误”的乱象。

## 二、机制迭代（`v0 -> v1 -> v2`）：从朴素回调到带代数的等待票据（Wait Tickets）

为了做到既精准唤醒、又绝不漏掉更新，Luna 编译器的局部依赖调度器经历了两轮演化。

### 第一次迭代（`v1`）：在推断变量上直接挂载观察者回调列表

`v1` 的思路很直观：每个推断变量 `?T` 维护一个 `watchers: Vec<TaskId>`。当子任务 A 发现 `?T` 未决时，就把自己的 `TaskId` 塞进 `?T.watchers`；等子任务 B 修改了 `?T`，就遍历 `watchers` 唤醒子任务 A。

但 `v1` 在真实的求解器中会遇到三个棘手的 Bug：
1. **观察与注册之间的竞态（Observation-Registration Race）**：子任务 A 在第 1 步读取 `?T` 发现它是版本 0（未决），准备去注册监听；就在注册之前（或者在合一器合并两个变量的瞬间），`?T` 的状态已经变成了版本 1。如果直接把 A 放进等待列表而不复查版本号，A 就会永远睡死过去！
2. **并查集合并（Union-Find Merge）导致监听丢失**：当两个未知的推断变量 `?T0` 和 `?T1` 被合一（`?T0 = ?T1`）时，`?T0` 被重定向到了代表元 `?T1`。如果后续 `?T1` 被赋值为 `i32`，原本挂在 `?T0` 上的等待者如果没被迁移到 `?T1`，就会彻底失联！
3. **重复入队风暴（Duplicate Wakeup Storm）**：一个任务如果同时观察了某一步合一触动的三个子状态，一次提交就会把它往就绪队列（Ready Queue）里重复塞三次。

### 第二次迭代（`v2`，Luna 最终方案）：仅挂起受阻子目标 + 携带代数（Generation）的等待票据

Luna 编译器在 `v2` 中引入了严谨的**局部依赖与等待票据协议（Wait Ticket Protocol）**。

首先，**粒度最小化**：当 `|item| item + 1` 因为 `item` 的类型 `?T0` 未决而无法继续时，编译器**只挂起该闭包体的类型检查子任务**，而外层的 `apply_first` 调用继续推进第二个兄弟实参 `41i32`！

其次，挂起动作必须通过一张结构化的 **等待票据（Wait Ticket）** 完成：

```
  WaitTicket {
      dependency_id: DepId(?T0),       -- 等待的具体依赖身份（推断变量、布局槽、候选集等）
      observed_gen:  Generation(0),    -- 决定挂起时观察到的状态代数（版本号）
      task_id:       TaskId(Closure#1),-- 受阻的子任务 ID
      task_gen:      TaskGen(3),       -- 子任务当前的执行代数（用于去重与防幽灵唤醒）
  }
```

让我们用一张连环漫画图，看看 `apply_first(|item| item + 1, 41i32)` 在局部依赖调度器中的完整生命周期：

```
  时间线    消费者任务 (Task A: 闭包体)         推断变量槽 (?T0)            生产者任务 (Task B: 41i32)
  ------   ---------------------------        ------------------         --------------------------
   t1      读取 ?T0 -> 发现 Unresolved(gen=0)
           生成票据 Blocked(?T0, gen=0)
   t2      向 ?T0 注册票据，并立即复查 gen:     watchers: [Task A]
           当前 gen 仍为 0 -> 确认安全挂起！     state: Unresolved(gen=0)
   t3      (Task A 休眠，不阻塞父调用)                                    检查 41i32 得到类型 i32
   t4                                         state 变为 Known(i32, gen=1) <--- 执行 unify(?T0, i32)
                                              触发 watchers 通知！
   t5      <--- 收到唤醒 (核对 TaskGen 有效)
           重新读取 ?T0 -> 拿到 Known(i32)
           完成 item + 1 检查 -> 产出 i32！
```

## 三、深度法则：无竞态唤醒的六大铁律与精细依赖粒度

在 Luna 编译器的内部实现中，局部依赖图严格遵守以下工程契约：

### 1. 先记录代数、注册后复查（Record-Register-Recheck）

当子任务调用 `register_wait(task, Blocked(dep_id, observed_gen))` 时，调度器会先把 `task` 挂到 `dep_id` 的监听表上，然后**立刻读取一次 `dep_id` 的当前代数 `current_gen`**：
- 如果 `current_gen != observed_gen`（说明在挂起瞬间状态已经推进了），调度器甚至不会让 `task` 真正休眠，而是当场将其重新推入就绪队列（`enqueue_once`）！
- 唤醒后，`task` 绝不盲目相信唤醒消息里附带的旧快照，而是必须重新观察（Re-observe）依赖项的最新状态。

### 2. 并查集代表元合并与失败传播（Representative Forwarding & Failure Propagation）

如果 `?T0` 与另一个未决变量 `?T1` 合一，并且 `?T1` 成为了新的并查集代表元（Representative），合一器会将 `?T0` 上的所有活跃等待票据完整迁移到 `?T1` 名下。

那如果生产者任务**失败**了呢？我们来看这段代码：

```flurry
fn missing_input() -> i32 {
    return apply_first(|item| item + 1, unknown_value); -- ❌ 编译期直接拒绝！
}
```

在这段代码中，第二个实参 `unknown_value` 是一个未声明的标识符。当生产者任务检查 `unknown_value` 失败时：
1. 编译器报告主诊断错误：`cannot find value 'unknown_value' in this scope`；
2. 生产者将推断变量 `?T0` 的状态推进为 **`Failed / Poisoned`（已失败状态，代数 +1）**；
3. 等待在 `?T0` 上的消费者任务 `|item| item + 1` 被立即唤醒，它观察到 `?T0` 处于 `Failed` 状态，于是**静默级联取消自身（Cascade Cancel）**并清理等待注册——既不会永远挂在半空中导致编译器卡死，也不会再额外报出一个虚假的“闭包参数类型未知”噪音错误！

### 3. 精细的依赖粒度：需要指针大小，绝不等值布局！

局部依赖图的另一个精妙之处在于：**只等待真正需要的最小属性，从而避免伪循环依赖（False Cycles）**。

请看下面这个经典的自引用链表节点定义：

```flurry
struct Link {
    next: ?*Link,
    value: i32,
}

const PTR_BYTES: usize = Type.size_of(*Link);
```

在计算 `Link` 的内存布局和 `PTR_BYTES` 时，如果编译器把“关于 `Link` 的所有信息”混成一个粗粒度的单点依赖，就会瞬间死锁：计算 `Link` 的布局需要知道字段 `next: ?*Link` 的大小，而如果 `*Link` 又去等待 `Link` 的完整布局完成，就构成了死循环！

在 Luna 的局部依赖图中，类型属性被拆分为独立的细粒度依赖键（Dependency Keys）：
- `TypeHead(Link)`：`Link` 是一个结构体类型头；
- `PointerLayout(*Link)`：指针类型的大小与对齐只取决于目标平台的地址宽度（例如 64 位平台上固定为 8 字节），它只需要知道 `Link` 是一个合法的类型头，**完全不需要等待 `Link` 内部字段的值布局（`ValueLayout(Link)`）计算完成**！

```
  [ 细粒度局部依赖图：天然无环！ ]
  PTR_BYTES
     | (依赖)
     v
  SizeOf(*Link)  --------(仅依赖指针表示，无需等待字段布局！)------->  TargetArch.PointerSize (8 bytes)
  
  ValueLayout(Link) -----(依赖字段 1)-----> Layout(?*Link) ---------> TargetArch.PointerSize (8 bytes)
                    \----(依赖字段 2)-----> Layout(i32)    ---------> 4 bytes
```

正因为依赖键被精确到了“类型头 vs 指针大小 vs 完整值布局 vs 候选集版本”，`Link` 和 `PTR_BYTES` 才能丝滑地一次性完成精化。

## 四、边界与编译期拒绝：真实的值级按值无限递归依然会被精准拦截

细粒度依赖消除了指针带来的“伪循环”，但如果程序员真的写出了一个在物理内存中按值无限包含自身的递归结构体，局部依赖图会沿着 `ValueLayout(BadLink) -> ValueLayout(BadLink)` 立即捕获到真实的环路并拒绝编译：

```flurry
struct BadLink {
    -- 注意：这里没有指针 `*`，而是试图在结构体内部直接按值内嵌自身！
    next: BadLink, -- ❌ 编译期直接拒绝！局部依赖图在计算 `ValueLayout(BadLink)` 时检测到真实的自依赖环路（无限大小类型）
    value: i32,
}
```

## 五、本期小结

| 机制组件 | 解决的痛点 | 核心保障 |
| :--- | :--- | :--- |
| **子目标级局部挂起** | 防止单个受阻实参阻塞整个父级调用 | 仅挂起缺少输入的闭包/表达式子任务，兄弟生产者继续执行 |
| **等待票据 (`WaitTicket`)** | 消除观察与注册之间的竞态窗口 | 记录 `observed_gen`，注册后立即复查代数，若已变更则当场入队 |
| **任务代数 (`TaskGen`)** | 防止重复唤醒风暴与过期回调 | 每个任务在同一代数最多在就绪队列中出现一次；任务完成或取消时清理注册 |
| **失败状态传播 (`Failed`)** | 防止上游报错导致下游挂起任务死锁或产生次生噪音 | 生产者报错后将槽位标记为 `Failed`，唤醒下游静默终止 |
| **细粒度依赖键** | 消除自引用指针结构体的伪循环依赖 | 区分 `TypeHead`、`PointerLayout` 与 `ValueLayout`，按需最小订阅 |

到现在为止，我们看到的都是“唯一路径”上的等待与唤醒。但在真实的编译器中，当我们遇到函数重载、泛型特化（如同时存在通用的 `Sample<T>` 和特化的 `Sample<i32>`）或者隐式契约求解时，往往会有**多个候选方案（Candidates）**同时摆在面前。

如果编译器为了试探候选方案 A 是否可行，修改了类型变量 `?T`，结果试探到一半发现方案 A 走不通，该怎么把做过的所有修改干净利落地撤销（Rollback）？如果通用的 `Sample<T>` 已经试探成功了，但更特化的 `Sample<i32>` 因为某个类型变量还没确定而处于 `Pending`（等待中）状态，编译器能不能急吼吼地直接选用 `Sample<T>`？
