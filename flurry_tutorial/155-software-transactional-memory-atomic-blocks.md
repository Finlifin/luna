# Flurry 演进手记 (155)：告别死锁与锁顺序噩梦——atomic(vars) { ... } 软件事务内存（STM）入门

在并发编程的世界里，有一句流传已久的苦涩名言：
**“基于锁（Lock-based）的并发编程本质上是反模块化的——你永远无法把两个各自正确加锁的原子操作，直接组合成一个更大的原子操作！”**

想象一下我们在边缘物联网网关里维护着一个**多通道带宽配额池**：
- 通道 A 的配额存在共享状态 `quota_a` 中，通道 B 的配额存在 `quota_b` 中；
- 当通道 A 发生突发流量时，我们需要从通道 B 临时借调 `100` 单位的配额给通道 A；
- 与此同时，另一个并发监控线程正在执行负载均衡，需要从通道 A 调拨 `50` 单位配额给通道 B。

如果你用传统的互斥锁（`Mutex`）来写：
1. **死锁（Deadlock）陷阱**：线程 1 先锁 `quota_a` 再锁 `quota_b`，线程 2 先锁 `quota_b` 再锁 `quota_a`——两个线程在生产环境迎头相撞，双双永久卡死！
2. **无法组合（Non-composable）**：如果你已经写好了 `deduct(slot, amount)`（内部加锁扣减再解锁）和 `deposit(slot, amount)`（内部加锁增加再解锁），当你先后调用 `deduct(b, 100); deposit(a, 100);` 时，在两步中间的那一瞬间，总配额凭空少了 `100`！其他读取总配额的线程就会看到一个破坏了“总配额守恒”不变量的中间脏状态！

为了彻底终结死锁与不可组合的噩梦，Flurry 在语言核心语法中直接引入了**软件事务内存（Software Transactional Memory, STM）**：
**`atomic(id*) { statement* }` 事务块**与 **`atomic fn` 事务函数**！

今天，我们就来看看如何用数据库事务般的体验，写出零死锁、可自由组合的高并发共享状态更新代码！

## 尝试 v0：细粒度锁的死锁深渊与中间脏状态泄漏

让我们先看看在传统锁模型下，为什么“从 `from_slot` 转账配额到 `to_slot`”这么简单的一个操作会变成并发地雷阵：

```
+-------------------------------------------------------------------------+
|  🎨 Code Cartoon：传统细粒度锁的“AB-BA 死锁”与“中间脏状态”              |
|                                                                         |
|  【噩梦 1：AB-BA 死锁】                                                 |
|    线程 1: transfer(A -> B)              线程 2: transfer(B -> A)       |
|    ────────────────────────              ────────────────────────       |
|    1. 锁住 lock(A) 🔒                    1. 锁住 lock(B) 🔒             |
|    2. 等待 lock(B) ⏳ ─────────┐ ┌───────── 等待 lock(A) ⏳             |
|                                ▼ ▼                                      |
|                        💥 永久互相等待（死锁！）                        |
|                                                                         |
|  【噩梦 2：单独加锁函数无法组合】                                       |
|    deduct(A, 100) [锁A -> 减100 -> 解锁A]                               |
|          │                                                              |
|          ├── 👁️ 此时监控线程读到：A 已减 100，B 还没加 100！总和错了！  |
|          ▼                                                              |
|    deposit(B, 100) [锁B -> 加100 -> 解锁B]                              |
+-------------------------------------------------------------------------+
```

## 演进 v1：`atomic(vars) { ... }`——像数据库事务一样原子更新内存！

在 Flurry 的表面语法（`docs/grammar/syntax`）中，软件事务内存通过两个核心构造呈现：
1. **事务块表达式**：`atomic(id*) { statement* }` —— 在圆括号中列出本次事务涉及的受管共享变量标识，在花括号内编写需要原子执行的语句序列；
2. **事务函数声明**：`atomic fn id(parameter*) (-> result)? clauses? block` —— 声明一个只能在事务上下文中调用並无缝参与外层事务组合的函数！

让我们用 `atomic(...) { ... }` 来重写刚才的配额调拨逻辑：

```flurry
-- 使用 atomic(from_quota, to_quota) { ... } 声明软件事务内存块：
-- 无论多少个工作线程同时正向或反向调拨配额，绝不会发生死锁，
-- 且外部观察者永远只会看到“调拨前”或“调拨全部完成后”的一致状态！
fn transfer_quota(from_quota: *u32, to_quota: *u32, amount: u32) -> bool {
    return atomic(from_quota, to_quota) {
        if from_quota.* < amount {
            -- 余额不足，直接返回 false，未发生任何修改
            return false;
        }
        from_quota.* -= amount;
        to_quota.* += amount;
        return true;
    };
}
```

### 揭秘 STM 的底层引擎：乐观读写日志（Read/Write Log）、冲突验证与自动重试

没有显式加锁，`atomic(from_quota, to_quota) { ... }` 是怎么保证原子性和隔离性的？
答案是**乐观并发控制（Optimistic Concurrency Control）**！让我们用一张 **Code Cartoon** 拆解一次事务块执行的生命周期：

```
+-------------------------------------------------------------------------+
|  🎨 Code Cartoon：STM 事务块的“记录日志 -> 验证版本 -> 原子提交/回滚”   |
|                                                                         |
|  【阶段 1：投机执行与私有日志记录（Speculative Execution）】            |
|    • 当事务读取 `from_quota.*` 时：                                     |
|      不直接加互斥锁，而是读取当前值与**版本号（Version）**，            |
|      记入本事务私有的 **读集日志（Read Set Log）**。                    |
|    • 当事务修改 `from_quota.* -= amount` 时：                           |
|      **不原地覆写共享内存！** 而是把新值写入本事务私有的                |
|      **写集日志（Write Set Log）**！此时其他线程完全看不到半成品修改！  |
|                                                                         |
|  【阶段 2：提交验证（Commit Validation）】                              |
|    • 到达 `atomic` 块出口时，STM 运行时检查读集日志中的所有变量：       |
|      “在我执行期间，有没有别的事务偷偷修改并提交了这些变量的版本号？”   |
|                                                                         |
|      ├─► 🟢 无冲突（版本号一致）：                                      |
|      │      将写集日志中的新值一次性原子发布到共享内存，递增版本号！✅  |
|      │                                                                  |
|      └─► 🔴 检测到并发冲突（版本号已变）：                              |
|             直接丢弃私有写集日志（**零副作用回滚 Rollback**），         |
|             回到 `atomic` 块开头用最新内存状态**自动重试（Retry）**！🔄 |
+-------------------------------------------------------------------------+
```

你看！因为事务在提交前根本不会原地篡改共享内存，也不会像传统死锁那样死抱着锁 A 去苦等锁 B，所以：
- **没有冲突时**：多个并发事务各自在私有日志里飞速运算并順利提交；
- **发生冲突时**：后提交的事务只需丢弃自己的私有写集草稿本，重新算一遍即可，从根本上消除了 AB-BA 死锁的可能！

## 演进 v2：用 `atomic fn` 实现事务的无缝模块化组合！

STM 真正让传统互斥锁望尘莫及的杀手锏，在于它的**可组合性（Composability）**！

假设我们把“扣减配额”和“增加配额”分别写成两个独立的 `atomic fn`：

```flurry
-- 独立的原子子操作 1：扣减配额
atomic fn deduct_quota(slot: *u32, amount: u32) -> bool {
    if slot.* < amount {
        return false;
    }
    slot.* -= amount;
    return true;
}

-- 独立的原子子操作 2：增加配额
atomic fn deposit_quota(slot: *u32, amount: u32) {
    slot.* += amount;
}

-- 将两个独立的 atomic fn 组合进同一个外层事务中！
fn atomic_rebalance(a: *u32, b: *u32, c: *u32, step: u32) -> bool {
    return atomic(a, b, c) {
        -- 在同一个事务日志上下文中连续调用多个 atomic fn：
        -- 如果第二次扣减 b 失败，连第一次对 a 的扣减也会自动回滚撤销！
        let ok1 = deduct_quota(a, step);
        let ok2 = deduct_quota(b, step);
        if not (ok1 and ok2) {
            -- 触发回滚：a 和 b 的修改草稿全部作废，保持原状！
            return false;
        }
        deposit_quota(c, step * 2u32);
        return true;
    };
}
```

请仔细品味上面这段 `atomic_rebalance`：
当 `ok1` 成功扣减了 `a`（记录在当前事务的写集日志里），而紧接着 `ok2` 发现 `b` 余额不足返回 `false` 时，我们要确保之前对 `a` 的扣减绝不能生效！
而在 STM 中，当事务块决定放弃或回滚，之前子事务函数 `deduct_quota(a, step)` 记在私有写集日志里的修改自动作废，共享内存里的 `a` 纹丝不动！

### 编译期安全红线：未声明在事务边界内的非事务函数与未受管操作不可混入！

既然 `atomic` 块依赖编译期与运行时的事务读写追踪，你不能把一个普通的、未经事务契约检验的任意外部函数当作 `atomic fn` 直接塞进事务里任意篡改不受管的全局状态：

```flurry
fn untrackable_external_mutation(p: *u32) {
    -- 普通非事务函数，未声明为 atomic fn 或 pure fn
    p.* += 1u32;
}

fn bad_atomic_call(slot: *u32) {
    atomic(slot) {
        -- ❌ 编译期直接拒绝！
        -- 在 `atomic` 事务块内部，不能调用会执行非事务内存写入或不可回滚副作用的普通函数！
        -- 事务内调用的辅助修改函数必须声明为 `atomic fn`（或满足纯度要求的 `pure fn`）。
        untrackable_external_mutation(slot);
    }
}
```

## 本篇小结

| 特性 / 语法 | 形式与规则 | 相比传统 Mutex 锁的核心优势 |
| :--- | :--- | :--- |
| **STM 事务块** | `atomic(id*) { statement* }` | 乐观读写日志 + 提交时版本验证，彻底消除加锁顺序引发的 AB-BA 死锁 |
| **STM 事务函数** | `atomic fn name(params...) -> R { ... }` | 支持将多个独立的原子子操作无缝组合成更大的原子事务（Composability） |
| **冲突自动回滚重试** | 提交验证发现读集版本变化时自动丢弃写集并重跑 | 外部观察者永远不会看到“扣了一半还没加上”的中间脏状态 |
| **调用边界静态把关** | 仅允许在事务内执行受管事务读写、调用 `atomic fn` 或纯函数 | 在编译期拦截未受事务日志追踪的野指针篡改 |

### 留给下一篇的悬念

刚刚我们看到了 STM 最核心的一个运行特征：
**当两个并发事务发生读写冲突时，`atomic { ... }` 块里的代码会被自动回滚，并且从头再执行一遍（甚至重试好几遍）！**

这时候，请你想一个极其惊悚的场景：
如果某个程序员在 `atomic(counter) { ... }` 块里面，顺手写了一句 **`println("transferring...")`**，或者发出了一个网络代数效应 **`send_rocket_launch_command()#`**，甚至在里面 `drop` 销毁了一个外部的唯一文件句柄——
一旦这次事务在提交时遇到了并发冲突，触发了 **3 次重试**，会发生什么？！
**火箭会被点火发射 4 次！那个唯一的文件句柄会被重复关闭 4 次！**

为了防止这种毁灭性的灾难，Flurry 的编译器是如何将我们在**第三卷学过的运行时纯度金字塔（Runtime Purity P0–P5）**、**仿射所有权（`Once` / `Drop`）**与**第七卷的代数效应行（`#Eff`）**联合起来，给 `atomic` 块打造一套严密的**纯度与效应隔离防火墙**的？
