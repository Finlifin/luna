# Flurry 演进手记 (122)：当生成的代码类型还待定时——CMTT 中的 `Any` 与代码见证（Code Evidence）

> **阅读指南**：在前面几回（第 116–121 回）中，我们的每一份表达式代码 `< Ψ |- T >` 和模式代码 `< T -| Ψ >` 都带着精确十分的静态类型标签。但在编写通用的元编程工具、缓存池或异构代码容器时，我们有时需要暂时放宽静态类型描述——比如用编译期通配类型 **`Any`**（或通配值 **`any`**）来传递代码值，或者写出 `< Ψ |- Any >`。结合 `docs/cmtt/any-and-code-evidence.md`，本篇我们将理清：
> 1. 把一段代码放进 `const code: Any = ...` 后，它的底层代码类别、上下文 $\Psi$ 和输出类型被“擦除”了吗？
> 2. 什么是 **代码见证（Code Evidence）**？为什么在 `~<code>` 接入的那一刻，编译器依然能明察秋毫地恢复它的真实契约？
> 3. 为什么禁用 `Any` 把模式代码伪装成表达式代码、无法抹掉未供应的开放上下文、更禁止写出 `~<any>` 让编译器“凭空捏造程序”？

---

## 一、 问题背景：想要“通用容器的灵活性”，又怕沦为“动态类型的火葬场”

假设我们在写一个协议解析器生成框架。协议里有很多不同种类的字段：有的字段解析代码返回 `u32`，有的返回 `bool`，还有的是用来匹配帧头的模式代码 `< u8 -| header: u8 >`。

在编译期组织这些代码片段时，我们很自然地想写一些通用的编译期辅助函数（比如缓存包装器、日志装饰器或列表存取工具），它们不想关心传进来的代码片段具体长什么样，于是使用了顶层通配类型 `Any`。

### 如果 `Any` 会抹掉代码的真实身份（Type Erasure）

如果一门语言把编译期的 `Any` 做成了类似 C 语言 `void*` 或动态语言那样的“完全黑盒擦除”，就会带来严重隐患：

```flurry
-- 假想初始写法：如果标注 Any 会把代码值的真实契约抹除干净
-- 问题 1：本来是产生 bool 的代码 '(true)，塞进 Any 后被接入到要求 i32 的地方，
--         难道编译器就稀里糊涂放行、或者硬把 bool 强转成 i32 吗？
-- 问题 2：本来是一段【模式代码】 '<number>，塞进 Any 后被当成【表达式代码】接入。
-- 问题 3：本来是一段需要外部提供 `needed: i32` 的【开放代码】，
--         塞进 Any 后隐藏了 `< needed: i32 |- ... >`，难道它就变成不需要输入的闭代码了吗？
```

**核心问题**：
我们在编译期使用 `Any`，只是为了**放宽外层的静态类型标注（Static Description）**，方便通用传递与存储；但非为了销毁那段代码与生俱来的**真实契约（Actual Code Evidence）**。

---

## 二、 核心机制：静态描述可以放宽，底层“代码见证”寸步不让

在 Flurry 的 CMTT 中（见 `docs/cmtt/any-and-code-evidence.md`），编译器严格区分 **外层静态描述（Static Description）** 与 **实际代码见证（Actual Code Evidence）**：

> **💡 核心心智模型：标注 `Any` 只是给电路板套了一个不透明的快递纸箱。**
> 当你写下 `const code: Any = '(value + 1i32);` 时：
> - **快递箱外面的标签（静态描述）**写着 `Any`，所以任何接收 `Any` 的编译期函数 `keep(value: Any) -> Any` 都可以愉快地传递这个箱子；
> - 但是，**箱子里面的电路板（实际代码见证）**毫发无损地保留着它的全部真实档案：
>   1. **代码类别（Category）**：它是 `expr`（表达式代码），并非 `pattern` 或 `arm`；
>   2. **原始上下文接口与绑定来源（Context & Identity）**：它绑定了外层形参 `value: i32`；
>   3. **主体与结果类型（Body & Result Type）**：它的结果类型是 `i32`，且包含必要的阶段与资源义务。
> - 一旦你写下 **`~<code>`** 准备拆箱焊接，编译器会立刻打开箱子，**从实际代码值恢复出完整的代码见证**，并逐项核验类别、阶段、Rank、上下文供应与结果类型。

下面对比 CMTT 中关于 `Any` 与 `any` 的 **四种不同信息状态**：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                 CMTT 中 Any / any 的四种信息状态与拆箱核验                   │
├───────────────────────────┬──────────────────────────┬───────────────────────┤
│ 静态状态                  │ 编译器此刻已知什么？     │ `~<...>` 接入时核验啥 │
├───────────────────────────┼──────────────────────────┼───────────────────────┤
│ 1. `q : Any`              │ 静态标签未说明实际种类   │ 拆箱恢复实际代码见证：│
│    (纸箱全盲)             │                          │ 核验类别 + Ψ + 结果 T │
├───────────────────────────┼──────────────────────────┼───────────────────────┤
│ 2. `q : < Ψ |- Any >`     │ 已知是表达式代码，且已知 │ 拆箱核验实际产出的    │
│    (结果通配)             │ 上下文接口 Ψ             │ 结果类型是否匹配目标  │
├───────────────────────────┼──────────────────────────┼───────────────────────┤
│ 3. 接口部分含 `Any`/`any` │ 允许部分类型或值通配匹配 │ 仍严格保持真实参数关联│
│    (局部通配)             │                          │ 、依赖次序与上下文要求│
├───────────────────────────┼──────────────────────────┼───────────────────────┤
│ 4. 直接写 `~<any>`        │ 只有一个空洞的通配符，   │ ❌ 没有任何代码主体见 │
│    (无中生有)             │ 根本没有给定任何程序主体 │    证，当场直接报错   │
└───────────────────────────┴──────────────────────────┴───────────────────────┘
```

### 经过 `Any` 传递后依然安全恢复见证并接入

让我们看一段真实的 Flurry 代码：代码片段经过了 `Any -> Any` 的编译期函数转发，并保存在 `const code: Any` 中，但在 `~<code>` 接入时，编译器良好恢复了它的 `expr` 类别、`value` 绑定身份以及 `i32` 结果类型：

```flurry
use std.prelude.*;

-- 通用的编译期恒等转发函数，静态签名只写 Any
pure comptime fn keep(value: Any) -> Any {
    value
}

fn through_any(value: i32) -> i32 {
    -- 1. 构造代码 '(value + 1i32)，经由 keep 转发后标注为 Any
    --    虽然静态标签放宽成了 Any，但底层依然保存着完整的代码见证。
    const code: Any = keep('(value + 1i32));

    -- 2. ✅ 在 ~<code> 接入点，编译器从本次编译期实例恢复出：
    --    • 类别：expr
    --    • 绑定：固定引用形参 value: i32
    --    • 结果：i32（与函数返回类型 i32 完全匹配。）
    ~<code>
}

test {
    println("through_any: {}", through_any(41i32));
}
```

## 三、 四大防伪红线：`Any` 并非指鹿为马的后门

既然每次 `~<code>` 都会严格审查底层的“实际代码见证”，那么任何企图利用 `Any` 或 `any` 蒙混过关的操作，都会在编译期被无情识破。让我们通过四个富有代表性的负例（见 `docs/cmtt/any-and-code-evidence.md`），看清编译器的防伪红线：

### 红线 1：目标类型无法篡改实际主体（`bool` 代码装进 `Any` 也变不成 `i32`）

```flurry
fn wrong_result() -> i32 {
    const code: Any = '(true);

    -- ❌ 编译期直接报错。
    -- 拆箱后发现 code 的实际见证产出的是 bool，
    -- 免因外层标了 Any、而目标函数要求 i32，就把 true 强行交付为 i32。
    ~<code>
}
```

### 红线 2：类别放宽免生跨类别转换（模式代码装进 `Any` 亦无法当表达式接）

```flurry
fn wrong_kind() -> u32 {
    const pattern: < u32 -| number: u32 > = '<number>;
    const code: Any = pattern;

    -- ❌ 编译期直接报错。
    -- 拆箱后发现 code 的实际见证是【模式代码 (pattern)】，
    -- 而当前位置是函数返回值的【表达式位置 (expr)】。
    -- 正确做法：必须把模式代码接到 match 或 let 的模式位置。
    ~<code>
}
```

### 红线 3：上下文无法被 `Any` 藏匿抹除，且 `~<any>` 不会凭空编造程序

1. 如果一段代码原本是开放代码 `< needed: i32 |- i32 >`，哪怕你把它赋值给 `const hidden: Any = open_code;`，它的未知/隐藏上下文也**有别于空上下文**。接入时如果没供应 `needed`，照样报错。
2. 如果你直接写 `~<any>`，企图让编译器根据返回类型 `u32` 自动猜一个程序出来：

```flurry
fn missing_program() -> u32 {
    -- ❌ 编译期直接报错。
    -- any 只是一个没有给定程序主体的通配符，缺乏任何代码接入见证。
    -- 编译器不会替你瞎猜一个 0u32 或某个局部变量塞进去。
    ~<any>
}
```

### 红线 4：运行期条件无法决定 `comptime` 代码值（哪怕标成 `Any` 也不行）

初学者最容易犯的另一个阶段错误是：拿一个**运行期**布尔参数 `flag: bool` 去 `if flag { '(1u32) } else { '(2u32) }` 里挑选代码值，还以为给 `const code` 标个 `: Any` 就能瞒天过海：

```flurry
-- 负例：企图用 runtime 变量决定 comptime 代码值
fn late_choice_broken(flag: bool) -> u32 {
    -- ❌ 编译期直接报错：(Stage Error)
    -- flag 在运行期才有值，而 const code 必须在编译期确定是哪一份代码值。
    -- 就算写成 const code: Any = ... 也改不了 flag 处于 runtime 阶段的事实。
    const code = if flag { '(1u32) } else { '(2u32) }
    ~<code>
}

-- ✅ 正确写法：在编译期构造一份【内部包含 runtime if】的单一代码值。
fn runtime_choice_valid(flag: bool) -> u32 {
    -- 代码结构在编译期 100% 确定，而 if flag 的分支跳转留到运行期执行。
    const code = '(if flag { 1u32 } else { 2u32 });
    ~<code>
}

test {
    println("{} {}", runtime_choice_valid(true), runtime_choice_valid(false));
}
```

## 本篇小结

| 核心概念 / 场景 | 编译器行为与契约 | 为什么安全？ |
| :--- | :--- | :--- |
| **`const code: Any = '(...)`** | 放宽静态标签，底层完整保留代码见证（类别、$\Psi$、主体、结果） | 允许异构容器与通用辅助函数传递代码，同时完好保留任何静态检查依据 |
| **`const code: < Ψ \|- Any >`** | 锁定表达式类别与上下文 $\Psi$，仅放宽结果类型描述 | 接入时根据实际产生的结果类型与目标位置做精确核对 |
| **隐藏开放上下文** | 隐藏 `< needed: i32 \|- T >` 免使其变成闭代码 `< \|- T >` | 接入时仍强制要求供应全部所需的 runtime 绑定 |
| **`~<any>` 与跨类别接入** | 直接在编译期报错 | 禁止无主体凭空造码，禁止将模式代码当成表达式接入 |
