# Flurry 演进手记 (010)：给数据包做外科手术——模式优先级、括号分组 `(p)` vs `(p,)` 与范围模式

在前面的旅程中，我们的传感器监控系统已经能够解析单字节报文、用 `?T` 和 `!Err T` 处理噪声与异常，并通过指针与绑定规则安全地维护状态。

今天，固件工程师把通信协议升级到了 V2 版本：传感器网关不再只发单字节，而是发来带有**有符号校准偏移量（`i32`）**、**可选采样读数（`?u32`）**以及**复合状态包**的数据流。他向你提了四个看似简单、却暗藏语法玄机的分类需求：

1. **校准档位过滤**：网关发来的采样值是一个 `?u32`。只有当它**有值**，并且恰好落在校准档位 `1` 或 `2` 时，才触发快速校准。
2. **工作区间留档**：当无符号读数落在常规工作区间 `10..20`（半开区间，含 10 不含 20），或者恰好是特殊标定值 `30` 时，我们要把**这整个匹配成功的数值本身**绑定到变量 `number` 上记录日志。
3. **低温补偿区间**：传感器的环境温度偏移量是有符号整数 `i32`。当温度落在零下区间 `-3..=-1`（闭区间，即 `-3`、`-2` 或 `-1`）时，启动加热补偿。
4. **单通道与元组包装消歧**：有些接口直接传一个 `u32` 标量，有些批处理接口传的是**单元素元组 `Tuple<u32>`**。我们在写模式加括号分组时，绝不能把“给模式加括号 `(p)`”和“匹配单元素元组 `(p,)`”混为一谈！

如果你来自 C、Rust 或其他语言，在把 `or`、`?`、`not`、`..`、`as` 和 `if` 守卫组合进同一个模式时，很容易凭直觉写错括号，或者在单元素元组上栽跟头。让我们像做外科手术一样，一层层解剖 Flurry 的模式语法树！

## 第一版：凭直觉组合模式——当 `or` 撞上 `?`、`not` 与 `as`（v0）

面对需求 1（匹配 `?u32` 中的 `1` 或 `2`）和需求 2（匹配 `10..20` 或 `30` 并整体绑定为 `number`），如果我们不假思索地顺手写下 v0 版本，很容易写出下面这样让人提心吊胆的代码：

```flurry
use std.prelude.*;

-- v0：试图靠直觉组合 `?`、`or`、`not` 与 `as`
fn is_fast_calibration_v0(sample: ?u32) -> bool {
    sample match {
        -- 痛点 1：我想匹配“有值，且值为 1 或 2”。
        -- 如果写成 `1u32? or 2u32?` 能跑，但如果有 10 个档位，难道要写 10 个 `?` 吗？
        -- 反过来，如果漏了括号写成 `1u32 or 2u32?`，左边的 `1u32` 甚至连 `?` 都没带！
        1u32? or 2u32? => true,
        _ => false,
    }
}

fn is_not_calibrating_v0(code: u32) -> bool {
    code match {
        -- ❌ 潜在灾难！作者想写“既不是 1 也不是 2”，结果写成了：
        (not 1u32) or 2u32 => true,
        _ => false,
    }
}
```

停下来看看 `is_not_calibrating_v0` 里的 `(not 1u32) or 2u32`！
如果输入 `code` 是 `2u32`，它会发生什么？
1. 先看第一支 `not 1u32`：因为 `2u32` 不等于 `1u32`，所以 `not 1u32` **直接匹配成功**！
2. 哪怕输入是 `1u32`，第一支失败了，第二支 `2u32` 也不匹配；可一旦输入是 `2u32`，它竟然因为满足了左边的 `not 1u32` 而返回了 `true`！

让我们画一张 **Code Cartoon**，看看为什么“把算术/逻辑表达式的习惯直接套进模式”会引发事故：

```text
  作者脑子里的意图：                  `(not 1u32) or 2u32` 的真实判定树：
  "排除掉 (1 或 2)"                   input = 2u32
         │                                 │
         ▼                                 ▼
    not (1u32 or 2u32)              ┌── [ 尝试左支: not 1u32 ]
         │                          │     2u32 != 1u32 ──► ✅ 匹配成功！(直接进分支！)
         ├─ input = 1 ──► ❌ 失败   │
         ├─ input = 2 ──► ❌ 失败   └── [ 右支: 2u32 ] (永远成了多余的摆设或死逻辑)
         └─ input = 9 ──► ✅ 成功
```

再比如，当我们想把范围模式 `10u32..20u32`、选择模式 `or 30u32` 和整体绑定 `as number` 组合在一起时：
- `10u32 or 20u32 as number` 到底是把 `number` 绑在右半边的 `20u32` 上，还是绑在整组 `10u32 or 20u32` 上？
- 如果不加括号写 `1u32 or 2u32 as value`，为什么它能工作，而一旦只有半边绑定（比如 `(1u32 as value) or 2u32`）就会被编译器当场拦截？

要彻底掌控复杂数据的解构，我们不能靠猜——我们需要一张清晰的**模式优先级地图**。

## 第二版：模式的六层结合优先级与精准括号手术（v1）

在 Flurry 中，模式（Pattern）拥有自己独立、严谨的结合层次表（详见 `docs/control-flow/pattern-matching/index.md`）。

请注意一条黄金原则：**模式优先级决定的是“一颗模式树如何组合出边界”，而不是 `match` 各个分支的尝试顺序。**

让我们用一张从**最紧（最先结合）**到**最松（最后兜底）**的六层阶梯图，把 Flurry 的模式优先级刻进脑海里：

```text
  ══════════════════════ Flurry 模式结合优先级（由紧到松）══════════════════════

  [第 1 层：最紧] 名称投影          E.variant
        │         (先确定完整的模式头，例如 Packet.data)
        ▼
  [第 2 层]       应用与解构        P(...)  /  P{...}  /  E<...>
        │         (把载荷模式或类型参数挂到模式头上)
        ▼
  [第 3 层]       成功包装后缀      p?  /  p!
        │         (紧贴着左侧已经成型的模式，剥开 ?T 或 !Err T 的成功层)
        ▼
  [第 4 层]       选择（析取）      p or q
        │         (把左右两个候选模式并列；两侧导出的绑定结构必须兼容！)
        ▼
  [第 5 层]       整体绑定          p as name
        │         (比 `or` 更松！把左侧整个模式匹配到的完整值绑给 name)
        ▼
  [第 6 层：最松] 守卫与顺序匹配    p if expr  /  p and expr is q
                  (接在整个左侧模式之后；其中 `if` 后面的 expr 按普通表达式解析)
  ══════════════════════════════════════════════════════════════════════════════
```

看懂了这张图，刚才所有的疑惑瞬间迎刃而解！

### 1. `(1u32 or 2u32)?` vs `1u32? or 2u32?`

因为第 3 层的后缀 `?` 比第 4 层的 `or` **结合得更紧**：
- 如果你不加括号写 `1u32 or 2u32?`，编译器会把它解析成 `1u32 or (2u32?)`——左边变成了普通整数 `1u32`，右边却是可选模式 `2u32?`，类型直接冲突！
- 如果你写 `1u32? or 2u32?`，它是合法的：分别匹配两个存在分支。
- 但最优雅的写法是用括号先把选择包起来：**`(1u32 or 2u32)?`**！括号先建立一个完整的内部子模式 `1u32 or 2u32`，外层的 `?` 再一次性剥开 `?u32` 的外皮！

### 2. `not (1u32 or 2u32)` vs `(not 1u32) or 2u32`

前缀模式 `not`、`error`、`ref`、`async` 会取得当前范围内其后的完整模式。为了让“否定整组选择”与“只否定第一支”绝对清晰，我们用括号明确划定边界：
- **`not (1u32 or 2u32)`**：否定整组选择（既不是 1 也不是 2）。
- **`(not 1u32) or 2u32`**：只把否定限制在第一支。

### 3. `((10u32..20u32) or 30u32) as number` 与负数范围 `-3..=-1`

再看第 4 层（`or`）和第 5 层（`as`）的关系：
因为 **`p as name` 比 `p or q` 更松**，所以当你写 `1u32 or 2u32 as value` 时，它天然被解释为 **`(1u32 or 2u32) as value`**！
但如果反过来，你故意用括号把 `as` 锁在 `or` 的一边，而另一边不提供同名绑定呢？

```flurry
-- ❌ 编译期直接拒绝！
fn bad_or_binding(x: u32) -> u32 {
    x match {
        -- 括号强行把 `as val` 限制在了左支，导致右支 `2u32` 没有导出 `val`！
        -- `or` 的铁律：两侧导出的绑定结构必须完全兼容，加括号也不能让非法绑定变合法！
        (1u32 as val) or 2u32 => val,
        _ => 0u32,
    }
}
```

而在组合**范围模式**（如 `10u32..20u32`）与 `or`、`as` 时，规范强烈建议**用括号明确包裹完整范围**，例如 `((10u32..20u32) or 30u32) as number`。
同时，对于需求 3 的低温负数十进制字面量，Flurry 的字面量模式原生支持带负号的数值字面量（如 `-3`、`-3.5`），因此你可以直接写出清爽的闭区间范围模式 **`-3..=-1`** 或替代模式 **`(-3) or -4`**！

> **🔍 语法小贴士：模式里的负号 `-` 能接任意表达式吗？**
> 不能！在模式位置上，`-` **只接数值字面量**（如 `-3`、`-1.5f64`），用来构成负数数值字面量模式，并不会把任意算术表达式（如 `-(a + b)`）引入模式中。
> 另外要注意：模式守卫 `p if expr` 后面的 `expr` 是按**普通表达式规则**解析的——所以在 `if a == 1 and b == 2` 里面，`and` / `or` 是布尔逻辑运算符，编译器绝不会糊涂地把它们当成外层的模式组合子！

让我们把前三个需求整合进干净利落的 `v1` 代码中：

```flurry
use std.prelude.*;

-- 需求 1：用 (1 or 2)? 把选择放在 option 内部
fn selected(value: ?u32) -> bool {
    value match {
        (1u32 or 2u32)? => true,
        _ => false,
    }
}

-- 需求 2：范围 + or + 整体绑定 as
fn selected_number(value: u32) -> u32 {
    value match {
        ((10u32..20u32) or 30u32) as number => number,
        _ => 0u32,
    }
}

-- 需求 3：负数范围模式 `-3..=-1` 与前缀 `not` 分组
fn check_temp_offset(offset: i32) -> str {
    offset match {
        -3..=-1 => "heating_compensation",
        (-4) or -5 => "deep_freeze_alert",
        not (0..=50) => "out_of_normal_range",
        _ => "normal",
    }
}
```

## 第三版：括号的三副面孔——分组 `(p)`、单元素元组 `(p,)` 与单元 `()`（v2）

现在只剩下最后一个、也是无数程序员最容易踩坑的细节：**括号在模式里到底意味着什么？**

假设硬件层有两个长得很像的接口：
- 接口 A 返回一个普通的标量 `u32`；
- 接口 B 返回一个单元素元组 `Tuple<u32>`（在值表达式里构造为 `(9u32,)`）。

在模式匹配或 `let` 解构中，如果你写下 `let (number) = ...`，它到底是在解构一个单元素元组，还是仅仅给模式 `number` 加了一对分组圆括号？

Flurry 给出了最正交、最无歧义的答案：**圆括号 `(p)` 永远只用于分组，绝不新增解构层！只有带上逗号的 `(p,)` 才是单元素元组模式！**

让我们画一张 **Code Cartoon** 对比这四兄弟：

```text
  ┌───────────────────┬──────────────────────────┬────────────────────────────────┐
  │     模式写法       │         真实身份          │          要求的主语类型          │
  ├───────────────────┼──────────────────────────┼────────────────────────────────┤
  │  let (p) = val;   │ 分组模式 (Parenthesized) │ 直接就是 p 的类型 (如 u32)      │
  │                   │ ──► 剥掉括号，直接用 p！  │ ❌ 不新增任何元组解构层！       │
  ├───────────────────┼──────────────────────────┼────────────────────────────────┤
  │  let (p,) = val;  │ 单元素元组模式 (1-Tuple) │ 单元素元组 Tuple<T>             │
  │                   │ ──► 靠末尾逗号 `,` 验明正身│ 拆出唯一的元素交给 p！          │
  ├───────────────────┼──────────────────────────┼────────────────────────────────┤
  │  let (p, q) = val;│ 两元素元组模式 (2-Tuple) │ 两元素元组 Tuple<T1, T2>        │
  ├───────────────────┼──────────────────────────┼────────────────────────────────┤
  │  let () = val;    │ 单元模式 (Unit Pattern)  │ 单元值 () (void)               │
  └───────────────────┴──────────────────────────┴────────────────────────────────┘
```

来写一段完整的测试代码，亲眼验证 `(number)` 与 `(number,)` 的分野：

```flurry
use std.prelude.*;

-- 1. `(number)` 只是模式分组，主语直接就是 u32！
fn grouped_value(value: u32) -> u32 {
    let (number) = value;
    number
}

-- 2. `(number,)` 才是单元素元组模式，主语是 Tuple<u32>！
fn single_tuple_value(tuple_val: Tuple<u32>) -> u32 {
    let (number,) = tuple_val;
    number
}

-- 3. `()` 匹配单元值
fn consume_unit(u: void) {
    let () = u;
}

test {
    println("{} {}", selected(2u32), selected(null));
    println("{} {}", selected_number(15u32), selected_number(25u32));
    println("{}", grouped_value(9u32));
    println("{}", single_tuple_value((9u32,)));
    println("{}", check_temp_offset(-2));
}
```

运行这段测试，输出丝毫不差：

```text
true false
15 0
9
9
heating_compensation
```

反之，如果你试图用 `let (number,) = 9u32;` 去解构一个普通整数：

```flurry
-- ❌ 编译期直接拒绝！
fn wrong_tuple_pattern(value: u32) -> u32 {
    -- `(number,)` 要求主语是单元素元组 Tuple<u32>，但 value 只是标量 u32！
    let (number,) = value;
    number
}
```

编译器会立刻指出类型不匹配：分组括号 `(p)` 可以随便加在任何模式外层改变结合范围（比如 `((number))` 依然匹配 `u32`），但只要你写下了那个关键的逗号 `(p,)`，你就向编译器发出了明确的“拆开一层单元素元组”指令！

## 本篇小结

回顾我们从 v0 到 v2 的外科手术式演进：

| 演进阶段 | 遇到的痛点 / 歧义 | Flurry 的解决方案与机制 |
| :--- | :--- | :--- |
| **v0** | `1? or 2?` 冗余、`(not 1) or 2` 逻辑反转、范围与 `as` 边界不清 | 暴露凭直觉混用表达式优先级与模式优先级的隐患 |
| **v1** | 复杂模式组合顺序难以心算 | 明确**六层模式优先级**（投影 → 应用 → `?`/`!` → `or` → `as` → `if`/`and is`），支持 `(1 or 2)?`、`((10..20) or 30) as number` 与负数范围 `-3..=-1` |
| **v2** | 给模式加括号 `(p)` 与单元素元组解构容易混淆 | 严格区分分组括号 **`(p)`**（不增加解构层）、单元素元组模式 **`(p,)`** 与单元模式 **`()`** |

### 留给下一篇的悬念

在这一篇里，我们在整数 `u32` 和 `i32` 上愉快地使用了范围模式 `10u32..20u32` 和 `-3..=-1`。对于整数来说，世界是黑白分明的：如果一个数不在 `..0`（小于 0）里，那它一定在 `0..`（大于等于 0）里。

但是，第二天算法工程师走过来，让你把传感器的原始整数读数乘上校准系数，变成了 64 位浮点数 **`f64`**！
你信心满满地在代码里写下了两行匹配来穷尽所有浮点数：

```flurry
value match {
    ..0.0 => "negative",
    0.0.. => "non-negative",
}
```

结果——**编译器当场报错，拒绝通过穷尽性检查（Non-exhaustive match）！**
你大吃一惊：小于 `0.0` 和大于等于 `0.0` 合起来，难道还没有覆盖数轴上的所有实数吗？！
更诡异的是，当你试图加一行 `f64.NaN => "nan"` 去补洞时，编译器依然无情地拒绝了你！
