# Flurry 演进手记 (116)：为什么字符串拼接宏和 AST 宏还不够好——带上下文类型的代码值（CMTT）登场

> **阅读指南**：欢迎来到《Flurry 演进手记》第六卷！在第五卷中，我们用 Trait、一致性（Coherence）与 `derive fn` 构建了优雅的静态多态契约。但系统编程还有一块最硬的骨头：**编译期代码生成（Code Generation）**。比如，我们要写一个协议解析器生成器或正则表达式编译器，在编译期把一张状态转移表直接编译成零分支跳转冗余的有限状态机（FSM）原生代码。为什么 C 语言的文本宏、C++ 模板、甚至 Rust 的 `proc-macro`（过程宏）和普通的未类型化 AST 拼接，总是逃不开“定义时岁月静好，展开后报出一堆莫名其妙的变量名冲突或类型错误”的魔咒？本篇我们将正式请出 Flurry 元编程体系的基石——**上下文模态类型论（Contextual Modal Type Theory, CMTT）**！

---

## 一、 痛点：为什么传统宏总是“展开后才翻车”？

假设我们在开发一个高性能网络网关，需要编写一个编译期状态机生成器：给定一组协议字节匹配规则，自动生成一段在运行期读取当前状态 `state` 和当前输入字节 `byte`、并算出下一个状态的跳转代码。

### 尝试 `v0`：字符串/Token 拼接宏与“无类型 AST 树”的双重噩梦

在传统语言中，如果你用 C 预处理器宏、或者用未类型化的语法树（Untyped AST / TokenStream，如 Rust `proc-macro` 中的 `quote!`）来拼接生成这段状态机代码，你会经历怎样的折磨？

```flurry
-- 假想 v0：传统“无类型 AST / Token 拼接宏”的伪代码心智模型
-- 宏作者在拼接代码片段时，编译器对这段代码需要什么变量、产出什么类型一无所知：
--
-- let step_fragment = untyped_quote! {
--     if state == 0 and byte == 97 { 1 } else { false }
-- };
--
-- 灾难 1（延迟爆雷的类型错误）：
--   then 分支返回整数 1，else 分支返回布尔值 false！
--   但定义这颗 AST 节点时编译器完全不报错，直到别的程序员调用宏展开时才炸裂！
-- 灾难 2（幽灵自由变量与命名冲突）：
--   片段里凭空写了一个自由变量 `state` 和 `byte`。
--   如果调用者作用域里恰好看不到 `byte`，或者调用者后来重定义了一个同名局部变量
--   `let byte = true;`，展开后的代码就会发生指鹿为马的绑架（Variable Capture）！
```

让我们把传统宏的三大顽疾总结出来：
1. **代码片段是个“黑盒包裹”**：编译器在宏定义阶段，只知道你手里握着一串 Token 或一棵未检查的语法树。它既不知道这段代码**产出了什么类型**，也不知道这段代码内部**偷偷依赖了外部作用域的哪些运行时变量**！
2. **展开前无类型契约，展开后报错张冠李戴**：一旦生成逻辑包含复杂的条件分支或循环组装，任何类型不匹配都要等到最终接入用户函数、完全展开之后才暴露，报错行号指着宏展开处，用户看得一头雾水。
3. **只能拼表达式，没法安全地拆装模式匹配（Pattern）与分支（Match Arm）**：状态机最核心的结构是 `match` 分支！但在传统 AST 宏里，一个模式 `pat` 匹配成功后到底导出了哪些新变量供右侧分支体 `body` 使用，完全没有类型层面的关联保证。

## 二、 破局（v1）：CMTT——给每一段代码装上“显式上下文接口”

为了终结“瞎子摸象式”的 AST 拼接，Flurry 没有把代码片段当成无类型的 Token 串，而是引入了源自逻辑学与类型论前沿的 **CMTT（Contextual Modal Type Theory，上下文模态类型论）**。

在 Flurry 中，**所有被引用的代码（Quoted Code）都是编译期（`comptime`）的一等公民值，而且每一份代码值都携带着精确的“上下文模态类型”！**

什么是“上下文模态类型”？简单来说，一段代码不仅要在类型里写明它自己是什么，还要把**它与周围运行时环境的“插头与插座（运行时绑定上下文 $\Psi$）”**明明白白地写在类型签名上！

更惊艳的是，Flurry 的 CMTT 提供了 **两阶段（Two Stages）、三种一等代码值（Three Code Categories）**，精准覆盖了构建状态机所需的全部语法积木：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                 Flurry CMTT 的三种一等带类型代码值 (Rank-1)                  │
├──────────────────────┬───────────────────────────┬───────────────────────────┤
│ 1. 表达式代码 (Expr) │ 2. 模式代码 (Pattern)     │ 3. 分支代码 (Quoted Arm)  │
├──────────────────────┼───────────────────────────┼───────────────────────────┤
│ 语法: '(expr)        │ 语法: '<pattern>          │ 载体: quote fn (case pat) │
│ 类型: < Ψ |- T >     │ 类型: < T -| Ψ >          │ 内部: Arm(Γ; T; Ψ; U)     │
│                      │                           │                           │
│   ┌──────────────┐   │   ┌──────────────┐        │   ┌───────────────────┐   │
│ Ψ │              │ T │ T │              │ 导出 Ψ │ Γ │ [模式 T ──▶ Ψ]    │ U │
│ ──▶  表达式主体  ├──▶│ ──▶   模式结构   ├───────▶│ ──▶       │           ├──▶│
│   │              │   │   │              │        │   │       ▼           │   │
│   └──────────────┘   │   └──────────────┘        │   │ [分支主体 (Γ, Ψ)] │   │
│                      │                           │   └───────────────────┘   │
│ • 输入: 给定上下文 Ψ │ • 输入: 匹配主语类型 T    │ • 将外部上下文 Γ、模式 T、│
│ • 输出: 产生 T 类型值│ • 输出: 成功时产生新绑定 Ψ│   成功绑定 Ψ 与主体 U 锁死│
└──────────────────────┴───────────────────────────┴───────────────────────────┘
```

仔细观察上面这张图中两个极其传神的符号方向：
- **表达式代码类型 `< Ψ |- T >`**：竖线在左、横杠在右（`|-`），代表**“消费左侧的运行时绑定上下文 $\Psi$，计算出右侧的 $T$ 类型结果”**；
- **模式代码类型 `< T -| Ψ >`**：横杠在左、竖线在右（`-|`），代表**“接收左侧被匹配的 $T$ 类型主语，匹配成功时向右导出新的运行时绑定上下文 $\Psi$”**！

## 三、 初体验：从封闭代码到带上下文的开放代码（v1 -> v2）

让我们写下第六卷的第一段 CMTT 代码，亲眼看看“带上下文类型的代码值”是如何在编译期生成、组合，并在运行期零开销执行的！

### 演进到 `v1`：不依赖局部变量的封闭代码 `< |- u32 >`

如果一段表达式代码不依赖任何外部局部运行时变量（即上下文 $\Psi$ 为空），它的类型就写作 `< |- T >`：

```flurry
use std.prelude.*;

-- 在编译期（comptime）直接构造并返回一段封闭的运行时表达式代码
pure comptime fn answer_code() -> < |- u32 > {
    '(42u32)
}

fn answer() -> u32 {
    -- 使用 ~<...> 将编译期算出的代码值接入（Splice）到当前运行时位置！
    ~<answer_code()>
}

test {
    println("{}", answer());
}
```

注意这里的阶段边界（Two Stages）：
- `answer_code()` 是一个 `pure comptime fn`，它在**编译期**运行，返回的不是数字 `42`，而是一份类型为 `< |- u32 >` 的代码值 `'(42u32)`；
- 在 `answer()` 函数体内部，`~<answer_code()>` 先在编译期调用 `answer_code()` 拿到代码值，再将代码主体 `42u32` 直接接入到 `answer()` 的运行时返回位置。**最终生成的机器码里没有任何运行时代码对象或动态解释器，跟手写 `42u32` 完全一致！**

### 演进到 `v2`：带显式上下文接口的开放代码与卫生绑定保护

那么，如果我们要生成的是一步状态判断或数值转换，它需要读取运行时变量 `input` 呢？在 CMTT 中，我们直接把 `input` 声明在代码类型的上下文接口 `< input: bool |- bool >` 中，并且在创建代码时就锁定绑定身份，彻底免疫后续同名局部变量的遮蔽（Shadowing）污染：

```flurry
use std.prelude.*;

-- 接收一段类型为 < x: bool |- bool > 的代码，在编译期给它外面套一层取反！
pure comptime fn invert(code: < x: bool |- bool >) -> < x: bool |- bool > {
    '(not ~<code>)
}

fn selected(value: bool) -> bool {
    -- 1. 声明一段开放代码，它的接口要求运行时提供一个 input: bool
    const original: < input: bool |- bool > = '(input);

    -- 2. 将虚拟端口 input 连接到当前形参 value，并套上一层 not
    const combined = '(not ~[input = value]<original>);

    -- 3. 哪怕我们在接入前故意声明一个同名的局部变量 value = false 试图搞破坏：
    let value = false;

    -- ✅ ~<combined> 依然牢牢认准第 2 步绑定好的【函数形参 value】！
    -- 当传入 selected(true) 时，依然准确返回 true！
    not ~<combined>
}

test {
    println("selected: {}", selected(true));
}
```

如果我们在编写编译期生成器 `invert` 时，不小心把代码里的类型搞错了（比如对一个 `i32` 做了布尔取反，或者漏掉了上下文供应），编译器需要等到调用者展开时才发现吗？**不需要！在定义阶段当场就会被拒绝：**

```flurry
pure comptime fn broken_code_generator(
    code: < x: i32 |- i32 >,
) -> < x: i32 |- i32 > {
    -- ❌ 编译期在生成器定义处直接拒绝！
    -- ~<code> 的结果类型是 i32，不能对 i32 应用布尔运算符 not！
    -- 根本不需要等到有人调用 broken_code_generator，Bug 在定义时即被秒杀！
    '(not ~<code>)
}
```

> **💡 核心心智模型：CMTT 带来的三大质变**
> 1. **创建即检查，签名即契约**：`< Ψ |- T >` 把代码片段所需的输入绑定 $\Psi$ 和输出类型 $T$ 变成了静态类型的一部分。生成器还没被调用，编译器就已经在虚拟上下文 $\Psi$ 中完成了对代码主体的类型检查！
> 2. **引用保留绑定身份（Identity Preservation）**：当代码引用一个已有的运行时变量（如上面的形参 `value`）时，它记录的是该变量的**真实编译器绑定身份**，而不是脆弱的文本名字。后来出现的同名 `let value = false;` 绝不会篡改已建立的引用！
> 3. **运行时零代码对象开销**：所有 `'(...)` 与 `< Ψ |- T >` 都只存在于 `comptime` 阶段。一旦通过 `~<...>` 接入完成，目标程序里只有纯粹的原生指令，还会继续接受移动、清理、效应与阶段检查！

## 本篇小结

| 核心概念 | 传统无类型宏（C 宏 / Token 拼接） | Flurry CMTT（上下文模态类型论） |
| :--- | :--- | :--- |
| **代码片段的类型** | 无（仅为一串 Token 或未检查 AST） | `< Ψ \|- T >`（表达式）、`< T -\| Ψ >`（模式）与 `Arm` |
| **错误发现时机** | 延迟到宏调用展开后，报错位置混乱 | 生成器定义阶段即在虚拟上下文 $\Psi$ 中完成类型与阶段检查 |
| **自由变量与卫生性** | 极易发生同名变量意外捕获（Capture） | 显式上下文端口 + 绑定身份锁定，免疫后续同名遮蔽 |
| **运行期开销** | 零（文本替换） | 零（`comptime` 完成接入，不生成任何 runtime 代码对象） |
