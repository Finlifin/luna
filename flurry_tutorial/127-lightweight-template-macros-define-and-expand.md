# Flurry 演进手记 (127)：轻量级文件内语法减负——模板宏 `define id` 与 `$id` 按组展开

> **阅读指南**：在前面的第 116–126 回中，我们学习了基于 CMTT 的带类型代码值（`'(...)`、`'<...>`、`quote fn`）。它们是构建跨模块代码生成器与状态机的重型武器。但在日常编码中，我们常常遇到一种简单得多的需求：**“我只是想在当前文件里少复制粘贴十几个格式一模一样的常量声明或测试辅助语句！”** 为这种小事动用 CMTT 显然杀鸡用了牛刀。本篇我们将结合 `docs/macro/template-macro.md` 与 `docs/grammar/syntax`，认识 Flurry 专为文件内轻量级语法减负设计的 **模板宏（Template Macro）**：`define id N`、`define id N ...` 与 `define id(params)`！

---

## 一、 痛点：杀鸡用牛刀的疲惫 vs. C 语言 `#define` 的全局污染

假设我们在编写一个协议状态机或硬件寄存器映射文件，需要在文件开头定义几十个状态码常量或一批格式完全相同的简单辅助函数：

```flurry
const STATE_IDLE = 0;
const STATE_HEADER = 1;
const STATE_PAYLOAD = 2;
const STATE_CRC = 3;
const STATE_DONE = 4;
```

### 审视 `v0`：要么手敲样板代码，要么忍受 C 风格 `#define` 的失控

面對这种简单的表面语法重复，如果我们只有两种极端选择（`v0`）：
1. **极端 A（纯手写或硬上重型宏）**：为了省掉重复的 `const ... = ...;`，如果去写一套完整的 AST 构造宏，定义宏的代码比省下来的代码还要长三倍！
2. **极端 B（C/C++ 的 `#define` 预处理宏）**：
   - C 语言的 `#define` 没有显式的调用前缀（随便一个普通标识符都可能是宏，读代码时防不胜防）；
   - 它会顺着 `#include` 污染整个编译单元甚至下游头文件；
   - 它不支持“按每 $N$ 个 Token 一组自动循环展开”，要把 10 对 `(名字, 值)` 变成 10 条 `const` 声明，你还是得写 10 行宏调用！

**核心诉求**：
我们需要一种**极致轻量、作用域严格限制在当前文件内、调用时必须显式带 `$` 前缀、且原生支持“按每 $N$ 个 Token 分组批量展开”**的局部 Token 模板工具！

---

## 二、 破局（v1）：三类 `define` 模板宏与 `$id` 显式展开

Flurry 的 **模板宏（Template Macro）**（见 `docs/macro/template-macro.md`）正是为此而生！它工作在词法阶段，直接将捕获到的源码 Token 序列代入替换体，然后再把展开后的结果交还给正常的语法、名称与类型检查器。

它的语法极其简洁，共提供 **三种捕获模式**：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                  Flurry 模板宏 (Template Macro) 的三种模式                   │
├────────────────────────┬──────────────────────────┬──────────────────────────┤
│ 模式名称               │ 1. 定义语法 (`define`)   │ 2. 调用语法 (`$`)        │
├────────────────────────┼──────────────────────────┼──────────────────────────┤
│ A. 固定 Token 个数     │ define name N {          │ $name tok₀ tok₁ ...      │
│    (Fixed Count)       │     ... $0 ... $1 ...    │ (自动向后捕获紧随的      │
│                        │ }                        │  精确 N 个 token)        │
├────────────────────────┼──────────────────────────┼──────────────────────────┤
│ B. 按组重复捕获        │ define name N ... {      │ $name                    │
│    (Repeated Groups)   │     ... $0 ... $1 ...    │   tok₀ tok₁              │
│                        │ }                        │   tok₂ tok₃              │
│                        │                          │ $  ◀── 末尾以 `$` 结束！ │
├────────────────────────┼──────────────────────────┼──────────────────────────┤
│ C. 命名参数序列捕获    │ define name(a, b) {      │ $name(1 + 2, x * y)      │
│    (Named Parameters)  │     ... $a ... $b ...    │ (圆括号内可含多个 token，│
│                        │ }                        │  按逗号分隔对应命名参数) │
└────────────────────────┴──────────────────────────┴──────────────────────────┘
```

> **💡 核心心智模型：如何一秒读懂模板宏里的 `\$` 符号？**
> 在阅读上面的 Flurry 代码时，你会看到两种 `$`：
> 1. **在 `define` 替换体内部**：`$0`、`$1`（编号从 `0` 开始）或 `$value` 代表**参数占位符**，展开时会被替换成捕获到的源码 Token；
> 2. **在宏调用处**：`$constant_function`、`$constants ... $`、`$print_value(...)` 以显式的 **`$` 前缀**发起调用（按组重复模式还在末尾加一个结束标记 `$`），让读者一眼就能看出“这里发生了一次局部模板宏展开”，绝不会与普通函数调用混淆！

### 演进到 `v1`：三招搞定函数生成、批量常量表与多 Token 表达式捕获

让我们把这三种模式放在一起，看看它们是如何消除文件中的重复样板的：

```flurry
use std.prelude.*;

-- 模式 A：固定捕获 2 个 token（$0 为函数名 token，$1 为返回值字面量 token）
define constant_function 2 {
    fn $0() -> i32 {
        $1
    }
}

$constant_function one 1
$constant_function two 2

-- 模式 B：按每 2 个 token 一组重复捕获（2 ...），直到遇见结束标记 $！
-- 每一组独立代入替换体，瞬间生成多条 const 声明！
define constants 2 ... {
    const $0 = $1;
}

$constants
    FIRST  10
    SECOND 20
    THIRD  12
$

-- 模式 C：命名参数捕获（圆括号内的整段 token 序列 `1 + 2` 都会赋给 $value！）
define print_value(value) {
    println("{}", $value);
}

test {
    println("funcs: {} {}", one(), two());
    println("consts sum: {}", FIRST + SECOND + THIRD);
    $print_value(1 + 2)
}
```

看看上面的模式 B（`define constants 2 ...`）：
在 `$constants` 和末尾的 `$` 之间，我们一口气写了 `FIRST 10 SECOND 20 THIRD 12` 共 6 个 Token。词法展开器自动把它们按每 2 个 Token 切成一组：
- 第 1 组 `(FIRST, 10)` $\implies$ `const FIRST = 10;`
- 第 2 组 `(SECOND, 20)` $\implies$ `const SECOND = 20;`
- 第 3 组 `(THIRD, 12)` $\implies$ `const THIRD = 12;`
三组结果按顺序无缝拼接，连每行开头的 `const`、等号 `=` 和末尾的分号 `;` 全都省掉了！

## 三、 严格边界：模板宏与 `quote fn` / CMTT 的分工红线（v2）

既然模板宏这么轻便，为什么我们还需要前面整整 11 篇讲的 CMTT 和 `quote fn`？在使用模板宏时有哪些必须警惕的边界？

`docs/macro/template-macro.md` 明确划定了四条核心边界：

1. **可见性严格限制在当前文件内（File-Local & Top-Down）**：
   模板宏**只在当前源文件内有效**，且必须按源码顺序**先 `define` 定义、后 `$name` 使用**。它不能导出到其他模块，彻底杜绝了 C 语言头文件宏跨模块污染的顽疾！
2. **模板宏是纯 Token 替换，参数出现多次就会求值多次！（与 `quote fn` 截然不同）**
   请特别注意：模板宏在词法阶段只做纯 Token 插入，**不会**像 `quote fn` 那样先对实参求值一次再绑定！如果在替换体里写了两次 `$x`，而调用者传了一个有副作用的函数调用，展开后就会执行两次！
   - **黄金选型法则**：如果只是省掉当前文件内的声明样板，用 `define` 模板宏；如果要封装带运行时求值契约、要求实参严格求值一次、或需要跨模块导出复用的代码组件，请务必使用 **`quote fn` 或 CMTT**！
3. **分组数量不匹配、漏写结束 `$` 或引用越界参数（如在 `define m 2` 里写 `$2`）会在词法展开阶段立即报错，绝不以残缺 Token 序列继续编译**。
4. **展开后的代码不享有任何“法外特权”**：模板宏展开后的结果会原封不动地交回编译器前端，继续接受完整的语法解析、名称绑定、类型检查、移动与效应检查！

让我们看看违反模板宏契约时的编译期拒绝例：

```flurry
-- 定义一个按每 2 个 token 一组重复的模板宏
define pair_constants 2 ... {
    const $0: u32 = $1;
}

-- 负例 1：按组重复调用提供的 token 总数不能被 2 整除（只给了 3 个 token）
-- ❌ 编译期直接拒绝！(词法宏展开阶段立即报错)
-- 最后一个分组缺少第 2 个 token ($1)，编译器绝不拿未初始化的参数继续展开！
$pair_constants
    ALPHA 1u32
    BETA
$

-- 负例 2：展开后的代码违反了 Flurry 的静态类型规则
-- ❌ 编译期直接拒绝！(展开后交由类型检查器捕获，报错同时保留调用位置与定义来源)
-- 将 "not_a_number" 代入 $1 后得到 `const BAD: u32 = "not_a_number";`，类型不匹配！
$pair_constants
    BAD "not_a_number"
$
```

### 演进到 `v2`：在状态机测试中结合模板宏与 CMTT

在实际工程中，模板宏与 CMTT 是一对互补的好搭档：我们可以用 CMTT 构建核心的状态机代码生成器，而在当前文件的单元测试末尾，用一個 3 行的 `define` 模板宏批量生成十几组状态机验收断言！

```flurry
-- 演进到 v2：用轻量模板宏消除当前文件内测试断言的重复样板
define assert_eq_pair 2 ... {
    assumes $0 == $1;
}

test {
    $assert_eq_pair
        (1 + 1) 2
        (20 + 22) 42
        (10 * 3) 30
    $
}
```

## 本篇小结

| 维度 | 模板宏（Template Macro：`define` / `$id`） | CMTT 与 `quote fn` |
| :--- | :--- | :--- |
| **工作阶段与操作对象** | 词法阶段，直接捕获与替换源码 `token*` 序列 | 类型与具象化阶段，操作带上下文类型的代码值 `< Ψ \|- T >` |
| **可见性范围** | 仅限当前文件内，按源码顺序先定义后使用 | 一等编译期值与模块成员，可跨模块、跨包导出与组合 |
| **三种捕获形式** | 固定个数 `define id N`、按组重复 `define id N ...`、命名 `define id(a)` | 普通参数、`comptime` 参数、`implicit quote`、`quote lambda` |
| **实参求值次数** | 纯 Token 替换（`$x` 出现多次则展开多次） | `quote fn` 普通实参严格只求值一次，拥有独立逻辑 `return` 边界 |

### 留给下一篇的悬念

到现在为止，我们已经认识了：
1. 重型、带完整上下文类型检查的 **CMTT（`'(...)`、`'<...>`、`quote fn`）**；
2. 极轻、只在当前文件内按固定个数或分组替换 Token 的 **模板宏（`define`）**。

但是，在这两者之间，还有一片非常广阔的中间地带：
- 比如，我想设计一种**自定义的领域特定语法（DSL）**——像类 SQL 查询语法、状态机箭头语法 `state A --(byte)--> state B`、或者自定义的声明块；
- 这种语法在展开前还不是标准的 Flurry 表达式（所以不能直接放进 CMTT 的 `'(...)` 里），但它又比简单的固定个数 Token 替换复杂得多——它需要在编译期**用真正的 Flurry 函数去巡检、切片、匹配和重组输入的 `TokenStream`**，甚至希望编译器能为宏的输入参数自动生成一张专属的 **LL(1) 语法解析器**！
