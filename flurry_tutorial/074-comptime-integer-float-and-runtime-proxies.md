# Flurry 演进手记 (074)：为什么整数字面量叫 Integer——编译期无限精度类型向运行时 Proxy 的 Splice 落地

在 C 或 C++ 里写底层或神经网络算子时，几乎每个工程师都踩过这样一个让人吐血的坑：
你想在代码里算一个张量缓存区的总字节数，或者一天的纳秒数，于是顺手写下：
`uint64_t total_ns = 24 * 60 * 60 * 1000 * 1000 * 1000;`
结果程序一跑，算出来的 `total_ns` 实际上是一个莫名其妙的负数截断值。
为什么？因为在 C 语言里，省略后缀的整数字面量 `24`、`1000` 默认是 32 位有符号 `int`。在赋给左边 64 位的 `uint64_t` 之前，右边的乘法已经在 32 位 `int` 里溢出爆炸了。为了防坑，你严禁不像念咒一样在每个数字后面贴满 `ULL`：`24ULL * 60ULL * ...`。

而在 Flurry 中，当你写下：
```flurry
let total_ns: u64 = 24 * 60 * 60 * 1000 * 1000 * 1000;
```
哪怕你在编译期算 $2^{256}$ 再除以 $2^{200}$，中间过程也**永免因为位宽欠缺而溢出**。

更有趣的是，如果你去查 Flurry 基础类型文档（`docs/basics/primitives.md`），你会发现一个关键事实：
**在 Flurry 中，省略后缀的整数字面量 `42` 的类型既非 `i32` 亦非 `i64`，它的原生类型名叫 `Integer`。而省略后缀的浮点字面量 `3.14` 的原生类型名叫 `Float`。**

为什么会有专门活在 $U_1$ 编译期宇宙里的 `Integer` 和 `Float`？它们在跨越宇宙落入 $U_0$ 运行时的时候，又是怎么变成 CPU 寄存器认识的 `i32`、`u8` 或 `f64` 的？
今天，我们就来揭开 Flurry 跨宇宙类型体系中最精妙的设计：**编译期专属无限精度类型（`Integer` / `Float`）** 与 **同名运行时代理（Runtime Proxy）**。

---

## 字面量过早绑定固定位宽的原罪

为什么传统语言里的整数字面量这么难用？
因为它们把**编译期数学常数（Mathematical Constant）**和**运行时硬件寄存器表示（Machine Word Representation）**混为一谈了。

1. **中间计算无谓溢出**：比如计算静态张量分块大小 `(1000000 * 1000000) / 500000`，最终结果 `2000000` 明明能轻松放进 `i32` 里，但因为中间乘积超过了 $2^{31}-1$，固定位宽字面量当场溢出报错；
2. **到处强写类型转换**：同一个常数 `4`，给数组下标用得是 `usize`，给量化权重偏置用得是 `i8`，给 GPU 线程块配置用得是 `u32`。如果字面量一出娘胎就被焊死成 `i32`，你的代码里就会充斥着毫无意义的 `.as(usize)`、`.as(u32)`。

---

## $U_1$ 编译期专属的数学王国——`Integer` 与 `Float`

在 Flurry 的 2LTT 双宇宙架构下，语言设计者做出了一个简洁清晰的决定：
**既然字面量最先诞生在编译期（$U_1$），那就让未加后缀的字面量拥有纯粹的编译期数学类型。**

- **`Integer`**：未加后缀的整数字面量（如 `0`、`42`、`1000_000_000_000_000_000`）的类型。它是**仅存在于 $U_1$ 编译期宇宙的任意精度整数（Arbitrary-Precision Integer）**。
- **`Float`**：未加后缀的浮点字面量（如 `0.5`、`3.14159265358979323846`）的类型。它是**仅存在于 $U_1$ 编译期宇宙的高精度浮点表示**。

这意味着，只要你的字面量运算发生在编译期 `Integer` 之间，你可以做任意大小的加减乘除、幂运算或循环边界计算，全然无须担心 32 位或 64 位寄存器溢出：

```flurry
-- 定义一个在编译期计算张量总元素数的纯编译期函数：
-- 参数和返回值可以直接使用编译期任意精度类型 Integer。
pure comptime fn giant_ratio(scale: Integer) -> Integer {
    -- 中间乘积高达 10^24，远超 u64 上限，但在 Integer 中精确无损。
    let numerator: Integer = 1_000_000_000_000 * 1_000_000_000_000 * scale;
    let denominator: Integer = 500_000_000_000_000_000_000_000;
    numerator / denominator
}
```

当然，如果你从一开始就明确想要一个固定位宽的整数字面量，你随时可以加上显式类型后缀，比如 `42i32`、`255u8`、`16usize`、`0.5f32`。

## 跨宇宙的两大家族——Comptime-Only 落地 vs 同名 Runtime Proxy

现在问题来了：既然 `Integer`、`Float` 还有 `Type` 都只活在 $U_1$ 编译期宇宙里，那当我们在普通的运行时函数里写 `let x: u8 = 200;` 或者 `let s: str = "conv2d";` 时，它们是怎么从 $U_1$ 来到 $U_0$ 的？

在 Flurry 中，跨越 $U_1$ 与 $U_0$ 的基础类型被清晰地划分为**两大家族**：

```
+-------------------------------------------------------------------------+
|  U1 编译期类型穿越到 U0 运行时的两大家族                       |
|                                                                         |
|  【家族 A：仅存于 U1 的编译期专属类型（Comptime-Only Types）】          |
|    • Type    ──► 🚫 严禁进入 U0 运行时存储  （没有运行时表示）          |
|    • Integer ──► 🌉 通过 Splice 落地为目标固定位宽整数：                |
|                  u8 / i8 / u16 / i16 / u32 / i32 / u64 / i64 / usize... |
|                  （无上下文约束时，默认落地为 i32）                     |
|    • Float   ──► 🌉 通过 Splice 落地为目标固定位宽浮点：                |
|                  f16 / f32 / f64 ...                                    |
|                  （无上下文约束时，默认落地为 f64）                     |
|                                                                         |
|  【家族 B：双宇宙同名代理类型（Same-Named Runtime Proxy Types）】       |
|    • bool, str, Symbol, 以及固定位宽数值 i32, u8, usize, f32...         |
|    • 它们在 U1 编译期宇宙中有完整的编译期实现，                         |
|      同时在 U0 运行时宇宙中拥有一个**同名的 Runtime Proxy（代理类型）**  |
|      通过 Splice 时，U1 的 `str` / `i32` 直接无缝映射为 U0 的同名类型   |
+-------------------------------------------------------------------------+
```

让我们结合具体的张量量化代码，看看这两大家族在编译期和运行时是如何表现的：

### 1. `Integer` 与 `Float` 的按需 Splice 与越界拦截

当你把一个编译期的 `Integer` 表达式交给运行时变量时，编译器会先在 $U_1$ 中以无限精度算出最终的 `Integer` 结果，然后在 **Splice 落地到目标固定位宽类型（如 `u8`、`i32`、`usize`）的那一刻**，检查最终结果是否落在目标类型的表示范围内。

```flurry
fn quantize_bias_demo() {
    -- ✅ 1. 中间过程在 U1 的 Integer 中高达 10^18，但最终结果是 200，
    --       Splice 到 u8 (0..=255) 时完全合法。
    let safe_byte: u8 = (1_000_000_000_000_000_000 / 5_000_000_000_000_000);

    -- ✅ 2. 当上下文没有指定具体整数类型时，Integer 默认 Splice 为 i32，
    --       Float 默认 Splice 为 f64：
    let default_int = 42;       -- 落地类型为 i32
    let default_flt = 3.14;     -- 落地类型为 f64

    -- ❌ 编译期直接报错。
    -- 编译期算出 Integer 结果为 300，在向目标类型 u8 (0..=255) 执行 Splice 时，
    -- 超出 u8 表示范围，编译期静态拦截。
    let overflow_byte: u8 = 150 + 150;
}
```

### 2. 为什么 `Integer` 禁止直接当成运行时变量存储？

因为 `Integer`（以及 `Float`、`Type`）属于家族 A（**Comptime-Only Types**），在 $U_0$ 运行时宇宙里**没有**名为 `Integer` 的硬件寄存器类型。如果你试图声明一个运行时的 `Integer` 参数或结构体字段，编译器会立刻报错：

```flurry
-- ❌ 编译期直接报错。
-- `Integer` 是仅存在于 U1 编译期的任意精度整数类型，禁止充当 U0 运行时参数存储。
-- 请改为：`comptime x: Integer`，或者使用具有运行时表示的固定位宽类型如 `x: i64`。
fn bad_runtime_integer_param(x: Integer) -> i32 {
    0i32
}
```

### 3. 家族 B：双宇宙同名代理（`str`、`Symbol`、`bool`）

那为什么 `str`、`Symbol`、`bool` 既能写在 `comptime fn` 里，又能写在普通运行时 `fn` 里呢？
因为它们属于家族 B。
- 在 $U_1$ 编译期宇宙里，`str` 是编译器内部管理的不可变 UTF-8 字符串切片，你可以对它做编译期解析（比如刚刚在第 072 篇见到的 `ParseFormat(format)`）；
- 在 $U_0$ 运行时宇宙里，有一个同名的运行时代理类型 `str`（指向目标二进制只读数据段或运行时切片的 UTF-8 字符串视图）。
当你把编译期的 `str` 传给运行时代码时，`Splice` 就像一座隐形天桥，自动把 $U_1$ 的编译期字符串物化为 $U_0$ 的运行时同名代理 `str`。

## 本篇小结

| 类型类别 | 代表类型 | 在 $U_1$（编译期）的身份 | 在 $U_0$（运行时）的落地方式（`Splice`） |
| :--- | :--- | :--- | :--- |
| **编译期专属数值** | `Integer`、`Float` | 任意精度整数与高精度浮点数（未加后缀字面量的原生类型） | 不可直接作为运行时类型存储；按目标上下文 `Splice` 为 `i32`/`u8`/`usize`/`f64` 等固定位宽类型（无约束时默认 `i32` / `f64`），并在落地时严格检查范围 |
| **编译期专属元类型** | `Type` | 所有类型的类型（活在 $U_1$） | 无运行时表示，严禁进入 $U_0$ 运行时值存储 |
| **双宇宙同名代理类型** | `bool`、`str`、`Symbol`、`i32`、`u8`、`usize`、`f32`... | 具备完整的编译期值语义与运算能力 | 在 $U_0$ 拥有同名的 **Runtime Proxy**，`Splice` 时直接映射为对应的运行时类型 |

### 下一篇预告

看到这里，我们的静态形状张量库 `Tensor` 已经拥有了编译期维度、Normal-Form 类型身份、`where` 子句推导以及无限精度 `Integer` 计算。

现在，我们要进入第四卷的收官之战——**在运行时张量算子的函数体内部，嵌入编译期结构生成与循环展开。**

想象一下：
1. 在一个 3x3 卷积核或小维度张量点积算子里，我们不想在运行时跑带分支跳转的 `for` 循环，而是想用 **`inline for i in 0 .. 9`** 让编译器在编译期把循环**摊平（Unroll）**成 9 条紧挨着的乘加指令。
2. 更进一步，如果我们有一个异构张量元组 `tensors: Tuple<Tensor<f32, 4>, Tensor<i32, 8>, bool>`，普通运行时 `for` 循环根本没法遍历它（因为每个元素的类型都有所差异。）。但如果我们用 **`inline for (idx, elem) in tensors'tuple_enumerate`** 呢？
3. 在一个运行时函数内部，我们想用 **`comptime { ... }`** 块现场算一个常量，或者用 **`inline if`** 根据通道数选择不同的硬件加速分支——那么没被选中的分支，还会被编译器做类型检查吗？

下一篇 **`075-comptime-blocks-and-inline-control-flow.md`**，我们将用 `comptime { ... }` 块、`inline if` 与 `inline for` 完成第四卷的华丽收官。
