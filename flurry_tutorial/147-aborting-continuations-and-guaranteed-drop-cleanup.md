# Flurry 演进手记 (147)：当 Continuation 被中止（Abort）时——跨越挂起栈帧的 Drop 逆序清理保证

> **系列导读**：在上一期（146）中，我们了解了如何用 `catch continuation: builtin.Continuation` 捕获挂起的剩余计算，并懂得了为什么单次恢复（One-Shot）契约是防止栈上唯一资源被双重释放（Double Free）的基石。但硬币还有另一面：如果双重恢复会导致 **Double Free**，那么**“0 次恢复（捕获了 Continuation 却决定放弃不恢复它）”**会不会导致挂起栈帧上的资源**永远不被析构（Memory / Resource Leak）**？今天，我们将揭开 Flurry 协程与限定 Continuation 最令人安心的安全底牌——**放弃清理协议（Abandonment Protocol）**、**隐藏中止通道**与 **C 栈帧屏障**。

## 一、协程与生成器的“半途而废”难题：传统方案的资源泄漏难题

在编写流式数据管道或带超时的微型运行时任务时，“只取前几个结果就提前停止”是再常见不过的操作：
- 一个传感器采样生成器 `produce()` 准备在循环里连续产出 1000 个采样值，并在进入循环前打开了一个硬件总线锁卫兵 `let trace = ProducerTrace {};`；
- 外层的消费者只需要取**第 1 个**采样值做健康检查，拿到第 1 个值后，消费者直接退出了 Handler，不再调用 `resume`。

在传统的无栈协程或粗糙的有栈协程库中，当你直接丢弃一个处于挂起状态的协程句柄时，往往面临两种糟糕的结局：
1. **直接回收栈内存，跳过析构函数**：协程栈上的局部变量 `trace` 根本没机会运行 `Drop::drop`，硬件总线锁永远没有释放，整个系统瞬间死锁。
2. **伪装成普通业务异常往上抛**：把取消协程伪装成一个普通的业务错误或异常抛回挂起点——结果被协程内部某段业务代码写的 `catch (_)` 兜底逻辑不小心吞掉了，协程非但没停下来，反而还在后台继续诈尸运行。

Flurry 是如何用一套严密的生命周期协议，彻底解决这两个问题的？

## 二、只取第一个值就退出——见证 `ProducerTrace` 的自动清理

在 Flurry 中，我们上一期就强调过：**`builtin.Continuation` 本身就是一个严格的 `Once` 线性资源**。
这不仅意味着你不能把它复制两份，还意味着：**如果你在 Handler 分支里既没有用 `resume` 消费它，也没有把它转移（Move）进调度队列，那么当 `continuation` 离开当前分支作用域时，就会自动触发它的放弃清理协议（Abandonment Protocol）。**

让我们把上一期的 `produce()` 拿过来，在 Handler 分支里打印完第一个数字后**故意不写 `resume;`**，看看会发生什么：

```flurry
effect yield_number(value: u32, catch continuation: builtin.Continuation);

struct ProducerTrace {}

impl Drop for ProducerTrace {
    fn drop(*self) -> void {
        println("cleanup producer");
    }
}

fn produce() -> #[yield_number] void {
    let trace = ProducerTrace {}
    for value in 0u32..3u32 {
        yield_number(value)#;
    }
    -- ⚠️ 注意：如果第一轮挂起后没有被恢复，这行代码绝不应该被执行。
    println("finished");
}

test {
    (produce()# {
        yield_number(value, continuation) => {
            println("first: {}", value);
            -- 注意：这里没有调用 resume。
            -- 当分支结束时，尚未消费的 continuation 离开作用域，自动触发放弃协议。
        },
    }).use(pool);
}
```

运行这段代码，控制台精确地输出：
```text
first: 0
cleanup producer
```

请注意观察这两条输出背后的深刻含义：
1. `println("finished")` **没有执行**——因为我们在 `value == 0` 挂起时放弃了剩余计算，后续循环和循环后的正常代码被彻底中止；
2. `cleanup producer` **准时执行了**——尽管 `produce()` 的栈帧当时正处于暂停挂起状态，Flurry 运行时绝不会粗暴地只把栈内存还给 `pool` 了事，而是精准地清理了挂起栈帧上尚存的局部变量 `trace`。

## 三、隐藏中止通道（Hidden Abort Channel）是如何工作的？

当 `continuation` 在未恢复的状态下离开清理范围时，Flurry 的控制后端在幕后到底做了什么？

```text
  [ Handler 分支退出，发现手头的 continuation 尚未消费且未被转交 ]
                                │
                                ▼
  ┌─────────────────────────────────────────────────────────────────────┐
  │ 1. 启动【隐藏中止通道（Hidden Abort Channel）】重新切入被挂起的计算 │
  │    （从挂起点 yield_number(0)# 开始，沿着挂起调用链向限定边界回退） │
  ├─────────────────────────────────────────────────────────────────────┤
  │ 2. 按作用域声明逆序（LIFO），依次执行挂起栈帧上所有尚存资源的清理： │
  │    ──► 执行 defer 块与活跃局部变量（如 trace）的 Drop::drop()       │
  │    ⚠️ 核心规则：此通道【不属于用户错误行 !Err】，绝不经过用户 catch arm  │
  ├─────────────────────────────────────────────────────────────────────┤
  │ 3. 到达本次 Handler 的限定边界（Delimited Boundary）后立即停止      │
  │    确认所有恢复权、借用与环境依赖均已终结后，                       │
  │    将不再存活的执行栈槽安全归还给其分配来源实例 pool                │
  └─────────────────────────────────────────────────────────────────────┘
```

### ⚠️ 为什么“隐藏中止通道”绝对不能走用户的错误处理分支（`! { catch ... }`）？

这是 Flurry `effect-abi` 中最关键的一条设计隔离线：
> **放弃（Abort）通过独立于用户错误结果 ABI 的隐藏中止通道执行尚存责任的清理；中止不属于用户错误行，绝不经过用户的 `catch` 分支。**

设想一下，如果 `produce()` 内部在调用 `yield_number(value)#` 的外围包了一层业务错误重试逻辑：
- 用户写 `expr! { catch err => ... }` 的本意是处理业务上的 `ParseErr` 或 `TimeoutErr`；
- 如果把 Continuation 的放弃伪装成一个能被用户 `catch` 捕获的错误，那么内部代码一旦拦截了这个错误并 `continue` 循环，外部 Handler 明明已经退出了，内部的被挂起计算却无法被终止。
- 通过将 **隐藏中止通道** 与 **用户错误结果 ABI** 彻底物理隔离，Flurry 保证了：一旦恢复权被放弃，被挂起的计算就只能老老实实按逆序执行 `Drop` 和 `defer` 清理直到限定边界，任何业务错误处理器都无法劫持或阻止这一清理过程。

## 四、深入微型运行时：当 Continuation 被移入调度队列，或者跨越 C 语言栈帧时

在构建我们的微型运行时调度器时，关于 Continuation 的生命周期还有两个必须掌握的高级法则：

### 法则 1：转移所有权（Transfer to Queue）vs 放弃（Abandon）

在协程调度器里，当一个任务调用 `pause()#` 挂起时，Handler 分支通常会把这个 `continuation` **移动（Move）进运行时的就绪队列 `ready_queue.push(continuation)`**，然后结束当前分支去调度下一个任务。

这时候，当前 Handler 分支结束时会触发放弃清理吗？
**当然不会。** 因为根据第三卷的位置树移动规则，当你执行 `ready_queue.push(continuation)` 时，`continuation` 的唯一消费责任已经**转移给了队列**。原分支不再持有该恢复权，自然不会在退出时中止它；等到将来某个事件到达、调度器从队列里弹出这个 `continuation` 并恢复它（或者当整个队列被销毁且任务被取消）时，才由当时的唯一持有者负责恢复或放弃清理。

```text
[ 调度队列中的恢复权状态机 ]
  请求挂起 ──► 分支取得 K1 ──(Move 转移责任)──► 存入等待队列 Queue（原分支退出时不触发放弃。）
                                                      │
                        ┌─────────────────────────────┴─────────────────────────────┐
                        ▼ (正常事件到达：移出并恢复)                                ▼ (任务取消/队列销毁：放弃)
               消费 K1 并切入继续执行                                      走隐藏中止通道逆序 Drop 挂起帧并归还栈
```

### 法则 2：C 语言栈帧屏障（The C Frame Barrier）

如果在被捕获的挂起区域中间，夹着一层通过 FFI 调用的 **C 语言函数栈帧**（即 `Flurry 主体 -> C 函数 -> 回调回 Flurry -> 发起 yield# 挂起`），会发生什么？

Flurry 的 ABI 对此做出了极其诚实且安全的规定：
1. **允许挂起并随后恢复（Suspend & Resume OK）**：只要由于栈池地址稳定，保留中间的 C 栈帧并在稍后正常 `resume` 恢复它是完全合法的；
2. **严禁跨越 C 栈帧执行放弃（Abort Across C Frame Forbidden）**：因为 C 语言栈帧内部可能持有未知的 `malloc` 内存或操作系统锁，而 C 语言没有 Flurry 的隐藏中止清理元数据，**绝对不能静默跳过 C 栈帧去假装完成了资源清理**。如果编译器无法在编译期静态排除这种跨越 C 栈帧的放弃，就会保留运行时屏障检查——一旦在运行期真正发生越过 C 栈帧屏障的放弃操作，将立即触发确定性的安全 `trap`，绝不静默破坏内存或泄漏未知的外部资源。

## 五、本节核心概念速查表

| 场景 / 机制 | 运行时与编译器行为 | 核心安全保证 |
| :--- | :--- | :--- |
| **正常消费恢复权** | 在分支内调用 `resume`（或显式恢复） | 消费当前单次令牌，继续执行主体直至完成或下次挂起 |
| **转移恢复权所有权** | 将 `continuation` 移动（Move）入队列/结构体 | 责任移交新持有者，当前分支退出时不触发中止清理 |
| **放弃恢复权（Abort）** | 未恢复也未转移的 `continuation` 离开作用域 | 触发**隐藏中止通道**，沿挂起帧逆序执行 `Drop` 与 `defer`，随后归还栈槽 |
| **隐藏中止通道隔离** | 独立于 `!Err` 错误返回 ABI | 绝不经过用户的错误 `catch` 分支，防止清理过程被业务逻辑意外吞没 |
| **C 栈帧屏障** | 挂起链中含有外部 C ABI 栈帧 | 允许正常挂起与恢复；**禁止跨越 C 帧放弃**（实际越界放弃触发安全 `trap`） |
