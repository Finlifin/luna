# Flurry 演进手记 (004)：为什么 a<b 不是小于号——词法边界、空白规则与省略分号的哲学

在 [上一篇 (003)](./003-let-does-not-freeze-your-object.md) 中，我们打造了一台支持热切换的传感器监控器 `SensorMonitor`。当时在写代码示例时，你一定注意到了几条我们在“语法小贴士”里顺手提过的规矩：
- 写小于号时，我们写了 `attempts < 3u8`，两边各留了一个空格；
- 写 `let monitor = SensorMonitor { channel: 1u8 }` 时，末尾居然没有写分号 `;`；
- 写单行注释时，我们用了 `--` 而不是 `--`。

今天，当我们准备给 `SensorMonitor` 加上**泛型采样窗口配置**、**阈值比较告警**以及**底层硬件 C 接口绑定**时，一个刚刚从 C++ 或 Rust 转过来的同事接手了键盘。他凭着肌肉记忆敲下了 20 行代码——结果编译器报出了一连串让他瞪大眼睛的词法与语法错误。

为什么 Flurry 要在“空格”、“分号”和“花括号边界”上定下这些看似独特的规矩？难道只是为了标新立异吗？
恰恰相反。这些规则是为了**在词法与语法的第一道关口，零代价地消灭困扰了 C++ 和 Rust 几十年的语法歧义顽疾**。

让我们从那位同事写下的 初始代码开始，亲历一场“编译器的眼睛是怎么看代码的”奇妙旅程。

## 一、 带着 C++/Rust 肌肉记忆踩中的三个坑

假设我们要写一个阈值检查函数：如果传感器读数减去基线偏置后小于阈值，或者处于某个配置结构体的启用状态，就触发采样。

同事一口气写下了这样的 初始代码：

```flurry
-- ❌ 编译期直接拒绝：（包含多处 C++/Rust 习惯导致的词法与语法错误）
use std.prelude.*;

struct ThresholdConfig {
    enabled: bool,
    limit: i32,
}; -- 坑 1：多余的 `};`

fn check_reading_initial(reading: i32, offset: i32) -> bool {
    let adjusted = reading-offset;        -- 坑 2：`-` 两侧没有空格。
    if adjusted<10i32 {                   -- 坑 3：`<` 两侧没有空格。
        return true;
    };                                    -- 坑 1：多余的 `};`

    if ThresholdConfig { enabled: true, limit: 10i32 }.enabled { -- 坑 4：花括号边界。
        return true;
    }
    false
}
```

这段代码在 C++ 或 Rust 程序员眼里再正常不过了，但在 Flurry 编译器眼里，它却寸步难行。
让我们先把最显眼的**空白规则**和**分号规则**拎出来，看看编译器到底看到了什么。

## 二、 空白敏感的中缀运算符——终结 `>>` 与 `::<T>` 的千古难题

为什么 `reading-offset` 和 `adjusted<10i32` 会被拒绝？

先问一个困扰了编程语言设计者四十年的问题：
在拥有泛型 `Foo<T>` 的语言里，当你写下下面这行代码时，`<` 和 `>` 到底是**泛型尖括号**，还是**小于号/大于号**，或者是**右移运算符 `>>`**？

```text
  C++98 的难题：
  vector<vector<int>> matrix;
                   ^^ 词法器直接切成了右移运算符 `>>`。逼着全世界程序员写了十几年 `> >`。

  Rust 的做法（Turbofish `::<T>`）：
  let x = foo<Bar>(1);
             ^ 如果允许直接写 `foo<Bar>(1)`，解析器根本分不清这是泛型调用，
               还是 `(foo < Bar) > (1)` 的比较表达式。
               于是 Rust 被迫发明了 `foo::<Bar>(1)` 这种略显突兀的“比目鱼”语法。
```

为什么 C++ 和 Rust 会陷入这个泥潭？
因为它们的词法器** completely 忽略了人类排版时最自然的视觉信号——空白（Whitespace）**。

你想想看：任何一个神志清醒的程序员，在写泛型类型的时候都会紧贴着写 `BitVec<4>`、`Array<Array<i32, 2>, 2>`；而在写小于号比较的时候，都会在两边留出呼吸感：`a < b`。

Flurry 敏锐地捕捉到了这一直觉，将它升格为了一条简洁、确定、零回溯的词法核心规则（详见 `docs/basics/lexical.md` 与 `docs/grammar/index.md`）：

> **当 `+`、`-`、`*`、`/`、`%`、`<`、`>`、`<=`、`>=` 的两侧都有空白（空格、制表符、换行等）时，词法器将其识别为中缀二元运算符；只要至少有一侧紧贴着非空白字符，它就不是中缀运算符。**

下面来看看词法器（Lexer）是如何在毫秒之间完成分流的：

```text
  源码输入流                   两侧都有空白？         词法器产出的 Token 角色
  ───────────────────────────  ──────────────  ──────────────────────────────────────
  1. `adjusted < 10i32`            ✅ 是        `adjusted`  [中缀小于 <]  `10i32`
  2. `BitVec<4>`                   ❌ 否        `BitVec`    [泛型左括 <]  `4`  [泛型右括 >]
  3. `Array<Array<i32, 2>, 2>`     ❌ 否        嵌套泛型右括号 `>>` 自动拆解，绝不误判为右移。
  4. `reading - offset`            ✅ 是        `reading`   [中缀减号 -]  `offset`
  5. `-42` 或 `call(-x)`           ❌ 否        [前缀负号 -] `42` / `x`
  6. `ptr.*`                       ❌ 否        `ptr` `.`   [后缀解引用 *]
  7. `*u32`                        ❌ 否        [前缀指针类型 *] `u32`
```

你看，仅仅依靠“两侧空白”这一个极其轻量、而且本来就符合全人类代码格式化规范的约束，Flurry 一举收获了三大红利：
1. **泛型永远不需要写 `::<T>`（Turbofish）**：无论是类型位置还是表达式位置，`foo<u32>(x)` 紧贴着写就是泛型应用，`foo < u32` 空开写就是比较运算，词法阶段就已经泾渭分明。
2. **彻底告别 `>>` 歧义与位运算混淆**：况且 Flurry 本就没有 `>>` 右移运算符，再配合空白规则，多少层泛型嵌套 `Foo<Bar<Baz<u8>>>` 都稳如泰山。
3. **`*` 与 `-` 的多重身份瞬间消歧**：中缀乘法 `a * b`、前缀指针类型 `*T`、后缀解引用 `p.*`，以及中缀减法 `a - b` 与前缀取负 `-x`，全部在词法扫描的一瞬间各归其位。

## 三、 分号省略法则与外层结构边界——为什么 `if` 不会吞掉花括号？

修正了运算符两侧的空格后，我们再来看前面代码中的另外两个问题：**分号 `;`** 与 **`if` 条件里的结构体构造**。

### 1. 谁决定了用逗号 `,` 还是分号 `;`？什么时候省略 `;`？

在很多语言里，程序员经常搞不清什么时候该写 `};`，什么时候不该写：
- C/C++ 里，`struct Foo { ... };` 必须加分号，但 `void bar() { ... }` 又不用加分号；
- Rust 里，`let x = if cond { 1 } else { 2 };` 必须加 `};`，但作为独立语句的 `if cond { ... }` 又不用加 `;`。

Flurry 把分隔符规则彻底统一成了两条极其纯粹的公理（详见 `docs/grammar/index.md`）：

1. **分隔符由“当前项自身的语法类别”决定，而不是由外层大括号决定**：
   - **一般项**（结构体字段、函数参数、`match` / `when` 的分支臂、元组元素等）：项与项之间一律用**逗号 `,`**。
   - **语句与语句级定义**（`let`、`var`、`return`、普通表达式语句、`fn`、`struct` 等）：句与句之间一律用**分号 `;`**。
2. **右花括号吞分号原则**：
   - **当任何一条语句或定义的最后一个 token 已经是 `}` 时，它后面本应出现的分号 `;` 省略不写。（永远不要写 `};`）**

让我们画张图对比一下：

```text
  示例 A：最后一个 token 是 `)` 或标识符 ──► 必须写 `;`
  let x = compute(10);
                     ▲ 最后一个 token 是 `)`，后面写 `;`

  示例 B：最后一个 token 是 `}` ──► 省略 `;`。
  let monitor = SensorMonitor { channel: 1u8 }
                                             ▲ 最后一个 token 是 `}`，不写 `;`。

  let grade = score match {
      90..=100 => "A",   ◄── match 臂是“一般项”，臂与臂之间用逗号 `,`
      _ => "B",
  }                      ◄── 整条 let 语句最后一个 token 是 `}`，省略 `;`。
```

哪怕是在同一个 `struct` 内部，字段定义（一般项，用 `,`）和关联函数定义（以 `}` 结尾的语句级项，省略 `;`）也能和谐共处，再也不用背诵“哪种大括号后面要加分号”的绕口令了。

### 2. 外层结构边界：为什么 `if cond { ... }` 的 `{` 不会被条件吞掉？

再看前面代码中的第 4 个坑：

```flurry
-- ❌ 编译期直接拒绝。
if ThresholdConfig { enabled: true, limit: 10i32 }.enabled {
    true
}
```

为什么这行代码在 `if` 条件里直接写 `ThresholdConfig { ... }` 会出问题？
这涉及到所有拥有 `Type { field: val }` 语法和后缀扩展应用 `expr { ... }` 的语言（包括 Rust 和 Go）都必须面对的核心解析问题：**外层结构边界（Outer Structural Boundary）**（详见 `docs/grammar/index.md`）。

在 Flurry 中，`expr { ... }` 是一种通用的**后缀扩展应用（Extended Application）**语法（结构体构造 `ThresholdConfig { ... }` 也是它的体现）。
想象一下，当你写下：

```flurry
if enabled {
    true
}
```

如果没有边界限制，解析器读完条件里的标识符 `enabled` 后，抬头看到后面紧跟着一个 `{`——它怎么知道这个 `{` 是 **`if` 分支体的开始**，而不是把 `enabled { ... }` 当成一次后缀扩展调用呢？

为了保证 `if`、`while`、`for` 等控制流结构绝不产生歧义，Flurry 的解析器实施了严格的**外层边界传递**：

```text
  解析 `if <条件> { <主体> }` 时的边界锁：

  if   enabled   { return true; }
       ───────   ▲
          │      └── 外层 `if` 声明：“我后面需要一个 `{` 作主体。
          │          条件表达式在最外层遇到 `{` 时必须立刻停下，不准吞掉它。”
          ▼
     条件在此结束。
```

更精妙的是，**这条边界限制还会穿透 `matches` 传递给它内部的模式**。
试想如果你写：

```flurry
enum Signal {
    empty,
    data { value: i32 },
}

fn check_signal(sig: Signal) -> bool {
    -- ✅ 完全合法。外层边界穿过 `matches` 传给 `.empty`，
    -- 所以 `{` 不会被当成 `.empty { ... }` 的模式载荷，而是稳稳地作为 `if` 的主体。
    if sig matches .empty {
        true
    } else {
        false
    }
}
```

那么，如果我们**真的**想在 `if` 条件里构造一个结构体，或者在 `matches` 里匹配带花括号的 `.data { value: _ }`，该怎么告诉编译器“里面的 `{ ... }` 属于我，外面的 `{ ... }` 才属于 `if`”呢？

答案简单极了：**用圆括号 `( ... )` 划出封闭的内部范围。**
一旦进入圆括号 `(`，解析器就知道在遇到配对的 `)` 之前，里面的 `{ ... }` 绝不可能是外层 `if` 的主体，因此恢复完整的扩展应用解析：

```flurry
fn check_with_parens(sig: Signal) -> bool {
    -- ✅ 圆括号内的 `{ ... }` 属于 ThresholdConfig 构造，括号外的 `{` 属于 if。
    if (ThresholdConfig { enabled: true, limit: 10i32 }).enabled {
        return true;
    }

    -- ✅ 圆括号内的 `{ value: _ }` 属于 .data 模式，括号外的 `{` 属于 if。
    if (sig matches .data { value: _ }) {
        return true;
    }

    false
}
```

## 四、 嵌套块注释 `{- ... -}` 与“去关键字化”的 ABI 属性

现在，我们要把 `check_reading` 接入底层的硬件 C 驱动库，并在调试时临时注释掉一大段已经包含注释的代码。

在 C、C++ 或 Java 中，当你用 `/* ... */` 临时注释掉一段代码时，如果那段代码里恰好已经有一条 `/* 内部注释 */`，外层的 `/*` 就会和内层的第一个 `*/` 提前配对，导致剩下的半截代码裸露在外，引发雪崩式的编译错误。

在 Flurry 中：
- 单行注释使用 **`--`**；
- 块注释使用 **`{- ... -}`**，并且**原生支持任意层级的嵌套**。

而且，当你翻开 `docs/basics/lexical.md` 的关键字表，准备声明一个遵循 C 语言调用约定（ABI）的驱动回调函数时，你会发现一个惊人的事实：
**Flurry 里根本没有 `extern` 关键字。甚至连 `Type`、`Any`、`u32`、`attrs`、`builtin` 都不是词法关键字。**

为什么？因为 Flurry 极其克制地保护着词法命名空间的纯洁性：
- 像 `u32`、`Type`、`Any` 只是内置环境（`builtin.prelude`）中绑定的普通编译期名称，按正常的作用域规则解析；
- 而函数的调用约定（ABI）属于编译期元数据，直接通过通用的 **`^expr` 属性前缀**（写作 `^attrs.abi(.c)`）来挂载，根本不需要专门为此污染一个 `extern` 关键字。

让我们把这一章学到的所有词法与语法智慧融合在一起，写出清晰无歧义的完整代码：

```flurry
use std.prelude.*;

struct ThresholdConfig {
    enabled: bool,
    limit: i32,
}

{-
  外层块注释：即使内部包含内层块注释，也能正确配对嵌套。
  {-
    内层注释：旧版调试逻辑已废弃
    let old = a + b;
  -}
-}

-- 没有 `extern` 关键字。使用 `^attrs.abi(.c)` 属性指定 C ABI
^attrs.abi(.c)
fn check_reading(reading: i32, offset: i32) -> bool {
    -- 1. 二元运算符 `-` 和 `<` 两侧留出空白
    let adjusted = reading - offset;
    if adjusted < 10i32 {
        return true;
    } -- 2. 以 `}` 结尾，省略分号。

    -- 3. 用圆括号包裹条件内部带 `{}` 的结构体构造，与 if 主体边界清晰分离
    if (ThresholdConfig { enabled: true, limit: 10i32 }).enabled {
        return true;
    }

    false
}

test {
    assumes check_reading(12i32, 5i32);
    assumes check_reading(50i32, 0i32);
}
```

> **🔍 语法小贴士：属性前缀 `^expr` 是怎么挂载的？**
> 看到 `^attrs.abi(.c)` 了吗？在 Flurry 中，任何以 `multi` 列表规则解析的语法元素（比如顶层定义、结构体字段、甚至是函数调用里的每一个实参。）前面，都可以递归地挂载任意多层 `^expr` 属性前缀（由内向外生效）。比如在调用函数时写 `keep_flag(^{ trace: 1 } true)`，属性精确地修饰 `true` 这个实参，绝不会改变实参求值次数或吞掉后面的标识符。

## 本篇小结

通过上述几个示例的对比，我们看清了 Flurry 表面语法背后深思熟虑的工程权衡：

| 表面规矩 | 错误示范 (`初版`) | 正确写法 (`完整版`) | 背后的设计哲学 |
| :--- | :--- | :--- | :--- |
| **中缀运算符空白** | `reading-offset`、`a<b` | `reading - offset`、`a < b` | 在词法期将中缀运算与泛型 `<T>`、前缀 `-x`、后缀 `.*` 彻底分离，消灭 `>>` 与 `::<T>` |
| **省略末尾分号** | `if cond { ... };` | `if cond { ... }` | 分隔符由项自身决定；凡以 `}` 结尾的语句/定义一律省略 `;`，消除视觉噪音 |
| **外层结构边界** | `if Config { ... }.ok {` | `if (Config { ... }).ok {` | 防止条件或 `matches` 模式把 `if` 主体的 `{` 误吞为后缀扩展应用 |
| **注释与关键字** | `/* ... */`、`extern "C"` | `{- ... -}`、`^attrs.abi(.c)` | 块注释支持安全嵌套；用统一的属性系统替代零散的修饰符关键字 |
