# Flurry 演进手记 (053)：“纯函数”不是非黑即白——运行时纯度的六层阶梯（P0 到 P5）全解

在 [第 023 篇](./023-why-default-params-require-p3-stability.md) 讨论默认参数时，我们第一次听说了 `P3`（稳定观测）；在 [前两篇 (051 & 052)](./052-exit-states-and-fact-preservation.md) 讨论内存效果与契约时，我们又看到了 `P0`、`P1`、`P2`、`P4` 和 `P5`。

如果你学过 Haskell、或者在 C/C++ 里用过 `__attribute__((pure))` / `__attribute__((const))`、或者在 Rust 里写过 `const fn`，你可能会问：
> **“一个函数要么有副作用，要么是纯函数（Pure），为什么 Flurry 非要把运行时纯度拆成 `P0` 到 `P5` 足足六层阶梯？”**

为了回答这个问题，让我们先来做三个关键工程问题：

1. **考题一（读取指针算不算纯？）**：
   函数 `load_value(source: *i32) -> i32` 只做了一件事：`source.*`。它没有任何写入，没有任何 I/O。
   如果我们在 `var v = 1; let a = load_value(v.ref); v = 2; let b = load_value(v.ref);` 里调用它两次，因为传入的指针地址 `v.ref` 完全相同，编译器能把第二次调用直接消除、复用第一次的结果 `1` 吗？**当然不能。** 但如果在两次调用之间，编译器已经证明没有任何代码写入 `v` 呢？这时候就**可以复用**了。
2. **考题二（死循环算不算纯？）**：
   函数 `pure fn spin() { while true {} }` 没有任何外部写入，也没有任何 I/O，它的结果完全由输入决定（实际上不返回结果）。
   如果有人写了 `spin(); println("done");`，编译器看到 `spin()` 是纯函数且返回值没人用，能把 `spin()` 当死代码直接删掉吗？**绝对不能。** 删掉它，原本永远不打印 `"done"` 的程序就会突然打印出 `"done"`。
3. **考题三（返回相同内容的新字符串算不算纯？）**：
   函数 `fresh_text() -> String` 每次都在堆上分配一块独立缓冲区，里面装着 `"same"`。
   虽然每次返回的字符串内容都一模一样，编译器能把 `let s1 = fresh_text(); let s2 = fresh_text();` 优化成只调一次、然后把 `s1` 按位复制给 `s2` 吗？**绝对不能。** 那样退出作用域时同一块堆内存就会被 `Drop` 释放两次（Double Free）。

看到了吗？
**“只读内存”、“在某个区间内状态版本不变”、“不依赖可变内存版本”、“生成新资源身份”以及“保证有限步内终止”**，是五个完全正交、对应着完全不同编译器优化前提与语言契约的维度。
把它们笼统地塞进一个“纯函数”标签里，要么逼得你连指针都不敢读，要么会导致编译器做出引发崩溃或死循环的错误优化。

今天，我们就把 Flurry 的 **`P0` 到 `P5` 六层运行时纯度阶梯** 彻底拆解清楚。

## 一、 把所有“只读/无副作用”混为一谈引发的三大惨案

假设一门假想的语言没有区分 `P1`、`P2`、`P3`、`P4` 和 `P5`，只有一个粗糙的“无写入即可随意复用/删除”概念。看看下面的代码会发生什么（详见 `docs/resource-management/runtime-purity.md` 常见示例）：

```flurry
use std.prelude.*;

-- 场景 1：只读指针（P2），但跨过了外部修改
fn load_value(source: *i32) -> i32
where outcomes read<source>
{
    source.*
}

-- 场景 2：无外部写入但发散的死循环（P4，但非 P5。）
pure fn spin() {
    while true {}
}

fn never_prints() {
    spin();
    println("done");
}

test {
    var value = 1i32;
    let first = load_value(value.ref);
    value = 2i32;
    -- 惨案 A：如果只看“load_value 只读 + 两次传入的指针位值 value.ref 相同”就做 CSE 复用，
    -- second 就会错误地变成 1，而不是真实的 2。
    let second = load_value(value.ref);
    println("{} {}", first, second);
}
```

在 Flurry 中，上面这段 `test` 严格输出 `1 2`；而在 `never_prints` 中，因为 `spin()` 虽然是 `P4` 但不是 `P5`（未证明有限完成），编译器**绝不会**删除 `spin();`，从而严格保留了“永不打印 `done`”的程序语义。

## 二、 一张图看懂 `P0` 到 `P5` 的六层纯度阶梯

首先记住一条基本原则：
**`P0`–`P5` 是编译器分析器与语言规范中的六个层级记号（不是六个语法关键字。语法上的关键字只有 `pure`、`spec`、`predicate`、`verified` 等）。**
这六层由下向上层层递增，具有严格的包含关系：**`P5` $\subset$ `P4` $\subset$ `P3` $\subset$ `P2` $\subset$ `P1` $\subset$ `P0`**（高级别永远可以用于要求低级别的位置）。

下面通过全景图，沿着阶梯从 `P0` 一步步爬到 `P5`：

```text

  ┌───────────────────────────────────────────────────────────────────────────────────┐

  │    = P4 + 在已满足的入口条件下【保证有限完成（终止）】并交付结果（无 trap/挂起） │
  │    ► 解锁能力：可安全删除未使用调用（DCE）、可安全将计算外提到循环之前（LICM）   │
  └─────────────────────────────────────────▲─────────────────────────────────────────┘
                                            │ (+ 证明有限完成 / 终止性)
  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐

  │    = P3 + 结果与完成行为【只由显式输入的值语义和常量决定】                        │

  │ 🛡️ P3：稳定观测 (Stable Observation)  ◄── 【默认参数 & spec fn / predicate 要求】 │

  │ 👀 P2：观测只读 (Read-Only Observation)                                           │

  │      （读取足迹明确，允许读取可变指针内容，允许返回带真实依赖的视图）             │
  │    ► 注意：因为两次调用间外部可能修改目标，不能仅凭指针地址相同就跨调用复用       │
  └─────────────────────────────────────────▲─────────────────────────────────────────┘
                                            │ (+ 禁止外部可见 write / kill / 新分配身份)
  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
  │ 🔧 P1：有界状态变更 (Bounded State Mutation)                                      │
  │    = 允许受契约约束的 read / write / kill 及封闭资源分配（如新建独立 String），   │
  │      状态影响有明确契约与足迹；【无 system (I/O)、无同步观测、无未知调用】        │
  │    ► 解锁能力：若两个 P1 操作的读写区域经分离证据证明不相交且有限完成，可重排     │

  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
```

让我们写一段涵盖从 `P0` 到 `P5` 典型函数的 改进代码，对照上面的阶梯图逐个体会：

```flurry
use std.prelude.*;

-- [P0：一般行为] 包含 println 外部输出事件
fn log_and_add_p0(a: u32, b: u32) -> u32 {
    println("adding {} and {}", a, b);
    a + b
}

-- [P1：有界状态变更] 修改了传入指针的目标，但足迹明确且无外部 I/O 事件
fn bump_counter_p1(counter: *u32)
where requires counter.* < 1000u32,
    outcomes read<counter> and write<counter>
{
    counter.* += 1u32;
}

-- [P2：观测只读] 只读指针内容，无外部修改；
-- 当放进一个没有相关写入的区间时，局部自动晋升为 [P3：稳定观测]。
fn read_counter_p2(counter: *u32) -> u32
where outcomes read<counter>
{
    counter.*
}

-- [P3 + 有限完成：可执行 predicate / spec fn 与默认参数]
-- 允许观察合法指针状态，发布带状态版本的事实。
predicate below_limit(source: *u32, limit: u32) {
    source.* < limit
}

-- [P4 + 有限完成 -> P5：总值纯]
-- 虽然内部用了局部可变变量 `var result`，但槽位完全私有、不逃逸，
-- 结果只依赖按值输入 left 和 right，且有限步必定完成，直达最高阶 P5。
pure fn smaller_p5(left: u32, right: u32) -> u32 {
    var result = left;
    if right < result {
        result = right;
    }
    result
}

test {
    var count = 5u32;
    assumes below_limit(count.ref, 10u32);
    bump_counter_p1(count.ref);
    println("count: {}, smaller: {}", read_counter_p2(count.ref), smaller_p5(8u32, 3u32));
}
```

运行输出：

```text
count: 6, smaller: 3
```

## 三、 编译器优化的“四大防混淆红线”与代码位置要求

理解了 `P0`–`P5` 的分层后，你会发现 Flurry 规范（`docs/resource-management/runtime-purity.md` §分析摘要）专门为程序员和编译器优化器划出了**绝对不能混淆的四条红线**：

### 红线 1：无写入 $\neq$ 无事件
原子读取（`atomic`）、设备寄存器读取（`volatile`）或同步观察虽然没有“修改内存”，但它们具有严格的**执行次数与先后次序语义**。因此它们归入 **`P0`**，绝不会被当成普通 `P2` 只读操作合并或删除。

### 红线 2：无内存效果 $\neq$ 可随意复制或丢弃实参
哪怕一个函数体是纯之又纯的 `P5`（比如 `pure fn pass_text(value: String) -> String { value }`，只把描述符和同一份资源责任原样转交出去），调用者依然消耗了这份 `String` 的仿射（`Once`）交付资格。优化器绝不能因为函数体是 `P4`/`P5` 就把一次交付复制成两次。
而且别忘了我们在 [第 021 篇](./021-call-evaluation-order-and-failure-boundaries.md) 学过的核心规则：**就算删除对一个未使用的 `P5` 函数的调用指令，也绝不等于可以顺带丢弃它实参表达式的求值、副作用与清理。**

### 红线 3：相同内容 $\neq$ 相同资源身份
回想开头提到的 `fresh_text() -> String`（每次分配一块内容为 `"same"` 的新堆缓冲区）。虽然两次调用的字符内容完全一样，但它们各自交付了**全新的可观察资源身份（Independent Resource Identity）**。
因此，新建拥有型堆资源的操作最多位于 **`P1`**（当分配器契约未知时为 `P0`），绝不会因为“返回的字符串字面内容相同”就被错判成 `P4` 或 `P2`。

### 红线 4：整个函数是 `P5` $\neq$ 内部指令可以无视前置条件随意上提
看看下面这个经典的数组安全读取函数 `value_or_zero`（见 `docs/resource-management/runtime-purity.md` 示例 4）：

```flurry
pure fn value_or_zero(values: Array<i32, n>, index: usize) -> i32
where n: usize
{
    if index < n {
        values[index]
    } else {
        0i32
    }
}
```

把整个 `value_or_zero` 当作一个黑盒来看，它对任何合法的按值数组和任意 `index: usize` 都能有限完成并返回一个确定的 `i32`——所以**整个函数边界是 `P5`（总值纯）**。
但是，在函数体内部，`values[index]` 的读取**严格依赖分支条件 `index < n`**。优化器绝对不能因为“整个函数是 `P5`”，就把 `if` 分支里面的 `values[index]` 提前上提到 `if index < n` 判断之前去推测执行（那样当 `index >= n` 时就会直接触发越界崩溃）。

让我们把这几条关键性质写进 进阶代码中：

```flurry
use std.prelude.*;

-- 整体是 P5（总值纯），但内部 values[index] 受分支条件 `index < n` 保护，绝不越界上提。
pure fn value_or_zero(values: Array<i32, n>, index: usize) -> i32
where n: usize
{
    if index < n {
        values[index]
    } else {
        0i32
    }
}

-- 可执行 spec fn：要求 P3 + 确定性 + 在合法入口下全定义（有限完成）
spec fn within_bounds(index: usize, length: usize) -> bool {
    index < length
}

test {
    let arr: Array<i32, 3> = [10i32, 20i32, 30i32];
    -- 传入越界下标 9usize，依然安全返回 0。
    println("{} {}", value_or_zero(arr, 1usize), value_or_zero(arr, 9usize));
    assumes within_bounds(1usize, 3usize);
}
```

运行输出：

```text
20 0
```

### 编译器防呆：在 `spec fn` 或 `pure fn` 里偷偷写外部状态或调 I/O？编译期拒绝

不同语法位置对纯度阶梯有着明确的要求：
- 写 `pure fn` 时，编译器强制核验函数体（含所有隐式 `Drop`）达到 **`P4`**；
- 写可执行 `spec fn` / `predicate` 或运行时默认参数时，编译器强制核验达到 **`P3` + 有限完成**。

如果你在 `pure fn` 里试图读取外部可变指针（那只有 `P2`/`P3`，不到 `P4`。），或者在 `spec fn` 里修改外部指针，编译器会直接报错拒绝：

```flurry
-- ❌ 编译期直接拒绝。
-- 错误：runtime `pure fn` 承诺 P4（结果只依赖显式输入的值语义），
-- 不能直接解引用读取外部可变指针 `source.*`（读取可变 pointee 属于 P2/P3，不属于 P4）。
pure fn invalid_pure_pointer_read(source: *i32) -> i32 {
    source.*
}
```

## 本篇小结

让我们用两张精炼的速查表，把 `P0`–`P5` 六层阶梯与语法位置要求收入囊中：

| 纯度层级 | 核心保证 | 对应典型操作 / 解锁的优化 |
| :--- | :--- | :--- |
| **`P5` 总值纯** | `P4` + 合法入口下保证**有限完成（终止）** | `smaller_p5`；允许**删除未使用调用（DCE）**与**循环不变量外提（LICM）** |
| **`P4` 值纯** | `P3` + 结果仅由**显式输入的值语义与常量**决定 | `pure fn` 承诺层；允许私有 `var`，允许跨外部内存修改做 **CSE 复用** |
| **`P3` 稳定观测** | `P2` + 所读对象与内容版本在**复用区间内稳定** | 默认参数、`spec fn`、`predicate` 要求层（需配合有限完成）；区间内可复用只读结果 |
| **`P2` 观测只读** | `P1` + **不修改/终结外部状态，不产生新资源身份** | `load_value(p)`；只读指针，但跨外部写入后不能复用旧值 |
| **`P1` 有界变更** | 允许有明确契约足迹的读写与封闭分配，**无外部事件** | `bump_counter_p1`、`fresh_text`；若两个 `P1` 足迹分离且有限完成，可安全**重排** |
| **`P0` 一般行为** | 包含 I/O、系统事件、原子/设备同步、未知调用 | `println`、含输出 `Drop` 的函数；保留严格执行次数与事件顺序 |

### 下一篇预告

仔细看我们在这一篇最后留下的那个 `❌ 编译期直接拒绝` 的例子：
在 `pure fn`（`P4`）里，编译器禁止读取**外部传入的可变指针** `source.*`。

但是，刚才我们在写 `smaller_p5` 时，明明在 `pure fn` 里面写了 `var result = left; result = right;`。
如果我更进一步，在 `pure fn` 内部声明一个局部变量 `var flag = false;`，然后**取它的指针 `let p = flag.ref;`**，甚至做一个二级指针 `let slot = p.ref;`，再通过 **`slot.*.* = true;`** 修改它，或者在 `pure fn` 里用 `BitVec` 切片原地写回 `word'bitvec[offset..(offset + 4)] = 0b1010;`，甚至调用高阶回调函数 `apply(action, false)` 呢？

为什么这些看起来“充满了指针解引用、可变赋值、位段写回和闭包调用”的代码，在 Flurry 的 `pure fn` 里居然**全部合法**？

在下一篇 **《Flurry 演进手记 (054)：`pure fn` 的真正含义——稳定观测、局部可变性与编译器合法优化前提》** 中，我们将彻底打破“纯函数 = 不能用 `var` 和指针”的刻板印象，看看 Flurry 的私有计算边界有多么强大。
