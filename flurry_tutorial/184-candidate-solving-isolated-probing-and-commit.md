## 一、开篇痛点：当多个候选实现同台竞技，如何防止“探测污染”与“抢跑误判”？

在 Flurry 中，无论你是调用重载函数、解析模式分支，还是为泛型接口匹配特化实现（Specialization），编译器都会面临一个核心问题：**从一组候选者（Candidates）中选出唯一合法的赢家。**

请看下面这段包含泛型基准实现与具体类型特化实现的代码：

```flurry
trait Sample<T> {
    const ID: i32;
}

impl<T> Sample<T> {
    const ID: i32 = 1;
}

impl Sample<i32> {
    const ID: i32 = 2;
}
```

这里有两个 `Sample` 的实现：
- **候选 C1（宽泛实现）**：`impl<T> Sample<T>`，对任意类型 `T` 均适用，`ID = 1`；
- **候选 C2（特化实现）**：`impl Sample<i32>`，专门针对 `i32` 特化，结构特指度（Specificity）高于 C1，`ID = 2`。

现在假设我们在某个泛型上下文中查询目标 `Sample<?M>::ID`，其中 `?M` 是一个尚未确定的推断变量（稍后会被兄弟参数确定为 `i32`）。

### 初代尝试（`v0`）：直接在主上下文试探 + 谁先通过就选谁

如果我们用最天真的方式（`v0`）编写候选求解器，会立刻踩中两个深坑：

1. **大坑一（探测污染 / Speculative Pollution）**：求解器先拿候选 C2（`Sample<i32>`）直接在主上下文里试探，顺手把主上下文里的 `?M` 强行合一成了 `i32`！哪怕后面发现 C2 的附加 `where` 约束不满足，主上下文里的 `?M` 已经被污染成 `i32` 了，其他变量和等待队列全被错误触发！
2. **大坑二（抢跑误判 / Premature Commit）**：为了不污染 `?M`，求解器不敢把未知的 `?M` 当成 `i32`，于是认为候选 C2（`Sample<i32>`）目前“无法判定（Pending）”。但此时它转头一看：咦，宽泛候选 C1（`Sample<T>`）对任何类型都成立，现在就能通过！于是 `v0` 急不可耐地直接锁定了 C1（`ID = 1`）！等到下一行代码确定 `?M = i32` 时，木已成舟，本来应该选中特化版 `ID = 2` 的程序，错误地输出了 `1`！

```
  [ v0 抢跑误判的灾难现场 ]
  查询目标: Sample<?M>  (此时 ?M 尚未揭晓，稍后会被兄弟实参赋值为 i32)
  ├── 探测 C1: impl<T> Sample<T>    ---> 立即匹配成功 (Applicable)!
  └── 探测 C2: impl Sample<i32>     ---> 因 ?M 未知而挂起 (Pending)...
  
  v0 错误决策：不管还在 Pending 的 C2 了，直接提交 C1 (ID = 1)！
  后果：当 ?M 随后揭晓为 i32 时，本该胜出的更特化候选 C2 被冤杀！
```

## 二、机制迭代（`v0 -> v1 -> v2`）：结构化索引、沙盒隔离探测与特指度栅栏

让我们看看 Luna 编译器的候选求解器（`resolve(goal)`）是如何演进的。

### 第一次迭代（`v1`）：仅回滚类型变量赋值的简单快照

`v1` 引入了一个简单的回滚栈（Trail Stack）：在试探每个候选前保存类型变量 `?M` 的旧值，试探失败就恢复旧值。

但 `v1` 忽略了：在 Luna 这样支持依赖类型、PTC 证明与局部等待票据的编译器里，一次候选试探不仅会修改类型变量，还会产生**嵌套子候选、项空洞填充（Term Holes）、局部证明前提、暂存的诊断错误、以及注册在依赖图上的等待票据**！如果只恢复类型变量，失败候选留下的幽灵等待票据和半截诊断就会在后台疯狂泄漏。

### 第二次迭代（`v2`，Luna 最终方案）：全状态沙盒隔离探测（`isolated_trial`）+ 特指度等待栅栏

在 Luna 的最终设计（`v2`）中，`resolve(goal)` 由四个严密的阶段组成：

```
  [ 目标: resolve(Sample<?M>) ]
               |
               v  1. 结构化索引检索 (包含所有可能兼容的更精细键!)
       候选集: { C1: Sample<T>,  C2: Sample<i32> }
               |
               +-------------------------------+
               |                               |
               v  2. 沙盒隔离探测               v  2. 沙盒隔离探测
  +-------------------------+     +-------------------------+
  | isolated_trial(C1)      |     | isolated_trial(C2)      |
  | 独立事务日志:            |     | 独立事务日志:            |
  | - 类型赋值 / 项空洞      |     | - 发现需等待 ?M 是否为 i32|
  | - 证明前提 / 暂存诊断    |     | - 生成沙盒等待票据       |
  | - 局部等待票据           |     | 结果: Pending(?M)       |
  | 结果: Applicable(Spec=1)|     +-------------------------+
  +-------------------------+                  |
               |                               |
               +---------------+---------------+
                               |
                               v  3. 特指度栅栏裁决 (Specificity Fence)
        C2 虽为 Pending，但其结构特指度 (Spec=2) > C1 (Spec=1)！
        ====> 严禁提前提交 C1！整体目标挂起等待 ?M 揭晓！
```

#### 关键设计 1：结构化索引必须返回所有潜在的特化候选

当求解器拿着 `Sample<?M>`（其中 `?M` 未知）去查索引表时，索引表**绝不能只返回通配符桶里的 `Sample<T>`**，而是必须把所有在 `?M` 具化后可能匹配的更精细键（如 `Sample<i32>`）一并检索出来纳入候选集！否则特化实现从第一步就会被漏掉。

#### 关键设计 2：`isolated_trial` 的全状态事务隔离

每个候选 `C` 都在属于自己的 `isolated_trial(parent_context)` 沙盒中运行。沙盒内部的所有写入都记录在事务日志中，一旦该候选被淘汰（Rejected）或挂起重跑，以下六类状态会被**100% 原子级回滚**：
1. 类型变量赋值与收窄（Type Assignments）；
2. 子级候选集状态（Nested Candidate Sets）；
3. 隐式证据与项空洞（Term Holes）；
4. PTC 事实前提与证明状态（Fact Premises & Proof States）；
5. 试探期间产生的暂存诊断（Staged Diagnostics）；
6. 试探期间注册的局部等待票据（Wait Registrations）。

#### 关键设计 3：特指度栅栏（Specificity Fence）——绝不在高优先级候选未决时抢跑

当所有候选完成一轮沙盒探测后，裁决器严格遵守以下铁律：
- 只有当某个 `Applicable`（已适用）候选的特指度严格高于所有其他 `Applicable` 候选，**并且没有任何可能击败它的更具体候选仍处于 `Pending`（未决）状态**时，才允许将其选为唯一赢家（Unique Winner）！
- 如果宽泛的 `Sample<T>` 已经 `Applicable`，但更具体的 `Sample<i32>` 因为等待 `?M` 而处于 `Pending`，求解器会挂起等待 `?M`。一旦 `?M` 揭晓为 `i32`，`Sample<i32>` 转为 `Applicable` 并凭借更高的结构特指度堂堂正正地胜出（得到 `ID = 2`）！
- 在最终提交（`commit`）赢家的事务之前，求解器还会对赢家依赖的所有前提做一次**最终重验（Revalidation）**，确认无误后才将类型替换、证据项和 IR 结果原子性地合并回父上下文。

## 三、深度法则：沙盒探测与 `comptime` 副作用的楚河汉界

既然沙盒探测（`isolated_trial`）会试探性地运行检查并随时回滚，那么一个极其深刻的问题来了：**如果某段代码里包含了不可逆的编译期副作用（比如用户显式调用了 `meta.compilation.err(...)` 触发自定义编译错误，或者修改了外部状态），沙盒探测会不会在试探半路上误触发它，或者把本该报错的 `comptime` 错误当成普通候选失败给悄悄吞掉？**

Luna 编译器对此划定了一条不可逾越的边界：

> **`isolated_trial` 只运行可隔离、可安全重放（Safely Replayable）的类型与契约检查；不可重放的编译期副作用操作（Non-replayable Comptime Side Effects）绝不在投机性沙盒中被静默丢弃！**

请看下面这段用户显式要求在编译期报错的代码：

```flurry
const FAIL: i32 = comptime {
    meta.compilation.err("explicit failure");
};
```

这里的 `comptime { meta.compilation.err("explicit failure"); }` 是用户**显式请求执行的编译期块**，而不是用来做重载筛选的试探条件。当编译器执行到这里时，它会直接将 `"explicit failure"` 作为确定性的编译期错误呈现给用户，绝不会把它当成某个“走不通的候选分支”静默吞掉！

## 四、边界与编译期拒绝：同等特指度的冲突与全军覆没的诊断保留

如果所有候选都探测完毕，没有唯一赢家怎么办？

### 拒绝例 1：两个适用候选难分伯仲（Ambiguous Candidates）

如果两个候选都适用，且结构特指度无法分出高下，求解器绝不按声明先后顺序“抓阄”，而是报错列出所有冲突候选：

```flurry
trait Merge<A, B> {
    fn select() -> i32;
}

impl<T> Merge<T, i32> {
    fn select() -> i32 { return 10; }
}

impl<U> Merge<i32, U> {
    fn select() -> i32 { return 20; }
}

fn trigger_ambiguity() -> i32 {
    -- 当 A = i32, B = i32 时，两个 impl 一样具体，谁也不比谁更特化！
    return Merge<i32, i32>.select(); -- ❌ 编译期直接拒绝！候选求解发现同等特指度的二义性冲突（`impl<T> Merge<T, i32>` 与 `impl<U> Merge<i32, U>`）
}
```

### 拒绝例 2：所有候选均被拒绝（No Applicable Candidate）

当一个候选在沙盒内因为某个 `where` 约束不满足而失败时，它在沙盒里产生的诊断不会立刻打印出来（因为如果别的候选成功了，这些诊断就没有意义）。但是，**如果所有候选最终全军覆没**，求解器不会只冷冰冰地甩出一句“找不到匹配实现”，而是会从各个沙盒的回滚记录中提取出**为什么每个候选会被淘汰的精准原因**，汇总成清晰可读的诊断报告！

## 五、本期小结

| 阶段 / 机制 | 核心设计 | 防止的编译器缺陷 |
| :--- | :--- | :--- |
| **结构化候选检索** | 查询含未知变量的键（如 `Sample<?M>`）时，一并返回所有潜在兼容的更具体键（`Sample<i32>`） | 防止因类型变量尚未揭晓而在第一步漏掉特化实现 |
| **`isolated_trial` 沙盒** | 事务化隔离类型赋值、候选集、项空洞、证明前提、暂存诊断与等待票据 | 防止失败或挂起的候选污染外部主推断区域 |
| **特指度等待栅栏** | 当更具体的候选仍处于 `Pending` 时，严禁提前提交已适用的宽泛候选 | 防止 `Sample<T>` 抢跑冤杀稍后揭晓的 `Sample<i32>` |
| **重验后原子提交 (`commit`)** | 提交赢家前重新核验依赖代数，一次性合并类型替换、证据与结果项 | 保证多线程/多阶段唤醒下的最终一致性 |
| **Comptime 副作用边界** | 仅对可隔离纯检查做投机探测；显式 `meta.compilation.err` 等操作确定性生效 | 防止编译期错误被当成候选试探失败而静默吞没 |

到这里，我们已经看清了单个定义内部的 Elaboration、局部依赖唤醒与候选求解。但是，在 Flurry 中，**Elaboration 是与 `comptime` 编译期求值紧密交织在一起的**！比如返回类型的函数 `SelectType(wide)` 本身就是一段要在编译期运行的代码。

当一个泛型函数（如 `keep_selected(wide: comptime bool, value: SelectType(wide))`）在定义点完成了检查，准备保存下来供后续成百上千个调用点实例化时，编译器到底应该把哪些东西“冻结（Freeze）”进归一化结果里？那些半途中的推断变量槽、等待票据和沙盒事务能不能留在冻结产物里？
