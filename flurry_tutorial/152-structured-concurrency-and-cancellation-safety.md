# Flurry 演进手记 (152)：绝不留下孤儿任务——结构化并发（Structured Concurrency）、取消传播与作用域退出

在上一篇末尾，我们留下了一个让所有并发系统程序员都会瞬间警觉的悬念：
在 Flurry 中，当你调用一个异步效应 `let pending = report(7u32)#;` 时，后台子工作在请求发出的那一刻就已经启动了。
如果程序员发出了这个请求，却**没有调用 `pending.await`**，代码就直接走到了 `# { async report(...) => ... }` 块的右花括号 `}`——这时候会发生什么？

在传统拥有 `go func()` 或 `tokio::spawn` 的语言里，无拘无束派生出去的任务就像断了线的风筝（被称作**孤儿任务 Orphan Task**）：
父函数明明已经返回了，父函数栈上的缓冲区明明已经销毁了，那个孤儿任务却还在后台偷偷运行。这不仅会导致隐蔽的资源泄漏，一旦孤儿任务允许借用父函数的局部变量，更是会直接引发严重的悬垂指针内存踩踏（Use-After-Free）。

为了彻底消灭“孤儿任务”，正如现代结构化程序设计用 `if`/`while` 块消灭了满天飞的 `goto` 一样，Flurry 将**结构化并发（Structured Concurrency）**直接熔铸进了 `async` 效应处理器的安装作用域中。

今天，我们就深入 `docs/algebraic-effect-and-delimited-continuation/async-algebraic-effect.md`，看清 Flurry 是如何做到**“任何子任务绝不活过安装它的 Handler 作用域”**的。

## 关于未等待 `Future` 的两个常见误区

当看到下面这段没有写 `pending.await` 的代码时，带着其他语言习惯的开发者往往会有两种截然相反的错误猜测：

```flurry
async effect report(value: u32);

(do {
    let pending = report(7u32)#;
    println("body end");
}# {
    async report(value) => println("report: {}", value),
}).use(runtime);

println("scope end");
```

- **错误猜测 A（Go / 传统线程派）**：“既然没写 `pending.await`，外层块会直接穿透往下走，先打印 `scope end`，至于 `report: 7` 什么时候打印、甚至主线程退出了还没打印完，那就听天由命了。”
- **错误猜测 B（Rust 惰性 Future 派）**：“既然 `pending` 在块末尾直接被丢弃（Drop）了，也没人 `.await` 它，那 `report(7u32)` 要么压根没执行，要么在 `pending` 变量离开作用域时被静默取消掉了。”

在 Flurry 中，**这两种猜测全都是错的。**

## 结构化并发核心规则——丢弃 `Future` 不取消任务，正常退出必等待全部子工作完成

让我们看看 `docs/algebraic-effect-and-delimited-continuation/async-algebraic-effect.md` 对上述代码行为给出的权威定义：

1. **丢弃尚未等待的 `Future` 不会自动取消工作**：
   `let pending = report(7u32)#;` 在发起请求时就已经登记了子工作。变量 `pending` 只是一个用于按需取回结果的凭证句柄；不调用 `pending.await` 只是代表“我不关心它的返回值”，绝不代表“把我刚发出去的后台上报任务掐死”。
2. **含有 `async` 分支的安装范围（Installation Scope）拥有它派生的全部子工作**：
   当控制流正常走到 `# { async report(value) => ... }` 范围的出口时，**该安装范围会自动等待其名下所有尚未完成的子工作执行完毕，然后才允许退出该范围。**

因此，运行上面那段代码时：
- `"body end"` 与 `"report: 7"` 的先后顺序取决于调度器何时运行子任务；
- 但 **`"scope end"` 绝对保证在 `"report: 7"` 完成以及当前安装范围的所有清理工作全部结束之后，才会打印出来。**

```
+-------------------------------------------------------------------------+
|  安装范围（Installation Scope）的结构化任务归属                |
|                                                                         |
|  ┌─── (do { ... }# { async report ... }).use(runtime) 安装范围边界 ───┐ |
|  │                                                                    │ |
|  │   主计算流 (Body)                     派生子工作 (Child Work)      │ |
|  │   ───────────────                     ───────────────────────      │ |
|  │   let pending = report(7u32)#; ────►  [ 子任务: report(7) ]        │ |
|  │   println("body end");                        │                    │ |
|  │          │                                    │ println("report:7")│ |
|  │          ▼                                    ▼                    │ |
|  │   ====== 🚧 结构化并发栅栏（Scope Exit Barrier）======             │ |
|  │   (主计算流在此等待所有归属本范围的子工作完成 + 范围资源清理完毕)  │ |
|  └──────────────────────────────────┬─────────────────────────────────┘ |
|                                     ▼                                   |
|                          println("scope end");                          |
|         （100% 保证此时没有任何残余子工作还在访问块内局部环境  ）       |
+-------------------------------------------------------------------------+
```

> **💡 核心心智模型：`runtime` 存活 $\neq$ 子任务可以逃出当前安装范围。**
> 也许你会问：“既然 `.use(runtime)` 里的 `runtime` 是我们在外层创建的运行时对象，而且在这个块结束之后 `runtime` 还活着，那子工作能不能挂在 `runtime` 身上继续跑，让当前 `# { ... }` 块先退出？”
> **绝对不行。** 一个 `runtime` 实例确实可以先后或嵌套服务多个 `# { ... }` 安装范围，但 **`runtime` 对象的存活，绝不能代替每个安装范围对自己的子工作履行等待和清理责任。** 只有这样，子工作才能安全地借用当前安装范围外围的栈上局部对象，而绝不会发生生命周期逃逸。

## 提前退出与协作式取消（Cooperative Cancellation）——绝不跳过任何一次 `Drop`

正常退出时等待所有子工作跑完，这很直观。
但如果主计算流在运行到一半时，因为遇到了一个错误（比如 `check_sensor()!` 失败返回 `error`）或者 `return` / `break` **提前退出了当前安装范围**，那些还在后台运行或挂起等待的兄弟子任务怎么办？

如果傻等它们跑完，一个卡在慢速请求上的子任务就会拖死整个错误处理流程；
如果像 C 语言 `pthread_cancel` 那样直接野蛮杀掉线程、把栈内存一扔了之，子任务手里持有的锁、文件句柄或缓冲区资源就会全部泄漏。

在 Flurry 中，安装范围的**提前退出（Early Exit）**严格遵循一套两步走的安全协议：
1. **第一步：先发起取消（Initiate Cancellation）**：
   - 对于**正在运行中**的子工作：设置取消请求标志，子工作在到达下一个允许的类型化效应控制点时安全执行退出；
   - 对于**已经处于挂起等待状态**的子工作：争夺并取得其唯一的恢复权（Continuation），直接将其转入**放弃协议（Abandonment Protocol）**——沿着隐藏中止通道重新进入挂起栈，逐帧执行所有已构造局部资源的 `Drop` 析构。
2. **第二步：等待全部清理完成后，再释放外层环境**：
   安装范围必须**等待所有被取消的子工作彻底停止并完成各自的 `Drop` 清理**，把借用的栈槽归还给栈池（Stack Pool）后，才允许销毁子工作所依赖的外层环境并向上传播错误。

```
+-------------------------------------------------------------------------+
|  提前退出时的取消传播与完整 Drop 清理保证                      |
|                                                                         |
|  主计算流 (Body)                        后台子工作 (Child Task)         |
|  ───────────────                        ───────────────────────         |
|  let job = long_work()#;  ───────────►  let guard = FileLock {};        |
|         │                               wait_io()#;  (⏸️ 挂起等待中)    |
|  ❌ 发生错误提前退出                           │                        |
|         │                                      ▼                        |
|  ┌──────┴───────────────────────┐       [ 收到范围取消信号  ]           |
|  │ 1. 向本范围未完成子工作      │ ────► 取得挂起 continuation，         |
|  │    发起 cancel(job)          │       切入隐藏中止清理通道：          |
|  │                              │       ──► 执行 `guard.drop()` 🔓      |
|  │ 2. 阻塞等待子工作清理完毕    │ ◄──── ──► 归还栈槽，报告已停止 ✅     |
|  └──────┬───────────────────────┘                                       |
|         ▼                                                               |
|  3. 安全释放外层环境，向调用者交付错误结果                              |
+-------------------------------------------------------------------------+
```

## 编译期安全红线：多个并发子工作共享 Handler 捕获时，严禁违背所有权契约

当我们在 `# { async op(x) => ... }` 的处理分支里捕获了外层的某个变量时，别忘了：**因为这是 `async` 分支，主体可能会连续发起十次 `op(x)#` 请求，从而派生出十个并发运行的子任务。**

这意味着，Handler 分支捕获的对象可能会被**多个子工作同时或先后访问**。
因此，`docs/algebraic-effect-and-delimited-continuation/async-algebraic-effect.md` 规定了一条严格的编译期资源红线：
> **handler 的捕获可能被多个子工作访问。共享、复制、所有权转交或串行执行必须满足实际对象契约；不能因为它们来自同一个 handler，就复制 `Once` 资源或允许冲突写入。**

来看一个被编译器静态拦截的负例：如果我们试图在一个 `async` 效应分支里，直接按值消费（Move）一个只能使用一次的非 `Copy` 资源 `OnceToken`，或者在无同步保护的情况下并发写同一个可变借用：

```flurry
struct OnceToken {
    id: u32,
}

fn consume_token(tok: OnceToken) -> u32 {
    tok.id
}

async effect spawn_worker(step: u32) -> u32;

fn bad_concurrent_capture() {
    let token = OnceToken { id: 99u32 }

    let _ = (do {
        -- 连续发起两次异步请求，产生两个子工作。
        let a = spawn_worker(1u32)#;
        let b = spawn_worker(2u32)#;
        a.await + b.await
    }# {
        -- ❌ 编译期直接拒绝。
        -- `async spawn_worker` 分支可能被多个子工作执行，
        -- 捕获的非 Copy 资源 `token` 只能按值交付（Move）一次，
        -- 绝不能因为写在同一个 handler 分支里就被多个子工作重复消耗。
        async spawn_worker(step) => consume_token(token) + step,
    }).use(runtime);
}
```

## 本篇小结

| 场景 / 机制 | Flurry 结构化并发规则 | 解决的核心安全问题 |
| :--- | :--- | :--- |
| **丢弃未 `.await` 的 `Future`** | 不取消已登记的子工作；子工作继续归属当前 Handler 安装范围管理 | 避免因未取返回值而意外中断后台上报/日志子任务 |
| **安装范围正常退出** | 自动阻塞等待本范围派生的所有未完成子工作执行完毕 | 彻底消灭脱离父作用域生命周期的“孤儿任务（Orphan Tasks）” |
| **安装范围提前退出** | 先向未完成子工作发起取消，并**等待其全部 `Drop` 清理完成**后再释放外层环境 | 保证异常退出时既不泄漏子任务持有的锁/文件，也不发生悬垂环境访问 |
| **Handler 分支环境捕获** | 多个子工作访问捕获变量时须遵守共享、复制或单次消费（`Once`）契约 | 在编译期拦截跨并发子任务的单次资源重复 Move 与未同步的数据竞争 |

### 下一篇预告

现在，我们已经能够写出兼具结构化并发安全与非染色优雅语法的异步网络协议代码了。
但是，当我们准备为边缘网关的**“传感器断线重连与指数退避重试协议”**编写单元测试时，一个让无数后端和嵌入式工程师头疼的难题出现了：

我们的重连协议逻辑是：
- 发送探测包 $\rightarrow$ 如果失败，睡眠等待 `1000ms` 重试第 1 次 $\rightarrow$ 再失败，睡眠等待 `2000ms` 重试第 2 次 $\rightarrow$ 再失败，睡眠等待 `4000ms` 重试第 3 次。
难道我们每次在 CI 里跑这个单元测试，都要**真的让 CPU 在那干等 `1 + 2 + 4 = 7` 秒钟**吗？如果测试 100 种超时和随机丢包组合，岂不是要跑几个小时？而且真实操作系统的定时器还有抖动，怎么在单测里 100% 确定性地复现“刚好在第 2999 毫秒收到乱序包”的极端边界情况？

在 Flurry 中，答案非常直接：**根本不需要改一行协议业务代码。只需在测试时把效应 Handler 从 `RealRuntime` 替换成带虚拟时钟的确定性仿真 Handler。**
下一篇 **`153-deterministic-simulation-testing-by-swapping-handlers.md`**，我们将结合 `handles` 能力绑定与 `.use(handler)`，亲手打造一套瞬间快进时间的**确定性仿真测试（Deterministic Simulation Testing）引擎**。
