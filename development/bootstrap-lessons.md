# 自举编译器备忘

这份记录留给用 Flurry 重写编译器的人。每个条目从一个真实程序出发，说明当前实现受什么约束、付出了什么代价，以及换一种实现后还得通过哪个反例。后续遇到新的取舍或移除旧限制时，在相应条目补上提交和证据。

## 2026-11-21 · 泛型别名里，知道类型身份仍然不足以给字面量定型

`typealias Alias<T> = Indexed<T, 7>` 在定义处已经知道两个位置谈的是同一个 `T`。这项证据足以证明 `T == T`。给 `7` 选择整数表示却要等到调用方提供 `T`。另一方面，若另一个参数要求 `Choice<T>`，枚举的声明已经确定，写错变体名可以在别名定义处报错。把这些情况合成一个“参数已知”标志，会让其中一种检查做出错误决定。[别名契约](../docs/type/user-defined-types/newtype-and-typealias.md)

在 `3f052ce8`，elaborator 沿用既有表达式检查器，在检查别名定义期间单独保存抽象 Type 参数的声明身份。进入独立声明时移出这组身份，返回时恢复。这样可以继续用原来的符号项证明形成条件。代价是检查器多了一项要随作用域保存的状态，别名展开时还要按实际参数再次检查相关表达式。[别名检查](../compiler/elaboration/src/program/aliases.rs) · [声明作用域](../compiler/elaboration/src/program/declaration_scope.rs)

自举时可以尝试让实参槽同时携带“可用于证明的身份”和“完成值表示还缺的输入”。检验时让一个违反形成条件的别名始终没有调用点，确认定义检查仍会拒绝它。再对一个合法别名交替传入不同整数宽度，检查一次溢出后，换一个有效类型仍能成功。[形成条件与调用隔离用例](../compiler/luna/tests/nominal_value_parameters.rs) · [具名整表与逐项变参用例](../compiler/luna/tests/normal_input_plans.rs)

## 2026-11-21 · 两条 VM 执行路径保留同一份字面量意图

考虑 `Key<ty, if choose() { .ready } else { .other }>`。当 `ty` 由 comptime 调用给出时，`.ready` 可能交付为 Symbol，也可能选中某个枚举的无载荷变体。另一分支的名字同样需要检查，实际调用只求值一次 `choose()`。把源码表达式一直留到 VM 里重新 elaboration，会把词法环境、控制流和重复求值的问题一并带过去。[实参执行次序用例](../compiler/luna/tests/normal_input_plans.rs)

当前实现让 NIR 的 `NormalFormArgument` 保存字面量拼写、源码位置和必要的控制流。字节码编译器再从中生成检查实参所需的结构描述。树解释器与字节码 VM 各自读取一种表示，在同一个入口按具体参数域完成检查。`2a5745b0` 增加裸符号时，两种表示、遍历器、复制预算和 dump 都要同步修改。共享的变体查找保留了普通表达式的命名规则和诊断。[NIR 实参](../compiler/nir/src/program.rs) · [字节码输入描述](../compiler/comptime_compiler/src/normal_types.rs) · [两条路径共用的域检查](../compiler/comptime_interpretor/src/input_domains.rs)

自举时值得尝试把待定字面量的种类、源码位置和大小计费集中在同一个不可变描述中。验收用两个变体顺序相反的枚举、一个 Symbol 域和一个带错误行及两层可选的枚举域。在同一个 VM 里重复提交同一拼写，必须得到各次调用自己的变体身份和包装层次。即使条件恒真，未选分支里的错误名字也要指向它自己的源码位置。[双执行路径与诊断用例](../compiler/luna/tests/nominal_value_parameters.rs)

加入浮点实参后，NIR 和字节码描述共用 `ContextualLiteral`，复制拼写的计费依据也集中到了这个类型上。树解释器与字节码 VM 仍各自保存源码跨度、分支关系和执行位置。当前取舍是让 elaborator 先按预算检查十进制拼写，等具体域出现后再解析一次并形成值。这样编译结果只需保存拼写和符号。自举时若改为保存解析好的十进制系数和指数，要一起衡量复制成本和反复解析成本。验收时把略高于 `f32` 舍入中点的 `1.000000059604644775390625000000001` 交给依赖域，结果位模式必须是 `0x3f800001`。先经 `f64` 舍入会丢掉决定结果的末位。另用同一 VM 检查未选分支中的溢出，再换到更宽的域重试。[浮点实参与失败恢复用例](../compiler/luna/tests/exact_floats.rs) · [逐项收集与具名整表用例](../compiler/luna/tests/normal_input_plans.rs)

## 2026-11-21 · 复用实参字节码也有成本

解释器可以复用同一段实参的编译结果。当前缓存保存受检实参描述、可选目标类型和代码，每次调用仍从自己的环境取值。为了让键比较和克隆也服从工作预算，查找前要遍历描述来计费，候选项还可能需要结构比较。当前采用有限表，满表或插入将超过总权重上限时整表清空。它使内存占用和失效逻辑容易审计，也可能同时丢掉仍然热门的代码。这些阈值是当前实现参数。[缓存与失败恢复用例](../compiler/comptime_interpretor/src/contextual_code.rs)

自举时若已有能表达源码归属与生命周期的稳定 IR 身份，可以实测用它引用实参代码的收益。比较时分别测冷编译、热查找及交错域调用。还要让同一段代码在不同调用环境中读出不同值，并验证预算耗尽后给足预算能够重试。命中编译结果和命中 invocation 的返回值是两件独立的事。[实参代码缓存](../compiler/comptime_interpretor/src/contextual_code.rs) · [调用开销用例](../compiler/luna/tests/contextual_input_costs.rs)

## 2026-11-21 · 属性快照里，已知没有属性和属性尚未就绪是两种信息

在 `Decorated` 的属性构造器内读取 `Plain` 的属性时，`Plain` 可以在文件后面声明。只要它没有附加属性，读到的就应当是空 Object。早期实现用全包的“正在求值属性”标志处理循环，这个例子也被拒绝。现在 elaborator 根据 HIR 的定义目标预先登记有供应者的声明身份。发布前，读取登记过的声明仍会报告未就绪，其他已确定身份的声明可以返回空对象。所有供应者求值、合并和检查成功后，一次发布整张冻结表。[源码回归](../compiler/luna/tests/attrs_and_meta_reflection.rs)

required invocation 的声明快照共享其创建时的不可变索引或冻结表，复制快照只保留所有者；读取才按声明查找并解码该属性 Object。发布不会改变早先捕获的快照。在 `8a72d984`，如果 A 读取带属性的 B，即使 B 不依赖 A，这一批的属性也会因 B 尚未发布而被拒绝。[快照所有权与预算](../compiler/nir/src/copy_budget/package/tests.rs)

现在，属性求值期间的 required invocation 可以向创建同一索引的 checker 请求 B。外层 VM 保留调用栈和局部值，B 在自己的声明作用域内使用剩余预算。每个供应者在这次属性求值期间保留已物化的结果，多个读取方共享按既有覆盖次序合并的冻结对象。整个包仍须通过属性消费者检查才能发布。本地取舍是同步进入源检查器，保留外层 VM，并在宿主线程栈不足时为下一层另接一段栈。仅设八层上限曾在默认测试线程上先触发栈溢出，因此现在单独控制两种资源：按剩余栈空间决定何时扩栈，同时活动的供应者仍暂限八层。最初按需读取和最终发布分别执行合并与冻结。自举时若采用显式 continuation，可将供应者深度交由资源预算控制。验收包括真正的环、超深的无环链，以及读取前先用 builder 生成声明，读取后检查包中同名见证只出现一次。[供应者调度](../compiler/elaboration/src/program/attributes/demands.rs) · [端到端用例](../compiler/luna/tests/attrs_and_meta_reflection.rs)

在 `a01a21fd` 还复现了一个交付缺口。B 用 `meta.StructBuilder.new().Build()` 生成类型，把该 Type 作为 `metadata` 的条目；仅编译 B 可以成功。若正在计算属性的 A 此时调用 `meta.attrs_of(B)`，A 的 VM 捕获的声明世界早于 B 生成的类型，解码这个 Object 会报告 `Type`。把 B 的条目改为普通 bool 后，同一次嵌套读取可以完成。[属性按需求值](../compiler/elaboration/src/program/attributes/demands.rs)

等待方现在从冻结值的类型和值载荷出发，沿字段类型、枚举载荷和 newtype 表示查找尚缺的生成声明。先交付依赖，再交付使用者。它们沿用供应者分配的身份。等待中的 VM 据此解码 Object，调用方的 builder 也把这些描述纳入自己的形成与有限存储检查，可以继续用收到的类型构造定义。最终包只从原生成方接收每个定义。跨种类验收用例让 B 返回枚举，其载荷为结构体，字段为 newtype；A 连读两次、反射到底层表示，并用枚举生成新的外层结构体。[声明依赖查找](../compiler/elaboration/src/program/attributes/layouts.rs) · [源码验收](../compiler/luna/tests/attrs_and_meta_reflection.rs)

当前取舍是为已有生成声明的属性求值维护临时索引，每次读取按接收方实有的布局查找缺项。接收 VM 在解码前验证描述。只有实际调用 builder 才会为它建立检查目录，按依赖顺序补验导入的声明，并检查有限存储。纯反射避免了这部分开销；同时读取和构造的程序仍需支付两个检查器的验证成本。自举时若让两者共有不可变的布局证据，需要把证据绑定到精确的声明世界，并保留失败恢复：同一 VM 读到错误载荷、冲突身份或耗尽预算后，这次导入的描述都应撤回，原有描述可继续使用。[接收与失败恢复](../compiler/comptime_interpretor/src/source_values.rs)

最终发布现在沿用同一轮源检查中按需读取所冻结的 Object。每个非空定义属性对象持有一个独立的共享句柄，提前读取与最终 NIR 可以持有同一份载荷；已知空的结果也可直接交付。目标合法性、键和值域仍由最终消费者逐个检查。例如提前读取函数上的布局属性可以得到 Object，但发布时仍须报错，因为只有结构体能采用该布局。全包合并仍会遍历原始属性，保留各项的词法来源和覆盖次序以供诊断。若要进一步复用这部分工作，自举实现需能同时保留选中的原始属性位置和冻结值。[源检查与发布](../compiler/elaboration/src/program/attributes.rs) · [真实包回归](../compiler/luna/tests/attrs_and_meta_reflection.rs)

用相同的源 HIR 测量 required invocation 预算：前面的结构体读取后面结构体的全部属性，后者的 metadata 只有一个字符串。字符串取 64、2048 和 4096 个 ASCII 字节时，修改前分别消耗 1983、21823、42303 步，修改后为 1899、19755、38187 步。原先第二次冻结的开销随载荷增长；交付已有句柄只需查询本轮定义表。

## 2026-11-21 · 重复调用同一函数时，签名遍历的成本可以复用

VM 在绑定实参前会遍历签名，按节点与载荷扣除预算，并检查结构深度。同一具名函数可以连续接收不同的实参，而源码签名在这个 VM 的生命周期内不可变。当前只保留最近一次成功遍历的签名引用与步数。下一次遇到同一棵签名树且预算充足时直接扣费，随后照常观察关联类型、检查实参和契约、执行函数体。预算不足时仍需遍历：访问记录字段名或为子节点预留步数可能提前失败，调用者此时还有剩余预算。

这个单槽在相邻调用间占用固定空间，交替调用不同具名函数会替换它。特化实例、闭包和 IIR 实例沿用逐次遍历。以现有 invocation 基准交替运行优化前后的 release 二进制，每组取七次中位数。64 个普通参数、只返回首参时，每次调用由 5.795 µs 降到 5.290 µs，堆分配从 11 次降到 6 次，均消耗 398 步。加入 256 次局部读取后，耗时由 11.670 µs 降到 11.142 µs，均消耗 973 步。自举时若将这一成本存入已准备的调用接口，仍要使低预算调用与首次遍历交付同样的失败位置和剩余步数。[调用入口与预算回归](../compiler/comptime_interpretor/src/invocation.rs) · [基准程序](../compiler/comptime_interpretor/benches/invocation.rs)

## 2026-11-21 · 求关联类型时保留已经遍历的前缀

设记录的第一个字段名很长，后面的字段类型依次投影关联项 A、B、A。A 和 B 各自有 comptime 初始化器，B 的函数体又显式读取 A。源 VM 原先在遇到尚未求值的投影时返回缺项，从类型根部重试。它已经能将外层三次投影合并成 A、B 两次求值，但仍把记录前缀遍历三遍。在基线 `3a333c3d`，仅把字段名从 1 字节延长到 4097 字节，就会多扣 12288 步。

现在结构遍历走到投影处，先结算已消耗的步数，再把剩余预算交给关联项初始化器。成功时从当前位置继续；失败时保留初始化器报告的源码位置及剩余预算。两个执行器中，同样的字段名变化都只多扣 4096 步。外层末次投影使用本次查询中 A 的结果，B 的函数体仍独立执行它对 A 的读取。运行时解释和具体 IIR 的类型观察仍只读所在快照已交付的选择。[投影与预算交接](../compiler/comptime_interpretor/src/selected_types/projection.rs) · [求值顺序与失败恢复](../compiler/comptime_interpretor/src/selected_types/observation_tests.rs)

当前取舍是让结构遍历的宿主栈帧在初始化器执行期间保持活动；剩余栈空间较小时在同一线程扩栈。类型结构沿用 64 层检查，字节码初始化器链由 VM 驱动。自举时若把结构遍历也迁到显式续延，续延需要携带已构造的字段、当前查询的关联项观察和交回的预算。若把观察放到 VM 全局，嵌套函数对 A 的读取就可能少执行一次。

## 2026-11-21 · 关联 Type 初始化器的定义检查和实例求值

设 `Selected(enabled)` 根据一个 bool 参数返回 bool 或 char。把它作为 `trait Source where enabled: bool` 中 `assoc Item: Type` 的默认值时，声明处已经知道结果属于 Type，分支选择仍依赖具体的 enabled。在基线 `deabc828`，仅检查这个声明就会尝试解释抽象的 enabled，报 `AbstractValueUnresolved`。现在泛型实现可保存检查并替换过的初始化程序；读取 `Holder<true>.as(Source<true>).Item` 作为局部注解或类型别名时，由该处的 required comptime 求值取得具体结果。若分支返回 `Wrapped<bool>`，交付的身份仍含 Wrapped 的 normal-form 头。[定义与选择](../compiler/elaboration/src/program/interfaces/associated.rs) · [经源码验证的实例](../compiler/luna/tests/deferred_associated_values.rs)

当前的取舍是继续向只读的签名查询提供已完成的闭合 Type。以同一个 Source 为例，若泛型函数的参数为 `T.as(Source<flag>).Item`，调用处提供 `true`、`Holder<true>` 和实参 `true`，签名特化仍会在选中初始化程序时报告 `selected associated value is not a completed Type template`。自举时，选中程序的查询需要把完整接口实例、接收者和成员身份交还给 elaboration；由请求方承担求值的预算、失败与生成定义的发布，再用结果继续检查该次调用。直接在 PTC 内运行初始化程序会使只读类型查询承担这些职责。[当前签名查询](../compiler/elaboration/src/program/interfaces/values.rs) · [只读投影](../compiler/type_resolution/src/associated/values.rs)

## 2026-11-21 · 泛型调用中由谁执行关联类型程序

`keep<false, Holder<false>>('n')` 的参数和返回值可以同为 `T.as(Source<flag>).Item`。在上一个阶段，类型别名能读出 char，同一投影一旦出现在函数签名却会在检查实参前失败。这次将单步选择的结果区分为已完成的类型和持有实现证据的初始化程序。遍历一份签名时，elaboration 遇到输入已齐的程序，借当前源码位置发起 required comptime invocation，再从该投影继续遍历。参数和返回值重复读取同一投影时共享这次遍历的结果。若接收者为 `Holder<flag>`，即使它已经匹配到泛型 impl，初始化器也仍然要等 flag 绑定。显式输入和普通 comptime 参数两种调用路径均有源码用例。[调用端](../compiler/elaboration/src/program/interfaces/call_types.rs) · [闭包捕获与依赖参数用例](../compiler/luna/tests/deferred_associated_values.rs)

源码 VM 还需要能执行这个程序。收集 dispatch 时将闭合投影及其所选程序保留为依赖，闭包构造检查具体捕获值时才向 VM 索取结果。例如同一个泛型闭包分别可以捕获 bool 和 char。闭包的保留值检查与具体 IIR 查询继续只读已交付的证据；缺失证据时不能把尚未执行的程序视为类型等式。[依赖收集](../compiler/materialization/src/lib.rs) · [VM 的捕获检查](../compiler/comptime_interpretor/src/selected_types/observation_tests.rs)

自举时有两笔开销值得处理。请求方交付具体的接口实例、接收者与成员，required VM 会在自己的声明快照里重新验证选择；当前节省了复制整个声明世界，代价是两次选择。逻辑查询使用类型查询预算，程序运行使用调用者的 required comptime 预算。运行时泛型函数的源码检查现在也可以完成，但具体 IIR 冻结仍缺少交付已观察类型的通道：把上例中的 `keep` 和入口改成 runtime 函数，实例化时仍报告 `selected associated value is not a completed Type template`。后续交付须保留完整选择依据、生成定义的身份以及求值失败的来源，避免在只读 IIR 查询中再执行用户代码。

## 2026-11-21 · 向具体 IIR 交付已求出的关联类型

若 `get` 的参数为 `Boxed<T.as(Source<flag>).Item>`，函数体可以只读字段。调用处对 flag=true 与 flag=false 分别得到 bool 与 char。此前在源码检查后丢弃了这次选择，IIR 再看同一函数签名时只看得到泛型初始化程序。现在每次成功的源码类型观察同时保留完整投影、实现声明、实现实参、初始化程序身份、结果类型及源码位置。IIR 在当前声明世界中重新选择，再按这几项取回类型。检查同一源码调用的不同部分时，仍只有一次初始化执行。用 `meta.StructBuilder` 作为类型程序的用例验证了 IIR 使用源码已经发布的那个结构体声明。[源码交付](../compiler/elaboration/src/program/interfaces/call_types.rs) · [生成类型的端到端用例](../compiler/luna/tests/required_definition_publication.rs)

冻结表随同一次编译的 NIR 与不可变声明快照共享，弱引用标记具体的已检查程序。独立构造的另一份初始化器即使正文相同也无法消费旧记录。源码表达式读取成员仍遵守原有的执行规则；如果两次观察为同一选择交付不同类型，仅在请求这个具体身份时报告冲突并附两个位置。自举时若要跨进程或跨修订重用记录，需要为初始化器和其调用的声明提供可校验的版本身份。进程内的程序身份只适用于本次冻结的声明世界。[记录和冲突检查](../compiler/nir/src/program/observed_types.rs) · [匹配原声明快照](../compiler/type_resolution/src/associated.rs)

本阶段还实测了没有源码观察可供交付的情形：泛型 `relay<flag>` 仅在函数体中取得 `leaf<flag>`，由入口调用 `relay<false>()`。如果 leaf 的签名引用上述 Item，投影要到 relay 实例化才首次闭合。已有交付可以支持这条路径；首次闭合时的缺项需要由实例化的编译阶段向源码 comptime 世界发起请求。

## 2026-11-21 · 在具体特化时第一次需要关联类型

`relay<flag>` 的签名可以完全不含关联类型，函数体里却有 `let callback = leaf<flag>`，而 `leaf` 返回 `?Holder<flag>.as(Source<flag>).Item`。源码检查 relay 时 flag 仍然开放；冻结入口 relay<false> 时才有足够信息求 Item。这个请求由具体 IIR 的特化器发起。它先在声明环境中选择实现、核对实参和初始化程序身份；若已有交付则沿用，否则把闭合的成员读取交给同一源码快照的 comptime VM。合约失败保留程序位置与拒绝原因。PTC 只负责选择所需的类型命题。[特化入口](../compiler/materialization/src/staged.rs) · [间接调用与失败恢复用例](../compiler/luna/tests/deferred_associated_values.rs)

特化器复用声明快照与已准备的代码，每次执行仍有独立的 VM 状态，并从请求方扣除实际消耗的步数。新观察暂存在本次类型遍历中，整个类型及其结果成功保留后再供同一声明环境的后续查询读取。如果元组的第二个投影失败，重试时必须重新获得第一个投影的结果。这个事务只覆盖类型观察和视图缓存。

目前，源码阶段已发布的生成类型可按原身份进入 IIR；若第一次在上述 leaf 特化时才运行调用 `meta.StructBuilder.Build` 的初始化程序，真实 sysroot 用例仍停在 VM 的 `interpretation Type`。冻结快照目前没有接入新定义发布。自举时需要将新声明及其布局连同类型身份交付给消费该类型的声明环境，并为失败的发布和旧快照分别维持一致性。仅交付一个新声明编号不足以恢复其字段与布局。

## 2026-11-21 · 给首次在特化期间生成的类型交付声明

## 2026-11-21 · 普通 comptime 实参也能发布生成的定义

在 `inspect(Built(flag), flag)` 中，`Built` 可以根据当前实例的 flag 构造一个 struct 或 newtype。实例键中要保存具体类型的身份，生成定义的字段和表示也必须随图交付。求值以包含实参表达式的函数或方法所在包分配身份，VM 交付返回值和本次全部生成定义。物化器先在候选声明快照中安装定义，再用新布局冻结值；两步都成功才让同次调用的后续参数读到这批声明。冻结失败会消耗已经使用的预算，原声明世界仍可继续使用。[真实 sysroot 的双实例用例](../compiler/luna/tests/required_definition_publication.rs) · [读取新布局的默认参数](../compiler/luna/tests/nominal_staging.rs)

当前实现需要在求值之后重新获取布局。一个调用的入口快照可以解释第一个操作数，却可能缺少它刚生成、随后默认参数要查询的 newtype。自举时若为绑定器缓存布局，缓存必须关联声明世界的版本。当前没有表达式所属包信息的全局初始化路径也缺少分配新定义身份的依据。另一个独立问题在源码检查阶段就会发生：泛型函数用 `match` 检查 `empty(Selected(flag))`，其中 `empty(comptime ty: Type)` 返回 `?ty`；检查器仍会在 flag 具体化前执行 Selected。实例阶段可以发布类型，源码阶段对这个待定结果的描述仍需补齐。

调用重写现在复用每个已求值实参的实例键表示，以及绑定完整参数列表时得到的替换和槽位映射。前例再插入一个运行时 char 形参：准备依赖前一项的默认值时需要查询一次 char 参数域，绑定最终参数列表时需要再查询一次。函数体和调用方共同使用第二次的绑定；原编号 1 的 char 参数在两边均成为运行时槽位 0。此处复用只跨同一次调用的重写过程，不缓存用户程序的 invocation。若调用接口和实现签名不同，两份参数域仍须分别检查。

## 2026-11-21 · 在开放定义中检查由实参决定的结果域

`empty(comptime ty: Type) -> ?ty` 的调用者可以用 `empty(Selected(flag)) match { null => true, _ => false }` 判断结果是否为空。检查函数定义时，检查器已知道这是可选值，可以检查模式覆盖；若分支取出 payload 再对它求逻辑非，仍需证明它支持相应操作。此时外围参数 flag 的具体值要等到调用方供应。若为了得到可选值的内层类型而执行 Selected，即使两个分支都合法，VM 也会遇到无法求值的抽象 flag。

对有已形成签名的直接调用，前端从参数域、结果域和声明约束提取本次需要观测的实参槽位，并跟踪这些实参读到的外围 comptime 形参和子句绑定。定义检查先用已有值身份；确实依赖待供应输入的 producer 取得本次检查专用的刚性参数。该参数记录 Type 或普通 comptime 值的 sort 和域，只供当前定义验证使用。调用帧保留已检查的 producer。具体调用重新检查原源码，生成的 struct 声明可同时在实例键、可选结果及字段布局中找到；同一程序以 true 和 false 调用时，两个字段分别为 bool 和 char。[定义检查和拒绝用例](../compiler/luna/tests/open_input_observation.rs) · [生成类型与结果域](../compiler/luna/tests/required_definition_publication.rs)

当前需要先扫描固定签名函数的直接调用和转发依赖，再用同一份源码分别做定义检查与具体实例检查。这个选择保留了声明顺序独立性，也意味着定义检查和实例检查会重复遍历。开放定义中的两次独立计算各自使用独立的检查身份；一个约束若需要证明两者相等，仍须有可复用的值身份或显式证据。携带可写捕获的默认参数、必须在原始 comptime 调用顺序中执行的依赖，仍由已有的调用续体路径处理，部分情形会被拒绝。自举时可以对比复用已检查的带作用域 producer 的成本，尤其要验证求值次数、默认参数写回顺序以及失败后的恢复。

## 2026-11-21 · 仅在实参正常交付的路径上观察身份

`accept(if select(flag) { return false; } else { bool }, true)` 有两个执行出口，但只有 else 会把 Type 交给第一个参数槽。定义检查可以用 bool 检查第二个实参。VM 仍在原位置调用 select，提前返回时跳过剩余实参和 accept。对于一段顺序代码，例如 `do { return true; bool }`，定义检查仍可读取已检查的尾表达式；执行时不会到达它。[源码回归用例](../compiler/luna/tests/ordinary_input_identity.rs)

检查器使用有预算的工作栈检查未知分支。如果能交付值的出口都给出相同身份，就保留该身份。未知条件或失败的 guard 可能改写外层绑定；处理后继出口前须使这些绑定上的旧事实失效。当前对 match 的写入分析合并所有 arm，因此会放弃某些实际可证明的身份。不同出口真的会交付不同类型时，调用者仍须从本次执行取得值。自举时值得比较这种静态观察与保留原 VM 调用现场各自的开销，特别是模式很多而每个分支可见绑定也很多的情况。[身份观察](../compiler/elaboration/src/program/input_observation/exits.rs)

## 2026-11-21 · 调用实参求到一半时的循环出口

`combine(prefix(), do { while ... { accept(probe(), Key<...>); }; result })` 同时有两次尚未完成的普通调用。Key 的输入执行 continue 或 break 时，prefix 的值仍属于 combine，已经求值的 probe 属于被中断的 accept。用寄存器作为未完成调用的键可以找到两者，却无法直接表达这次跳转结束了哪一个。现在字节码按求值嵌套保存调用，并在循环入口记录词法作用域深度与普通调用深度。直接跳转和声明实参子执行返回的跳转都恢复这两个深度。[字节码执行](../compiler/comptime_interpretor/src/bytecode.rs) · [源码用例](../compiler/luna/tests/type_input_execution_order.rs)

两种解释器共用实参槽的开启、交付和完成规则。只有当前正在求值的槽能接收值；默认实参按声明序读取和改写自己的绑定环境，已交付给 callee 的普通值保留。没有默认实参的调用省去了为这个环境复制所有值的开销。自举时要保留的是求值前缀的所有权：`empty(Selected(flag))` 的两个正常出口若真能交付不同类型，仍须由活动 VM 把本次取得的值交给源码检查区域，后者才能继续检查依赖它的源码。当前工作落实了执行侧的槽与退出规则，这一双向交接仍待实现。[实参帧](../compiler/comptime_interpretor/src/call_operands.rs)

## 2026-11-21 · 普通 comptime 参数可以接收 Type 描述数据

`Forward(comptime value: Type) -> Type { value }` 可以转发 `Selected(flag)` 产生的 Any 或 char。VM 原先在参数绑定时无条件提取具体类型项，即使整个函数只读取这个局部值也会拒绝 Any。现在完整的描述值保存在本次调用的局部环境中；替换表为它保留尚未获得具体身份的槽。若同一次调用的后续参数是 `x: value`、结果为 `?value`，或正文需要 `?value` 的布局，就在关闭相应类型时报告身份未定。另一项独立的 Type 参数仍可以为后续参数供应精确身份。此规则也适用于域由先前实参确定为 Type 的普通 comptime 值槽。[源码与双引擎回归](../compiler/luna/tests/gradual_type_data.rs)

自举时应分别保存实际值和进入类型项替换所需的证据。当前保留槽可以借已有 callable telescope 验证边界，但错误还指向该处的受检表达式或声明，未串联产生描述值的路径。不同出口产生不同具体身份时，VM 能在已检查的调用中区分它们；若外层源码本身尚待该身份才能检查，仍需要将活动调用交回源码检查区域。

如果函数的第一个 Type 实参只是输出数据，第二个才用于正文注解，第二个不变而第一个从 bool 换成 char 时，应能复用同一份受检执行代码，同时返回本次的第一个实参。此前 VM 在入口将两个值都写入类型替换，导致缓存把这两次调用当成不同的正文。现在签名用到的身份仍在入口绑定；其余拥有型 Type 值留在本次 activation，只有正文注解引用相应槽位时才提取身份。已取得的存储或值引用在入口保留快照，避免暂停期间外部修改改变已经交付的身份。入口有程序条件、结果保证或待证明的类型义务时，当前实现仍提前绑定。这样减少了正文缓存中的无关差异，但没有消除入口的表示检查和签名依赖扫描。[调用帧准备](../compiler/comptime_interpretor/src/invocation.rs) · [代码复用与暂停写回用例](../compiler/comptime_interpretor/src/input_bodies.rs)

## 2026-11-21 · 普通实参的替换成本与执行现场

一个已求出的 Type 实参可以在后续参数域、默认表达式、结果或约束中出现多次。例如签名中的两个位置都引用 T，而 T 的实参本身是一棵很大的类型树。检查器只求一次实参，但按当前 NIR 表示，每处替换都要构造一份结果。普通调用的源码检查现在从同一份 elaboration 预算支付这些构造，先按绑定深度找到实际引用，再计算对应实参的节点和载荷。嵌套函数的同号参数属于自己的作用域。预算不足时，已经交付的槽仍然有效，尚未检查完的参数域不会进入等待交付状态。当前实现为保留原有的 sort 与作用域检查，先遍历再构造，自举时可以比较这种双遍成本和边构造边计费的实现。[调用替换](../compiler/nir/src/types/input_binding.rs) · [源码调用检查](../compiler/elaboration/src/program/block_regions/ordinary_calls.rs)

同一段 `Selected(flag)` 分别返回 bool 或 char 时，写成 `consume(Selected(flag), flag)`，可以在 `consume(comptime ty: Type, flag: bool)` 中检查 `empty(ty)` 并匹配结果。显式形参把类型身份的作用域和实际值的取得时刻都定下来了。在调用者中直接写 `empty(Selected(flag))`，或先用普通 `let ty = Selected(flag)`，源码检查仍缺这层交接。未来的隐式实现需要保持原作用域中的 return、可变捕获以及同一调用中先前实参的效果；单纯把后续源码搬进普通闭包会改变这些行为。[实参执行次数与身份用例](../compiler/luna/tests/ordinary_input_identity.rs)

## 2026-11-21 · 调用的返回类型与实际交付的值

`identity<Byte(), true>(9)` 的签名依赖第一个子句实参。若 `Byte() -> Type` 返回 `u8`，检查器可以据此检查字面量 9。调用本身仍留在实参所在的位置。另一个例子是 `guarded<Selected(), true>`，其中 `Selected()` 返回 `u16`，而 `guarded` 要求 `T == u8`。即使可以写出实例成功形成时的函数类型，跳过这一行的分支仍须正常执行；真正执行到它时才会在形成实例的地方失败。把返回类型写进全局实参观察表，会令未执行的分支提前报错，在递归调用中还会混淆内外两次调用的约束主体。[形成与递归回归](../compiler/luna/tests/ordinary_callable_types.rs)

目前检查器沿已解析的声明查看直接调用的返回表达式，识别闭合类型、按值转交的 Type 形参，以及分支可确定或各分支返回同一身份的条件表达式。分析和比较都支付 elaboration 预算。子句实参的执行计划按源码顺序淘汰后续写入可能改变的证据，留下的身份仅供实例签名替换。普通调用先覆盖无入口类型约束的具体 comptime 接口。这个实现重复读取 HIR，因为任意源码位置还无法统一取得可复用的已检查函数体。自举时应比较从受检正文发布返回证据的成本，并保留原始 invocation 对控制转移、引用写回和契约失败的所有权。若结果确实取决于本次运行，例如未知条件的两支分别返回 char 和 bool，源码检查仍需要与原调用交接的续体。[返回分析](../compiler/elaboration/src/program/input_observation/return_projection.rs) · [普通实参回归](../compiler/luna/tests/ordinary_input_identity.rs)

## 2026-11-21 · 普通调用中已执行的实参前缀

`accept(Selected(flag), expected)` 中，Selected 可能实际交付 bool 或 char。默认参数可以把这次取得的 Type 传给 `inspect`，也可以更新自己的形参绑定。后一个默认参数要看见更新，最终进入 accept 正文的普通实参仍须是最初交付的值。两种引擎让调用帧持有原值，默认表达式首次需要某个绑定时才从已交付槽复制其内部表示。复制整个请求的成本先从同一 VM 预算扣除；若一个宽类型无力复制，其他绑定也不会在这次请求中提前发布。一个已经在默认环境中被移走的绑定不会从原槽重新出现。[调用帧](../compiler/comptime_interpretor/src/call_operands.rs) · [含两个实际类型的源码用例](../compiler/luna/tests/ordinary_input_identity.rs)

字节码在编译默认表达式时记录自由局部绑定，参考解释器在实际到达默认参数时分析同一段代码。前者付出指令存储，后者会重复遍历。两者都允许共享原有存储与闭包身份。有独立资源清理计划时，清理动作还可能隐式读取绑定，因此继续提供完整的存储句柄。声明端已经保留受检默认表达式。它的普通输入注解由声明自己的形参绑定；后来若要把模板交给 VM 按实际前缀特化，必须保留这层作用域，否则递归调用中内外两层的同号槽会混淆。这里交付的是执行中的词法输入。若调用者源码本身还等着 `empty(Selected(flag))` 的结果类型，下一步仍需让检查区域在原 VM 激活上取得本次身份，并把它限制在有效作用域内。

## 2026-11-21 · 从已检查程序到可迁移的控制 ABI

同一个 `fn(bool) -> bool` 值可以先后指向一个恒等函数和一个会触发契约失败的函数。两个目标具有不同的优化证据。机器函数指针需要一致的返回约定；仅凭调用处推测目标“应该不会失败”就改用单值返回，在不透明指针的 LLVM 中甚至可能通过汇编检查。host 为经过认证的直接调用保留标量返回，为间接调用保留统一入口。适配入口在正常值旁补上 null。动态清理计划选出的命名函数、闭包和现场构造的 handler 也要遵守这个接口。当前会生成部分未被取址的适配入口，优化器可以删除它们。自举时宜在确定取址用途后再物化适配器。

检查递归调用失败的清理时，O0 观察到两次 Drop，O3 一度观察到零次。计数器指针来自形参，先进入聚合，再由析构函数中的普通调用写回。给最外层形参加 readonly 会允许 LLVM 消去这些观察。当前行为分析在缺乏聚合内部指针来源证明且析构可能写入时撤回形参的只读和不逃逸证据。这会损失一些合法优化。自举时应让清理程序消费和返回按字段保留的指针来源，与普通调用共享行为证明。

机器控制字独立于 Flurry 错误返回。正常数据和控制字各占一个返回字段，void 使用空结构占据数据字段。栈上的任务上下文携带取消标志与池身份；调度者及 control backend 对该对象负责。跨线程实验覆盖显式交接、取消和相邻任务隔离；完整的捕获、恢复和按分段起源归还栈需要实现 continuation 后端。当前 C 边界覆盖已接通的标量和数据指针，聚合的 C ABI 参数分类还需要独立的目标实现。[原生 ABI 用例](../compiler/luna/tests/host_direct_abi.rs)

### 正文特化只依赖正文读取的槽

一个 comptime 函数可以用第一个 Type 实参确定第二个参数的域，用第三个 Type 实参确定正文里的类型。两次调用分别交付 bool 和 char 给第一个槽时，入口必须按各自的域检查第二个参数。若第三个槽相同，两次调用可以共享同一份已检查的正文。VM 现在按正文中的绑定深度收集所读槽，缓存键保留各槽的替换项和细化到 Type 的标志。即使在热路径上，比较递归的替换项也要扣除预算。

当前每个源码正文只保留最近一次特化。交替使用两组正文真正依赖的类型仍会重新生成代码；其好处是存储有界。该选择只影响代码准备，调用的参数准入、执行和可观察效果仍逐次发生。检查开放调用时如何把尚未交付的 Type 操作数接回外层源码区域，仍需要独立的续体。[正文特化与回归用例](../compiler/comptime_interpretor/src/input_bodies.rs)

### 在调用结束时交付已绑定的结果域

`empty(comptime ty: Type) -> ?ty` 的签名可以预先检查；在一次调用的参数准入后，VM 才持有该次调用完整的结果域。即使两个调用都返回 null，使用 bool 和 char 作实参的调用也应分别交付 `?bool` 和 `?char`。解释器的可选值本身带类型，但宿主若从值的表示反查声明的结果域，就会把每种值的存储方式变成跨阶段协议的一部分。

当前 VM 在正文返回、结果检查、后置条件和清理全部成功后，移动该帧的值和结果域。嵌套调用先把值交还其父帧；宿主最后接收根调用的结果。Elaboration 把交付的类型从当前调用的作用域换回调用者的作用域，预先保存的类型仍供执行前的检查使用。开放正文中途请求 Type 并恢复源码检查的位置仍需保存独立的检查续体。只保存结果无法重建已经发生的写入、提前返回或仍在等待的实参。[VM 调用会话](../compiler/comptime_interpretor/src/invocation/host.rs) · [elaboration 的调用结果](../compiler/elaboration/src/program/required/prepared.rs)

### 在原调用的实参槽交付数据

当 `accept(Selected(flag), .next = mark())` 的后续检查取决于第一个实参，VM 可以在它存入形参槽后交还控制。此时 `Selected` 已返回，`mark` 尚未执行。若后面的实参提前返回，先前的交付仍然有效，未填的槽也不会补发。递归可以让位于同一源码位置的两次调用同时等待不同实参；关联多个槽的检查器需要持有某一次动态调用的身份。当前只在接收者索取身份时为该调用分配令牌。

宿主可以借用当前槽，并按 VM 的剩余预算将可导出的数据冻结在该次调用的作用域里。Any 保留描述字段，comptime 值引用继续由 VM 持有。当前接口适用于已有字节码的普通调用。开放正文若必须知道某个实参才能生成后续代码，仍需把源码检查续体和可执行前缀一起交给驱动；仅凭这条交付通道还无法启动那个前缀。[调用会话](../compiler/comptime_interpretor/src/invocation/host.rs) · [真实 sysroot 用例](../compiler/luna/tests/ordinary_input_identity.rs)

### 源码检查区域持有原调用的实参请求

`empty(Forward(do { mark(); let ty = char; ty }))` 需要先确定 `?ty` 的元素类型。源码区域现在随请求保留调用的 HIR 身份、形参槽和已检查的 producer。检查器能从这个封闭实参取得 char 并恢复待检查的槽，同时把整个 `do` 块交回调用计划。这样 `mark()` 在字节码和参考解释器中都只在原位置执行一次。将 `?char` 赋给 `?bool` 仍在检查期报错。

当前关闭实参时保守地检查自由局部绑定。默认值和命名实参可能在另一个实参修改绑定之后才读取它，先前记录的局部值不能证明那次读取的结果。缺少静态证据时，区域可以带着具体槽位离开检查步骤；现有源码驱动还不能在开放正文中启动原调用的前缀。自举驱动要在持有该动态调用的上下文中恢复这个区域，并处理前缀提前退出。[源码实参请求](../compiler/elaboration/src/program/dependent_inputs/tasks.rs) · [返回值证据](../compiler/elaboration/src/program/input_observation/return_projection.rs)

### 后续实参依赖前一个实参的执行结果

对 `accept(Selected(flag), value)`，持有这次调用者绑定的驱动可以先提交已检查的 `Selected(flag)`，读取它在本次执行中交付的 Type，再按该类型检查并提交 `value`。每次提交执行一段字节码，调用者环境和已填槽位跨段保留。若第二段提前 return，驱动直接收到该返回值，callee 的函数体不会执行。

这种接口允许驱动在后续代码成形之前取得实参，代价是按段准备字节码。它目前要求驱动已经持有某次执行的绑定并选定具名函数；开放函数定义的源码检查器还需要把待恢复的 HIR 区域关联到相应的动态调用。单独重跑 producer 会重复此前的副作用。[按段执行](../compiler/comptime_interpretor/src/invocation/source_prefix.rs) · [真实 sysroot 用例](../compiler/luna/tests/ordinary_input_identity.rs)

### 观察实参的类型域也要扣本次预算

普通调用原来只对签名替换扣费。读取替换后的关联类型时，每个形参都会重新取得一份默认查询预算，因而调用者给定的额度不能约束整次准备。现由替换与类型观察共用余额；观察失败保留已消耗的工作，待供给的槽仍可重新准备。[变量替换](../compiler/nir/src/types/input_binding.rs) · [源码域查询](../compiler/elaboration/src/program/interfaces/call_types.rs)

对 `empty(Selected(flag)) match { null => true, _ => false }` 做了对照。把同一段匹配移进 `consume(comptime ty: Type) -> bool` 并调用 `consume(Selected(flag))` 后，两个 flag 分支都能执行。形参把 ty 绑定在消费它的代码内，检查外层可选形状已经足够。内联写法在检查 relay 的定义时提前索取了 ty 的身份。源码驱动应能表达这段绑定的作用域，并保留 producer 的求值位置；把元素存入有具体类型注解的变量仍需要证明身份相容。VM 单独执行一段前缀的测试不能验收这条源码路径。

### 在消费结果的位置绑定实际计算的 Type

例如 `nested(Selected(flag))` 的结果是 `??ty`。检查 `value? => value matches null` 时，只需知道 `value` 有一层可选结构；把内层载荷赋给 `bool` 仍需要证明 `ty` 的身份。源码检查器为每个被需求的普通 Type 实参建立独立的声明身份，先按这个身份检查模式和分支，检查匹配结果能否离开该作用域。实际求值时才取得本次调用的类型。

最初用一个普通 comptime 辅助函数承载这些身份。无载荷分支可以通过返回分支编号留在原调用者；读取载荷的分支必须移进辅助函数。这使得同一分支写外层变量、从外层循环跳出或向外层函数返回时，控制和存储都落到了错误的帧。把调用者的值复制到辅助函数也会让 guard 的写入失去原来的位置。

现在 NIR 的 `with-type-inputs` 保存实参准备、类型绑定和词法正文。调用者先求值 callee 和每个显式实参，按书写顺序存进新鲜局部变量。节点只读取这些位置，类型按对应形参的身份替入正文。比如先写 `.B = Right(flag)` 再写 `.A = Left(flag)` 时，执行顺序是 Right、Left，载荷 `Tuple<A, B>` 的类型顺序仍是 A、B。若夹在两者之间的 `null` 已经需要前一个实参提供可选元素类型，编译器在这里另起一层词法作用域。原调用继续负责缺省参数和后续实参。

字节码复用声明实参计划的调度器，在专门化后的正文执行期间借出调用者的局部存储，随后连同控制结果一起归还。树解释器在同一环境中执行正文。这样，guard 的写入、读取模式载荷后的 `return`、指向外层循环的 `break` 和 `continue` 都保有原来的目标。显式传入 `Any` 时，要求具体身份的消费点仍报告 `TypeContractUnresolved`。

自举时值得保留词法边界和求值次序。目前每层还要复制、特化正文并准备执行片段，交叉依赖多时可能重复走后缀；复制和替换使用 invocation 预算。对 comptime 值引用接收者，原调用保留拥有者的局部位置、字段路径和是否可整体替换的权限。计算得出的基值在后续实参之前进入私有局部存储；捕获整个字段值会割断方法写回原位置的路径。变参收集、运行时环境准备和词法 Type 绑定共用这条选择规则。类型由源码中更靠后的实参决定时，仍缺对应的交付方式。当前入口是普通 comptime 匹配。[源码实现](../compiler/elaboration/src/program/scoped_operands.rs) · [源码验收](../compiler/luna/tests/ordinary_input_identity.rs)

变参收集和展开可能已把调用改写成一串按源码顺序执行的局部绑定。词法 Type 作用域接收这些已有绑定，展开包只求值一次。形成具体身份的时刻也影响行为：若前一个实参返回 Any，而独立的后一个实参从调用者提前返回，就应当完成该返回；只有实际抵达使用该身份的操作才需要检查它。缺省实参仍由原调用帧交付。

### 调用准备中的源码位置

在 `cell.replace(...packet())` 中，展开包之前必须取得接收者。接收者是局部变量时，调用保留它的存储身份；若写成 `cell.produce().replace(...packet())`，则先执行一次 `produce()`，再展开包。在两种写法里，接收者都占据求值顺序中的一个位置，但前者可以没有对应的准备语句。把所有输入快照到临时变量会让方法悄悄修改副本；按准备语句数倒推实参序号又会错放展开包。

在宿主实现中，elaboration 合成调用时临时保留每个书写位置的语句边界，另留最后一个边界给尾部空展开包。相邻位置可以共享边界；一个位置也可包含多条环境取得语句。属性收集在同一坐标中展开字段，记录构造发生在字段之后。边界只需在组合期间存活，完成的 NIR 和两种 VM 均沿用原有调用与值引用表示。[调用准备](../compiler/elaboration/src/program/arguments.rs) · [接收者回归](../compiler/luna/tests/comptime_receivers.rs)

泛型方法给出了另一种失败方式。为确定 `Cell.put(cell, ...packet())` 的元素域，检查器可能先检查 `cell` 再确定参数传递方式。类型证据可以在这一步复用；若暂存的值被当作最终接收者，就会丢失原位置和 `let` 的整体替换限制。选定方法后须区分已经检查过的原始实参与真正由展开包解出的字段，只有后者属于包的临时存储。可调用值携带的阶段也要保留在实际调用处，参数推断处理的是其中的函数签名。

### 类型供应晚于值实参

对于 `empty(.value = do { ready = true; null }, .ty = Selected(ready))`，前面的块有两项要求。写入和可能的提前返回属于该实参的求值位置；构造带有具体元素类型的缺省可选值，则要等到后面的 Type 实参交付。把整块挪到类型之后会颠倒写入，先用占位类型构造值又会把错误身份交给 VM。

普通 comptime 匹配的调用准备把已经检查的可选、元组与匿名记录构造留到类型作用域内。普通字段、局部读取和块的控制效果在原位置执行。多个值离开同一个源码块时，目前通过一个临时元组带出该块，在构造前解包。这保留了局部作用域，代价是额外的打包和解包；在自举实现中可以把它们表示为续体的多个输入。执行期间确实需要晚到类型的操作仍需要自己的交付协议。[实现](../compiler/elaboration/src/program/scoped_operands/forward.rs)

调用路由可能已经为变参收集和展开包建立了局部绑定。准备阶段同时追踪尚未就绪的声明类型和延后构造的局部值。依赖这些值的元组构造按原顺序在调用前完成，独立的包和其他实参仍在其源码位置执行。这样，已检查的 producer、展开字段和见证类型都无需再求值一次。

### 为倒序实参保留已选分支

当后面的 Type 实参可能修改条件读取的变量时，应在前一个实参的位置运行原来的 `if` 或 `match`，包括模式观察、guard 和所选分支的可执行部分。分支选中后保存序号和构造所需的值。类型到达时以这个序号恢复该分支的构造；guard、分支内的调用和对可变局部的读取都只发生一次。直接从分支返回的路径无需生成序号。

没有值需要保存时，普通 NIR 只传分支序号。如果每个能返回的分支都携带相同完整类型的载荷，选中的分支直接交付一对值 `(序号, 载荷)`。判断相同时保留名义类型和调用依赖的身份。载荷类型或有无载荷因分支而异时，仍为各个带载荷的分支建立独立可选槽，只有选中的分支写入自己的槽。自举时可以为这种情况设计带标记的异构环境，使临时存储只随最大载荷增长。[分支构造](../compiler/elaboration/src/program/scoped_operands/forward/branches.rs)

在 12 个返回布尔载荷的分支和一个提前退出分支的用例里，同一次 `check()` 调用先后使用两种类型实参。改为直接交付后，字节码 VM 的预算步数从 9208 降到 6063，树解释器从 2560 降到 1652。该计数衡量这一用例消耗的 VM 预算。

### 固定宽度整数组成的 comptime 列表

格式计划每处理一个字段，就会向 `meta.List<u64>` 追加一个打包后的格式描述。若每次调用都逐个确认前缀中的值能用 `u64` 表示，构造整个列表的这部分检查次数会随字段数平方增长。首次检查不可变载荷时可以记录整数的符号类别，以及能容纳全部值的最小位宽。连结同类列表时取两者位宽的最大值。写入一个元素会使新列表的记录失效，旧快照仍保有原来的数值范围。

自举时值得保留这两步的区别。数值范围只依赖载荷，可以共享。是否符合元素类型则取决于本次调用，例如含有 `4294967296` 的列表交给 `meta.List<usize>` 时，64 位目标能接收，32 位目标会拒绝。混合表示和需要进一步解析的整数元素域仍逐项检查。实例化缓存和用户定义的相等性均不参与。[列表表示](../compiler/comptime_interpretor/src/list_values.rs) · [目标宽度与快照回归](../compiler/comptime_interpretor/src/bytecode_lists.rs)

对完整 sysroot 的公开方法执行 128 次 `words = words.concat([word])`，其中 `word: u64 = 281474976710655`，最后核对长度与末项。相同程序在字节码 VM 中从 191458 个预算步降到 78047，树解释器从 184892 降到 71481。首次接收外部构造的列表仍须检查每个值。

### 普通调用也能限定计算所得类型的作用域

`inspect(comptime ty: Type, value: ?ty) -> bool` 允许写 `inspect(Selected(flag), null)`。检查调用表达式时，只要知道第二个实参能在任一 `?ty` 下构造，就足以确定整个调用返回 `bool`。执行抵达这里时，`Selected(flag)` 给出本次具体身份，构造 `null` 和进入 `inspect` 都在同一次调用中完成。倒序书写具名实参时，如果前面的块从调用者返回，后面的类型函数也随之跳过。

宿主实现让调用和外层模式匹配复用同一套词法绑定。当结果本身携带这个身份，模式和分支可以在匹配的作用域内消费它；普通调用只在结果类型能离开作用域时封闭这次绑定。这个表示避免了为不同参数猜测类型或重放用户代码。代价是其他需要消费动态结果身份的表达式仍要建立各自的作用域。给只接受具体类型的实参提供证据也仍是独立问题，例如仅凭 `Selected(flag): Type` 无法在定义处证明布尔字面量具有该类型。[调用检查](../compiler/elaboration/src/program/scoped_operands.rs) · [源码回归](../compiler/luna/tests/ordinary_input_identity.rs)

在普通 comptime 块中，`let value = empty(Selected(flag))` 把一个 `?ty` 交给后续语句。检查器可以检查 `value matches null`，也可以拒绝把另一次调用所得的独立类型赋给 `value`。执行时，类型由那一次 `Selected` 交付。解构声明的几个名字来自同一个实参，即使后面只读其中一个，初始化也只执行一次。

初版把动态类型的作用域从初始化延续到整个块尾。一段平直的代码依次创建并消费 84 个互相独立的局部值时，宿主因生成的作用域嵌套过深而拒绝了这个程序。

现在只在含这类初始化的块内，从尾部逆序记录局部值和具体类型身份的最后一次使用。若某个作用域中间出现普通声明，编译器也把范围延长到这些名字最后一次被读写或捕获的位置，解构得到的名字同样处理。已经封闭的区域可以整体并入外层，互相独立的区域作为同级语句执行。后面的 `value'type` 即使只在类型项中留下了依赖，也能取得最初的类型身份。宿主为此在 elaboration 阶段多做一次有预算的依赖分析，真正重叠的类型仍可能要求 VM 逐层特化。这个入口目前覆盖普通 comptime 块中由直接调用初始化、且省略类型标注的局部声明。[局部作用域实现](../compiler/elaboration/src/program/scoped_operands/bindings.rs) · [两种解释器的回归用例](../compiler/luna/tests/ordinary_input_identity.rs)

### 标注读取不可变局部 Type

在 `let ty = Selected(flag); let value: ?ty = empty(ty);` 中，标注需要的具体身份由第一次初始化产生。检查器保留 `ty` 的存储，用一个刚性参数检查标注、调用签名和后续局部使用；VM 执行到标注时再从这个存储取得身份。`let alias = ty` 可以共享这一依据，两次独立调用仍各有自己的结果。闭包只在标注里使用外部 Type 时也需要记录这一依赖。包含 `Any` 的值可以先传递，执行路径真正要求具体身份时才可能得到 `TypeContractUnresolved`。

范式头的实参也可能包含这些局部值。检查 `Key<if false { ty } else { bool }>` 时，收集语法上出现的所有名字会提前要求 `ty` 给出身份。宿主改为沿着已经检查过的 NIR 观察所选分支，每遇到一个实际需要的局部 Type，就取得符号依据并重新观察。这个过程计入 elaboration 预算，较宽的实参可能重复遍历；自举时可让结构观察在缺少输入的位置挂起并继续。结果始终保留原范式头。检查器把这些词法依据和可冻结的 comptime 值分开存放，块退出时恢复父层依据。[标注处理](../compiler/elaboration/src/program/scoped_operands/annotations.rs) · [源码回归](../compiler/luna/tests/ordinary_input_identity.rs)

直接写 `let value: ?Selected(flag) = null` 时，调用可以改写外层局部，实参中的 `return` 也可以退出外层函数。旧实现在检查函数定义时执行标注，读不到本次调用的 `flag`。现在普通 comptime 局部声明把产生 Type 的已检查表达式保留在标注位置，与普通调用共用有序的实参求值机制。执行先取得具体身份，再进入初始化和使用该身份的语句。如果初始化之前就退出，这两步都应跳过。最后使用位置的分析也要读标注中的表达式，否则只在后续标注里被读一次的局部可能过早离开作用域。

宿主仍需在执行前检查初始化。若从已检查的表达式或被调用函数的返回路径能确定类型，就用它检查右侧的值；其余情况保留独立的刚性类型身份。例如 `?Selected(flag)` 足以检查 `null`，而给 `Selected(flag)` 直接赋 `true` 需要额外的类型依据。这次接线覆盖普通表达式产生的局部标注。签名、范式头实参的取得与 CMTT 生成器仍有各自的检查入口。

### 在局部类型标注中形成范式应用

`let value: ?Key<Selected(flag)> = null` 需要在调用者拥有 `flag` 时执行实参，保留 `Key` 的头。现在静态观察遇到开放计算时，宿主将完整的 NIR 实参计划作为标注输入交给 VM。该计划已经保存具名实参的源码顺序、默认值和提前返回。通过高阶参数传入范式函数时，同一调用还负责取得实际的头。实参的返回值可以决定最终类型，范式函数体不参加这次计算。

观察可能先读到不可变的局部 Type，再在后面的实参遇到无法静态计算的调用。此时必须撤销这次观察新增的身份需求。例如后一个实参可能直接从函数返回，先前实参中的 `Any` 根本不会被用来形成具体类型。动态执行由完整计划重新决定需要哪些身份。自举时可以让观察先产生待提交的需求集。宿主暂用持久映射的快照和输入列表长度回退。

没有外部绑定、开放类型或调用者控制转移的范式计算，仍可在检查时完成，为 `meta.List<Element()> = [true]` 这类初始化提供具体的元素域。第一版把整个开放结果交给一个类型变量。对 `?Key<Selected(flag)>`，外层的可选结构足以检查 `null`。但在 `let xs: meta.List<Selected(flag)> = []` 中，空列表的检查需要知道产生结果的头和元素域。把整个结果当作未知类型会丢掉已经由构造过程保证的事实。

现在对声明身份已知、每个形参的域都是 `Type` 的头，VM 先执行一次完整形成，再用范式模式同时取得各个实参。检查器以这些实参的独立身份重建原来的头，因此可以检查空列表，也会拒绝在元素域仍未知时直接放入 `true`。这条路径复用普通范式模式的元数据检查，用户定义的多参数头也适用。取字段只使用当次形成的实际结果，不向 PTC 加入单射或不等公理。含普通值形参、变参收集值或头身份只在调用时才确定的应用，目前仍可作为整体交付。[标注检查](../compiler/elaboration/src/program/scoped_operands/annotations.rs) · [源码回归](../compiler/luna/tests/ordinary_input_identity.rs)

### 范式实参的词法域

在 `let value: ?Shape<bool, marked(n)> = null` 之后调用接受 `?Shape<T, width>` 的泛型函数，需要保留这次形成所得的 `width`。检查器现在为已知头的每个实参建立词法绑定，把形参域中的声明身份一并重命名到这次应用。例如 `Tagged<T, tag: T>` 的第二个绑定依赖第一个，传入 `Type` 时，VM 可以按实际域取得一个类型值。变参收集得到的 `meta.List<Type>` 同样占一个普通值槽。模式按书写顺序公开绑定，转换字段所需的域从已经形成的完整应用中取得。

宿主复用了范式模式和既有实参调度器。这样可直接检查每个操作数的求值次数、提前退出及域错误后的恢复，代价是复合值会经历从冻结项恢复成 VM 值、再冻结交付的往返。自举实现可直接交付已形成的实参向量，并在接收域中验证；缓存或共享这条向量时仍要保留当次调用的词法身份。对头也需要在执行中取得的应用，以及含有 `lift` 运行时环境的应用，检查器继续交付整个形成结果。拥有收集值的身份本身也无法证明该列表的长度和各个元素的静态类型。[标注检查](../compiler/elaboration/src/program/scoped_operands/annotations.rs) · [实参交付](../compiler/comptime_interpretor/src/declaration_plan.rs)

### 从已形成的收集值恢复初始化所需的元素结构

`let pair: Tuple<bool, ?Selected(flag)> = (true, null)` 中，右侧的 `null` 需要知道第二个元素有一层可选类型；内部类型由当次执行的 `Selected` 决定。检查器沿已检查的列表构造、拼接、定长展开和块尾读取元素结构。范式应用按原顺序形成成功之后，VM 从完成的列表按位置读取所需的值，沿可选类型和指针类型逐层取出内部身份。整个过程同样适用于用户的变参头和普通布尔值列表。某个元素提前退出时，后续投影和初始化随之跳过。

宿主会为需要在定义检查时引用的动态元素生成一次索引读取与词法绑定，额外的 NIR 随这类元素的数量增长。自举时可以用一个批量投影从同一冻结值交付多个位置，并继续保留接收域检查、失败边界与调用者的控制流。未知宽度的展开和元素域尚可能变为 `Type` 的列表，暂时保留整个值。已知的类型实参可以先确定依赖的元素域，例如 `Bag<Type, ...[?Selected(flag)]>`。[结构观察](../compiler/elaboration/src/program/scoped_operands/annotations/collections.rs) · [两种 VM 的源码回归](../compiler/luna/tests/ordinary_input_identity.rs)

### 分支汇合时保留哪些构造信息

局部标注的实参含有 `if` 或 `match` 时，两个分支可能交付不同的完整身份，同时都足以检查初始化式。例如一支交付 `[bool, ?bool]`，另一支交付 `[bool, ?Selected(false)]`，初始化 `(true, null)` 只需要两支共有的两个位置、首项的身份、第二项的可选构造。检查器在已检查的普通表达式和上下文化实参上使用同一个汇合规则。提前返回的路径不向后继提供值；长度冲突会丢失定长证据，元素构造有分歧时只保留两者的公共外层。多个展开各自汇合后再拼接，因此添加独立条件不会产生分支组合表。

目前这层结构观察要额外走一次已检查的构造，消耗 elaboration 步数。它也不追踪不同条件之间的相关性；最终的身份、条件副作用和载荷取自 VM 真正完成的那条路径。自举时可以在检查控制流汇合点时直接产出这些证据，复用已经形成的元素向量。[构造汇合](../compiler/elaboration/src/program/scoped_operands/annotations/construction.rs)

同一条规则也用于整个局部标注。写成 `let item: if flag { ?bool } else { ?Selected(false) } = null;` 时，定义检查可以确定最外层的可选构造。执行到声明处，检查器安排的绑定从实际形成的类型取得内部身份。提前返回可以跳过整个绑定；若所选分支以 `Any` 构造可选类型，当次执行仍会在取得具体身份时报告错误。检查完整身份与检查其公共结构可以共用一个形成结果，既保留条件的副作用，也免去了为分支分别复制后面的初始化式。[标注的词法绑定](../compiler/elaboration/src/program/scoped_operands/annotations.rs)

### 生成 quote 时，构造器的类型操作数属于哪个调用帧

`'(T { flag: true }.flag)` 中，字段初始化属于生成的 runtime 代码，取得 `T` 的计算属于正在进行的生成器调用。同样的花括号语法也能调用函数。宿主在定义检查时辨认出 Type 操作数，把对应的源码位置随已检查的生成器保存；探测失败会恢复位置集合。实际生成时直接在生成器的数据帧里取得类型，再用当次的字段描述检查构造。这个区别可以通过两次对同一个生成器布尔变量取反来观察：若先在 quote 边界取变量快照，再把表达式交给 VM，两次读取会得到同一个旧值。

宿主仍要在实际生成时重新 elaboration quote，因此需要保存这些阶段信息。自举时可把已检查的 Type 操作数和 runtime 字段直接编码在带阶段的构造节点中。字段布局是另一项证据：若类型生产函数沿各出口返回同一输入，定义检查可以保留该身份，实际调用照常执行。若字段完全来自尚待执行的可变 builder，则还需要一种能从已检查的构造过程取得字段描述、又不会提前发布名义类型的机制。[生成器中的类型计算](../compiler/elaboration/src/program/cmtt/generators/type_inputs.rs)

在 `'(schema.kind { value: true }.value)` 中，判断花括号的用途只需要知道字段 `kind` 的声明域是 `Type`。其具体值属于生成器，字段 `value` 的初始化属于生成的代码。连续构造两份 quote 可以复用同一份字段证据。如果两次之间有调用、写入或取址，宿主目前会一起丢弃可能过期的结构观察，连同嵌套检查帧暂存的快照。这会拒绝一部分实际上互不影响的更新。自举时应让对位置的写入和别名信息随已检查的构造步骤传递，这样才能只更新受影响的字段，也能在不同分支重新汇合时核对证据。

### 从 comptime 函数内的写入取得字段证据

工厂可以先令 `state.pair` 与 `state.saved` 取自同一份值，再写 `state.pair.a = last`。生成器随后使用返回值组装 quote 时，`pair.a` 应当采用 `last`，`saved.a` 仍采用原类型。定义检查可以在已检查的 NIR 上沿赋值的位置更新字段证据。每次写入只复制该路径的父节点及其字段表，其他子树与旧快照共享。实际生成仍执行原调用。

普通函数的 NIR 可能到生成器之后才产出。宿主在观察一个直接调用时按声明取得函数体，以该调用的值实参建立局部环境，必要时通过函数签名替换阶段参数。目前能处理直线代码中的局部绑定、整值替换和嵌套字段写入；遇到引用接收者、尚未解析的调用效果或控制流，会停止从这份函数体推断。自举时可用带依赖的函数体查询复用同一份检查结果，并在调用边界传递接收者的位置和写入信息。这仍是对成功返回值的观察，不应触发一次额外的调用或定义发布。[结构观察实现](../compiler/elaboration/src/program/constants/structural_calls.rs)

接收者的写入可以沿已检查的调用链传回。对工厂中的 `draft.add_field(.flag, Flag)`，两个 `List.append` 实例分别替换草稿的字段名列表和类型列表。宿主用已检查的投影定位接收者，在临时环境里观察方法体，成功后才更新调用方的对应位置；其他值实参保留传入时的快照。普通函数、带声明参数的方法和有 NIR 主体的编译器操作共享这一过程。当前只观察至多一个引用实参的调用；要推广到多个可能重叠的位置，自举引擎需要在同一抽象存储中表示这些别名。

生成器在本地调用 `Build()` 后可以立即引用新类型，例如 `'(T { flag: true }.flag)`。检查未调用的生成器也需要发现缺字段或字段类型错误。宿主沿直线语句观察已经检查过的字段写入，从构造请求取出有序的字段名与类型，为该次构造分配一个仅在这次定义检查中可见的类型变量。这个变量指向当时的字段快照。对同一个 builder 再次添加字段，先前类型的字段集仍取自原快照。真正调用时，VM 检查实际请求并发布名义类型。

目前宿主需要再遍历一遍这段 NIR。遇到无法解释其写入的调用时，就失去本段可变状态的证据；此时可能无法检查本来合法的 quote。检查器分配的类型变量有词法作用域，不能写入包的名义声明表。[局部 builder 的字段观察](../compiler/elaboration/src/program/constants/generator_layouts.rs)

类型的公开名字和字段布局也是两项独立的输入。`generate(name: Symbol)` 可以用实参给 struct 命名，只要已有证据足以检查 quote 用到的字段。局部检查环境将来自外层的未观察值保留为未知量；通过已检查的函数继续观察其他字段时，无需先取得这个名字。每次成功的 VM 构造负责发布实际名字和身份。

生成器的 `if` 和 `when` 可以沿每个分支传递字段信息。两个分支都调用 `builder.add_field(.flag, bool)`，后面的 `Build()` 可以使用这个字段；如果其中一个分支直接返回 quote，就只需要考虑继续执行的另一个分支。`when` 按顺序检查条件，没有兜底 arm 时还要考虑所有条件都为假的路径。块内临时名字在出口离开作用域；比较不同出口时按字段递归保留共同部分，分支前共享且从未改写的节点可以直接复用。

当前宿主在分支入口复制局部绑定表，共享表内的字段描述；一个无法说明写入范围的条件会使后继路径失去既有的可变字段信息。循环和带计算模式的 `match` 尚缺少相应的出口处理。自举时可令已检查语句的控制转移与写入信息共用同一份表示，避免在条件检查和合并字段时分别遍历。[生成器的分支检查](../compiler/elaboration/src/program/cmtt/generators/statements.rs)

把分支移入普通 comptime 工厂后，生成器只看到一次调用。宿主在工厂的已检查 NIR 上分别观察各分支，合并结果值和对外层位置的写入。条件已经确定时只需观察选中的分支；用户代码的实际调用仍由 VM 执行。工厂内显式的提前返回会越过嵌套块，宿主目前在遇到不能解释的中途返回时放弃这次观察。自举时应使调用者和被调函数沿用相同的控制转移表示，以便同时描述正常返回、提前返回和接收者的最终状态。[工厂的结构观察](../compiler/elaboration/src/program/constants/structural_calls.rs)
