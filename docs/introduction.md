# Flurry：为下一代系统软件而生

Flurry 是一门面向系统级编程的语言，诞生于对现有系统语言的深入反思。它的目标不是再造一个"更好的 Rust"或"更安全的 C++"，而是从语言理论的第一原理出发，以最大化**程序正确性、性能、抽象能力、开发友好度和语义健全性**为核心约束，设计一套一致且有原则的系统。

## 问题域

现代数字基础设施——操作系统、网络协议栈、数据库、虚拟机、嵌入式固件——对系统编程语言有着极致要求：毫秒级响应、GB 级吞吐、零意外崩溃。C/C++ 给了开发者无与伦比的底层控制力，但也留下了数十年的漏洞遗产。Rust 通过所有权借用检查大幅改善了内存安全，但仍有若干根本局限：

- **`unsafe` 是不可避免的**：驱动、FFI、某些数据结构必须用 `unsafe`，而这道门之后缺乏有力的形式化支撑。
- **泛型与元编程是事后拼接的**：过程宏、`const` 泛型、trait 特化各自有边界，没有统一的理论根基。
- **抽象与控制的摩擦**：高层抽象有时与底层优化目标发生冲突，开发者不得不手工绕过。

Flurry 的答案是：**把这些问题都当成语言设计问题，而不是库或工具链问题**。

## Flurry 的核心原则

### 1. 元编程即类型论

Flurry 用**两级类型论（2LTT）**统一了泛型、编译时计算和元编程：

- **`U₁`（编译期宇宙）**：类型、`comptime` 函数、范式（normal form）、属性都在此执行。
- **`U₀`（运行时宇宙）**：最终生成的机器代码运行于此。

两个宇宙通过 **Lift、Quote、Splice** 三个操作交互，通常是隐式的。这意味着"写泛型代码"和"写编译期程序"在 Flurry 中是同一件事，由统一的规则约束，而不是分散在不同机制里。

### 2. Normalization / Instantiation 两阶段

编译时计算分为两个阶段：

- **Normalization（定义端）**：在函数或类型被*定义*时，编译器对其进行符号执行、类型推导、约束检查，尽可能在此阶段暴露错误。
- **Instantiation（调用端）**：在泛型函数被具体类型*调用*时，触发进一步的编译期求值和特化。

这使"缺少 trait 约束"等错误能在定义端就被捕获，而不是推迟到调用端让用户困惑。

### 3. 分级安全

| 等级 | 含义 |
|------|------|
| `normal` | 默认。编译器通过仿射类型、可达性分析、副作用系统提供内存与并发安全。 |
| `unsafe` | 显式 opt-out 静态检查，用于驱动、FFI、特定数据结构。需明确标注。 |
| `verified` | 需要更强的形式化保证，编译器要求提供逻辑规范（`requires`/`ensures` 子句等）。 |

三个等级可以共存于同一代码库，逐步迁移，相互调用时有明确的边界规则。

### 4. 代数效应

Flurry 用**代数效应（algebraic effects）**统一了异步、迭代器、错误传播、状态注入、日志等"副作用"场景，取代了各自为政的 `async/await`、`try/catch`、Monad 等机制。效应在函数签名中声明，由调用方安装处理器，被调方只描述"需要什么"，不关心"如何做"。

### 5. 模式匹配是一等公民

模式不仅用于 `match`，还可以出现在参数、`while is`、`if is`、自定义 pattern view 等位置。Flurry 还探索位向量模式、跨元素匹配等方向，使模式匹配成为语言的骨干，而非语法糖。

## 与其他语言的对比

| 特性 | C/C++ | Rust | Zig | Flurry |
|------|-------|------|-----|--------|
| 内存安全（默认） | ✗ | ✓ | △ | ✓ |
| 编译时元编程 | △（模板） | △（过程宏） | ✓（comptime） | ✓（2LTT, normalization） |
| 形式化验证路径 | ✗ | ✗ | ✗ | ✓（`verified` 等级） |
| 代数效应 | ✗ | ✗ | ✗ | ✓ |
| 统一泛型理论 | ✗ | △ | △ | ✓ |

## 当前状态

Flurry 目前处于编译器早期开发阶段（词法 → 解析 → AST lowering → HIR → 名称解析）。语法定义已有数百行草稿，语义设计仍在持续演进。本文档集记录的是**设计意图**，部分特性尚未在编译器中完整实现。
