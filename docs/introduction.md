# Flurry：为下一代系统软件而生

Flurry 是一门面向系统级编程的语言，诞生于对现有系统语言的深入反思。它的目标不是再造一个"更好的 Rust"或"更安全的 C++"，而是从语言理论的第一原理出发，以**程序正确性、性能、抽象能力、开发友好度和语义健全性**为核心约束，设计一套一致且有原则的系统。

## 问题域

现代数字基础设施——操作系统、网络协议栈、数据库、虚拟机、嵌入式固件——对系统编程语言提出了严格要求：毫秒级响应、GB 级吞吐、零意外崩溃。C/C++ 给了开发者充分的底层控制力，但也留下了数十年的漏洞遗产。Rust 通过所有权借用检查改善了内存安全，但仍存在以下局限：

- **`unsafe` 不可避免**：驱动、FFI、某些数据结构必须使用 `unsafe`，而 `unsafe` 块之后缺乏充分的形式化支撑来保证正确性。
- **泛型与元编程缺乏统一基础**：过程宏、`const` 泛型、trait 特化各自有边界，因此没有统一的理论根基将它们连接起来。
- **抽象与控制存在摩擦**：高层抽象有时与底层优化目标冲突，开发者不得不手工绕过抽象层。

Flurry 的答案是：**把这些问题都当成语言设计问题，而不是库或工具链问题**。

## Flurry 的核心原则

### 1. 元编程即类型论

Flurry 用**两级类型论（2LTT）**统一了泛型、编译时计算和元编程。2LTT 源自类型论中将不同计算阶段（phase）严格分层的思想，它的核心优势在于：泛型代码和编译期程序受同一套规则约束，消除了分散在不同机制中的不一致性。

- **`U₁`（编译期宇宙）**：类型、`comptime` 函数、范式（normal form）、属性都在此执行。
- **`U₀`（运行时宇宙）**：最终生成的机器代码运行于此。

两个宇宙通过 **Lift、Quote、Splice** 三个操作交互，通常是隐式的。因此，"写泛型代码"和"写编译期程序"在 Flurry 中是同一件事，由统一的规则约束。

### 2. Normalization / Instantiation 两阶段

编译时计算分为两个阶段：

- **Normalization（定义端）**：在函数或类型被*定义*时，编译器对其进行符号执行、类型推导、约束检查，尽可能在此阶段暴露错误。
- **Instantiation（调用端）**：在泛型函数被具体类型*调用*时，编译器触发进一步的编译期求值和特化。

这一设计使"缺少 trait 约束"等错误能在定义端被捕获，而不是推迟到调用端让用户困惑。

### 3. 分级安全

| 等级 | 含义 |
|------|------|
| `normal` | 默认。编译器通过仿射类型、可达性分析、副作用系统提供内存与并发安全。 |
| `unsafe` | 显式 opt-out 静态检查，用于驱动、FFI、特定数据结构。调用方需明确标注。 |
| `verified` | 需要更强的形式化保证，编译器要求开发者提供逻辑规范（`requires`/`ensures` 子句等）。 |

三个等级可以共存于同一代码库，团队可逐步迁移，而且等级之间有明确的边界规则来保证相互调用时的安全性。

### 4. 代数效应

Flurry 用**代数效应（algebraic effects）**统一了异步、迭代器、错误传播、状态注入、日志等"副作用"场景。代数效应的核心思想来自程序语义学：将副作用的*描述*与*处理*分离——被调方在签名中声明"需要什么效应"，调用方安装处理器来决定"如何实现"。这种分离取代了各自为政的 `async/await`、`try/catch`、Monad 等机制，使不同类型的副作用获得统一的组合方式。

### 5. 模式匹配是一等公民

模式不仅用于 `match`，还可以出现在参数、`while is`、`if is`、自定义 pattern view 等位置。Flurry 还支持位向量模式和跨元素匹配等方向，从而使模式匹配成为语言的骨干结构，而非语法糖。将模式提升到一等地位，是因为系统编程中大量逻辑本质上是对数据形状的判别与提取——统一的模式语法减少了手写掩码和条件分支的样板代码。

## 与其他语言的对比

| 特性 | C/C++ | Rust | Zig | Flurry |
|------|-------|------|-----|--------|
| 内存安全（默认） | ✗ | ✓ | △ | ✓ |
| 编译时元编程 | △（模板） | △（过程宏） | ✓（comptime） | ✓（2LTT, normalization） |
| 形式化验证路径 | ✗ | ✗ | ✗ | ✓（`verified` 等级） |
| 代数效应 | ✗ | ✗ | ✗ | ✓ |
| 统一泛型理论 | ✗ | △ | △ | ✓ |

## 当前状态

Flurry 目前处于编译器早期开发阶段（词法 → 解析 → AST lowering → HIR → 名称解析）。语法定义已有数百行草稿，语义设计仍在持续演进。本文档集记录的是**设计意图**，部分特性尚未在编译器中实现。
