# 可达依赖与有效性

## Intro

一个视图能否使用，取决于它实际指向的资源。复制视图、把它放进容器或传给另一个函数，都不会改变这个来源。

读取视图取得的独立数值则不同：数值已经交付，不需要让原来的存储继续存在。

## 语法

~~~text
reachability_type -> &expr expr
reference -> expr.ref
projection -> expr.id
~~~

`&r T` 为 T 描述外部有效性要求；它不是另一种取址运算。

## 正式定义

### 要求与拥有

`&r T` 表示 T 的相应使用要求 r 中的资源及相关事实保持有效。多个限定合并要求；限定本身不延长生命，不授予写入或释放许可。这一机制的作用类似于 Rust 的生命周期参数，但 Flurry 用显式的可达性集合取代隐式的生命周期推断，从而让跨调用边界的依赖关系在接口中直接可见。

值自己拥有的内部资源与外部要求分别解释。拥有字符分配的 String 可以转交其分配；而拥有元素缓冲区的指针容器，仍须暴露元素实际指向外部对象的要求。

函数边界可使用保守的要求上界。实际要求可以扩大到包含它的上界，但不能无依据删掉仍然需要的来源。没有显式写出限定，不等于没有依赖或访问。

### 三类有效性

| 条件 | 破坏它的操作 | 后果 |
|---|---|---|
| 存储及当前生命周期仍存在 | 释放、结束对象、重建世代 | 不能继续按旧对象访问 |
| 位置含有适合当前操作的值 | 移出、部分初始化、破坏类型条件 | 不能执行需要该值的读取或清理 |
| 关于内容的事实成立 | 修改相关字段、元素或管理状态 | 旧的等式、形状或搜索关系不能继续使用 |

普通标量写入可以保留存储，同时改变内容。而缓冲区重分配则会结束旧分配；此时容器描述符仍可用，但旧元素视图不再可用。

同一地址再次用于新对象，不使旧指针的目标身份复活。视图绑定的是创建时的目标；来源变量后来改指其他分配，不会重定向旧视图。

### 依赖传播与移除

取址建立对实际目标的要求。复制视图传播既有要求，不制造对中间视图槽位的依赖。读取后取得独立标量，不把来源槽位永久附着到标量上。

对单个精确位置的完整覆盖，在合法清理旧值后，编译器可以用新值要求替换旧要求。然而，未知别名、部分覆盖或汇总了多个实例的位置，不足以证明旧依赖全部消失。

### 跨作用域交付

结果、写入外部对象的值和捕获环境，都必须在相关清理之后仍满足依赖。把局部地址装进堆容器不会延长局部对象的生命；擦除类型也不会删除这项要求。

来源根 `.constant`、`.heap`、`.local`、`.global`、`.tls`、`.external` 表示粗粒度来源类别，不证明具体对象永远有效。不同调用的局部存储不能合并成一个全程序的 `.local` 对象。

## 常见示例

### 数值可以离开来源

~~~flurry
fn make_number() -> i32 {
    let local = 23i32;
    local
}

-- 拒绝：返回指针需要已结束的局部位置。
fn escape_address() -> *i32 {
    let local = 23i32;
    local.ref
}
~~~

### 复制视图不依赖中间变量

~~~flurry
test {
    let text = "hello".to_string();
    let view = do {
        let first = text.as_str();
        let second = first;
        second
    }
    println("{}", view);
}
~~~

两次复制都保留同一个字符目标，因此内层块结束不使它失效。

### 容器的管理存储与元素目标不同

~~~flurry
fn make_values() -> Vec<i32> {
    let values = Vec.new();
    let local = 23i32;
    values.push(local);
    values
}

-- 拒绝：堆中的元素仍保存局部地址。
fn make_addresses() -> Vec<*i32> {
    let values = Vec.new();
    let local = 23i32;
    values.push(local.ref);
    values
}
~~~

两者都可以把容器自己的缓冲区转交出去，但只有后者额外依赖即将结束的 local。

### 旧视图不能用新容量补证

~~~flurry
-- 拒绝：若 push_str 更换字符分配，old_view 的目标未获保持保证。
fn read_after_growth() {
    let text = "hello".to_string();
    let old_view = text.as_str();
    text.push_str(" more");
    println("{}", old_view);
}

fn read_current() {
    let text = "hello".to_string();
    text.push_str(" more");
    let current = text.as_str();
    println("{}", current);
}
~~~

read_current 在更新后取得实际当前视图。判断是否扩容必须依据实现契约及入口状态，不能从操作后的长度或容量反推旧分配未被替换。

### 返回依赖的保守上界

~~~flurry
fn longest(first: &r1 str, second: &r2 str) -> &r1 &r2 str
where r1: Type.vars.ReachSet, r2: Type.vars.ReachSet,
    outcomes read(first) and read(second)
{
    if first.len() >= second.len() {
        first
    } else {
        second
    }
}
~~~

实现实际返回其中一个输入；接口用两个来源要求的并集保守描述它，不声称结果同时指向两块字符存储。

## 与 Rust / Zig / C / C++ 的关键差异

Rust lifetime 与引用规则是表达来源生命约束的对应物；Flurry 还用具体内存效果说明内容修改、目标终结和可保持关系。[Rust 引用](https://doc.rust-lang.org/reference/types/pointer.html)

C/C++ 可通过 owner、句柄和显式约定表达来源，但普通裸指针类型不会自动传递这些证明义务。Zig 同样可用 allocator 与对象约定管理来源；`&r T` 将要求显式交给跨边界检查。

## 运行时实现设计引导

静态依赖不要求每份指针都携带一张依赖表。无法静态消除的检查按具体协议保留，例如句柄世代、访问租约或容器状态。

动态检查成功只发布其实际验证的事实。仅观察一次"地址仍相同"，不足以证明对象世代未改变，更不足以阻止稍后的并发终结。

## 编译器实现引导

编译器分别维护资源责任图和操作依赖图。分析区域身份至少包括对象实例与生命周期世代；内容事实另带版本，不把每次写入都当作新世代。

- 取址：建立当前目标及访问所需事实。
- Copy：传播目标关系，保留源。
- move：迁移依赖和责任，更新源位置状态。
- write：失效重叠的旧内容事实，应用真实写后关系。
- kill：撤销当前区域存活依据，不递归执行依赖者析构。
- 出口：应用剩余清理后，核验所有对外结果与保留关系。

编译器用反向依赖索引查找受影响事实，避免每次写入扫描全部值。资源循环可以用分量或摘要保守处理；汇总精度不足时留下具体义务，不能以归并对象来制造有效性。
