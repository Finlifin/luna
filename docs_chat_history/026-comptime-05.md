## 1. ordinary 与 loose 的关系

建议答复：它们是 normalization 的两种检查强度；其区别应落到哪些检查 query 必须在 normalization 完成。ordinary 按当前环境检查操作的 requirement，并传播适用的结果命题，不要求所有前置计算先取得具体值。loose 允许指定的检查推迟，嵌套 runtime 定义仍保持 ordinary。

依据与取舍：作者本轮已确认操作契约与检查 query 的视角。此前“loose 允许更多延迟”可以保留，但必须说明延迟的是哪些检查，而不能按整个未知值依赖链一起弱化。具体必检项目仍按已确认规则，未补造完整清单。

## 2. HIR 阶段判断强度的依据

建议答复：按语法和显式上下文确定 ordinary/loose，进而确定需要在 normalization 完成的检查类别。HIR 中逐步取得类型、绑定和契约信息，是执行这些检查的过程；暂时无法取得某个求值结果，不得据此将 ordinary 改成 loose。

依据与取舍：构造决定强度是此前确认；强度落实为检查 query 的完成要求是本轮补充。不能混淆模式已经可判断、检查已经完成和结果已经算出这三个状态。

## 3. ordinary 内嵌 comptime block 的范围

建议答复：A 的修正版。只有 block 内按构造属于 comptime 的部分采用 loose；其内新定义的 runtime 函数仍采用 ordinary。读取外部定义不会使该定义或外层函数跟着变成 loose。

依据与取舍：这是已有结论的重述。删除原 A 的“及其直接依赖”，因为这句话可能把检查弱化传播到 block 外，违反此前确定的边界。

## 4. 生成的 runtime 函数引用外部时，defer 携带什么

建议答复：外部引用按已有规则标为 defer。建议保留外部绑定身份、未知输入及结果契约；ordinary 中依赖其契约的 requirement 检查可以先完成，依赖具体值的计算继续等待。父环境实例化替换具体结果并兑现遗留义务，coherence 仍按已有边界检查。

依据与取舍：记录方式是建议，外部引用的 defer 已确认。本轮纠正的是：引用目标尚未执行并不意味着后续全部检查都要重新等到实例化。能否依赖未证明的结果契约，见本轮追问 2。

## 5. loose 中禁止带子句参数的开放分散定义

建议答复：Other，限制声明自身引入的子句参数，覆盖该规则所说的各类开放分散定义，而非只限制 implementation。目标可以引用父 comptime 环境的输入和局部值，但在生成具体定义时必须已经确定。成员函数自身的子句参数不因这一条被一并禁止。

依据与取舍：作者用“不能有子句参数”限制开放分散定义，不是禁止引用父环境。原 A 容易过度禁止依赖父环境的类型构造；B 又只覆盖 impl。成员函数的排除是本次建议，避免把“开放候选集”与“成员函数可参数化”混为一谈。

## 6. coherence 是否与编译顺序无关

建议答复：B，并要求同一检查范围、同一输入及同一源程序执行顺序下，编译器调度顺序和增量缓存命中情况不能改变 coherence 的结论。loose 中源码规定的线性可见性仍然有效。跨模块哪些定义进入检查范围，留模块主题。

依据与取舍：这同时保留线性可见性和静态 impl 先检查的已有结论。A 擅自规定模块/包闭包；C 则把工具执行顺序变成语言含义。这里不主张交换两条生成定义的源码语句必须等价。

## 7. 三种 defer 是否统一

建议答复：统一理解为允许相应计算在当前 normalization 暂不取得具体结果，并保留其依赖与后续求值；不默认把依赖它的所有检查一并延迟。ordinary 中规定的 requirement 检查仍须完成，足够的结果契约可以使这些检查继续。类型、默认值、调用替换分别保留各自的结果要求。

依据与取舍：本轮 query 模型使 defer 的三个用途有了统一说明，但没有取消此前各位置的显式 defer 规则。作者示例省略 defer 是否有意，见本轮追问 3，不能由助手推断为新的隐式规则。

## 8. ordinary 中 Any 可以做什么

建议答复：每项操作能否使用，由当前环境能否满足其 requirement 决定；操作还可通过结果契约向适用环境传播命题。未知具体类型的值不因此任意可用，也不必只靠 inline 控制流取得事实。签名、先前操作契约、refinement 和本轮示例中的 PTC assumes 都可能提供相应依据。

依据与取舍：操作契约与 assumes 提供元组命题已由作者说明。不是给 Any 列一张特许操作表；只知元组也不自动知晓长度、成员类型或成员能力。assumes 的保证方式仍见追问 1。

## 9. refinement 命题提取失败

建议答复：命题提取提供当前 requirement 检查能够使用的事实；无法提取的部分不能当作证明前提。已有契约足以支持某操作时无需等具体求值；若 ordinary 中必检的 requirement 仍无法成立，就不能只凭未来会实例化而放行。refinement 的遗留约束仍在既定时点检查。

依据与取舍：这保留此前命题提取与实例化执行的规则，并把操作结果命题纳入事实来源。结果命题必须对应其绑定及适用路径，不能推导成所有命题永久有效。

## 10. defer 调用依赖 runtime 参数

建议答复：runtime 实参不阻止编译时类型计算：类型构造的 requirement 可以先检查，其具体结果或契约用于检查调用。若当前只有结果契约，就只能完成不需要具体值的那些检查，必需的类型求值按既定 defer 规则等待 comptime 输入。真正读取 runtime 值的需求不由 defer 或 PTC 凭空满足。

依据与取舍：本轮强调检查依赖与求值依赖的区分。PTC 可以描述当前尚未求出的结果性质，不意味着它已经获得未来 runtime 数据；运行时依赖类型和 quote 的更多机制仍留既定主题。

## 11. defer 失败的诊断归属

建议答复：A。实例化时触发的失败优先归触发该实例化的调用点，并关联 defer 原定义及必要依赖链。定义中当前就能确定的错误仍在 normalization 报告，不先推迟再改换归属。

依据与取舍：作者已选择实例化失败归调用点。这题不需要重新打开；附带原始位置是诊断建议，不更改失败阶段。

## 12. 可选子句参数默认值的执行时点

建议答复：A 的定义端解释。未包 defer 的默认表达式在定义的 normalization 中直接执行，不要求纯；如果需要尚未知的子句参数或其他输入，应显式延迟，不能静默推迟到调用端。取得的默认结果供省略该参数的调用使用。

依据与取舍：作者确认了“normalization 中直接执行、不要求纯、defer 才延迟”；定义端解释是我建议补足的部分。它与作者将调用点信息移交 implicit 参数的决定相符。不能再从“normalization 执行”推导出“整个构建中物理执行恰好一次”；不纯默认值在增量重算中的行为还需与第 17、23 题一起约束。若你原意是 B，请只改这一题即可。

## 13. 延迟默认值是否能读 implicit 参数

建议答复：Other，本题现在不规定 implicit 在默认值中的可见性或绑定顺序。只限定：defer 不创造名称可见性，不把 runtime 输入变成 comptime 输入。以后若参数规则允许某个 implicit 在该默认表达式中可见，且求值时它是已知的 comptime 输入，就没有必要仅因它是 implicit 而另行禁止。

依据与取舍：这是条件式建议，不是确认当前已经允许这种引用。A 提前决定注入顺序，B 无依据地排除编译时 implicit，C 新增未确认的 capability 标记。作者已明确函数主题再讲 implicit，当前不增加独立追问。

## 14. 违反 pure 承诺

建议答复：A，但违约范围先限定为该承诺支撑的求值替换、缓存复用和特化结果不受保证；不能声称编译器会自动发现不纯并使缓存失效。编译器仍应维持自身的内部完整性，不能把用户承诺解释为破坏宿主进程内存的许可证。

依据与取舍：不验证 pure 已确认，违约后果尚未确认。B 承诺自动失效却没有检测机制，C 又把纯性改成必检性质。这里不把违约定义成 runtime UB，也不替内存安全体系制定新规则。

## 15. 不纯 comptime 允许哪些副作用

建议答复：Other，当前只确认编译时求值可以不纯，并支持程序化编译诊断。文件、网络、时间及编译器状态的具体操作是否存在、如何暴露，不在本轮补造。执行器只能执行实际提供的操作，不能由“不要求纯”推出任意宿主能力都开放。

依据与取舍：原 A 引入尚未确认的 capability 体系，B 承诺任意宿主访问，C 排除了作者保留的不纯表达力。这里保留未定的能力范围，但不让它阻碍当前执行模型讨论。

## 16. 两种执行模型的资源耗尽

建议答复：B。资源充足且输入相同的对应计算，应遵守相同的值、类型及副作用语义；预算可以不同，资源耗尽均使该次必需编译时求值失败，不得自动退回 runtime 执行。诊断可以说明是 interpretation 还是 execution 的预算耗尽。

依据与取舍：不同预算和语义一致已确认；禁止资源失败静默改换阶段是建议。相同输入可能因预算不同而一边成功、一边失败，所以不能承诺两者成功集合完全相同，也不把真实时间限制称为严格确定的步骤限制。

## 17. query 缓存适用范围

建议答复：comptime 与 query 在编译计算中交织，因此不能把 query 只理解为独立 pure 函数外加的一层缓存。query 可以包含检查、契约信息与 comptime 求值；是否可缓存另行取决于输入、依赖和可观察副作用。显式 pure 调用仍按此前候选规则准入，不能据此把外围含不纯计算的 query 整体视为纯。

依据与取舍：计算模型统一已确认，缓存算法仍是提案。建议把契约和其上下文依赖纳入对应检查结果的有效性管理：具体值相同但相关契约或候选集变了，不能仅凭值缓存继续沿用旧检查结论。此处不规定全局所有 query 的唯一键结构。

建议答复：统一理解为允许相应计算在当前 normalization 暂不取得具体结果，并保留其依赖与后续求值；不默认把依赖它的所有检查一并延迟。ordinary 中规定的 requirement 检查仍须完成，足够的结果契约可以使这些检查继续。类型、默认值、调用替换分别保留各自的结果要求。

-- axiom scalar_is_a_zero_rank_tensor where T { 
--     Tensor<T, .dims = []> == T

comptime predicate broadcastable(shape_a: meta.List<Integer>, shape_b: meta.List<Integer>) {
    (shape_a, shape_b) match {
        ([], _) => true,
        (_, []) => true,
        ([...a_rest, a_last], [...b_rest, b_last]) if a_last == b_last => broadcastable(a_rest, b_rest),
        ([...a_rest, 1], [...b_rest, b_last]) => broadcastable(a_rest, b_rest),
        ([...a_rest, a_last], [...b_rest, 1]) => broadcastable(a_rest, b_rest),
        _ => false
    }
}

pure comptime fn broadcast_shape(shape_a: meta.List<Integer>, shape_b: meta.List<Integer>) -> meta.List<Integer> {
    (shape_a, shape_b) match {
        ([], _) => shape_b,
        (_, []) => shape_a,
        ([...a_rest, a_last], [...b_rest, b_last]) 
            if a_last == b_last or a_last == 1 or b_last == 1 => broadcast_shape(a_rest, b_rest) ++ [math.max(a_last, b_last)],
        _ => meta.compilation.err("Shapes are not broadcastable")
    }
}

impl Add<Tensor<T, .dims = shape_b>> for Tensor<T, .dims = shape_a>
where T, shape_a: meta.List<Integer>, shape_b: meta.List<Integer>, requires T:- Add<T, assoc Output = T>
{
    comptime {
        -- 如果把broadcastable检查放在impl的子句约束里，根据impl的习惯，如果不满足约束，那么就找不到这个impl,
        -- 用户可能会对为什么不能add两个张量感到困惑（此时他还未意识到张量形状不符合约束），
        -- 因此我们把该约束延迟到instantiation时再检查
        assumes broadcastable(shape_a, shape_b);
    }
    
    assoc Output: Type = Tensor<T, .dims = broadcast_shape(shape_a, shape_b)>;
    fn add(*self, other: Tensor<T, .dims = shape_b>) -> Tensor<T, .dims = shape_a> {
        const broadcasted_shape = broadcast_shape(shape_a, shape_b);
        
        inline if broadcasted_shape.is_empty() {
            return self[0] + other[0],
        }

        var result: Output = undefined;

        -- 在 comptime 计算右对齐的虚拟填充长度
        const pad_a = target_shape.len() - shape_a.len();
        const pad_b = target_shape.len() - shape_b.len();

        -- 获取当前最外层维度的实际大小（如果是虚拟填充，视作大小为 1）
        const dim_a = inline if pad_a > 0 { 1 } else { shape_a[0] };
        const dim_b = inline if pad_b > 0 { 1 } else { shape_b[0] };
        const out_dim = target_shape[0];

        for i in 0..out_dim {
            -- 利用 [] 进行拓扑投影（降维切片）
            -- 广播规则：如果是虚拟 Padding 则不降维；如果维度为 1 则强行读 0 索引
            let slice_a = inline if pad_a > 0 { self } 
                          else { self[inline if dim_a == 1 { 0 } else { i }] };
                          
            let slice_b = inline if pad_b > 0 { other } 
                          else { other[inline if dim_b == 1 { 0 } else { i }] };
            -- 编译期递归：继续静态分发给 (N-1) Rank 的 Add implementation
            result[i] = slice_a + slice_b;
        }

        result
    }
}
