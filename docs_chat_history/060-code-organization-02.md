## 二、路径形式已经找到，不重新设计语法

按你的指引核对了 AST 的路径节点，并与 grammar/syntax 对照。已有六类复合形式：

~~~text

projection_multi_path -> path . { path* }

对应的使用片段如下，分别示意独立的导入，不要求把它们全部写在同一作用域中：

~~~flurry

use @codec.Packet;
use codec.Packet as WirePacket;
~~~

分组 use 最后一个 token 是 `}`，按现行风格不再补分号。pub/private 的修饰沿用你刚确认的规则，不增加 Rust 风格的限定可见性语法。

## 三、七项预填审阅

### N1. `.path` 的“上一层”沿静态容器，还是只沿模块树？

普通运行时块、函数体、struct 内部和文件模块，并不是同一种包含关系。例如在无子句的 Outer.Inner 结构定义内，父静态容器是 Outer；所在文件模块可能仍是 codec。

- **A. 沿已有的静态作用域包含关系。** 在运行时块中写 use，先找到其所属静态容器；前导点从该容器向父静态容器移动。mod 与满足已确认条件的 struct／enum／union 不因名字查找而被分成两套体系。
- **B. 只沿模块树。** struct／enum／union 和函数、普通块都不计层级；前导点总是从所属模块向父模块移动。文件导航更直接，但与其他静态容器的父级查找要分别说明。

**预填答复：A。** 普通路径的首名按当前合法词法环境逐层查找；显式前导点定位父静态容器，`@` 定位当前 package 根。显式定位后，从指定容器选成员，不在未找到时继续偷偷向外搜索；投影后续各段也只在已经选中的容器中查找。越过 package 根时报静态错误，umbrella 不是更上一级语言作用域。

因此，在函数里增加一层普通 do 块，不应改变同一条相对 use 指向哪个静态容器。`@` 是 use 路径里的根定位，不与文件级构造宏导入 `@use` 混为一种导入机制。

### N2. 同一层的直接声明、显式导入和通配导入怎样竞争？

这里仅处理同一个实际查找层级；内部作用域遮蔽外部作用域，不能被“外部是显式导入”翻转。

- **A. 直接声明和显式导入组成确定命名项，优先于本层通配导入。** 两个确定命名项若指向不同声明，报重名；没有确定项时再汇集通配候选。声明顺序不决定静态导入结果。
- **B. 本层所有来源同等竞争。** 直接声明、显式导入、通配导入只要带来不同同名来源就歧义；规则更少，但无法通过一个显式 use 消除通配冲突。
- **C. 本层按源码顺序遮蔽，后写者胜出。** 所有来源可统一为顺序绑定，但移动 use 或调整文件收集顺序容易改变静态结果，还要额外规定自动模块的排列。

**预填答复：A。** 分层查找，每层先确定命名项，再通配项；本层已选中的名字，不因类型不合或不是所需种类就退回外层。多个通配路径到达同一原始声明时合并身份，到达不同声明时保留歧义；何时报错见 N6。

| 同一层中的情况 | 预填结果 |
|---|---|
| 本地 Packet，加一个通配引入的其他 Packet | 本地声明胜出 |
| 显式导入 Packet，加一个通配引入的其他 Packet | 显式导入胜出 |
| 本地 Packet，加一个显式导入的其他 Packet | 重名错误，需要改名或 as |
| 两个通配引入不同 Packet | 歧义，不能先到先得 |
| 两个通配经不同出口引入同一个 Packet | 一个声明身份，保留各自访问路径 |
| 内层通配引入 Packet，外层显式导入另一个 Packet | 内层胜出 |

builtin.prelude 的自动导入，预填为包根的一份普通通配来源，不另设“永远赢”或“永远输”的内建优先级。std.prelude 的显式通配按同一规则处理；若它再次带来同一 builtin 声明，按身份去重，不因导入了两次而歧义。

统一命名空间也需要在失败时保持统一。例如以下是刻意写出的拒绝案例：

~~~flurry
fn example() {
    while : retry true {
        let retry = 1;
        break retry;
    }
}
~~~

按预填，break 先找到内层 retry，随后发现它不是可用的循环标签并报错；不会因为语法位置需要 label 就跳过这个局部绑定、改用外层同名标签。类型位置、属性表达式也不能借用途重新搜索一个被遮蔽的同名来源。

同一顺序块内重复 let 的情形，预填为新绑定从自己的声明完成后遮蔽旧绑定，初始化表达式仍在引入新绑定之前解析。静态定义不由这种顺序规则取得同名重载能力；旧绑定的资源责任沿用资源管理章，不能因名字被遮蔽而消失。

### N3. `pub use` 能否把来源声明本身的非公开性提升为公开？

这是与你要求避免的重导出 bug 最直接的一项。下面两条导入都能在当前包内找到来源，但来源声明的许可不同：

~~~flurry
private mod backend {
    pub struct Packet {}
    struct Scratch {}
}

pub use backend.Packet;
pub use backend.Scratch;
~~~

- **A. 再导出不能扩大原始声明自身许可的访问范围，但可以绕开不公开的组织路径。** Packet 本身 pub，可从隐藏 backend 中导出；Scratch 本身仅包内可见，不能被公开。声明作者与接口组织者的权限分工清楚。
- **B. 只要当前作用域能访问来源，就能通过 pub use 新建公开出口。** 两条都成立。可见性约束原有路径，不限制其他合法持有者再次公开；私有定义的封装意义也随之改变。
- **C. 声明所属 package 可以提升，外部 package 不可以。** 两条在本包均成立；包内其他模块也可以把作者未标 pub 的定义公开，需接受这一包级信任边界。

**预填答复：A。** 第一条成功，第二条静态拒绝。backend 的 private 限制从外部经过 backend 的路线；它不把内部显式 pub 的 Packet 永久降为 private。使用者可以通过当前包的公开 Packet 入口访问它，不需要同时取得 backend 的访问资格。

同样，已有 pub 声明先经普通 use 取得一个内部别名，再显式 pub use 这个别名，可以建立公开入口；但原始声明非 pub 时，增加任意多层别名都不能洗掉限制。这里每一段来源路径都要在**书写这条 use 的作用域**中可访问，不能从不可访问的中间模块直接“穿透取原始声明”。

普通 use 的新名字按你给出的默认规则在包内可见；private use 限制这个名字在所属模块及子模块中可见。实际访问还受来源声明的许可限制。普通 use 不因引入了一个 pub 来源，就自动成为面向其他包的 pub 出口；pub use 才明确要求建立该出口。

### N4. 自动发现的文件／目录模块，在哪里声明自身的可见性？

这是取消逐文件 mod 声明后留下的实际缺口。考虑：

~~~text
src/
├── lib.fl
└── codec/
    ├── mod.fl
    └── text.fl
~~~

codec 内部某个 Packet 可以经包根显式导出；但如果希望使用者直接走 package.codec.text，就还需要声明 codec 与 text 两个模块入口可公开。

- **A. 自动模块同样默认包内可见，由自己的文件／mod.fl 中的 configuration 指定模块属性。** 与三档默认可见性一致，也沿用已有 configuration 附着所属定义的模型；只为调整目录模块属性时才需要添加 mod.fl。
- **B. 自动模块默认包内可见，允许在父模块用 pub use 提升它的入口。** 不需要文件级 configuration；但必须规定这类模块能被提升的例外，以及原名再导出时不被误判为重复定义。
- **C. 自动文件／目录模块默认 pub，内部声明仍默认包内可见。** 无需额外模块标记；代价是自动模块与显式 mod 的默认可见性不同，文件布局直接成为可观察的公开路径。

**预填答复：A。** 文件自己的 configuration 修饰该文件模块，目录的 mod.fl 修饰目录模块；缺少 configuration 时仍使用包内默认值。没有 mod.fl 的目录照常成立，需要自定义该目录的可见性时再添加入口文件。

这里先确定承载位置，不假造一个已经存在的 attrs 函数、属性键或枚举类型名。若你已有可见性对应的 configuration 写法，可以直接补在此处；否则下一轮再给具体表面形式。当前 grammar 的 module_def／filescope 也需要在此项确认后接入所属模块的 configuration，不能把 struct 已支持的配置位置直接当作文件模块已定稿的事实。

### N5. `pub use source.*` 遇到 source 的包内／private 成员，应过滤还是拒绝整条导入？

普通 use 与公开聚合的目标不同。普通通配需要能在包内导入可访问的包内成员；公开聚合则不能因 source 有一个内部辅助项就不稳定。

- **A. 普通通配汇集当前位置可访问的成员；公开通配只汇集 source 的 pub 成员入口。** 不适合公开的成员被过滤；显式点名再导出不合法成员仍报错。内部增加辅助定义不破坏公开聚合。
- **B. 两种通配先汇集当前位置可访问的全部成员，pub use 再逐一要求均可公开。** 任何内部成员使整条公开通配失败；需要频繁改为枚举导入，但不发生静默过滤。

**预填答复：A。** source 的成员包括它的直接声明和合法导入入口；不包括仅因父级查找而在 source 内可用的祖先名字。公开通配只导出其中公开的入口，并按 N3 检查它们的来源许可。

因此，“source 自己用过某个短名”不能证明这个短名是 source 的 pub API。尤其不能把 source 的普通 prelude 导入、普通 use 别名，自动抬升成下游的公共接口。

若 source 同名的本地非公开声明遮蔽了一个公开通配候选，先按 N2 选名字，再按本条判断是否进入公开集合。不能为了凑出可导出的结果，跳过本地声明，把本已被遮蔽的候选重新翻出来。

显式再导出与通配过滤不矛盾：N3 允许接口作者明确点名导出某个可访问的 pub 来源；N5 限制通配默认收集哪些入口。两者都保持来源身份。

### N6. 通配歧义是在出现时立即报错，还是到使用时才报错？

- **A. 内部通配歧义到实际使用该名字时报告；公开出口的歧义必须由提供它的包报告。** 内部未使用的冲突不会阻止无关代码，但一个已声明要公开的名称不能把歧义留给下游消费者。
- **B. 任何通配汇集出现不同同名来源都立即报错。** 诊断最早，代价是未使用冲突也影响包的可编译性，并且显式遮蔽应在最终报错前先计算完毕。
- **C. 全部推迟到实际使用，包括公开出口。** 可以保留从未用到的歧义 API，但提供包自己通过检查不足以保证使用者能唯一解析它声明的出口。

**预填答复：A。** 显式导入路径找不到目标、访问越权、两个确定命名项重名，仍在导入／声明检查时报错；“延迟”仅针对尚未被使用的内部通配候选冲突。

同一声明经菱形路径到达并不歧义；两个恰好结构相同的类型、值相同的常量，仍是两个声明，不能用结构等价或值相等冒充身份去重。公开接口检查以 N2 的最终优先级和 N5 的公开集合为准。

### N7. 模块之间的循环再导出，是否允许由真实声明提供名称来源？

这里讨论同一合法编译世界内的模块导入关系，不顺带允许 package 依赖环或宏准备依赖环。

~~~flurry
mod source {
    pub struct Packet {}
}

pub mod left {
    pub use @source.Packet;
    pub use @right.*;
}

pub mod right {
    pub use @left.*;
}
~~~

- **A. 允许；根据真实声明求出导入与出口的稳定结果。** left.Packet 和 right.Packet 指向同一个 source.Packet；环不会复制声明，也不会凭空制造声明。
- **B. 导入／再导出关系必须无环。** 实现与解释更直接，但上面没有求值递归的组织方式也必须拆开。

**预填答复：A。** 去掉 source.Packet 的真实来源后，单独两个互相通配的空模块不会凭空出现 Packet；若再写一条显式要求取得 Packet 的导入，则最终报告找不到来源。空的通配环自身可以稳定为空，不需要伪造一个“循环声明”。

需要分别处理四种结果：唯一来源、不同来源歧义、没有来源、来源存在但不可访问。不能在遇到递归查询时先返回“没有”，再把这个暂时结果缓存为最终结论。

## 四、再导出实现检查与验收

### 局部读码发现

你明确指出 AST 可以确认 path 形式，我据此读取了路径节点；又针对“避免重导出 bug”做了有限的只读检查。以下是当前工作区代码的观察，不用它们决定 Flurry 语义，也没有宣称完成端到端编译验证：

1. ItemScope 把 imports 与 reexports 分开保存；构建过程也确实将 pub use 放进 reexports。但当前 Resolver 的 lookup_in_scope 只遍历 imports，没有读取 reexports。这个查找入口会漏掉仅由再导出引入的名字。
2. 该入口追踪导入来源时只查来源的直接声明，没有继续取得来源模块经导入／再导出建立的成员。这不足以覆盖两跳及更长的导入链。
3. 同一入口在找到第一个导入候选后立即返回，尚不能表达“不同来源同名”与“相同来源多路径”的区别。
4. Visibility 枚举已经有 Public／Package／Private 三项，但上述查找入口没有依据访问者检查它们。枚举存在本身不能证明可见性检查已经完成；导入结构另用布尔 is_reexport，也不足以独立保存三档导入入口可见性。

读码定位：`compiler/ast/src/lib.rs` 的路径节点、`compiler/resolve/src/item_scope.rs` 的导入集合、`compiler/resolve/src/module_builder.rs` 的导入登记、`compiler/resolve/src/resolver.rs` 的查找入口、`compiler/resolve/src/import.rs` 与 `binding.rs` 的导入／可见性表示。本轮不改这些文件；正式文档的实现引导只写 IR 契约与算法，不引用源码位置。

### 建议的实现骨架，随 N1–N7 一起审阅

解析结果至少保留三类信息：原始声明身份、当前名称绑定的作用域及可见性、形成这个结果的有效来源路径。别名不是新的声明身份；声明相同也不意味着所有来源路径具有相同的访问权限。

1. 登记静态直接声明、导入指令与它们的可见性。顺序局部绑定仍按自己的作用域推进，不能为了处理静态 use 把后面的 let 提前可见。
2. 解析每个 use 的定位和路径。确定命名项的名字预先占住本层位置；目标尚未求出时，状态是待解，不能暂时借通配候选填上。

## 三、七项预填审阅

### N1. `.path` 的“上一层”沿静态容器，还是只沿模块树？

普通运行时块、函数体、struct 内部和文件模块，并不是同一种包含关系。例如在无子句的 Outer.Inner 结构定义内，父静态容器是 Outer；所在文件模块可能仍是 codec。

- **A. 沿已有的静态作用域包含关系。** 在运行时块中写 use，先找到其所属静态容器；前导点从该容器向父静态容器移动。mod 与满足已确认条件的 struct／enum／union 不因名字查找而被分成两套体系。
- **B. 只沿模块树。** struct／enum／union 和函数、普通块都不计层级；前导点总是从所属模块向父模块移动。文件导航更直接，但与其他静态容器的父级查找要分别说明。

**预填答复：A。** 普通路径的首名按当前合法词法环境逐层查找；显式前导点定位父静态容器，`@` 定位当前 package 根。显式定位后，从指定容器选成员，不在未找到时继续偷偷向外搜索；投影后续各段也只在已经选中的容器中查找。越过 package 根时报静态错误，umbrella 不是更上一级语言作用域。

因此，在函数里增加一层普通 do 块，不应改变同一条相对 use 指向哪个静态容器。`@` 是 use 路径里的根定位，不与文件级构造宏导入 `@use` 混为一种导入机制。

### N2. 同一层的直接声明、显式导入和通配导入怎样竞争？

这里仅处理同一个实际查找层级；内部作用域遮蔽外部作用域，不能被“外部是显式导入”翻转。

- **A. 直接声明和显式导入组成确定命名项，优先于本层通配导入。** 两个确定命名项若指向不同声明，报重名；没有确定项时再汇集通配候选。声明顺序不决定静态导入结果。
- **B. 本层所有来源同等竞争。** 直接声明、显式导入、通配导入只要带来不同同名来源就歧义；规则更少，但无法通过一个显式 use 消除通配冲突。
- **C. 本层按源码顺序遮蔽，后写者胜出。** 所有来源可统一为顺序绑定，但移动 use 或调整文件收集顺序容易改变静态结果，还要额外规定自动模块的排列。

**预填答复：A。** 分层查找，每层先确定命名项，再通配项；本层已选中的名字，不因类型不合或不是所需种类就退回外层。多个通配路径到达同一原始声明时合并身份，到达不同声明时保留歧义；何时报错见 N6。

| 同一层中的情况 | 预填结果 |
|---|---|
| 本地 Packet，加一个通配引入的其他 Packet | 本地声明胜出 |
| 显式导入 Packet，加一个通配引入的其他 Packet | 显式导入胜出 |
| 本地 Packet，加一个显式导入的其他 Packet | 重名错误，需要改名或 as |
| 两个通配引入不同 Packet | 歧义，不能先到先得 |
| 两个通配经不同出口引入同一个 Packet | 一个声明身份，保留各自访问路径 |
| 内层通配引入 Packet，外层显式导入另一个 Packet | 内层胜出 |

builtin.prelude 的自动导入，预填为包根的一份普通通配来源，不另设“永远赢”或“永远输”的内建优先级。std.prelude 的显式通配按同一规则处理；若它再次带来同一 builtin 声明，按身份去重，不因导入了两次而歧义。

统一命名空间也需要在失败时保持统一。例如以下是刻意写出的拒绝案例：

~~~flurry
fn example() {
    while : retry true {
        let retry = 1;
        break retry;
    }
}
~~~

按预填，break 先找到内层 retry，随后发现它不是可用的循环标签并报错；不会因为语法位置需要 label 就跳过这个局部绑定、改用外层同名标签。类型位置、属性表达式也不能借用途重新搜索一个被遮蔽的同名来源。

同一顺序块内重复 let 的情形，预填为新绑定从自己的声明完成后遮蔽旧绑定，初始化表达式仍在引入新绑定之前解析。静态定义不由这种顺序规则取得同名重载能力；旧绑定的资源责任沿用资源管理章，不能因名字被遮蔽而消失。

### N3. `pub use` 能否把来源声明本身的非公开性提升为公开？

这是与你要求避免的重导出 bug 最直接的一项。下面两条导入都能在当前包内找到来源，但来源声明的许可不同：

~~~flurry
private mod backend {
    pub struct Packet {}
    struct Scratch {}
}

pub use backend.Packet;
pub use backend.Scratch;
~~~

- **A. 再导出不能扩大原始声明自身许可的访问范围，但可以绕开不公开的组织路径。** Packet 本身 pub，可从隐藏 backend 中导出；Scratch 本身仅包内可见，不能被公开。声明作者与接口组织者的权限分工清楚。
- **B. 只要当前作用域能访问来源，就能通过 pub use 新建公开出口。** 两条都成立。可见性约束原有路径，不限制其他合法持有者再次公开；私有定义的封装意义也随之改变。
- **C. 声明所属 package 可以提升，外部 package 不可以。** 两条在本包均成立；包内其他模块也可以把作者未标 pub 的定义公开，需接受这一包级信任边界。

**预填答复：A。** 第一条成功，第二条静态拒绝。backend 的 private 限制从外部经过 backend 的路线；它不把内部显式 pub 的 Packet 永久降为 private。使用者可以通过当前包的公开 Packet 入口访问它，不需要同时取得 backend 的访问资格。

同样，已有 pub 声明先经普通 use 取得一个内部别名，再显式 pub use 这个别名，可以建立公开入口；但原始声明非 pub 时，增加任意多层别名都不能洗掉限制。这里每一段来源路径都要在**书写这条 use 的作用域**中可访问，不能从不可访问的中间模块直接“穿透取原始声明”。

普通 use 的新名字按你给出的默认规则在包内可见；private use 限制这个名字在所属模块及子模块中可见。实际访问还受来源声明的许可限制。普通 use 不因引入了一个 pub 来源，就自动成为面向其他包的 pub 出口；pub use 才明确要求建立该出口。

### N4. 自动发现的文件／目录模块，在哪里声明自身的可见性？

这是取消逐文件 mod 声明后留下的实际缺口。考虑：

~~~text
src/
├── lib.fl
└── codec/
    ├── mod.fl
    └── text.fl
~~~

codec 内部某个 Packet 可以经包根显式导出；但如果希望使用者直接走 package.codec.text，就还需要声明 codec 与 text 两个模块入口可公开。

- **A. 自动模块同样默认包内可见，由自己的文件／mod.fl 中的 configuration 指定模块属性。** 与三档默认可见性一致，也沿用已有 configuration 附着所属定义的模型；只为调整目录模块属性时才需要添加 mod.fl。
- **B. 自动模块默认包内可见，允许在父模块用 pub use 提升它的入口。** 不需要文件级 configuration；但必须规定这类模块能被提升的例外，以及原名再导出时不被误判为重复定义。
- **C. 自动文件／目录模块默认 pub，内部声明仍默认包内可见。** 无需额外模块标记；代价是自动模块与显式 mod 的默认可见性不同，文件布局直接成为可观察的公开路径。

**预填答复：A。** 文件自己的 configuration 修饰该文件模块，目录的 mod.fl 修饰目录模块；缺少 configuration 时仍使用包内默认值。没有 mod.fl 的目录照常成立，需要自定义该目录的可见性时再添加入口文件。

这里先确定承载位置，不假造一个已经存在的 attrs 函数、属性键或枚举类型名。若你已有可见性对应的 configuration 写法，可以直接补在此处；否则下一轮再给具体表面形式。当前 grammar 的 module_def／filescope 也需要在此项确认后接入所属模块的 configuration，不能把 struct 已支持的配置位置直接当作文件模块已定稿的事实。

### N5. `pub use source.*` 遇到 source 的包内／private 成员，应过滤还是拒绝整条导入？

普通 use 与公开聚合的目标不同。普通通配需要能在包内导入可访问的包内成员；公开聚合则不能因 source 有一个内部辅助项就不稳定。

- **A. 普通通配汇集当前位置可访问的成员；公开通配只汇集 source 的 pub 成员入口。** 不适合公开的成员被过滤；显式点名再导出不合法成员仍报错。内部增加辅助定义不破坏公开聚合。
- **B. 两种通配先汇集当前位置可访问的全部成员，pub use 再逐一要求均可公开。** 任何内部成员使整条公开通配失败；需要频繁改为枚举导入，但不发生静默过滤。

**预填答复：A。** source 的成员包括它的直接声明和合法导入入口；不包括仅因父级查找而在 source 内可用的祖先名字。公开通配只导出其中公开的入口，并按 N3 检查它们的来源许可。

因此，“source 自己用过某个短名”不能证明这个短名是 source 的 pub API。尤其不能把 source 的普通 prelude 导入、普通 use 别名，自动抬升成下游的公共接口。

若 source 同名的本地非公开声明遮蔽了一个公开通配候选，先按 N2 选名字，再按本条判断是否进入公开集合。不能为了凑出可导出的结果，跳过本地声明，把本已被遮蔽的候选重新翻出来。

显式再导出与通配过滤不矛盾：N3 允许接口作者明确点名导出某个可访问的 pub 来源；N5 限制通配默认收集哪些入口。两者都保持来源身份。

### N6. 通配歧义是在出现时立即报错，还是到使用时才报错？

- **A. 内部通配歧义到实际使用该名字时报告；公开出口的歧义必须由提供它的包报告。** 内部未使用的冲突不会阻止无关代码，但一个已声明要公开的名称不能把歧义留给下游消费者。
- **B. 任何通配汇集出现不同同名来源都立即报错。** 诊断最早，代价是未使用冲突也影响包的可编译性，并且显式遮蔽应在最终报错前先计算完毕。
- **C. 全部推迟到实际使用，包括公开出口。** 可以保留从未用到的歧义 API，但提供包自己通过检查不足以保证使用者能唯一解析它声明的出口。

**预填答复：A。** 显式导入路径找不到目标、访问越权、两个确定命名项重名，仍在导入／声明检查时报错；“延迟”仅针对尚未被使用的内部通配候选冲突。

同一声明经菱形路径到达并不歧义；两个恰好结构相同的类型、值相同的常量，仍是两个声明，不能用结构等价或值相等冒充身份去重。公开接口检查以 N2 的最终优先级和 N5 的公开集合为准。

### N7. 模块之间的循环再导出，是否允许由真实声明提供名称来源？

这里讨论同一合法编译世界内的模块导入关系，不顺带允许 package 依赖环或宏准备依赖环。

~~~flurry
mod source {
    pub struct Packet {}
}

pub mod left {
    pub use @source.Packet;
    pub use @right.*;
}

pub mod right {
    pub use @left.*;
}
~~~

- **A. 允许；根据真实声明求出导入与出口的稳定结果。** left.Packet 和 right.Packet 指向同一个 source.Packet；环不会复制声明，也不会凭空制造声明。
- **B. 导入／再导出关系必须无环。** 实现与解释更直接，但上面没有求值递归的组织方式也必须拆开。

**预填答复：A。** 去掉 source.Packet 的真实来源后，单独两个互相通配的空模块不会凭空出现 Packet；若再写一条显式要求取得 Packet 的导入，则最终报告找不到来源。空的通配环自身可以稳定为空，不需要伪造一个“循环声明”。

需要分别处理四种结果：唯一来源、不同来源歧义、没有来源、来源存在但不可访问。不能在遇到递归查询时先返回“没有”，再把这个暂时结果缓存为最终结论。

## 四、再导出实现检查与验收

### 局部读码发现

你明确指出 AST 可以确认 path 形式，我据此读取了路径节点；又针对“避免重导出 bug”做了有限的只读检查。以下是当前工作区代码的观察，不用它们决定 Flurry 语义，也没有宣称完成端到端编译验证：

1. ItemScope 把 imports 与 reexports 分开保存；构建过程也确实将 pub use 放进 reexports。但当前 Resolver 的 lookup_in_scope 只遍历 imports，没有读取 reexports。这个查找入口会漏掉仅由再导出引入的名字。
2. 该入口追踪导入来源时只查来源的直接声明，没有继续取得来源模块经导入／再导出建立的成员。这不足以覆盖两跳及更长的导入链。
3. 同一入口在找到第一个导入候选后立即返回，尚不能表达“不同来源同名”与“相同来源多路径”的区别。
4. Visibility 枚举已经有 Public／Package／Private 三项，但上述查找入口没有依据访问者检查它们。枚举存在本身不能证明可见性检查已经完成；导入结构另用布尔 is_reexport，也不足以独立保存三档导入入口可见性。

读码定位：`compiler/ast/src/lib.rs` 的路径节点、`compiler/resolve/src/item_scope.rs` 的导入集合、`compiler/resolve/src/module_builder.rs` 的导入登记、`compiler/resolve/src/resolver.rs` 的查找入口、`compiler/resolve/src/import.rs` 与 `binding.rs` 的导入／可见性表示。本轮不改这些文件；正式文档的实现引导只写 IR 契约与算法，不引用源码位置。

### 建议的实现骨架，随 N1–N7 一起审阅

解析结果至少保留三类信息：原始声明身份、当前名称绑定的作用域及可见性、形成这个结果的有效来源路径。别名不是新的声明身份；声明相同也不意味着所有来源路径具有相同的访问权限。

1. 登记静态直接声明、导入指令与它们的可见性。顺序局部绑定仍按自己的作用域推进，不能为了处理静态 use 把后面的 let 提前可见。
2. 解析每个 use 的定位和路径。确定命名项的名字预先占住本层位置；目标尚未求出时，状态是待解，不能暂时借通配候选填上。
3. 将普通成员查找与公共出口查询区分，按 N2、N3、N5 的同一组规则传播候选。对循环部分保留有限的声明身份与导入边，不枚举无限长的重复路径。
4. 传播到稳定后，再判定缺失、歧义或访问失败。不能把第一轮暂时唯一的候选提交为最终绑定。
5. 只对最终选定的名字检查其用于当前位置是否合适，例如 break 要求可用的循环标签。种类不合不得重启另一套名称搜索。
6. 增量依赖包含被查询的名字集合、公开出口集合和目录成员集合；来源新添同名声明也要让此前“唯一”的结果失效。

特别注意：存在显式项优先和过滤时，不能不加条件地把所有可达声明做一个并集就宣布完成。先保留显式名字占位和遮蔽约束，再在允许的边上传播；若路径前缀最终歧义，依赖该前缀的候选不能继续被当作有效导入。

下面是接受候选 A 后应覆盖的验收情景，不是本轮已经运行的测试：

| 情景 | 预期 |
|---|---|
| pub use 后在当前模块使用引入名 | 与普通导入一样可查到，不因进入另一张表而丢失 |
| 一次别名、两次再导出后取得原始类型 | 保持同一声明与 package 归属 |
| 隐藏模块中的 pub 声明经公开出口提供 | 外部走公开出口成功，走隐藏模块路径失败 |
| 默认包内声明经多层别名尝试 pub use | 不能扩大原始声明许可 |
| 同包普通通配导入包内成员 | 在合法访问范围内可用，不能只收 pub |
| 公开通配遇到内部辅助成员 | 过滤，不泄露，也不因辅助成员存在而全条失败 |
| source 只有父级可查到的名称 | 不把祖先名称伪装为 source 自己的成员 |
| 相同声明经两条公开路径到达 | 不歧义，合法路径可独立证明可达 |
| 不同声明经两个同级通配到达 | 保留歧义，交换 use 顺序结果不变 |
| 显式项遮蔽通配项 | 不受导入解析先后、缓存命中顺序影响 |
| 有来源的循环与空通配循环 | 前者保留真实来源；后者稳定为空 |
| 来源新增一个冲突导出 | 增量结果与全量解析一致 |
