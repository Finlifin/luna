## 二、enum 章节的全貌

我的建议是先区分三个问题：一个值属于哪个变体；变体声明向用户提供什么名称与载荷接口；变体如何通过存储表示区分。三个问题互有关联，但“有变体身份”本身没有规定必须额外存放一个整数标签。

现有 docs/data-structures/index.md 已用“若干变体之一”介绍普通 enum，并展示无载荷、带载荷和层级分组。现行 grammar 还列出按表达式、按模式声明变体的形式。这些材料足以建立章节范围，尚不足以把所有形式解释为同一种标签方案。

建议 enum 正式篇仍按七段组织；以下只是内容规划，不是正式文本：

| 段落 | 要解决的读者问题 |
|---|---|
| Intro | 一个 enum 值表示若干情况中的哪一种，以及该情况携带什么数据；特殊表示形式另行建立边界 |
| 语法 | 无载荷、位置载荷、命名字段、层级分组、表达式变体、模式变体这六种形式 |
| 正式定义 | 声明引入的类型与名称、构造和载荷访问、分组含义、变体集合、显式值与模式的职责 |
| 常见示例 | 简单状态、带数据的选择、层级命名；定制编码示例等其规则确认后再放入 |
| 跨语言差异 | 只比较已确认的用户行为；编写时查阅对照语言官方资料，不从类比反推 Flurry |
| 运行时实现设计引导 | 在已确定表示契约下构造、判别、提取载荷；合法性前提和失败路径明确列出 |
| 编译器实现引导 | 收集变体与路径、检查声明约束、建立表示与判别契约，再对接既有模式匹配分析 |

其中，精确位布局、跨元素编码、DST、从任意比特构造值的安全契约，留给程序生成/BitVec 及相邻布局章节。本轮只问 enum 自身必须拥有的接口边界，不展开那些算法。

之后的顺序保持为 union，再到参数化数据类型与反射接口；不重开已经收束的类型匹配系列。

## 三、已有语法的局部索引

以下摘取 docs/grammar/syntax 已有产生式；expr、pattern、struct_field、enum_variant 沿用全局定义。这里只罗列各形式，不重新规定 PEG 备选顺序。

```text

pattern_enum_variant -> id: pattern
```

### 1. 现有圆括号里的载荷名字，究竟是什么？

具体不一致：docs/data-structures/index.md 写了 `circle(radius: f64)`，并用 `Shape.rectangle(10.0, 5.5)` 构造；docs/grammar/syntax 则将圆括号形式定义为 `id (expr*)`，单独为命名字段提供 `id { struct_field* }`。圆括号中写冒号并不自动说明这里声明了可投影的字段。

- A. 圆括号只有位置载荷；现有示例改成 `circle(f64)`，载荷名字不属于该声明接口。保留位置构造，示例修正最小。
- B. 原示例的意图是命名字段，应改为大括号载荷；圆括号继续表示位置载荷。位置与命名接口清楚分开，原来的构造示例也要一起改。
- C. 圆括号可以声明带名字的载荷，并仍允许位置构造；需要补充这种名字的可见性与对应语法。保留现有示例，但会增加一套接口规则。

建议答复：B。若要公开 radius、width、height 这些字段名，就使用现有命名字段形式，并沿用刚确认的完整字段标签与声明顺序初始化规则。例如以下是待确认的修订示例：

```flurry
enum Shape {
    circle { radius: f64 },
    rectangle { width: f64, height: f64 },
    point,
}

let shape = Shape.rectangle { width: 10.0, height: 5.5 }
```

我的理由：不需要为圆括号中的冒号额外发明含义。此候选同时提议 struct 变体复用普通 struct 的命名与初始化顺序；尚未确认的字段默认值等细则不在这里顺带定案。

### 2. 层级分组引入新的类型，还是只组织同一 enum 的变体路径？

```flurry
enum Event {
    network.{
        connected,
        received(u32),
    },
    stopped,
}

let event = Event.network.received(3);
```

这沿用现有层级声明形式，但 event 的类型以及 Event.network 是否能用作类型仍待本题确认。

- A. 分组只组织名称；叶子是 Event 的变体，network 本身不是另一种值或独立类型。实现需要保留路径，但不增加嵌套载荷。
- B. 每个分组都定义一个独立 enum，外层通过携带该 enum 的变体包含它。类型与构造形成真实嵌套，不能把它描述成纯命名分组。
- C. 分组指称外层 enum 的一个受限类型，表示该组叶子的集合。需要规定它与外层的类型关系及转换，不能只靠路径语法推出。

建议答复：A。例中构造出的值属于 Event，分组用于组织叶子的完整路径。

我的理由：这与现有介绍“避免命名空间污染”的措辞最接近。选 A 也不自动承诺“用组名一次匹配整组”；是否提供这种简写可在后续匹配接口中单独说明。

### 3. 等号变体的表达式定义什么？

grammar 明确允许 `id = expr`，但现有材料没有给出足以覆盖普通 enum 的完整契约。用下面的形态区分候选，数值意义尚待确认：

```flurry
enum Status {
    ready = 1,
    busy = 2,
}
```

- A. expr 给出该变体的显式编码值，必须在编译时确定，并满足该 enum 的表示要求。名称与编码分开，不因此获得任意整数互转。
- B. expr 给出一个已有 enum 值，当前名字成为它的别名；不建立新的变体身份。例中的整数不能直接按编码解释。
- C. expr 的职责由 enum 所选的表示契约定义，普通 enum 并无统一的整数标签解释。需要在对应契约里确定值域与合法性。

建议答复：A，先把它理解为显式编码入口；这里不预填具体整数宽度、转换方法或标签读取 API。

我的理由：这为程序与外部编码对应提供直接用途，又避免把“显式编码”解释成完整的整数类型接口。如果它其实属于更通用的表示构造，应选 C，不必为了这个示例保留整数标签假设。

### 4. 显式编码与未写编码的变体可以怎样混合？

本题依赖第 3 题选 A；若选 B/C，只需写“不适用，归对应契约”，无需为错误前提补规则。

- A. 允许混合；首个隐式值为 0，其后隐式值是前一个变体编码加 1。分组如何参与顺序还需与第 2 题的决定一致，溢出应拒绝。
- B. 同一 enum 一旦显式指定编码，就要求所有叶子变体显式给出编码。编写多一些，但插入或移动声明不隐式改变其他显式接口。
- C. 允许混合，但隐式编码由表示契约选择，源码相邻关系不承诺数值递增。必须限制用户对未指定编码的依赖。

建议答复：B。全部未指定编码的普通 enum 仍可由实现选择表示；只有作者开始指定编码时才要求完整指定。

我的理由：这是我提出的保守接口，不是从现有材料得到的事实。它减少“插入一个变体改变后续编码”的隐含影响；若语言希望支持递增便利，A 也可行，但要把顺序与溢出写成明确规则。

### 5. 两个变体能否指定相同编码？

仍以第 3 题 A 为前提。具体场景是两个不同名字都指定同一编码，而无其他已声明的判别依据。

- A. 拒绝重复编码；不同变体必须可区分。检查直接，名称不会因编码相等自动变成别名。
- B. 允许，同编码声明是同一变体的别名。必须说明匹配与穷尽性按共同身份处理，而不是把它们计成两个独立情况。
- C. 允许且仍是不同变体，表示契约必须提供额外判别信息。不能再声称指定的编码独自确定变体。

建议答复：A。需要别名时另按明确的命名机制处理，不从编码碰撞推导别名语义。

我的理由：如果声明声称存在两个不同情况，却无法从值中分辨，构造后再匹配就没有明确答案。B、C 都能解决，但解决的是不同语言设计，不能混用。

### 6. 冒号变体的 pattern 负责表示，还是只负责识别？

docs/control-flow/pattern-matching/bitvec.md 的 Utf8CodePoint 使用 `one: 0b0(ascii_char: BitVec<7>)`，并配置 pattern_view_defined 等属性。这里暂不展开比特段、DST 或转换安全，只确认 enum 这一层的职责。

- A. pattern 定义变体的表示约束与载荷绑定，属于 enum 的表示定义；它不是任意可执行匹配代码的自动逆函数。可用的模式范围及构造规则归具体表示契约。
- B. pattern 只提供已有值的命名识别方式；这类声明未必引入可独立构造的新变体。文档需要将“识别入口”与普通变体构造区别说明。
- C. pattern 的职责完全由所选属性/表示契约决定；enum 通则只登记这种声明形式，不统一承诺 A 或 B。

建议答复：A 作为目前的理解；可构造的模式范围、重叠处理及反向构造算法都留在对应表示篇，不在这里猜出一套通用模式求逆机制。

我的理由：现有示例的固定比特与命名载荷很像直接描述表示，但仅有一个例子不能证明所有 pattern 都能如此解释。若 pattern_view_defined 本身会切换整个声明的意义，C 更准确。

### 7. 普通载荷变体与模式变体属于同一个可混合的 enum 模型吗？

grammar 的 enum_variant 列表容纳各种形式，却没有单凭列表证明所有组合在语义上都合法。

- A. 默认可以混合；语言或表示契约必须为两类变体建立统一、无冲突的判别与构造规则。表达力最大，需要较强的兼容性条件。
- B. 普通 enum 与按模式定义表示的 enum 分属不同表示模式；同一定义中不能任意混用这两类变体。语法可统一，语义按类别约束。
- C. 是否可混合由选定表示契约决定；enum 通则不提供一个独立的“混合自动布局”规则。

建议答复：C。普通变体仍有普通 enum 的契约；一旦采用定制表示，就检查所选契约是否支持所用形式。

我的理由：这样不会把 bitvec 示例中的配置未经确认推广为全部 enum 的布局机制。此候选没有发明新的配置键或用户可扩展协议；“表示契约”这里只指最终需要写清的表示规则。

### 8. 普通 enum 的变体集合何时固定？

本题只讨论某个已经确定的普通 enum 类型，不讨论类型工厂可以生成不同类型，也不重新讨论规范化与实例化。

- A. 由该类型定义固定；后续为它补充方法或 trait 实现不增加变体。用户可以按固定变体集合理解匹配。
- B. 可由定义外的声明扩充；需要明确谁能扩充、何时集合封闭，以及依赖方如何检查匹配覆盖。现有 extend 不自动视为已经支持该用途。

建议答复：A。先为普通 enum 确定封闭的变体集合。

我的理由：这让“处理了哪些情况”成为局部可检查的接口。选 A 并不同时决定漏分支必定报错、运行时失败或其他行为；那仍按既有 match 契约及其待定项处理，不在本题偷偷增加规则。

### 9. 普通 enum 的语义是否要求独立存放一个标签？

- A. 只要求能判别变体并取得相应载荷；具体是否存在独立标签、标签放在哪里，由表示契约决定。语言的通用变体接口不暴露固定对象布局。
- B. 所有普通 enum 都保证存在一个独立存储的标签，标签以外再存载荷。用户可依赖这一表示组成，具体类型与布局还需规定。
- C. 按类型类别提供不同保证，例如无载荷枚举与带载荷枚举分别定义；需要列出分类依据，不能依优化结果临时改变用户保证。

建议答复：A。文档先描述可观察的变体行为，再由选定表示补上布局承诺。

我的理由：有唯一变体身份，并不能证明内存里必须多放一个字段。反过来，选 A 也不意味着编译器获得任意破坏 ABI 的自由；明确指定的表示契约始终需要遵守。

### 10. 作者示例中 `.width 20` 限定的对象是什么？

此前 NodeIndex/SOA 的 Tag 示例使用了 `.width 20`，其叶子是无载荷变体。这个例子中，整个值的编码宽度与判别信息宽度可能一致，因此不能由它判断带载荷 enum 的规则。

- A. 限定变体判别编码的宽度，带载荷时载荷另行计入布局。enum 篇可以解释这个属性的对象，精确布局留后续。
- B. 限定整个 enum 值的表示宽度，包括载荷；不能满足宽度要求的定义非法。它是整体表示约束，不只是标签约束。
- C. 这项配置只对特定表示模式有定义；普通 enum 不承诺统一解释。其适用条件和含义一起留给表示篇。

建议答复：C，当前只保留该 Tag 示例的使用事实；不要靠一个无载荷示例推导所有 enum 的宽度通则。如果它明确就是标签宽度，请直接改为 A。

我的理由：这题只需要确定属性管哪一层，不需要现在展开位顺序、跨元素存储或 unsafe 转换。

### 3. 等号变体的表达式定义什么？

grammar 明确允许 `id = expr`，但现有材料没有给出足以覆盖普通 enum 的完整契约。用下面的形态区分候选，数值意义尚待确认：

```flurry
enum Status {
    ready = 1,
    busy = 2,
}
```

- A. expr 给出该变体的显式编码值，必须在编译时确定，并满足该 enum 的表示要求。名称与编码分开，不因此获得任意整数互转。
- B. expr 给出一个已有 enum 值，当前名字成为它的别名；不建立新的变体身份。例中的整数不能直接按编码解释。
- C. expr 的职责由 enum 所选的表示契约定义，普通 enum 并无统一的整数标签解释。需要在对应契约里确定值域与合法性。

仅允许特定类型。复杂场景有pattern variant,或者直接在那个复杂的类型上定义case view。

### 4. 显式编码与未写编码的变体可以怎样混合？

本题依赖第 3 题选 A；若选 B/C，只需写“不适用，归对应契约”，无需为错误前提补规则。

- A. 允许混合；首个隐式值为 0，其后隐式值是前一个变体编码加 1。分组如何参与顺序还需与第 2 题的决定一致，溢出应拒绝。
- B. 同一 enum 一旦显式指定编码，就要求所有叶子变体显式给出编码。编写多一些，但插入或移动声明不隐式改变其他显式接口。
- C. 允许混合，但隐式编码由表示契约选择，源码相邻关系不承诺数值递增。必须限制用户对未指定编码的依赖。

见上。

### 5. 两个变体能否指定相同编码？

仍以第 3 题 A 为前提。具体场景是两个不同名字都指定同一编码，而无其他已声明的判别依据。

- A. 拒绝重复编码；不同变体必须可区分。检查直接，名称不会因编码相等自动变成别名。
- B. 允许，同编码声明是同一变体的别名。必须说明匹配与穷尽性按共同身份处理，而不是把它们计成两个独立情况。
- C. 允许且仍是不同变体，表示契约必须提供额外判别信息。不能再声称指定的编码独自确定变体。

建议答复：A。需要别名时另按明确的命名机制处理，不从编码碰撞推导别名语义。

我的理由：如果声明声称存在两个不同情况，却无法从值中分辨，构造后再匹配就没有明确答案。B、C 都能解决，但解决的是不同语言设计，不能混用。

见上。

### 6. 冒号变体的 pattern 负责表示，还是只负责识别？

docs/control-flow/pattern-matching/bitvec.md 的 Utf8CodePoint 使用 `one: 0b0(ascii_char: BitVec<7>)`，并配置 pattern_view_defined 等属性。这里暂不展开比特段、DST 或转换安全，只确认 enum 这一层的职责。

- A. pattern 定义变体的表示约束与载荷绑定，属于 enum 的表示定义；它不是任意可执行匹配代码的自动逆函数。可用的模式范围及构造规则归具体表示契约。
- B. pattern 只提供已有值的命名识别方式；这类声明未必引入可独立构造的新变体。文档需要将“识别入口”与普通变体构造区别说明。
- C. pattern 的职责完全由所选属性/表示契约决定；enum 通则只登记这种声明形式，不统一承诺 A 或 B。

建议答复：A 作为目前的理解；可构造的模式范围、重叠处理及反向构造算法都留在对应表示篇，不在这里猜出一套通用模式求逆机制。

我的理由：现有示例的固定比特与命名载荷很像直接描述表示，但仅有一个例子不能证明所有 pattern 都能如此解释。若 pattern_view_defined 本身会切换整个声明的意义，C 更准确。

实际上，pattern view defined指的就是用pattern来定义enum variant,现在已经内化到语言基础中，不再需要attribute。discrete tag属性意思是，variant布局完全基于用户定义的pattern，variant的互斥性基于pattern的互斥性，这里应该需要用z3来对bitvec进行互斥检查。而dst和base_type两个属性则直接引出了flurry四大程序合成设计之一的匹配自动机，到那个主题再讲（所以这个例子怕是有点太超前了，可以想一个更合适的例子，比如用u32 base来编码riscv instruction）。

### 7. 普通载荷变体与模式变体属于同一个可混合的 enum 模型吗？

grammar 的 enum_variant 列表容纳各种形式，却没有单凭列表证明所有组合在语义上都合法。

- A. 默认可以混合；语言或表示契约必须为两类变体建立统一、无冲突的判别与构造规则。表达力最大，需要较强的兼容性条件。
- B. 普通 enum 与按模式定义表示的 enum 分属不同表示模式；同一定义中不能任意混用这两类变体。语法可统一，语义按类别约束。
- C. 是否可混合由选定表示契约决定；enum 通则不提供一个独立的“混合自动布局”规则。

建议答复：C。普通变体仍有普通 enum 的契约；一旦采用定制表示，就检查所选契约是否支持所用形式。

我的理由：这样不会把 bitvec 示例中的配置未经确认推广为全部 enum 的布局机制。此候选没有发明新的配置键或用户可扩展协议；“表示契约”这里只指最终需要写清的表示规则。

### 8. 普通 enum 的变体集合何时固定？

本题只讨论某个已经确定的普通 enum 类型，不讨论类型工厂可以生成不同类型，也不重新讨论规范化与实例化。

- A. 由该类型定义固定；后续为它补充方法或 trait 实现不增加变体。用户可以按固定变体集合理解匹配。
- B. 可由定义外的声明扩充；需要明确谁能扩充、何时集合封闭，以及依赖方如何检查匹配覆盖。现有 extend 不自动视为已经支持该用途。

建议答复：A。先为普通 enum 确定封闭的变体集合。

我的理由：这让“处理了哪些情况”成为局部可检查的接口。选 A 并不同时决定漏分支必定报错、运行时失败或其他行为；那仍按既有 match 契约及其待定项处理，不在本题偷偷增加规则。

### 9. 普通 enum 的语义是否要求独立存放一个标签？

- A. 只要求能判别变体并取得相应载荷；具体是否存在独立标签、标签放在哪里，由表示契约决定。语言的通用变体接口不暴露固定对象布局。
- B. 所有普通 enum 都保证存在一个独立存储的标签，标签以外再存载荷。用户可依赖这一表示组成，具体类型与布局还需规定。
- C. 按类型类别提供不同保证，例如无载荷枚举与带载荷枚举分别定义；需要列出分类依据，不能依优化结果临时改变用户保证。

没有指定pattern、expr时，基本上只能靠tag来区分，有两者时那就是靠它们的互斥检查。

### 10. 作者示例中 `.width 20` 限定的对象是什么？

此前 NodeIndex/SOA 的 Tag 示例使用了 `.width 20`，其叶子是无载荷变体。这个例子中，整个值的编码宽度与判别信息宽度可能一致，因此不能由它判断带载荷 enum 的规则。

- A. 限定变体判别编码的宽度，带载荷时载荷另行计入布局。enum 篇可以解释这个属性的对象，精确布局留后续。
- B. 限定整个 enum 值的表示宽度，包括载荷；不能满足宽度要求的定义非法。它是整体表示约束，不只是标签约束。
- C. 这项配置只对特定表示模式有定义；普通 enum 不承诺统一解释。其适用条件和含义一起留给表示篇。

B，因为我们常靠这个信息来阻止packed struct，如果设置了base type则以base type为准。
