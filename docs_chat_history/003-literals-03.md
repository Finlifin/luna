## 可行性评估与关键澄清

### 脱糖 B + 两种合法后缀目标（关键，已对齐）

规范形态（DRAFT 表述，待你点头后写入正式定义）：

```text
lit id   ~>   Type.id(lit)
```

其中 `Type` 为该字面量的 comptime 类型（如整数 → `Integer`，字符串 → `str`，短名或 `builtin.…` 全路径）。

`id` 解析到的函数必须满足二者之一：

| 形态 | 约束 | 直观角色 |
|------|------|----------|
| M1 | `comptime` 函数，恰有一个 `self` 参数 | 挂在 comptime 类型上的「方法」，调用仍写成 `Type.id(lit)` |
| M2 | 普通函数，恰有一个 `comptime` 参数（不是 `self`） | 不以方法挂在 comptime 类型上，但仍可作为后缀目标 |

**后果**：文档/traits 旧例 `(100u32).px()`（先后缀成 `u32` 再实例调用）与「单后缀 + 直接 B」不一致，应改写为对 `Integer` 的一次后缀（见问题 4 重述）。

### Parser「只看 token」的推论

词法跳过空白后，`23u32` 与 `23 u32` 若都得到 `[int("23"), id("u32")]`，则 **parser 无法区分**，后缀 apply 以 **token 流中「字面量 token 后紧跟 id token」** 触发，而非源码字符紧贴。

这与「后缀」口语略有张力，但是一致的 token 语法。须确认：是否**任意**这样的 id 都尝试按后缀解析（失败则报错），还是仅当查找成功才改写，否则回退为其它解析（问题 2）。

### 关于 `\0` 与 `"…"c`（答作者反问；类比，非 Flurry 承诺）

**转义 `\0` 本身（写入 char/str 内容为 U+0000）**：

| 语言 | 普通字符串/字符里的 `\0` |
|------|--------------------------|
| C/C++ | 有；表示 NUL 字节/字符 |
| Rust | 有（`'\0'` / `"...\0..."`） |
| Swift | 有 |
| Zig | 支持相关逃逸；字符串字面量类型常带哨兵 `0` |

**「按 C 行不行」——建议拆成两件独立规则（请你拍板，问题 3）：**

1. **转义表含 `\0`**：表示内容中的 NUL。与 C/Rust/Swift 一致；对 Flurry 无冲突，且已在转义候选中采纳。
2. **`"…"c`（C ABI 串）是否自动尾附 NUL、是否禁止内容中出现 NUL**：
   - **C 源字面量**：静态存储常隐式尾 `'\0'`；内容中间也可以有 `\0`，但 `strlen` 会提前停——属 C 语义坑。
   - **Rust `c"..."`**（类比）：**自动**尾附 NUL，且**禁止**内部 NUL（含 `\0`），得到 `&CStr`，避免静默截断。
   - **Zig**（类比）：许多字符串字面量带 `:0` 哨兵，与 C 互操作方便。

**建议（待确认，非 canon）**：转义保留 `\0`；`"…"c` 的 extension **自动追加**尾 NUL，并在内容已含 NUL 时 `emit_err`（偏 Rust `c"..."`，比静默 C 更适合系统语言文档读者）。若你要「纯 C 坑兼容」，可改为允许内部 NUL。
