## 完整回答、可行性评估、问题与候选项

我理解这个例子的教学重点是：**同一个张量加法定义，可以在形状尚未具体化时按契约检查，在形状确定后生成对应阶数的实现，而元素加法仍在运行时发生。** 标量、向量、矩阵由形状列表统一描述；PTC、comptime 计算和 runtime 计算分别承担其中不同的工作。

你修改的几个基础点，我也一并更正了理解：

- Flurry 不允许你所说的重名定义，函数名与字段名也不能靠重载区分。我撤回此前围绕同名函数候选构造的解析问题；这不取消 trait implementation 自身的匹配与 coherence 检查。
- `Splice.splice` 就是带 comptime 参数的普通 runtime 方法：编译时实例化，运行时调用该实例。因此不能把自定义 splice 一概写成“整个转换在编译时完成，运行时只剩常量”。
- PTC 命题有明确的可执行语义；`assumes` 在 normalization 提供检查所需的命题，在 instantiation 直接执行并验证。我不再把它解释成需要另造机制兑现的神秘证明对象，也不再追问是否可执行。
- 静态作用域是你给出的无子句定义规则下，供命名解析起步的 `mod`、`struct`、`enum`、`union` 作用域；`mod` 本身也是类型。你已撤回的其他作用域分类不会进入现行文档。这里的“没有实例化方法”也不能被我混写成“不参与编译器 instantiation 过程”。

**这个例子中，三个程序共用的是一条形状递归。**

以下方括号仅表示数学上的形状列表，空列表表示零阶。

| 输入形状 | 广播结果 | 外层投影之后的加法 |
|---|---|---|
| [128, 128] 与 [128, 128] | [128, 128] | 两个 [128] 相加 |
| [128, 128] 与 [] | [128, 128] | [128] 与同一个标量相加 |
| [128, 128] 与 [128] | [128, 128] | 矩阵的一行与原向量相加 |

最后一种最能解释虚拟填充：向量缺少最左边的一维，因此遍历矩阵行时，向量保持自身；只有两边都进入对应的实际维度，才进行降维投影。某维长度为 1 时，反复使用该维的第 0 个切片。这不要求先实际复制出一个广播后的输入张量。

你的零阶类型等式把递归终点接到了元素类型本身：零阶 Tensor 就是 T。因此，**零阶说的是类型和形状，并不意味着标量值必须在编译时已知。** 矩阵中的元素依然可以来自 runtime 输入。

**两阶段检查在这个例子里有具体分工。**

定义 normalization 时，shape_a、shape_b 尚未知。ordinary 需要检查操作的 requirement；PTC 让后续操作使用“两个形状可以广播”等事实，而不要求当场生成全部张量代码。`broadcastable` 提供可用于这一检查过程、也能在实例化时执行的命题；`broadcast_shape` 负责实际计算结果形状。两者有关联，但声明了前者，不能凭空假定后者的所有结果性质都已证明。

当一次调用确定形状后，实例化执行 `assumes`，计算结果形状、填充长度及相关维度，选择 `inline if` 分支，并确定每次降阶调用使用的实现。runtime 保留的是遍历元素和执行加法的代码。你这里写的是普通 `for`，所以不能把“循环上界在编译时已知”进一步说成“语言保证展开整个循环”；同样，静态确定调用目标不等于语言保证消除所有调用。

**把广播条件放在 implementation 体内，还有明确的诊断目的。**

你保留元素加法能力作为 implementation 的适用条件，却把形状相容性放进实例化时执行的 `assumes`。因此，不相容形状触发的是这个张量加法实现内部的检查失败，而不是仅仅因为形状条件不满足而使这个实现不可用。这让错误可以落在“为什么这两个形状不能相加”上。它不是允许不合法的形状进入 runtime。

这也纠正了我上一轮的表述：这里应直接讲“PTC 语句在两个过程中怎样工作”，不需要向用户展示一套额外的 obligation 管理术语。

为了说明 ordinary 如何检查递归体，编译器引导至少需要能引用下面这些性质。它们是从你给出的算法提炼的**候选数学契约**，不是我新增的 Flurry API：

- 广播成立时，结果阶数等于两输入阶数的最大值。
- 对非零阶结果执行本例的投影后，两片段仍可广播。
- 两片段的广播结果，恰好是外层结果形状去掉首维；这样递归加法的结果才适合写入结果切片。
- 每次降阶后，两输入阶数的最大值减少 1；输入有虚拟填充时，不要求两边的阶数都减少。

我把你给出的形状算法独立转写成了数学检查，枚举阶数 0–3、各维为 1–3 的组合，核对了 940 对相容形状：上述降阶关系成立。**这只是算法推演，不是 Flurry 编译器通过了示例，更不证明当前 PTC 自动求解器已能建立所有这些性质。**

1. **零阶应怎样接到标量加法？**

   按你给出的类型等式，两个形状都为空时，操作数已经是 T。原例仍写 `self[0]`、`other[0]`，但尚未给出普通 T 可以如此索引的契约。更重要的是，当前 Tensor implementation 没排除双零阶；经类型等式归约，它可能与 T 已有的标量 Add 实现重叠，或重新依赖自身。

   - **A（建议）**：这条 Tensor implementation 只覆盖至少一边非零阶的情况；双零阶由已经要求存在的元素 Add 实现处理。删除 Tensor 方法里的双零阶分支，递归自然终止。这个限制决定实现适用范围，与体内用于诊断的广播相容性检查分工不同。
   - **B**：保留它覆盖双零阶，但给出已有的 coherence 规则如何排除重叠，以及基例如何明确调用元素加法。实现契约会更多；我不能自行添加优先级或标量索引机制。

2. **形状计算处的 defer 是示例省略，还是这些位置已有不同规则？**

   `Output` 的类型构造和局部 `const` 都调用了依赖未知 shape 的 `broadcast_shape`。你已说明上一个格式化例子是忘写 defer；本例也需要与那条规则接上，不能仅因为函数 pure，就由我默认它可以在所有位置自动保留。

   - **A（建议）**：仍用此前的显式延迟规则，待整理示例时为确需延迟的位置补齐标记；ordinary 依靠可用结果契约继续检查。
   - **B**：关联类型或局部常量中的某些位置本来就允许保留依赖计算；由你点明哪些位置及其依据，不将例外推广到所有类型表达式。

3. **implementation 内 comptime block 的命题，怎样供成员检查使用？**

   我的理解是：这里的 `assumes` 要为这个具体 implementation 后续关联类型和方法提供广播事实。这个作用域边界尚不能只由“每个操作传播命题”推出。

   - **A（建议）**：这类 implementation 级 comptime 检查建立适用于其后续成员检查的事实，并在对应实例化时执行验证。传播的是与该实例相关的命题，不是让 block 内任意局部绑定向外可见。
   - **B**：命题仅在 block 内可用；成员需要从自己的契约或检查语句取得事实。这样就要调整当前示例中的检查位置。

4. **几处局部笔误，我建议按下面一组修正。**

   - **A（建议）**：方法返回广播后的 `Output`；将未定义的 `target_shape` 统一为已定义的 `broadcasted_shape`；语句末尾的逗号改为分号；范围表达式按 grammar 写成 `0 .. out_dim`；以 `}` 结束的两条切片绑定删除后面的分号。局部 `const` 的命名也按当前常量风格统一。
   - **B**：保留某处写法的设计意图，并指出它所依赖的定义或规则；其余按 A 修正。

   返回类型这一项有实质影响：原方法返回左操作数形状，前三个测试恰好都没有暴露问题。把第三个测试交换操作数，左边是 [128]、右边是 [128, 128]，广播结果仍为 [128, 128]，就与原方法签名不符。

还有一个适合留在 Tensor 示例说明中的条件边界：**若允许维度为 0，逐维取 max 不适用所有广播情况。** 你的谓词允许 [0] 与 [1] 配对；按“长度 1 的轴复用到另一侧长度”的规则，结果应为 [0]，当前函数却得到 [1]。教学例可以明确只讨论正维度；若要涵盖空张量，建议按“相同则保留；某侧为 1 则取另一侧”构造结果。这是该算法的边界，不需要上升成 comptime 通则。
