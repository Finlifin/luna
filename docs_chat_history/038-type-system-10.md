## 四、恢复的三个预填问题

### 1. 结构信息与物理布局信息是否分别有自己的可用条件？

对应 036 第 6 题。这里的“分开”是信息含义与查询前提分开，不是要求拆成两个 API 或两种描述对象。

- A. 分开。字段名称、声明顺序、字段类型与属性描述结构；偏移、大小、对齐描述布局。各项观察依据自身需要的输入与契约取得，结构已知不表示所有物理数值已知。
- B. 反射统一要求具体表示完整确定，再提供结构与布局信息；即使某些字段信息可提前知道，也不承诺提供相应观察。

建议答复：A。一个入口可以同时组织这些信息，但不能让“能观察字段结构”自动要求求出所有字段的布局，也不能由字段声明顺序推导物理排列顺序。

我的理由：SOA 与派生例子首先使用的是类型的种类与字段信息。某一步真的需要偏移或大小时，再满足相应布局前提；这能直接接上 ordinary 按已知契约检查的既有模型。

这里没有规定 Type.repr_of 的完整返回形式，也没有承诺反射能任意读取尚未取得的字段列表。操作是否成立与描述数据是否已完整求出，仍按已有阶段规则区分。

### 2. 尚未应用参数的类型定义，是否也是普通结构反射的对象？

对应 036 第 7 题。沿用当时 Cell 的例子：它声明一个 T 类型的 value 字段。观察尚未选择 T 的声明，与观察给定 T 后得到的类型，是否属于同一反射接口的对象范围？

- A. 普通类型反射针对类型值；尚未具体求出的类型结果可按既有契约参与检查。未应用的定义入口另按定义信息处理，不自动视为已应用类型。
- B. 同一结构反射也直接接受未应用的参数化定义，返回信息保留参数的绑定关系。必须说明其中字段类型指称哪一组参数，不能将它们当成普通具体类型使用。

建议答复：A。先定义对类型值的反射；工具能查看一个声明，不意味着这个声明就要以同一种对象参与所有类型观察操作。

我的理由：这样能让“从某个类型的结构生成代码”与“分析一个参数化定义模板”各有清楚输入。若你已有统一模型，B 可以成立，但应给出参数指称的公开契约，而不靠编译器内部占位符解释给读者。

这一题不重新讨论类型模式匹配、调用结果身份或 normal form，也不新建一套 LSP API。

### 3. 已产生并供程序使用的类型值，其字段和布局结构是否保持稳定？

对应 036 第 8 题。具体场景：SOA 工厂已经返回一个类型，其他代码据其字段和布局进行检查；之后某次反射或生成操作还想改变这个类型的字段。

- A. 该类型的字段结构与影响布局的属性保持稳定；需要改变这些内容时构造另一个结果，再按已有类型身份规则使用。
- B. 可以保持同一个类型身份并改变结构；语言必须明确此前的类型事实、已生成代码和实例如何受影响。它会产生用户可观察的变化，不能只描述缓存处理。

建议答复：A。产生类型之前可以逐步准备构造描述；已经返回并供程序使用的类型不再原地改变字段、变体或布局属性。

我的理由：这让前面的反射结果、参数化检查与实际存储具有稳定的共同依据。它不禁止 impl 或派生按各自规则提供操作实现，也不重新引入已移除的 extension 系统。结构与操作实现是不同的确认对象。

此候选沿用作者确认的工厂结果复用，不把“重新计算还是命中缓存”变成是否改变结构的开关。

## 四、恢复的三个预填问题

### 1. 结构信息与物理布局信息是否分别有自己的可用条件？

对应 036 第 6 题。这里的“分开”是信息含义与查询前提分开，不是要求拆成两个 API 或两种描述对象。

- A. 分开。字段名称、声明顺序、字段类型与属性描述结构；偏移、大小、对齐描述布局。各项观察依据自身需要的输入与契约取得，结构已知不表示所有物理数值已知。
- B. 反射统一要求具体表示完整确定，再提供结构与布局信息；即使某些字段信息可提前知道，也不承诺提供相应观察。

建议答复：A。一个入口可以同时组织这些信息，但不能让“能观察字段结构”自动要求求出所有字段的布局，也不能由字段声明顺序推导物理排列顺序。

我的理由：SOA 与派生例子首先使用的是类型的种类与字段信息。某一步真的需要偏移或大小时，再满足相应布局前提；这能直接接上 ordinary 按已知契约检查的既有模型。

这里没有规定 Type.repr_of 的完整返回形式，也没有承诺反射能任意读取尚未取得的字段列表。操作是否成立与描述数据是否已完整求出，仍按已有阶段规则区分。

### 2. 尚未应用参数的类型定义，是否也是普通结构反射的对象？

对应 036 第 7 题。沿用当时 Cell 的例子：它声明一个 T 类型的 value 字段。观察尚未选择 T 的声明，与观察给定 T 后得到的类型，是否属于同一反射接口的对象范围？

- A. 普通类型反射针对类型值；尚未具体求出的类型结果可按既有契约参与检查。未应用的定义入口另按定义信息处理，不自动视为已应用类型。
- B. 同一结构反射也直接接受未应用的参数化定义，返回信息保留参数的绑定关系。必须说明其中字段类型指称哪一组参数，不能将它们当成普通具体类型使用。

建议答复：A。先定义对类型值的反射；工具能查看一个声明，不意味着这个声明就要以同一种对象参与所有类型观察操作。

我的理由：这样能让“从某个类型的结构生成代码”与“分析一个参数化定义模板”各有清楚输入。若你已有统一模型，B 可以成立，但应给出参数指称的公开契约，而不靠编译器内部占位符解释给读者。

这一题不重新讨论类型模式匹配、调用结果身份或 normal form，也不新建一套 LSP API。

### 3. 已产生并供程序使用的类型值，其字段和布局结构是否保持稳定？

对应 036 第 8 题。具体场景：SOA 工厂已经返回一个类型，其他代码据其字段和布局进行检查；之后某次反射或生成操作还想改变这个类型的字段。

- A. 该类型的字段结构与影响布局的属性保持稳定；需要改变这些内容时构造另一个结果，再按已有类型身份规则使用。
- B. 可以保持同一个类型身份并改变结构；语言必须明确此前的类型事实、已生成代码和实例如何受影响。它会产生用户可观察的变化，不能只描述缓存处理。

建议答复：A。产生类型之前可以逐步准备构造描述；已经返回并供程序使用的类型不再原地改变字段、变体或布局属性。

我的理由：这让前面的反射结果、参数化检查与实际存储具有稳定的共同依据。它不禁止 impl 或派生按各自规则提供操作实现，也不重新引入已移除的 extension 系统。结构与操作实现是不同的确认对象。

此候选沿用作者确认的工厂结果复用，不把“重新计算还是命中缓存”变成是否改变结构的开关。

显然builder的build是transactional的。
