## 二、我的评估与教学安排

### 变体集合封闭，不要求每个 base 值都成为合法变体

封闭性回答“这个 enum 有哪些变体”；模式互斥回答“同一个 base 值是否同时属于两个变体”。它们都没有单独证明这些变体覆盖 base type 的所有值。

建议正式定义分别列出三项：变体集合、变体间的互斥条件、合法表示集合。外部输入不在合法表示集合内时如何处理，归相应构造/匹配入口的契约。不能因为 base 是 u32，就承诺全部 u32 值都可以直接当作该 enum 使用。

### 整组匹配的正确性先于区间优化

用户可依赖的是“匹配该组任一叶子”。展开函数与区间选择写到编译器引导，避免用户依赖某次分配出来的 tag 连续性。

供以后实现引导使用的候选不变量是：优化前后接受的合法 enum 值集合相同。用户指定的 tag 分散时，回到叶子匹配仍应保留功能；不能将优化失败当作整组匹配不合法。

### 互斥检查与匹配自动机分开写

对固定宽度表示，可以把每个变体的约束记作数学谓词 P_i(x)。两变体互斥要求不存在满足 P_i(x) 且 P_j(x) 的合法 base 值。找到这样的值就是重叠反例；未找到反例与证明不存在反例不能混写。

这是建议的检查契约，不是已确认的具体求解器算法。如何处理求解超时或不能翻译的模式，后续实现篇必须定义；本轮不凭“用 Z3”自动生成拒绝规则，也不把任意 case 函数交给求解器。

### RISC-V 教学例子：先取 ADD 与 SUB 两种编码

我建议只展示 RV32I 的 ADD/SUB 子集，先让读者看到“操作字段决定变体，寄存器字段成为载荷”。它们都占一个 32 位指令字，不需要跨元素例子。下表按指令位编号从高到低排列，**尚不规定 Flurry 模式的位序或内存字节序**。

| 指令 | 31:25 | 24:20 | 19:15 | 14:12 | 11:7 | 6:0 |
|---|---|---|---|---|---|---|
| ADD | 0000000 | rs2 | rs1 | 000 | rd | 0110011 |
| SUB | 0100000 | rs2 | rs1 | 000 | rd | 0110011 |

编码已核对 RISC-V 官方 [rv_i 指令定义](https://raw.githubusercontent.com/riscv/riscv-opcodes/master/extensions/rv_i)；rs2、rs1、rd 的位段位置已核对官方 [参数位段表](https://raw.githubusercontent.com/riscv/riscv-opcodes/master/arg_lut.csv)。这里保留规范惯用的寄存器字段名；后续 Flurry 绑定名可使用完整单词。

按表推导，两种编码的第 30 位不同，因此这个子集的互斥性可直接说明，不必让读者先理解通用求解器。例子只介绍两种指令；其他指令字不被暗示为合法变体。

先给编码表而不直接粘完整 Flurry enum，是因为 base type 与 BitVec 主语的衔接，以及既有文档未锁定的位序，需要先明确。下面第 1 题只处理前者；精确位序留表示篇。也不据此重新引入已移除的属性。

## 三、union 的章节规划

现有 docs/data-structures/index.md 只提供了简短基线：“所有字段共享同一块内存，同一时刻只有一个字段有效”，以及“访问通常需要在 unsafe 上下文中”。它没有定义这里的“有效”或区分初始化、写入、读取。docs/type/user-defined-types/unions.md 仍为空。

我的判断：union 篇首先要回答选择某个字段究竟意味着什么，然后才能写构造、读写与资源规则。如果用户必须知道最后初始化的成员，却没有任何运行时标记，文档就必须明确谁负责保留这项信息；不能把存储重叠本身当作识别当前成员的办法。

| 正式篇段落 | 内容安排 |
|---|---|
| Intro | 多种字段类型共享存储；读者需要承担或获得的成员选择依据 |
| 语法 | union 声明；确认后的构造、投影和写入形式 |
| 正式定义 | 成员有效性、初始化、切换、读取前提、unsafe 边界与布局保证 |
| 常见示例 | 先用不涉及清理的数值成员；再展示与外部状态配合的使用意图 |
| 跨语言差异 | 确认 Flurry 行为后再查对照语言规范，不预先借用其他语言的活跃成员规则 |
| 运行时实现设计引导 | 共享存储与成员操作的前后置条件；不凭空增加隐藏 tag |
| 编译器实现引导 | 布局计算、访问条件检查、与资源分析的接口；无法确定的状态必须有明确处理方式 |

资源释放细节、成员引用在切换后的可达性、别名规则和完整 Splice 派生条件留给对应主题。本轮只问 union 必须承诺到哪一步，不重建另一套资源管理机制。之后继续参数化数据类型与反射接口。

现有相关产生式如下；expr、clauses、configuration、definition、statement 沿用全局 grammar：

```text

union_variant -> id : expr
```

## 四、预填问题

### 1. base type 为 u32 时，BitVec 模式如何满足现行主语限制？

冲突边界的两端：作者本轮说“pattern 是 base type 上的 pattern”，并建议 u32 base 的指令编码；docs/control-flow/pattern-matching/bitvec.md 的正式定义则说“被匹配值的类型必须是 BitVec。否则为静态错误”。需要明确中间是哪项规则，不应悄悄让整数普遍获得隐式位视图。

- A. 在 enum 的表示模式中，遇到比特段模式时按 base 值的 BitVec 视图解释；普通模式匹配仍保留现行 BitVec 主语限制。表示声明拥有这项约定。
- B. 所有相应比特段模式都可直接作用于有确定表示的 base 值；现行“只匹配 BitVec”需要修订。适用面更广，须定义可接受的类型范围。
- C. base_type 只确定存储单位，表示模式实际统一作用于 BitVec；“base type 上”是在说明编码来源，并不表示以 base 值作为模式主语。这样需要按此含义表述 enum 通则。

建议答复：A。它容纳你建议的 u32 指令例子，同时把适用范围写在 enum 表示声明上。若你意在 B，应明确修改普通比特模式的规则，而不是让两篇文档各自保留一个相反限制。
u8、u16、u32、u64、usize、u128、ArbitrarySizedInteger<any, .signed = false>作为base type时是特别豁免，但是你依然不能直接对这些类型的值进行bitvec matching,其取bitvec。

### 2. expr variant 的“特定类型”先列哪些？

本题只列允许作为显式编码表达式结果的类型，不追问 case view 的内部实现，也不把未给出的混合编码规则塞进来。

- A. 仅整数族；具体支持哪些整数类型随整数类型目录列清。表达式变体是简单数值编码入口。
- B. 整数族及 bool、char；它们各按自身值域检查。比 A 多几个明确类别，仍不接收任意复杂对象。
- C. 还包含其他指定类型，请直接给清单；如果不同类型有不同约束，一并写在清单旁。不能将这解释成任意具备相等操作的类型都可用。

### 3. union 的“一个成员有效”是怎样的状态？

- A. 它描述初始化与使用历史中的逻辑状态；union 对象不自动携带运行时判别标记。调用者或外层抽象必须有选择成员的依据。
- B. union 只是一块有多个类型入口的存储，不维护“活跃成员”这项语言状态；某次读取是否允许，由其目标类型与存储合法性条件决定。现有“只有一个字段有效”需要改写。
- C. union 自动携带成员判别信息，并据此管理访问。布局和行为都需要说明这部分额外状态。

建议答复：A。先保留现有“一个成员有效”的含义，但不假设对象中存在隐藏标签。这里不预先规定所有有效性都能被静态跟踪。

我的理由：A 与当前介绍的文字最接近；B 也可能符合你的设计，但它会直接改变跨成员读取的解释。选 A 后，是否允许通过非活跃成员观察表示仍由第 6 题决定。

### 4. union 的直接构造采用哪种已有表面形态？

以下只有声明沿用现行 grammar；构造形式及其含义均是待确认候选。

```flurry
union Number {
    integer: u32,
    floating: f32,
}
```

- A. 使用只含一个完整命名项的扩展调用，例如 `Number { integer: 1 }`；一次构造恰好选择一个成员。与普通 struct 的表面构造接近，但字段数量要求不同。
- B. 使用成员构造调用，例如 `Number.integer(1)`；成员名提供相应构造入口。需要说明该入口与普通成员声明的关系。
- C. union 没有这种直接构造糖，必须由明确提供的构造操作建立值；具体接口由作者给出，不虚构标准库方法。

### 5. 普通直接构造、完整成员写入、成员读取分别需要什么安全条件？

先限定 RHS 已经是合法成员值，且没有尚未处理的旧资源或成员引用；不把“写入”偷偷当作自动清理旧对象。

- A. 直接构造与完整成员写入可以在安全上下文进行；成员读取要求 unsafe，并满足其合法性前提。写入选择成员，读取依赖外部选择依据。
- B. 三种操作都要求 unsafe；由更高层接口集中承诺合法使用。规则一致，但每次建立一个明确成员也需 unsafe。
- C. 直接构造与完整写入可以安全进行；读取在静态条件足以证明合法时也可安全，否则要求 unsafe。需要给出可依赖的证明条件。

### 6. 写入一个成员后，通过另一个成员读取是什么行为？

具体场景：先把 Number 的 integer 成员初始化为一个合法 u32，再在 unsafe 中读取 floating。这里不使用任何未确认的转换函数。

- A. union 不提供这种跨成员位解释；读取非活跃成员违反访问前提。静态已知违反时拒绝，未被静态排除的执行违反属于 UB，unsafe 不改变该前提。
- B. 允许按另一成员类型解释共享存储，但必须满足目标类型的表示有效性、大小及初始化要求；unsafe 由调用者承担这些条件。不能将其扩成任意位串都能得到合法目标值。

建议答复：A，位表示转换继续走你已指出的 BitVec 路线；这是我对 union 职责的候选划分，不是由“存在 BitVec 转换”推导出的既定禁令。

我的理由：两条路线都可设计得一致，但文档必须明确选边。若选择 B，后续需要写清它与 BitVec 转换共同遵守哪些表示合法性条件，不应复制另一套相互冲突的规则。

### 7. union 成员涉及资源清理时，本章承诺什么？

相邻 docs/resource-management/drop-elaboration.md 有“不实现 Drop 的类型，其 drop 操作默认为递归 drop 各字段”的概括。union 的重叠字段不能在未区分当前成员时被当作独立字段逐个清理；这条概括对 union 的适用范围必须明确。

- A. 允许含有需要清理的成员，但 union 不自动逐成员清理；外层抽象或显式实现负责当前成员的资源责任。覆盖前必须处理旧责任，具体机制归资源篇。
- B. 仅在编译器能确定当前成员时自动清理该成员；不能确定又没有显式管理方案时拒绝需要该清理的操作。需要资源分析提供明确的可判定条件。
- C. union 成员不允许需要此类自动清理的类型。类型限制最简单，但限制可表达的数据。

建议答复：A。共享存储并不提供当前成员的运行时判别依据；首版不要把“递归所有字段”直接用于 union。

我的理由：这不是新增一套析构 API，而是明确通用字段概括的适用边界。尚存成员引用的失效规则、责任怎样转移、清理失败路径及 Splice 自动派生仍归相关主题，本轮不追问那些细节。

### 8. 普通定长 union 的默认布局提供哪些精确保证？

先限定成员都是定长类型，未采用额外布局配置。此题不决定 packed 或 DST 规则。

- A. 所有成员从偏移 0 开始；union 对齐取成员对齐的最大值，大小为最大成员大小向该对齐向上取整。计算规则直接、可检验。
- B. 只保证成员共享起始位置、容量足够且满足各成员对齐；允许额外填充或更强对齐。精确大小依具体布局契约，不能从最大成员单独推出。

### 7. union 成员涉及资源清理时，本章承诺什么？

相邻 docs/resource-management/drop-elaboration.md 有“不实现 Drop 的类型，其 drop 操作默认为递归 drop 各字段”的概括。union 的重叠字段不能在未区分当前成员时被当作独立字段逐个清理；这条概括对 union 的适用范围必须明确。

- A. 允许含有需要清理的成员，但 union 不自动逐成员清理；外层抽象或显式实现负责当前成员的资源责任。覆盖前必须处理旧责任，具体机制归资源篇。
- B. 仅在编译器能确定当前成员时自动清理该成员；不能确定又没有显式管理方案时拒绝需要该清理的操作。需要资源分析提供明确的可判定条件。
- C. union 成员不允许需要此类自动清理的类型。类型限制最简单，但限制可表达的数据。

建议答复：A。共享存储并不提供当前成员的运行时判别依据；首版不要把“递归所有字段”直接用于 union。

我的理由：这不是新增一套析构 API，而是明确通用字段概括的适用边界。尚存成员引用的失效规则、责任怎样转移、清理失败路径及 Splice 自动派生仍归相关主题，本轮不追问那些细节。

so,union几乎只在跟外部语言交互时使用，对于任何场景flurry总是有高级得多的办法。

### 8. 普通定长 union 的默认布局提供哪些精确保证？

先限定成员都是定长类型，未采用额外布局配置。此题不决定 packed 或 DST 规则。

- A. 所有成员从偏移 0 开始；union 对齐取成员对齐的最大值，大小为最大成员大小向该对齐向上取整。计算规则直接、可检验。
- B. 只保证成员共享起始位置、容量足够且满足各成员对齐；允许额外填充或更强对齐。精确大小依具体布局契约，不能从最大成员单独推出。

C abi，并且所有成员类型要求Sized。
