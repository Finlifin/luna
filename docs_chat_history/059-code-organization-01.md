## 一、直接承接的结论

### 本次补充

1. 模块组织基本延续 OLD-2024，在其上增加 umbrella 层级。这里已获得使用该部分旧设计作为基础的授权，不再询问旧模块设计是否整体作废。
2. 六个内置包是 **builtin、meta、std、build、attrs、verification**。
3. attrs 的属性构造接口采用普通表达式的名称解析。可以写完整路径，也可以通过正常 use 缩短路径；不为属性表达式另建优先搜索规则。
4. std.prelude 不默认导入。需要时在 package root 显式写 `use std.prelude.*;`，随后按普通名称解析使用。
5. 源码由目录扫描发现，所有 `.fl` 文件都尝试识别为 Flurry 源码；不再要求 mod file 声明。
6. scripts 在代码组织中有更重要的位置。这里先确认其地位变化，具体职责通过 O5 收束。
7. 静态作用域已有定义，本轮直接使用，不重开作用域分类。

### 与已有主题接合

- 静态作用域按作者给出的无子句限制（含其 parent 条件），由相应 mod、struct、enum、union 定义提供名称解析起点。mod 本身也是类型，用于模块管理，没有构造实例的方法。
- 参数化定义继续遵循 normalization／instantiation。查找“某静态容器中的一个参数化定义”，不等于已经取得该定义每个实例的全部成员。
- 名义类型与 trait 的定义归属按 package 判断；普通 use 不改变原声明身份，也不隐藏已进入实现世界的 coherence 冲突。
- open fn 的分散定义在 package 内封闭。增加 umbrella 不能未经确认就把这个边界改大。
- 构造宏必须在使用者源码的解析之前准备好；现行宏文档已允许依赖包及本包的 scripts 提供这些宏。普通 use 与文件级宏导入 `@use` 分别承担自己的名称引入工作。

依据：[编译流水线](docs/compilation/phases.md)、[包归属与一致性](docs/traits/coherence.md)、[构造宏](docs/macro/construction-macro.md)、026 中作者对静态作用域的原始定义。

## 二、内容规划

我建议用下面八个部分展开，不把“代码组织”缩成一页目录示例。

| 部分 | 要定义的对象与关系 | 教学案例 |
|---|---|---|
| 1. 工程全貌 | umbrella、package、构建目标、模块各自的边界 | 一个应用包依赖同工程中的库包 |
| 2. 源码发现与模块树 | 扫描根、根文件、目录、mod.fl、普通文件、同名冲突 | 添加一个文件后出现哪个模块；错误文件是否被忽略 |
| 3. 静态作用域与路径 | mod 是类型、包含关系、父级查找、包根与依赖入口 | 包根导入后，子模块怎样使用短名 |
| 4. use 与再导出 | 单项、分组、通配、别名、遮蔽、歧义、公开出口 | 两个来源同名；同一声明经两条路径到达 |
| 5. 可见性与接口边界 | 默认可见性、pub、文件／模块／package 的关系 | 子模块访问父定义，跨包访问与再导出 |
| 6. 内置包与构建环境 | 六个入口、显式 prelude、attrs 普通解析、build 上下文 | 同一源码在不同构建中取得不同配置 |
| 7. Scripts 与生成源码 | 工程脚本、宏准备、生成物、宿主与目标、依赖顺序 | 脚本先提供宏，src 再使用宏；识别自举环 |
| 8. Manifest 与构建交付 | package 描述、umbrella 成员、依赖、目标、产物与增量失效 | 构建一个成员、复用依赖、修改生成输入后重建 |

每部分正式写入时仍按七段骨架展开。manifest 的字段名、命令行、umbrella 描述文件名及脚本执行 API 不在本轮凭空指定。

我对整个主题的核心判断是：**源码发现、名称可见性、包依赖和构建执行需要分别描述。** 例如，发现一个文件不等于执行它；能解析一个包名不等于其中所有成员都变成当前作用域短名；同处一个 umbrella 也不能直接证明两个包共享私有成员或 impl 归属权。

## 三、六个内置包的职责

| 包 | 作者已明确的职责 | 本轮需要守住的边界 |
|---|---|---|
| builtin | 最基础的语言内容 | 包名入口与包内成员短名的导入分别解释 |
| meta | comptime 的基础设施，以及编译器暴露的 comptime 接口 | 编译器接口的可用阶段按各自契约检查 |
| std | 跨平台系统编程基础内容 | prelude 只是可显式 use 的组织接口 |
| build | 当前工程与构建的信息，例如 build.mode | “当前”绑定到哪个构建实例，见 O6 |
| attrs | 语言属性构造接口 | 按普通名称解析，没有属性专属的优先搜索 |
| verification | 程序验证内容，例如 Set、Map | 验证规格不因处于一个包里就归到 PTC |

“内置包”没有被我解释为六个包都采用同一种实现或链接形式；尤其 build 可以交付当前构建的信息，这与 std 中普通定义的来源不同。

本次列表直接更新此前包含 math 的六入口记述。math 此后的具体路径、是否经某个 prelude 再导出，需要在内置包布局节确定；这里不擅自把它搬到一个新路径。

### Prelude 与属性的教学前提

本轮 Flurry 示例在需要短名的包根显式导入 prelude：

~~~flurry
-- package root
use std.prelude.*;

mod feature {
    fn answer() -> u32 {
        42
    }
}
~~~

你已说明包根的一次 use 可以按一般解析流程达到预期效果，因此不需要为 prelude 发明“向所有文件逐份注入”的特殊规则。外部使用者能否从该包再取得这些导入，则是 O4 的独立问题。

属性接口的完整路径和别名复用现有形式：

~~~text
attribute -> ^expr
use_statement -> use path
projection_path -> path . id
projection_all_path -> path . *
path_as_bind -> path as id
~~~

例如已有的 `attrs.derivation.default` 可以经正常 use 引入别名。是否遮蔽其他名字、是否产生歧义，都交给普通解析；属性位置不偷偷多查一次 attrs。

## 四、首轮预填审阅

### O1. Umbrella 是否只组织多个包，而不扩大语言中的 package 边界？

考虑一个 umbrella 中包含 editor 和 model 两个包，editor 需要 model。目录名称只用于说明关系，不是预设的保留目录。

~~~text
project/
├── editor/
│   ├── package.fl
│   └── src/main.fl
└── model/
    ├── package.fl
    └── src/lib.fl
~~~

- **A. Umbrella 管理成员和共同构建事务，成员仍是独立的 package 语义边界。** 成员之间通过声明的依赖使用接口；同处一个工程不自动取得另一个包的私有访问或本地 impl 权限。已有 coherence 与 open fn 边界可直接保持。
- **B. Umbrella 也是语言中的共同组织域，成员自动获得某些跨包名称或定义权限。** 可以支持更紧密的内部工程协作，但必须重新界定哪些权限由 package 决定，哪些改由 umbrella 决定。

**预填答复：A。** Umbrella 可以统一安排成员、构建参数和共享资源；它不自动成为名称路径中的额外一节，也不把全部成员静态作用域合并成一个包。成员间要有明确依赖；构建某个成员，不因旁边还放着另一个成员就把后者所有 impl 纳入它的实现世界。

这不要求成员脱离 umbrella 配置后仍能独立构建；共享工程配置与保持 package 的语义身份可以同时成立。依赖如何写、版本如何解算，留 manifest 一节。

### O2. “扫描整个目录”的默认源码根，指 src，还是整个 package 目录？

沿用旧结构时，package 旁边还可能有 scripts、resources、docs。仅有“.fl 都尝试识别”还不能决定这些文件进入哪个编译上下文。

- **A. 默认递归扫描 package 的 src；scripts、manifest 及显式注册的生成源码各按自身角色处理。** src 内的文件自动参与源码发现，工程其他位置不会意外成为 runtime 源码；角色边界明确。
- **B. 默认递归扫描整个 package，再按目录和文件角色分类所有 .fl 文件。** 发现入口更统一，但必须说明普通源码如何与文档示例、工具脚本、描述文件和嵌套包划界。

**预填答复：A。** 按旧模型承接 exe 的 src/main.fl 与 lib 的 src/lib.fl 作为默认包根文件；src 内全部 .fl 都尝试作为源码处理。需要额外源码根时，由构建描述明确纳入，不通过某个 use 恰好被写到才决定文件是否存在。

进一步的候选边界：

- 纳入当前源码集合的文件，语法错误不能因为无人引用而静默忽略。
- 发现与登记不等于执行所有 comptime 主体、实例化所有泛型或运行所有测试；相应工作仍按阶段与需求承担检查责任。
- scripts 内的 .fl 也属于 Flurry 源码，但有独立的工程角色，不自动并入 src 的 runtime 模块树。
- 构建输出只有经明确纳入才成为源码；不能在一次目录扫描中无界地追着脚本新写出的文件继续编译。

同包多个目标、main.fl 与 lib.fl 共存时的目标选择，留 manifest／目标模型继续定义，本轮不靠另一份根文件的存在擅自创建第二个 package。

### O3. 无 mod.fl 的目录，以及同名文件与目录，怎样映射到模块？

“每个文件和目录对应模块”来自旧设计；现在取消逐项声明后，需要给自动发现一个唯一结果。

~~~text
src/
├── main.fl
├── codec/
│   ├── mod.fl
│   └── text.fl
└── utility/
    └── checksum.fl
~~~

- **A. 目录自动建立模块，mod.fl 可选，提供该目录模块自身的声明；同级文件与目录同名时拒绝。** 目录无需空入口文件；每个模块的文件系统来源确定，不自动合并两份主体。
- **B. 目录自动建立模块，并允许同名 foo.fl 与 foo/ 合并为一个模块。** 便于把文件模块逐步拆成目录，但要定义 foo.fl、foo/mod.fl、目录子项和内联 mod 的合并边界。
- **C. 非根目录必须含 mod.fl 才能成为模块；扫描到缺入口的源码目录时报错。** 保留目录入口的强约定，代价是纯粹容纳子模块的目录也要维护入口文件。

**预填答复：A。** 上例得到 codec、codec.text、utility、utility.checksum；codec/mod.fl 的声明属于 codec，不再建立一个 codec.mod。main.fl 提供包根的声明，也不额外包一层名为 main 的文件模块。

同级 codec.fl 与 codec/、显式内联 `mod codec { ... }` 与自动发现的 codec，都不能按扫描顺序选一个，也不隐式合并。这里的“同名冲突”针对同一模块槽位；codec/mod.fl 为其所属目录提供声明，是这条文件映射规则的一部分，不被误判成第二个 codec。

已有的普通定义重名限制继续适用。声明文件如何枚举，不应影响模块身份、绑定结果或最终错误。

### O4. 普通 use 是否只建立本地名称，而不自动把该名称作为公开出口？

包根写 `use std.prelude.*;` 后，包内代码能按普通规则找到导入名；但另一个包是否应因此从这个包取得同样的名字，是另外一个选择。

- **A. 普通 use 建立当前作用域的名称绑定；向外再导出需要明确的公开依据。** 子作用域仍可经正常父级查找使用绑定，但一个内部便捷导入不会自动扩大包的 API。
- **B. 静态作用域中的普通 use 同时把导入纳入该作用域的默认对外成员集合。** 以模块聚合接口更简洁，但在 package root 导入整个 prelude 也会扩大它的默认出口。

**预填答复：A。** Prelude 只是一份正常导入。对子模块的词法可用性、对外投影的成员资格和最终访问权限分别判断；use 本身不授予超出来源许可的公开访问。

再导出沿用原声明身份，不能生成“本包新定义”的类型或 trait。相同来源经不同路径到达，不应仅因路径不同而变成两份 impl 或两个名义类型。

本轮只确认导入不自动扩大公开接口；具体 pub／再导出表面形式、私有项对子模块的可见性、通配与显式导入的优先级，放下一检查点，不在这里预设一套 Rust 可见性语法。

### O5. Scripts 的提升，是否包含可独立选择运行的一般工程脚本？

现行宏文档已经确定：scripts 可以提供先于 src 准备的构造宏。这说明其不只是与源码无关的附属文件，但还没有限定“提升”后的全部角色。

- **A. Scripts 是工程中的通用脚本入口，可以准备宏、生成源码和产物，也可以承载独立选择的工程任务。** 需要明确每个入口的依赖和执行时机；不是每次扫描目录就执行所有脚本。
- **B. Scripts 只作为主源码编译的前置设施，承担宏和构建辅助，没有独立任务入口。** 初始系统较小，但一般工程工具还要放在其他包或外部工具中。

**预填答复：A。** Package 及 umbrella 的工具需求可以显式组织这些入口；发现脚本、编译脚本和执行脚本分别发生。脚本能够交付给后续步骤的东西必须明确，例如宏接口、生成源码或构建输入，不直接把任意脚本局部名字注入 runtime 包根。

特别需要保留真实的依赖方向：如果 src 的解析需要某个宏，而准备该宏又需要先解析同一份 src，形成的是自举环。脚本仍可以使用已经具备的依赖或独立工具；并非一律禁止引用同工程代码。

我不在这一选择中顺带决定 scripts 是否有独立 package 身份、脚本入口如何命名、执行器采用哪种载体，以及宿主／目标 API 的具体分配。它们进入 scripts 专节，避免“脚本地位提高”被误写成“一切在同一个 comptime 环境里无序运行”。

### O6. build 描述定义所属的构建实例，还是顶层消费者的一份全局上下文？

需要处理的不只是读取模式，而是：某依赖包自己的代码读取 build.mode 时，它观察的是谁的构建？这也决定同一依赖源码在不同目标中怎样复用检查结果。

~~~flurry
-- package root
use std.prelude.*;

fn report_mode() {
    if build.mode matches .debug {
        println("debug");
    } else {
        println("other");
    }
}
~~~

- **A. build 绑定到当前源码所属的具体构建实例，其输入确定后保持稳定。** 不同目标或配置可以分别取得对应值；依赖查询和缓存必须区分实际使用的构建输入。
- **B. build 统一描述最外层构建发起者，依赖也读取同一份顶层环境。** 向整个依赖图传递应用配置更直接，但依赖行为会受消费者环境影响，并须保留这种额外依赖。

**预填答复：A。** 构建系统可以把 umbrella 或应用选择的配置显式传给成员／依赖实例；定义内部的 build 引用仍固定到本实例的环境，不因后来被内联、被模板使用或从另一个作用域调用就重新解释“当前”。

应分别记录“编译脚本在哪个宿主上执行”和“本次产物面向哪个目标”，不能在交叉构建时把二者混为一谈。这里仅确定需要区分这两种信息，不发明 build.host、build.target 等具体成员。

读取尚由本次构建求值反过来决定的 build 数据，需要识别真实依赖环或尚不可用的输入。不能把可变的全局 build 对象作为所有查询的隐含共享状态。不同构建输入也不自动意味着同一包中的名义类型具有不同语言身份；那个问题由包身份与实例化规则另行处理。

下面只是便于评估上述候选的骨架，不是新增编译阶段的语言承诺：

~~~text

  → 按显式构建依赖执行后续生成和产物交付
~~~

实际 query 可以按需交错执行；必须保持这些依赖，不要求把所有源码机械地跑成一个固定全局 pass。

尤其不要把三种环混在一起：

- 两个模块的声明相互引用，未必就是需要拒绝的求值环。
- 再导出出现循环，需要基于声明身份处理重复路径及歧义，不能仅用递归调用栈草率判断名称不存在。
- 为解析 A 必须先执行 B，而执行 B 又必须先解析 A，是实质的准备依赖环。

后两类的具体算法在各自章节定义。本轮先固定对象和边界，避免过早规定“整个依赖图中只要有环就一律禁止”。

目录扫描具有一个容易被低估的影响：新增一个文件可以改变模块声明集合。实现应记录这一结构依赖，而不只追踪已经打开的文件内容；否则增量编译可能继续使用一份不知道新模块或重名冲突的结果。

## 三、六个内置包的职责

| 包 | 作者已明确的职责 | 本轮需要守住的边界 |
|---|---|---|
| builtin | 最基础的语言内容 | 包名入口与包内成员短名的导入分别解释 |

| std | 跨平台系统编程基础内容 | prelude 只是可显式 use 的组织接口 |

“内置包”没有被我解释为六个包都采用同一种实现或链接形式；尤其 build 可以交付当前构建的信息，这与 std 中普通定义的来源不同。

### Prelude 与属性的教学前提

本轮 Flurry 示例在需要短名的包根显式导入 prelude：

~~~flurry
-- package root
use std.prelude.*;

mod feature {
    fn answer() -> u32 {
        42
    }
}
~~~

你已说明包根的一次 use 可以按一般解析流程达到预期效果，因此不需要为 prelude 发明“向所有文件逐份注入”的特殊规则。外部使用者能否从该包再取得这些导入，则是 O4 的独立问题。

属性接口的完整路径和别名复用现有形式：

~~~text
attribute -> ^expr
use_statement -> use path
projection_path -> path . id
projection_all_path -> path . *
path_as_bind -> path as id
~~~

例如已有的 `attrs.derivation.default` 可以经正常 use 引入别名。是否遮蔽其他名字、是否产生歧义，都交给普通解析；属性位置不偷偷多查一次 attrs。

## 四、首轮预填审阅

### O1. Umbrella 是否只组织多个包，而不扩大语言中的 package 边界？

考虑一个 umbrella 中包含 editor 和 model 两个包，editor 需要 model。目录名称只用于说明关系，不是预设的保留目录。

~~~text
project/
├── editor/
│   ├── package.fl
│   └── src/main.fl
└── model/
    ├── package.fl
    └── src/lib.fl
~~~

- **A. Umbrella 管理成员和共同构建事务，成员仍是独立的 package 语义边界。** 成员之间通过声明的依赖使用接口；同处一个工程不自动取得另一个包的私有访问或本地 impl 权限。已有 coherence 与 open fn 边界可直接保持。
- **B. Umbrella 也是语言中的共同组织域，成员自动获得某些跨包名称或定义权限。** 可以支持更紧密的内部工程协作，但必须重新界定哪些权限由 package 决定，哪些改由 umbrella 决定。

**预填答复：A。** Umbrella 可以统一安排成员、构建参数和共享资源；它不自动成为名称路径中的额外一节，也不把全部成员静态作用域合并成一个包。成员间要有明确依赖；构建某个成员，不因旁边还放着另一个成员就把后者所有 impl 纳入它的实现世界。

这不要求成员脱离 umbrella 配置后仍能独立构建；共享工程配置与保持 package 的语义身份可以同时成立。依赖如何写、版本如何解算，留 manifest 一节。

### O2. “扫描整个目录”的默认源码根，指 src，还是整个 package 目录？

沿用旧结构时，package 旁边还可能有 scripts、resources、docs。仅有“.fl 都尝试识别”还不能决定这些文件进入哪个编译上下文。

- **A. 默认递归扫描 package 的 src；scripts、manifest 及显式注册的生成源码各按自身角色处理。** src 内的文件自动参与源码发现，工程其他位置不会意外成为 runtime 源码；角色边界明确。
- **B. 默认递归扫描整个 package，再按目录和文件角色分类所有 .fl 文件。** 发现入口更统一，但必须说明普通源码如何与文档示例、工具脚本、描述文件和嵌套包划界。

**预填答复：A。** 按旧模型承接 exe 的 src/main.fl 与 lib 的 src/lib.fl 作为默认包根文件；src 内全部 .fl 都尝试作为源码处理。需要额外源码根时，由构建描述明确纳入，不通过某个 use 恰好被写到才决定文件是否存在。

进一步的候选边界：

- 纳入当前源码集合的文件，语法错误不能因为无人引用而静默忽略。
- 发现与登记不等于执行所有 comptime 主体、实例化所有泛型或运行所有测试；相应工作仍按阶段与需求承担检查责任。
- scripts 内的 .fl 也属于 Flurry 源码，但有独立的工程角色，不自动并入 src 的 runtime 模块树。
- 构建输出只有经明确纳入才成为源码；不能在一次目录扫描中无界地追着脚本新写出的文件继续编译。

同包多个目标、main.fl 与 lib.fl 共存时的目标选择，留 manifest／目标模型继续定义，本轮不靠另一份根文件的存在擅自创建第二个 package。

### O3. 无 mod.fl 的目录，以及同名文件与目录，怎样映射到模块？

“每个文件和目录对应模块”来自旧设计；现在取消逐项声明后，需要给自动发现一个唯一结果。

~~~text
src/
├── main.fl
├── codec/
│   ├── mod.fl
│   └── text.fl
└── utility/
    └── checksum.fl
~~~

- **A. 目录自动建立模块，mod.fl 可选，提供该目录模块自身的声明；同级文件与目录同名时拒绝。** 目录无需空入口文件；每个模块的文件系统来源确定，不自动合并两份主体。
- **B. 目录自动建立模块，并允许同名 foo.fl 与 foo/ 合并为一个模块。** 便于把文件模块逐步拆成目录，但要定义 foo.fl、foo/mod.fl、目录子项和内联 mod 的合并边界。
- **C. 非根目录必须含 mod.fl 才能成为模块；扫描到缺入口的源码目录时报错。** 保留目录入口的强约定，代价是纯粹容纳子模块的目录也要维护入口文件。

**预填答复：A。** 上例得到 codec、codec.text、utility、utility.checksum；codec/mod.fl 的声明属于 codec，不再建立一个 codec.mod。main.fl 提供包根的声明，也不额外包一层名为 main 的文件模块。

同级 codec.fl 与 codec/、显式内联 `mod codec { ... }` 与自动发现的 codec，都不能按扫描顺序选一个，也不隐式合并。这里的“同名冲突”针对同一模块槽位；codec/mod.fl 为其所属目录提供声明，是这条文件映射规则的一部分，不被误判成第二个 codec。

已有的普通定义重名限制继续适用。声明文件如何枚举，不应影响模块身份、绑定结果或最终错误。

### O4. 普通 use 是否只建立本地名称，而不自动把该名称作为公开出口？

包根写 `use std.prelude.*;` 后，包内代码能按普通规则找到导入名；但另一个包是否应因此从这个包取得同样的名字，是另外一个选择。

- **A. 普通 use 建立当前作用域的名称绑定；向外再导出需要明确的公开依据。** 子作用域仍可经正常父级查找使用绑定，但一个内部便捷导入不会自动扩大包的 API。
- **B. 静态作用域中的普通 use 同时把导入纳入该作用域的默认对外成员集合。** 以模块聚合接口更简洁，但在 package root 导入整个 prelude 也会扩大它的默认出口。

**预填答复：A。** Prelude 只是一份正常导入。对子模块的词法可用性、对外投影的成员资格和最终访问权限分别判断；use 本身不授予超出来源许可的公开访问。

再导出沿用原声明身份，不能生成“本包新定义”的类型或 trait。相同来源经不同路径到达，不应仅因路径不同而变成两份 impl 或两个名义类型。

本轮只确认导入不自动扩大公开接口；具体 pub／再导出表面形式、私有项对子模块的可见性、通配与显式导入的优先级，放下一检查点，不在这里预设一套 Rust 可见性语法。

### O5. Scripts 的提升，是否包含可独立选择运行的一般工程脚本？

现行宏文档已经确定：scripts 可以提供先于 src 准备的构造宏。这说明其不只是与源码无关的附属文件，但还没有限定“提升”后的全部角色。

- **A. Scripts 是工程中的通用脚本入口，可以准备宏、生成源码和产物，也可以承载独立选择的工程任务。** 需要明确每个入口的依赖和执行时机；不是每次扫描目录就执行所有脚本。
- **B. Scripts 只作为主源码编译的前置设施，承担宏和构建辅助，没有独立任务入口。** 初始系统较小，但一般工程工具还要放在其他包或外部工具中。

**预填答复：A。** Package 及 umbrella 的工具需求可以显式组织这些入口；发现脚本、编译脚本和执行脚本分别发生。脚本能够交付给后续步骤的东西必须明确，例如宏接口、生成源码或构建输入，不直接把任意脚本局部名字注入 runtime 包根。

特别需要保留真实的依赖方向：如果 src 的解析需要某个宏，而准备该宏又需要先解析同一份 src，形成的是自举环。脚本仍可以使用已经具备的依赖或独立工具；并非一律禁止引用同工程代码。

我不在这一选择中顺带决定 scripts 是否有独立 package 身份、脚本入口如何命名、执行器采用哪种载体，以及宿主／目标 API 的具体分配。它们进入 scripts 专节，避免“脚本地位提高”被误写成“一切在同一个 comptime 环境里无序运行”。

### O6. build 描述定义所属的构建实例，还是顶层消费者的一份全局上下文？

需要处理的不只是读取模式，而是：某依赖包自己的代码读取 build.mode 时，它观察的是谁的构建？这也决定同一依赖源码在不同目标中怎样复用检查结果。

~~~flurry
-- package root
use std.prelude.*;

fn report_mode() {
    if build.mode matches .debug {
        println("debug");
    } else {
        println("other");
    }
}
~~~

- **A. build 绑定到当前源码所属的具体构建实例，其输入确定后保持稳定。** 不同目标或配置可以分别取得对应值；依赖查询和缓存必须区分实际使用的构建输入。
- **B. build 统一描述最外层构建发起者，依赖也读取同一份顶层环境。** 向整个依赖图传递应用配置更直接，但依赖行为会受消费者环境影响，并须保留这种额外依赖。

**预填答复：A。** 构建系统可以把 umbrella 或应用选择的配置显式传给成员／依赖实例；定义内部的 build 引用仍固定到本实例的环境，不因后来被内联、被模板使用或从另一个作用域调用就重新解释“当前”。

应分别记录“编译脚本在哪个宿主上执行”和“本次产物面向哪个目标”，不能在交叉构建时把二者混为一谈。这里仅确定需要区分这两种信息，不发明 build.host、build.target 等具体成员。

读取尚由本次构建求值反过来决定的 build 数据，需要识别真实依赖环或尚不可用的输入。不能把可变的全局 build 对象作为所有查询的隐含共享状态。不同构建输入也不自动意味着同一包中的名义类型具有不同语言身份；那个问题由包身份与实例化规则另行处理。

## 五、我建议的实现思路

下面只是便于评估上述候选的骨架，不是新增编译阶段的语言承诺：

~~~text
确定工程成员、构建目标与合法依赖
  → 按角色确定源码根与脚本入口
  → 发现源码并建立唯一的文件／目录到模块映射
  → 准备解析所需的宏，登记静态定义和导入边
  → 完成名称解析与可见性检查
  → 在相应依赖世界中检查类型、实现与实例化
  → 按显式构建依赖执行后续生成和产物交付
~~~

实际 query 可以按需交错执行；必须保持这些依赖，不要求把所有源码机械地跑成一个固定全局 pass。

尤其不要把三种环混在一起：

- 两个模块的声明相互引用，未必就是需要拒绝的求值环。
- 再导出出现循环，需要基于声明身份处理重复路径及歧义，不能仅用递归调用栈草率判断名称不存在。
- 为解析 A 必须先执行 B，而执行 B 又必须先解析 A，是实质的准备依赖环。

后两类的具体算法在各自章节定义。本轮先固定对象和边界，避免过早规定“整个依赖图中只要有环就一律禁止”。

目录扫描具有一个容易被低估的影响：新增一个文件可以改变模块声明集合。实现应记录这一结构依赖，而不只追踪已经打开的文件内容；否则增量编译可能继续使用一份不知道新模块或重名冲突的结果。
