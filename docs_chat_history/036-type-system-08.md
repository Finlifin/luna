## 三、我的内容判断

### 参数化章节应说明参数在类型中承担什么职责

带参数的数据定义可以公开自己的字段、约束和成员，但某个字段的具体布局仍依赖实参。读者需要区分“这个定义有一个 T 类型的字段”“T 满足某种布局性质”“这个字段占多少字节”。

comptime 章节已经解释 ordinary 如何利用契约，以及具体计算如何依赖输入。本轮不再投票这套阶段模型；要补的是类型接口提供哪些性质，哪些观察必须等到所需输入具备。

### Sized 不应成为“这个类型我已经完全算完了”的同义词

一个泛型定义可以依靠 T 满足 Sized 来检查操作，而不知道 T 最后有多少字节。反过来，一个类型依赖运行时对象，也不必因此尺寸可变：此前 NodeIndex 就是重要反例，其环境依赖不增加每个索引值的指针存储。

因此 Sized 的定义必须与“类型包含运行时依赖”“当前分析已拿到具体大小”分开。union 新确认的 Sized 要求，正好提供一个具体的使用入口。

### 反射应区分结构信息与布局信息

SOA 的既有设计需要取得输入类型的字段，再为字段构造相应存储。这说明结构观察与类型生成需要可连接，但并没有给出所有反射 API 的定稿。

建议本章先承诺信息的含义：字段名称、类型与声明顺序，和物理偏移、大小、对齐，各自描述什么。精确 API 名称、描述对象用列表还是映射、builder 有哪些方法，属于具体接口文档，本轮不要求作者拍板。

### 生成结果必须有可依赖的结构

类型被用于字段布局或生成代码后，如果还能保持同一个身份而改变字段结构，之前的布局结论、成员访问和代码就可能失效。这是用户可观察的一致性问题，不只是缓存实现细节。

第 8 题因此问“已经供程序使用的类型值是否还可改变结构”。它不质疑作者已确认的纯调用缓存，也不禁止构造类型之前逐步准备输入描述。

### 正式文档的内容分工

建议分别组织参数化类型与结构反射两篇，均保留七段骨架：Intro 用小例子建立区分；语法只列本篇用到的定义/应用；正式定义写可依赖的性质和观察条件；示例展示约束与反射用途；跨语言段在写入时按已确认行为查证；运行时引导说明类型信息如何决定表示；编译器引导说明如何依据契约检查并在输入具备后兑现布局。

Sized 可作为参数化篇的基础小节，并由 union、布局观察等章节引用。正式文件路径等内容收敛后再决定；本轮不创建 docs/ 占位，也不编写运行时反射系统。

## 五、预填问题

### 1. “comptime 不支持 union”是否仍允许处理 union 的类型信息？

现有 docs/type/boostrap.md 说明类型可作为编译时计算的输入和结果；作者现在排除了 comptime union。需要区分一个 union 实例，与描述其运行时类型的 Type 值。

- A. 排除 union 实例的 comptime 构造、存储和读写；仍可处理描述 union 的 Type 值，检查成员类型、计算目标布局，并通过允许的类型构造入口产生运行时 union 类型。类型信息不是 union 实例。
- B. 除实例操作外，也限制 comptime 动态构造 union 类型；只允许静态声明的 union 参与必要类型检查与布局。元编程开放面更小，需明确这个例外。

建议答复：A。这样“comptime 不支持 union”约束的是 union 值的执行能力，编译器和类型计算仍能描述它的 C ABI。

我的理由：这与阶段和值的既有区分一致。此前 Splice 候选曾笼统列入 union；不能继续据那份候选断言存在可直接 splice 的 comptime union 实例。至于运行时 union 的类型描述或代码引用，不应混同为已经取得一个 union 值。

### 2. Sized 要求大小不依赖运行时实例内容吗？

- A. 对每个确定的运行时类型，大小与对齐由该类型及目标布局确定，不随该类型某个实例的运行时内容改变；在泛型检查时可以只知道这一性质，尚不知道具体数值。
- B. 只要求对每个实例都能在使用时算出大小；允许计算依赖实例的运行时内容。范围更广，但 union 的 C ABI 要求还需更强的布局条件。

建议答复：A。类型依赖某个运行时对象并不自动排除 Sized；关键在于对象内容是否参与决定该值的存储大小。

我的理由：它能同时表达“NodeIndex 有动态依赖但尺寸固定”和“泛型 T 尚未知具体大小但满足 Sized”。如果采用 B，Sized 就不能单独支持当前 union 的布局前提，需要重新命名或拆开两种性质。

### 3. Sized 是如何获得和验证的？

- A. 由类型的布局规则确定，编译器可检查，并通过 Sized 约束供泛型使用；不能靠用户随意写一个实现，就使不满足布局条件的类型获得该性质。
- B. 按普通 trait 的实现机制提供，包括用户实现；实现者需要承担与布局一致的契约。需另行说明谁验证或信任这项承诺。
- C. 它只是布局判定的名称，不进入 trait 约束系统；使用其他既有命题接口描述。具体表面形式由作者提供。

建议答复：A。先保证这个性质的依据是类型布局，并使它能成为定义端可用的约束。若具体语法并不是 trait 形态，选 C 即可，不为沿用某种惯例强加 trait 身份。

我的理由：union 的成员合法性和内存容量会依赖它，单有同名方法或未经约束的声明不能说明尺寸成立。这里不发明一般 auto trait 系统。

### 4. 普通类型参数是否默认带 Sized？

以 Cell 的 value 字段为例：现行 docs/comptime/prompt.fl、docs/type/prompt.fl 等材料多次使用仅写 where T 的结构体；这些例子没有单独说明 Sized 的默认规则。

- A. 不隐含 Sized。某个操作或字段布局需要该性质时，定义必须具有相应约束或其他已知依据；只声明“这是一个类型”还不够。
- B. 普通类型参数默认带 Sized；接受非 Sized 类型时另有明确方式。旧例子可按默认约束解释，但放宽约束的方式还需给出。

建议答复：A。让 Type 所涵盖的类型与某个操作所需的布局性质分开；若第 3 题允许 trait 形态，可以用已有的 `where T :- Sized` 表达要求。

我的理由：这能避免把“可作为类型参数”和“可直接放入某个定长存储槽”混为一谈。但它可能要求给既有 Cell 类例子补约束；本轮只列出影响，不擅自判定这些材料错误。非 Sized 字段有哪些合法容纳方式，也不在这一题顺带决定。

### 5. 直接按值递归的类型，怎样判定布局能否成立？

```flurry
struct Link {
    next: *Link,
}

struct Loop {
    next: Loop,
}
```

两段都只是现行声明语法下的候选检查用例，未宣称第二段合法。

- A. 按布局依赖区分：若指针自己的表示无需嵌入所指对象，Link 的字段不产生按值展开循环；Loop 这种必须先知道自身完整大小的按值循环拒绝。不会自动替它插入间接存储。
- B. 允许按值循环，由语言自动选择间接表示或其他递归表示。需要规定新增存储、访问与资源行为，不能仅当成布局优化。
- C. 普通声明一律禁止递归引用，包括指针间接引用；递归结构必须通过其他明确的构造入口表达。

建议答复：A。判断的是实例化后实际需要的布局依赖，不能只看到类型名字再次出现就拒绝，也不能依靠递归调用最终“也许停下来”。

我的理由：此规则给出实现引导的关键检查对象：一个字段的存储布局是否真的依赖另一个完整对象布局。参数化递归还可能产生不断变化的新实例；第一个例子的有限循环检查不能被写成解决了任意类型计算的终止性，这部分不新增全局终止保证。

### 6. 结构反射是否分开提供声明信息与物理布局信息？

- A. 分开。字段名称、声明顺序、字段类型与已有属性描述类型结构；偏移、大小、对齐描述具体布局，按各项观察所需的输入取得。声明顺序不自动等于物理排列顺序。
- B. 只在具体布局完整确定后提供整套反射信息；即使字段名字已知，也不承诺提前遍历结构。接口简单，但限制参数化分析能直接观察的内容。

建议答复：A。对结构观察与布局观察分别给出前提；当前只知道某种性质时，仍按已有 PTC 契约支持相应操作，不声称所有字段描述都已经具体化。

我的理由：SOA 转换需要的是源类型字段结构，而布局计算需要的是成员尺寸和目标规则。它们可能同时具备，也可能在不同输入到齐后才具备。反射返回对象的 API 形状留具体接口篇，本题只确认信息含义和观察条件。

### 7. 尚未应用参数的类型定义，是否也是直接可反射的对象？

具体场景：工具希望知道 Cell 声明了一个 value 字段，但尚未选择 T；另一个工具已经持有应用参数后得到的类型，要查询其字段。

- A. 普通类型反射针对类型值，包括按既有契约处理尚未具体求出的类型结果；未应用的定义入口另用定义/源码信息接口描述，不自动把它当作一个已经应用的类型。
- B. 同一套结构反射也直接接收未应用的参数化定义；返回的信息保留参数绑定关系。需明确模板字段类型指称哪些参数，不能当成普通具体类型使用。

建议答复：A。先把已存在的类型值观察接口写清；编辑器需要查看声明，不意味着该声明必须以同一类型参与所有普通反射操作。

我的理由：这里是反射对象的界限，不重问 normal form 与普通类型工厂结果的等价关系。若你已打算统一声明模板与应用后类型的反射，B 可以成立，但参数的指称关系必须成为公开契约。

### 8. 已经被程序使用的类型值，还能通过反射改变字段结构吗？

- A. 类型值一旦产生，其字段结构与影响布局的属性保持稳定；反射用于观察。需要改变结构时构造另一个结果，再按既有类型身份规则使用。
- B. 可以保持同一个类型身份并改变这些内容；语言必须规定原来的布局事实、已生成代码与实例如何受到影响。用户能观察到这种变化，不能只用“缓存失效”解释。

建议答复：A。输入描述可以在产生类型结果之前准备；得到并使用该类型后，字段、变体和布局属性不再原地改写。

我的理由：这是类型结构的一致性边界，不限制已确认的 impl/extend 按自身规则增加接口，也不把是否重新命中纯调用缓存当作类型形状变化的开关。原来 SOA 设计中的构造工具只是实现方式之一，不在本题固定 builder 生命周期或 API。

## 三、我的内容判断

### 参数化章节应说明参数在类型中承担什么职责

带参数的数据定义可以公开自己的字段、约束和成员，但某个字段的具体布局仍依赖实参。读者需要区分“这个定义有一个 T 类型的字段”“T 满足某种布局性质”“这个字段占多少字节”。

comptime 章节已经解释 ordinary 如何利用契约，以及具体计算如何依赖输入。本轮不再投票这套阶段模型；要补的是类型接口提供哪些性质，哪些观察必须等到所需输入具备。

### Sized 不应成为“这个类型我已经完全算完了”的同义词

一个泛型定义可以依靠 T 满足 Sized 来检查操作，而不知道 T 最后有多少字节。反过来，一个类型依赖运行时对象，也不必因此尺寸可变：此前 NodeIndex 就是重要反例，其环境依赖不增加每个索引值的指针存储。

因此 Sized 的定义必须与“类型包含运行时依赖”“当前分析已拿到具体大小”分开。union 新确认的 Sized 要求，正好提供一个具体的使用入口。

### 反射应区分结构信息与布局信息

SOA 的既有设计需要取得输入类型的字段，再为字段构造相应存储。这说明结构观察与类型生成需要可连接，但并没有给出所有反射 API 的定稿。

建议本章先承诺信息的含义：字段名称、类型与声明顺序，和物理偏移、大小、对齐，各自描述什么。精确 API 名称、描述对象用列表还是映射、builder 有哪些方法，属于具体接口文档，本轮不要求作者拍板。

### 生成结果必须有可依赖的结构

类型被用于字段布局或生成代码后，如果还能保持同一个身份而改变字段结构，之前的布局结论、成员访问和代码就可能失效。这是用户可观察的一致性问题，不只是缓存实现细节。

第 8 题因此问“已经供程序使用的类型值是否还可改变结构”。它不质疑作者已确认的纯调用缓存，也不禁止构造类型之前逐步准备输入描述。

### 正式文档的内容分工

建议分别组织参数化类型与结构反射两篇，均保留七段骨架：Intro 用小例子建立区分；语法只列本篇用到的定义/应用；正式定义写可依赖的性质和观察条件；示例展示约束与反射用途；跨语言段在写入时按已确认行为查证；运行时引导说明类型信息如何决定表示；编译器引导说明如何依据契约检查并在输入具备后兑现布局。

Sized 可作为参数化篇的基础小节，并由 union、布局观察等章节引用。正式文件路径等内容收敛后再决定；本轮不创建 docs/ 占位，也不编写运行时反射系统。

### 5. 直接按值递归的类型，怎样判定布局能否成立？

```flurry
struct Link {
    next: *Link,
}

struct Loop {
    next: Loop,
}
```

- A. 按布局依赖区分：若指针自己的表示无需嵌入所指对象，Link 的字段不产生按值展开循环；Loop 这种必须先知道自身完整大小的按值循环拒绝。不会自动替它插入间接存储。
- B. 允许按值循环，由语言自动选择间接表示或其他递归表示。需要规定新增存储、访问与资源行为，不能仅当成布局优化。
- C. 普通声明一律禁止递归引用，包括指针间接引用；递归结构必须通过其他明确的构造入口表达。

建议答复：A。判断的是实例化后实际需要的布局依赖，不能只看到类型名字再次出现就拒绝，也不能依靠递归调用最终“也许停下来”。

我的理由：此规则给出实现引导的关键检查对象：一个字段的存储布局是否真的依赖另一个完整对象布局。参数化递归还可能产生不断变化的新实例；第一个例子的有限循环检查不能被写成解决了任意类型计算的终止性，这部分不新增全局终止保证。

### 6. 结构反射是否分开提供声明信息与物理布局信息？

- A. 分开。字段名称、声明顺序、字段类型与已有属性描述类型结构；偏移、大小、对齐描述具体布局，按各项观察所需的输入取得。声明顺序不自动等于物理排列顺序。
- B. 只在具体布局完整确定后提供整套反射信息；即使字段名字已知，也不承诺提前遍历结构。接口简单，但限制参数化分析能直接观察的内容。

建议答复：A。对结构观察与布局观察分别给出前提；当前只知道某种性质时，仍按已有 PTC 契约支持相应操作，不声称所有字段描述都已经具体化。

我的理由：SOA 转换需要的是源类型字段结构，而布局计算需要的是成员尺寸和目标规则。它们可能同时具备，也可能在不同输入到齐后才具备。反射返回对象的 API 形状留具体接口篇，本题只确认信息含义和观察条件。

具体场景：工具希望知道 Cell 声明了一个 value 字段，但尚未选择 T；另一个工具已经持有应用参数后得到的类型，要查询其字段。

## 三、我的内容判断

### 参数化章节应说明参数在类型中承担什么职责

带参数的数据定义可以公开自己的字段、约束和成员，但某个字段的具体布局仍依赖实参。读者需要区分“这个定义有一个 T 类型的字段”“T 满足某种布局性质”“这个字段占多少字节”。

### Sized 不应成为“这个类型我已经完全算完了”的同义词

一个泛型定义可以依靠 T 满足 Sized 来检查操作，而不知道 T 最后有多少字节。反过来，一个类型依赖运行时对象，也不必因此尺寸可变：此前 NodeIndex 就是重要反例，其环境依赖不增加每个索引值的指针存储。

### 反射应区分结构信息与布局信息

SOA 的既有设计需要取得输入类型的字段，再为字段构造相应存储。这说明结构观察与类型生成需要可连接，但并没有给出所有反射 API 的定稿。

建议本章先承诺信息的含义：字段名称、类型与声明顺序，和物理偏移、大小、对齐，各自描述什么。精确 API 名称、描述对象用列表还是映射、builder 有哪些方法，属于具体接口文档，本轮不要求作者拍板。

### 生成结果必须有可依赖的结构

类型被用于字段布局或生成代码后，如果还能保持同一个身份而改变字段结构，之前的布局结论、成员访问和代码就可能失效。这是用户可观察的一致性问题，不只是缓存实现细节。

我的理由：此规则给出实现引导的关键检查对象：一个字段的存储布局是否真的依赖另一个完整对象布局。参数化递归还可能产生不断变化的新实例；第一个例子的有限循环检查不能被写成解决了任意类型计算的终止性，这部分不新增全局终止保证。

其实从编译器实现可以看出来，norml_repr_query(Loop) -> norml_repr_query(Loop) -> norml_repr_query(Loop) -> ...，显然会循环依赖。同理可以简单推广到k步的循环发现。
而norml_repr_query(*Loop)却是不依赖norml_repr_query(Loop)的，因为所有指针位宽都跟usize一样。

### 6. 结构反射是否分开提供声明信息与物理布局信息？

- A. 分开。字段名称、声明顺序、字段类型与已有属性描述类型结构；偏移、大小、对齐描述具体布局，按各项观察所需的输入取得。声明顺序不自动等于物理排列顺序。
- B. 只在具体布局完整确定后提供整套反射信息；即使字段名字已知，也不承诺提前遍历结构。接口简单，但限制参数化分析能直接观察的内容。

建议答复：A。对结构观察与布局观察分别给出前提；当前只知道某种性质时，仍按已有 PTC 契约支持相应操作，不声称所有字段描述都已经具体化。

我的理由：SOA 转换需要的是源类型字段结构，而布局计算需要的是成员尺寸和目标规则。它们可能同时具备，也可能在不同输入到齐后才具备。反射返回对象的 API 形状留具体接口篇，本题只确认信息含义和观察条件。

### 7. 尚未应用参数的类型定义，是否也是直接可反射的对象？

具体场景：工具希望知道 Cell 声明了一个 value 字段，但尚未选择 T；另一个工具已经持有应用参数后得到的类型，要查询其字段。

- A. 普通类型反射针对类型值，包括按既有契约处理尚未具体求出的类型结果；未应用的定义入口另用定义/源码信息接口描述，不自动把它当作一个已经应用的类型。
- B. 同一套结构反射也直接接收未应用的参数化定义；返回的信息保留参数绑定关系。需明确模板字段类型指称哪些参数，不能当成普通具体类型使用。

建议答复：A。先把已存在的类型值观察接口写清；编辑器需要查看声明，不意味着该声明必须以同一类型参与所有普通反射操作。

我的理由：这里是反射对象的界限，不重问 normal form 与普通类型工厂结果的等价关系。若你已打算统一声明模板与应用后类型的反射，B 可以成立，但参数的指称关系必须成为公开契约。

### 8. 已经被程序使用的类型值，还能通过反射改变字段结构吗？

- A. 类型值一旦产生，其字段结构与影响布局的属性保持稳定；反射用于观察。需要改变结构时构造另一个结果，再按既有类型身份规则使用。
- B. 可以保持同一个类型身份并改变这些内容；语言必须规定原来的布局事实、已生成代码与实例如何受到影响。用户能观察到这种变化，不能只用“缓存失效”解释。

建议答复：A。输入描述可以在产生类型结果之前准备；得到并使用该类型后，字段、变体和布局属性不再原地改写。

我的理由：这是类型结构的一致性边界，不限制已确认的 impl/extend 按自身规则增加接口，也不把是否重新命中纯调用缓存当作类型形状变化的开关。原来 SOA 设计中的构造工具只是实现方式之一，不在本题固定 builder 生命周期或 API。
