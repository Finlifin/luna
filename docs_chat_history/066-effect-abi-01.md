## 对作者的完整回复

DRAFT — NOT CANONICAL：以下为本轮评估、候选设计与完整问题。内部执行图和类型记号不是 Flurry 表面语法，不引入库 API。

我读完了 nessa 的并发、异步效应、continuation 文档，也看了栈池与调度器的实现草图。**你的目标可以成立：同步 continuation 可以使用独立的栈池库，并发运行时再建立在同一套控制协议上。**关键是分别规定 handler 如何定位、剩余计算如何保存，以及谁决定何时恢复。

下面是候选方案；nessa 的设计用于理解意图，不直接成为 Flurry 的既定规则。

你列出的几种形态，可以整理成下面这张 ABI 地图：

| 形态 | handler 定位 | 控制转移 | 需要保存的状态 |
|---|---|---|---|
| 不恢复的错误处理 | 错误传播路径与匹配分支 | 退出失败计算，进入处理分支 | 错误载荷及沿途清理责任 |
| 可完全内联的效应 | 展开时确定 | caller、callee、handler 联合转成普通控制流 | 展开后仍存活的局部值 |
| evidence passing，无显式捕获 | evidence 指向处理入口 | 调用 handler，返回操作结果 | 普通调用状态及 handler 环境 |
| 动态查找，无显式捕获 | 查找当前有效处理上下文 | 找到入口后调用、返回 | 同上，另有动态处理上下文 |
| evidence passing，有捕获与恢复 | evidence 指向入口及限定边界 | 捕获到该边界，交给 handler | continuation、处理上下文、清理责任 |
| 动态查找，有捕获与恢复 | 动态找到入口及限定边界 | 同上 | 同上，另有查找所需状态 |
| nessa 式异步效应 | 以上某一种路由 | 启动子工作，交付 Future；等待时可能挂起 | 子工作状态、结果槽；挂起时的 continuation |

这里有两个需要精确区分的地方。

**第一，evidence passing 与 bubbling 并非完全互斥。**evidence 可以直接指出目标 handler，而控制转移仍通过逐层返回请求来完成。动态查找也可以只遍历 handler 链，找到以后直接调用，并不必展开调用栈。Generalized Evidence Passing 就将 evidence 路由与 yield bubbling 组合使用。因此我建议协议分别描述“定位入口”和“把控制交给入口”。[论文](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/08/genev-icfp21.pdf)

**第二，无显式 continuation 参数，只约束这次操作的处理方式。**它的 handler 仍可能请求外层的可挂起效应。因此，“这个入口直接返回”和“整条调用路径绝不挂起”必须分别记录；否则优化器会把仍需保存的调用状态消掉。

错误处理与完全内联两类可以各自保留专门的降码协议：前者约束错误交付和退出清理，具体采用带标签返回还是展开机制可以另定；后者承接你此前要求的 caller、callee、handler 联合展开。满足内联限制时，剩下的是局部变量、分支与跳转，无需在运行时构造独立 continuation。

对于其余几类，先固定一个共同的语义接口会比较稳妥。沿用现有 handler 文档中的记号：操作输入为 X、操作结果为 Y、主体结果为 A、整个处理结果为 B。下面是内部记号，不是新增 Flurry 语法或最终机器签名：

```text
直接处理：
    operation_handler(X) -> Y

捕获后处理：
    operation_handler(X, K) -> B
    resume(K, Y) -> B
```

**resume 的返回值是 B，这决定了 continuation ABI 不能只有“保存的栈指针”。**例如 handler 恢复主体，等主体完成后再修改结果，此时主体必须返回这一次 resume 的后继位置。ABI 至少还要表达恢复调用的返回关系。尾位置恢复可以消去这层返回关系，但不能要求所有恢复都在尾位置。

另外，路由标识必须区分完整的操作实例和同名 handler 的不同 occurrence。进入处理分支时使用该分支的外层效应上下文；deep resume 时恢复被捕获的处理上下文。动态查找链和 evidence 都必须遵守这条规则。

你最关心的栈池，可以从这里接入。

nessa 当前的 pool 将一批连续栈槽组织成 segment，并在 task 创建时领取栈槽；普通 continuation 的文档则描述复制帧、恢复时放回。这与草稿中的观察一致。但**池的分段扩容不等于调用栈按 prompt 分段**，仅将分配器换成 pool，还不能得到免复制的限定 continuation。[栈池实现](/tmp/flurry-effect-abi-nessa/engine/stack_pool/src/lib.rs)、[continuation 实现设想](/tmp/flurry-effect-abi-nessa/docs/dev/architecture.md:468)

我建议第一种池化后端采用“在限定边界进入独立栈”的办法：

1. 进入可能捕获 continuation 的控制域时，从 pool 取得栈槽，并在该栈上运行主体。只提供直接处理的边界无需因此领取新栈。
2. 主体发出捕获请求时，保存执行位置和必要机器状态，把该执行栈交给 continuation 持有；handler 在所选边界外运行。
3. 恢复时，消费这一次恢复权，重新接入保存的处理上下文，并把 Y 交到操作调用点，同时记录本次恢复应返回的位置。
4. 若再次挂起，产生代表新执行位置的恢复权。栈槽可以继续使用，无需每次 yield 都重新分配。
5. 主体结束或被放弃时，完成相应清理；相关引用和控制状态都不再使用该栈后，才把栈槽归还 pool。

这里的“控制域”是本方案的内部执行边界称呼，不建议为它新增关键字。

这一模型允许单线程的生产者、消费者同步轮流执行：库只需提供栈池和控制切换，调用方自己决定下一次恢复谁，无需任务队列、I/O 轮询器或并发运行时。

多层限定边界需要进一步处理。捕获到外层 prompt 时，可能要取走一串执行栈，并保存其中的 handler 边界；恢复以后，内层 handler 必须重新有效。因此第一版可以保证“不按存活栈字节数复制”，但不能仅凭使用 pool 就宣称任意深度的捕获、清理都是 O(1)。

**地址稳定性应该成为后端的明确契约。**Flurry 的操作参数可能指向被挂起主体的局部对象，主体内部也可能存在指向自身局部对象的指针。池化栈若保持地址不变，就能保留这些关系。若换成会移动帧的后端，则必须另行满足重定位条件。只复制字节再调整栈指针不足以维持这些关系。

协议可以分成以下几层；名称仅描述职责，尚不指定 trait 的公开名称：

| 协议职责 | 必须提供的保证 |
|---|---|
| handler 路由 | 取得正确 occurrence 的入口、环境及限定边界；维护分支与恢复各自的上下文 |
| continuation 控制 | 建立边界、保存与恢复执行位置、传递 Y 与 B、维护恢复的返回关系、执行放弃路径 |
| 栈与帧存储 | 分配、地址稳定性、容量边界、存活期与回收；可以使用 pool，也可以使用其他表示 |
| 并发调度 | 管理子工作、就绪与等待、结果发布、唤醒、取消及作用域退出 |

这样，evidence passing 与动态查找可以共用同一个 continuation 后端，同步与异步也可以共用同一个存储后端。

你要求 ABI 实现由协议提供，我建议把编译器与库的分工定在这里：**编译器认识控制转移的契约，库提供满足契约的表示和实现。**编译器需要知道哪些位置可能挂起、恢复后有哪些值仍有效、哪些资源需要清理，以及选定后端要求怎样的调用形式。pool 的布局、缓存、页管理和调度队列则由库决定。

普通 trait 方法本身不能让优化器理解一次任意的栈切换。因此协议底层仍需要受编译器识别的控制操作，或等价的、具有明确契约的降码入口。这与此前把 continuation 操作定位在 intrinsic 附近相容，也不要求语言内置一个固定的异步运行时。

另一个 ABI 问题会出现在函数值和独立编译处：某段代码已经按特定的挂起约定生成后，调用者不能只换一个 evidence 指针，就把它变成任意另一种栈表示。可选的处理方式包括按后端实例化、约定共同调用形式，或者提供明确的边界适配。适配不成立时，应在接入边界拒绝组合。

我倾向于让控制域的协议实例确定后端，并在编译该计算时落实相应约定。路由方式仍可独立选择。

nessa 的异步模型则可以放在这些协议之上。

我确认它的语义是：**发出 async effect 就创建子工作并返回 Future，await 才可能挂起当前工作。**Future 在这里保存结果的关联关系；工作不依赖 await 才启动。[nessa 异步效应设计](/tmp/flurry-effect-abi-nessa/docs/concurrency-and-async-algebraic-effect/async-algebraic-effect.md)

沿用这个意图，候选的执行关系可以是：

```text
发出异步操作
    → 路由到 handler
    → 并发协议登记子工作和结果槽
    → 调用者得到 Future，继续执行

等待结果
    → 已完成：交付结果
    → 未完成：通过可恢复效应交出当前 continuation
    → 结果发布：调度协议取得恢复权，安排继续执行
```

由此，等待、让出和作用域退出时的等待都可以建立在代数效应之上。运行时内部仍需要平台 I/O 和同步原语，但它们不必再引入一套与 continuation 无关的语言级挂起机制。非尾位置 resume 的返回关系，也可以用于让调度器在一段计算完成后重新取得控制。

有三项 nessa 的设计需要在迁入 Flurry 时细化。

**任务树、handler 上下文和 continuation 链应分别保存。**任务树记录谁负责等待、取消谁；handler 上下文记录当前能调用哪些处理入口；continuation 链记录恢复哪些计算。一个 task 内能安装多层 handler，所以任务树不能独自承担效应路由。子工作继承父级入口时，还要持有合法的环境依赖，不能靠访问父工作未来随时变化的“当前栈”来查找。

**结构化并发要约束 handler 环境的使用。**同一个 async handler 同时处理两个请求，可能同时访问自己的捕获。两个子工作都持有父作用域，并不能证明这些访问相容。协议必须通过环境的共享契约、显式复制、所有权转交或串行执行来满足资源规则；不能自动复制一个持有 Once 资源的环境。

**safe-point 只说明可以在哪些位置交出执行权，不自动证明可以在那里取消。**一个循环回边可能恰好位于数据结构不变量暂时尚未恢复的位置。调度切换与取消退出要分别约束：前者保存计算，后者还要完成允许的清理、释放依赖并交付取消结果。被挂起的工作也必须存在可执行的取消路径，不能等待它自行运行到下一个检查点。

结果到达、登记等待和取消之间，则需要一个明确的所有权交接协议，保证不会丢失唤醒，也不会让完成与取消各恢复一次同一个 continuation。这个状态协调属于并发协议，不应成为同步栈池的强制依赖。

与 Flurry 的资源系统相接时，我建议先立住两条边界：

- **恢复权与存储分别建模。**一个栈槽可以经历多次挂起，但每次产生的恢复权只能按其契约消费。不能因为两次挂起使用同一块内存，就重复使用旧 token。
- **放弃 continuation 必须处理其中尚存的资源责任。**操作参数可能仍引用这条栈，因此放弃还要考虑这些依赖。多次恢复也不能以复制栈字节来实现安全承诺：复制出来的两条计算可能消费同一份 Once 资源。

这与当前 [handler 文档](/home/fin/luna/docs/type/handlers.md)中的单次、不可逃逸基线有关；同时，[函数参数文档](/home/fin/luna/docs/functions/parameter-elaboration.md:68)明确 continuation 仍靠近 intrinsic，现有检查有限。我们不能直接从 nessa 的 continuation clone 用法推导 Flurry 已经具有对应的安全保证。

本轮我建议只先确定两个会影响整体形状的选择：

1. **continuation 后端在哪个范围内选定？**

   A. **按控制域选定（推荐）。**不同库可使用不同后端；计算需要按所选约定实例化，跨域组合需兼容或适配。  
   B. 按整个程序选定。独立编译和互操作较简单，但库很难局部选择自己的表示。  
   C. 每次捕获时动态选定。自由度更大，但所有相关代码必须预先满足共同的捕获约定，普通已编译调用栈不能无条件适配。

2. **第一版池化 continuation 协议要覆盖到哪一层生命周期能力？**

   A. **单次恢复，限制在仍存活的控制域内（推荐）。**允许同步驱动器或调度器暂存恢复权；作用域退出必须等计算结束或完成清理。这能先覆盖同步切换与结构化异步。  
   B. 单次恢复，但允许越过原控制域存活。需要把必要的环境、边界和资源依赖一起转成交付出去的所有权。  
   C. 第一版同时要求可复制、多次恢复。需要先定义被捕获资源、外部引用和清理责任的复制契约，栈池本身不能解决这些问题。

你也可以直接改写这两项的边界。
