## 二、我的总体判断

### 1. 现在最需要的是几套判断的边界

如果按文件名从“两级类型”一路写到“可达性”，很容易写出很多局部合理的章节，却无法判断一次调用究竟因为什么成立。

我建议先让整个类型系统回答六个具体问题：一个类型表达式是否成立；两种写法是否指同一类型；一个值能否用于给定的目标类型；当前操作有哪些可用能力；缺失的类型信息何时取得；运行时值需要携带什么信息。这里列的是文档需要回答的问题，不是发明六个新语言构造。

比如，把一个普通值交给可选类型参数，可能涉及构造包装；用一个受约束的类型参数调用方法，涉及命题证明；让延迟类型继续参与检查，涉及部分信息。若都叫“类型兼容”，就无法分别规定是否有运行时代价、是否可逆、能否传递，以及失败应该发生在哪里。

### 2. PTC 是连接操作与事实的框架，不应被写成能解决一切的求解器

comptime 主题已经确认：ordinary 可以先检查 requirement，再利用结果命题继续。类型主题接下来需要说明事实从哪里来、描述哪个对象、在哪些路径上有效，以及哪些类型关系能作为检查依据。

但不能由“所有 PTC 命题可执行”推出“所有命题在未知参数下都可证明”。可执行性保证具体输入具备后能进行相应计算；ordinary 的符号证明能力仍需要边界。也不能把一个纯函数的返回值契约自动当作该函数的完整数学定义展开。

我建议把“类型关系”“事实证明”“需要具体输入的求值”分别写清楚，然后说明它们怎样通过 query 依赖协作。无需要求实现有三套隔离的机器，更不应固定新 pass。

### 3. Any 的位置会决定其余章节的含义

备忘中的 Any 同时出现在 comptime 异构容器、延迟类型的占位与 runtime 函数的签名里。这三种位置不必有相同的运行时表示。

我目前最倾向的解释是：Any 描述当前掌握的类型信息不足；在 comptime 执行器中可以实际持有不同类型的值，在 ordinary 中按已知契约检查，在交付 runtime 实例前按该实例需要确定表示。它不自动等于“所有 runtime 值都有同一种动态盒子”。若作者另有 runtime Any，应明确它的包装与检查边界，而不是顺手从渐进类型理论带入。

这与“运行时依赖类型”也不同。一个结构的长度直到运行时才取得，仍可以有清楚的类型及受约束的布局访问方式；它不必因此成为 Any。

### 4. 类型身份必须早于类型工厂与缓存规范

同字段的两个结构是否相同、两次类型工厂调用是否得到同一类型、newtype 是否建立新身份，会直接影响 trait implementation、关联类型、coherence 和 query 缓存。

这些问题不能由编译器某次碰巧命中缓存来回答。应先定义可观察的类型身份，再让缓存遵守它。尤其不能把用户 Eq 对任意编译时值的比较，未经限制地提升成改变类型身份的权限。

### 5. 不要把所有“附加信息”都塞进一个限定类型演算

错误集合、代数效应、可达性依赖和捕获环境都可能出现在类型附近，但其含义不同：有的区分结果分支，有的描述控制转移，有的约束值在内存变化后还能否使用，有的决定一次操作从哪里取得额外输入。

可以共享语法和分析基础设施，但不能因此假定它们都按集合并集、同一种子类型规则或任意交换顺序组合。特别是“可达性只影响检查”与“依赖值必须在运行时可取得”也不能混为一谈。

### 6. data family 值得进入总图，但现在不能先给它套现成理论

TODO-data-family.md 的 C ABI、ECS、数据库与宿主语言例子，让我看到的是：作者希望通过不同的编译时构造入口定义数据类型，并用相同的声明方式接回语言。

这可能只是类型工厂的库级应用，也可能意味着不同数据表示家族具有不同的构造、布局和操作契约。两者对类型系统开放面的要求差很多。仅凭文件名，不能认定它就是某种外部语言的 type family，也不能认定每个例子都需要编译器插件或特殊关键字。

## 四、沿用的已确认基线

- comptime/runtime 是执行阶段，normalization/instantiation 是编译过程；类型是编译时计算的输入和结果。
- ordinary/loose 的边界由构造决定；未知输入不会自动使 ordinary 变成 loose。
- ordinary 检查操作 requirement，操作的结果命题可以支持后续检查；不必等待每项计算取得具体结果。
- PTC predicate 具有可执行语义；PTC assumes 在实例化直接执行。PTC 与 runtime 程序验证不能混同，也不开放任意用户逻辑公理。
- defer 的已确认用途、Any 占位与 refinement 命题提取沿用 comptime 结论；本轮讨论精确的类型关系，不重新投票是否保留这些机制。
- pure 的信任承诺不是用户定义逻辑公理的接口；参与缓存的值需要相应 comptime Eq/Hash。
- runtime 实际值不能被编译时直接读取；quoted 表示不等于已经取得未来的内存内容。
- Splice 方法是带 comptime 输入的普通 runtime 方法，两相与 proxy 沿用刚完成的文档。
- 不引入同名函数重载；trait 两相共享 coherence。这个结论不直接规定所有词法遮蔽规则。

## 五、逐题预填答复

### 1. 是否按上面的职责分层组织类型主题？

- A. 按语义关系和系统接口分层，再把现有文件映射进去。可以先暴露交叉依赖，文件路径暂不定。
- B. 保持现有文件顺序，逐篇补完再统一总述。启动快，但容易在后面的限定/依赖章节重开前面规则。

建议答复：A。先确定每层需要回答的问题与已知依赖，不立即重命名或迁移文件。每层将来都要有对用户的规则和对实现者的算法契约，但两种受众分段。

我的理由：目录目前把阶段、关系、类型构造和资源约束混在同一层级。先分类并不要求这些机制在实现中完全独立，而是避免同一个问题在多章得到不同答案。

### 2. 是否区分类型相等、子类型、一致性、转换与命题成立？

- A. 区分这些判断及其结果；可共享算法，但必须说明何时有代码转换、何时仅有证明。
- B. 对用户只有一个“可以用于目标类型”的判断；其他关系全部隐藏在实现中。界面少，但推导、代价和错误解释更难精确。

建议答复：A。类型相等关心是否同一个类型；子类型关心已有值能否按另一个类型使用；渐进一致性描述当前已知信息是否相容；转换描述如何产生或解释目标值；PTC 证明说明当前操作所需条件是否成立。它们之间如何衔接另行定义，不先把任何一项等同于另一项。

我的理由：例如，一个转换可以分配或失败，却不能由此把两边类型认定为相等。未知信息彼此相容也不能自动变成可传递的类型相等关系。这是全貌中最先要钉住的边界。

### 3. 命名声明、结构和别名怎样决定类型身份？

- A. 以声明身份为有名类型的基础，typealias 指称原类型，newtype 建立新身份；匿名/计算生成类型另按其构造契约判断。
- B. 默认按结构确定身份，只有 newtype 强制区别。匿名构造自然，但结构变化更容易影响相等和实现选择。
- C. 所有类型身份都由其所属构造器或 data family 定义，语言只规定最小一致性要求。开放面大，但普通声明也需要明确所属规则。

建议答复：A 作为普通声明的候选基线，data family 的扩展点再由第 18 题限定。相同字段、相同布局和相同可用方法都不足以单独推出两个有名类型相等。别名透明也不自动意味着 newtype 的转换、成员转发或布局已经确定。

我的理由：这能先稳定用户能观察的类型边界，避免提前要求所有类型都按结构展开比较。现有 newtype/alias 只有语法和用例，尚不能把这项建议记成已有语义。

### 4. 相同输入的类型工厂调用，是否必须得到相同类型身份？

- A. 普通可复用的编译时类型构造，按构造定义身份和语义输入稳定确定结果；不同 newtype 声明仍是不同声明。
- B. 每次执行构造都可以产生新类型身份；缓存与纯函数承诺必须显式考虑这种生成行为。
- C. 两种都存在，由构造器契约明确区分。表达力更多，需要保证调用者能识别其身份行为。

建议答复：A 作为本轮最小方案。不能让一次物理缓存命中与一次重新执行决定两个类型是否相等；实际影响身份的输入必须进入语义依赖。若要保留生成新身份的计算，再单独扩展 C，不暗中让所有工厂都具有这种行为。

我的理由：类型身份会被后续 trait、关联类型、类型模式和 ABI 使用。这里讨论的是对用户可见的同一性，不是要求编译器采用某种 interning 或哈希算法。

### 5. Any 的几个使用场景是否有同一种 runtime 表示？

材料边界：docs/type/refined-type.md 第 3 行写“鸭子类型不可做返回值”；comptime 文档则已允许延迟结果以 Any 及契约参与检查。它们可能适用于不同层，不直接判定为互斥。

- A. Any 首先表达未知类型信息；comptime 中可持有异构值，ordinary 中可作受契约约束的占位，但不自动提供统一 runtime 盒子。
- B. Any 也明确是通用 runtime 动态值类型，可以独立存储、返回并动态检查。需要定义包装、资源管理及失败行为。
- C. Any 只允许在 comptime，runtime 定义里不得以其作源语言签名；延迟类型的内部占位与它另行区分。

建议答复：A。对“不能作返回值”的原文先限定问题：拒绝的是最终无法确定表示的返回，还是连实例化后可确定的返回也禁止？我的建议是允许后者的描述能力，拒绝凭 Any 隐式创造 runtime 动态包装。这个细化待你确认，不直接删旧句。

我的理由：comptime 异构容器、ordinary 的未知信息、runtime 擦除值是三个问题。把它们一次合并会同时把运行时布局和类型失败时机带进来。

### 6. Any、草稿中的 any、推导空缺及被隐藏的类型如何区分？

- A. 区分未知类型信息、待求解变量、模式通配与明确隐藏的类型；分别给出后续操作可依赖什么。
- B. 统一成一种未知对象，按使用位置再决定约束和执行行为。实现入口少，但很难说明共享与独立未知量。

建议答复：A。Any 不默认与一次待求解的类型变量相同；草稿里的小写 any 暂不当作新增运行时字面量。对同一个未知量的重复引用可能需要保持相关性，两个通配位置则未必。若提供隐藏类型的封装，它还需要边界内可以使用的契约，不能仅靠 unknown 代替。

我的理由：备忘对 any 写了相容关系，但没有规定它是不是能存储、比较、进入 query 键的真实值。本轮先确定概念分类，不发明 existential 或 hole 关键字。

### 7. Refinement 描述的对象与失败阶段怎样划界？

- A. 同一类“类型附带条件”的表述，必须另外标明条件依赖什么、在哪个阶段验证；PTC refinement 先沿用编译时机制。
- B. 所有 refinement 都保证在 normalization 证明；未知条件直接拒绝。简单但与已有实例化检查方向冲突。
- C. 所有 refinement 都可转成 runtime 检查。需要扩展运行时语义，不能视为 comptime 结论的自然延伸。

建议答复：A。先把 PTC 中的类型性质、对具体值的条件、以及依赖内存状态的条件分清。已有 refinement 约束在 instantiation 执行的规则继续成立；关于 runtime 数据的条件不能被误写成编译器会提前读取该值。某项事实若依赖可变内容，还要说明它绑定的是哪次值或状态。

我的理由：否则后续可达性和运行时依赖类型会把“已证明过一次”错误理解为“永远成立”。这轮先要求标出接口，不制定完整失效算法。

### 8. Refinement 的两种草稿表面形式如何处理？

材料差异：023 作者答复使用前缀形式；docs/type/refined-type.md 使用后缀形式；grammar/syntax 尚未给出 refinement 产生式。以下是候选产生式，不是已定语法。

- A. 沿用作者答复中的前缀：`refinement_type -> refines { expr } expr`。符合类型表达式偏前缀的现有风格。
- B. 沿用章节草稿的后缀：`refinement_type -> expr refines { expr }`。贴近“对一个类型添加条件”的阅读顺序，但需处理嵌套。
- C. 本轮只确认 refinement 的职责，两种写法都保留为草稿，进入其专轮再定。

建议答复：C。这轮构建全貌，不需要为了画图就提前确定语法。如果你希望现在固定形式，我倾向 A，依据是作者之前的实际答复；不能仅因为那一条更晚就擅自覆盖另一文件。

我的理由：量化、绑定对象及 refinement 中的“自身”如何指称尚未统一，先选一个漂亮的括号次序并不能解决这些对象问题。

### 9. 类型构造器参数、全称量化与 higher-rank 的范围？

材料边界：docs/type/refined-type.md 第 18 行称“放弃 higher-ranked types”；grammar/syntax 存在 `forall_type -> forall<parameter*> expr` 和 `for_type -> for<parameter*> expr`。存在这两个产生式并不自动说明任意嵌套的 higher-rank 已被支持。

- A. 先区分参数化定义/类型构造器的传递，与值级函数参数内部的全称量化；后者逐位置决定是否支持。
- B. 直接支持全称类型在任意类型位置嵌套，并承担相应检查和注解规则。
- C. 仅保留定义端参数化，所有进一步的多态值与类型构造器参数都暂不开放。边界小，但可能限制已有类型工厂方向。

建议答复：A。保留编译时函数和类型构造的已确认基础；不要从“类型能作为值”推导出任意多态值都成立，也不要从一句旧的 higher-rank 禁令推出类型构造器完全不能作为输入。需要分别列出允许的量化位置，才知道旧句的真正范围。

我的理由：这是 Type、comptime 函数与普通函数类型相接的位置，不能用一个“支持/不支持泛型”的开关概括。

### 10. 类型推导的默认职责边界？

- A. 以局部推导和期望类型检查为主；需要时依据显式签名、子句及已知 comptime 输入继续检查。
- B. 默认追求全程序推导，通过跨定义约束反推接口。注解可能减少，但与开放定义、增量检查及诊断位置有较大张力。
- C. 每个绑定都要求完整类型注解。可控但损失现有局部推导使用方式。

建议答复：A。签名负责提供接口，表达式可以从局部环境合成类型，也可以接受期望类型的约束；子句参数推导不得靠一次任意求值试错来选结果。剩余未知如何等待，仍遵循 ordinary/loose 与 defer 的规则。

我的理由：这适合先给 C 背景读者可预测的注解边界。双向检查可作实现参考，但本轮不承诺完整算法、主类型性质或“所有省略都必能推断”。

### 11. 不同分支的结果怎样汇合？

- A. 先使用已有期望类型和已确认转换规则；没有共同依据就要求注解或报错，不自动创造匿名联合类型。
- B. 自动求一个公共上界，必要时生成联合、动态包装或新的 refinement 类型。表达力高，需要先定义上界是否唯一及运行时表示。
- C. 所有分支必须首先得到相同类型，完全不利用期望类型转换。容易解释，但可能过度限制 option/error 的自然构造。

建议答复：A。ordinary 分支检查、inline 实例化选支和普通 runtime 分支汇合要分别说明，不能用“最后只选一支”取消定义端规则。具体可用转换由第 12–14 题决定。

我的理由：Any 不应成为把不相容分支悄悄合并的兜底，更不能由编译器临时包装后改变用户可观察的资源与布局行为。

### 12. 普通值进入 option/error，是子类型还是构造转换？

来源：docs/type/prompt.fl 的 Option 段明确写“不知道是否应该表达为子类型关系”，后面又给错误集合的包含关系。

- A. 先作为受控的注入/构造规则；独立讨论是否还存在子类型关系。
- B. 统一表达为子类型，并明确其对传递性、变型、推导与表示的影响。

建议答复：A。一个成功值可以进入某种结果包装，并不足以证明在所有类型上下文中都能把源类型换成目标类型。错误集合扩大、成功值注入和去掉空错误限定也应分别陈述。

我的理由：这样能先解释用户程序怎样构造值，不预先把所有方便写法扩张成通用类型关系。

### 13. option/error/effect/reachability/closure 是否共享一套组合规则？

- A. 共享限定的表面组织，但各限定分别给出嵌套、相等、引入/消除和相互作用规则。
- B. 统一为通用集合限定演算，所有限定按同一组合律处理。简洁，但必须证明各种对象确实能共享那些律。

建议答复：A。备忘中的 error/effect 集合合并等式作为候选单独审阅，不类推到 option、可达性或闭包环境。限定的交换、幂等、空集合消去都需要各自依据；尤其不同的失败/控制流组合不能仅因书写接近就相等。

我的理由：这是避免“每篇限定类型章都悄悄带一套不兼容子类型关系”的关键。先做一张组合表，比直接制定万能 normalization 规则稳妥。

### 14. 复合类型的变型先怎么确定？

- A. 根据操作契约和可变性分别建立；在无法证明替换安全前，不自动把成员关系提升为整个容器关系。
- B. 所有复合类型默认随参数协变，再对写操作添加例外。使用方便，但例外可能穿透指针和开放方法。
- C. 所有参数化类型永远不变。保守，但会限制本可安全表达的只读使用。

建议答复：A。先问容器提供的是读取、写入、消耗还是其他能力，再决定哪些方向可替换。函数输入/输出、错误集合和可达性集合也不直接套同一变型规则。

我的理由：这不是向 Flurry 塞一种借用体系，而是要求类型替换保持已有操作契约。具体变型规则可以在对应类型章节中逐项闭合。

### 15. Trait 要求、结构能力与关联类型如何进入核心关系？

- A. trait 满足性是操作能力的证据；关联类型由适用 implementation 或其契约确定；结构能力与类型身份分别判断。
- B. 把“具有相同方法”作为类型相等或普遍子类型的依据，trait 主要是这一结构关系的名字。

建议答复：A。同一类型可以满足多个 trait，而这不让它变成多个相等的类型。开放类型的关联结果可以先通过契约参与检查，但具体结果需要何时确定仍依已有阶段规则。草稿里查询“是否有某方法”的形式先当结构能力提案，不据此宣布结构类型系统已存在。

我的理由：它能沿用 PTC 已确认的操作视角，又避免把成员查找、implementation 匹配和类型相等塞进同一个判断。

### 16. 孤儿原则、extend 与开放定义的全局范围如何纳入本轮？

材料：docs/traits/index.md 声称 impl 受包级孤儿限制、extend 可以绕过且局部可见；comptime 文档只确认共享 coherence、静态起点和 loose 整体检查，没有给出完整跨包集合。

- A. 本轮只保留已确认的 coherence 契约；上述包级与局部扩展细则单列待审，交给 trait/模块联合主题。
- B. 将现有 trait 章节这一整套规则作为继续设计的基线，并接受它对跨模块类型身份和方法可用性的影响。

建议答复：A。不能因为现成章节写得肯定，就自动替作者确认孤儿原则和命名扩展 API。类型全貌需要一个“此处依赖可用 implementation 集合”的接口，不需要在这一轮完整定模块系统。

我的理由：这不是重新追问两相是否共享 coherence，而是防止把未审过的包级政策当作这条已确认结论的组成部分。

### 17. 动态 trait 值首先承诺什么？

材料：docs/traits/index.md 直接写“数据指针 + vtable 指针”；closure-type.md 又说某些带动态依赖参数的 implementation 不能形成 trait object。这是适用范围需要接合，不是假定二者必然矛盾。

- A. 先规定它隐藏什么类型信息、仍能调用哪些操作，以及需要哪些环境；表示/布局按其接口类别另定。
- B. 所有动态 trait 值统一为固定两指针表示，环境只能通过该表示所允许的方式取得。
- C. 类型第一版暂只描述静态 trait 使用，将动态包装全部独立成后续主题。

建议答复：A。当前可以保留动态接口这个构造，但不要把任何实现了 trait 的依赖类型都默认可擦除。若某操作需要被隐藏的 runtime 环境，必须能通过实际值或调用环境取得；具体对象可用性条件留专轮。

我的理由：可调用能力与物理布局是相关但不同的契约。拿一个常见实现布局提前回答所有问题，会误判依赖类型能否跨接口传递。

### 18. data family 是库级工厂，还是类型系统的扩展边界？

来源：docs/type/user-defined-types/TODO-data-family.md 用不同构造入口生成 C ABI、ECS、数据库、宿主语言类型，再以 newtype 声明接入。

- A. 这些首先是返回 Type 的编译时工厂；核心类型规则保持统一，各入口提供具体构造契约。
- B. 核心明确支持多个数据表示家族，各家族决定布局、构造或操作契约，语言规定共同的跨家族边界。
- C. 每种家族都允许扩展类型相等、子类型或推导规则。开放面最大，需要为混合使用另建一致性条件。

建议答复：A 作为最小解释，同时在总图保留升级到 B 的位置。先看普通 Type 结果能否表达你需要的布局和接口；不要仅因调用入口不同就引入新种类的类型相等。C 不作为默认候选，除非你的目标就是可扩展类型逻辑。

我的理由：这里真正要问的是“工厂产物由谁定义语义”，不是是否喜欢一套 DSL。若你倾向 B，它将改变第 3–4 题的分工，应该优先改这一题。

### 19. 运行时依赖类型先保留什么范围？

来源：prompt.fl 的 Continuation 按运行时长度组织后续字段，并明确写“还没设计好”。它是设计方向，不是已有完整布局规则。

- A. 保留这种表达力作为目标，要求依赖值有明确的取得位置，布局访问与输入变化的契约可检查；本轮不补全通用演算。
- B. 初期只允许依赖在对象构造时取得、此后保持稳定的输入。检查更简单，但改变可用场景。
- C. 暂不接受运行时依赖类型，把可变长度数据全部表示为显式描述符及普通容器。实现边界小，但明显缩减草稿目标。

建议答复：A。不能由编译时类型计算自动读取 runtime 长度；可以在编译时生成使用该长度的布局访问程序。长度是否可修改、修改如何影响已有引用是该类型与内存接口的契约，不把它推迟成“实现自然会处理”。

我的理由：先承认“类型知道如何使用依赖值”与“类型检查时已经知道依赖值”不同，就能把布局表达力和阶段边界接起来，而无需现在定完整内存模型。

### 20. 闭包、依赖上下文与 CMTT 是否是一种实体？

材料：closure-type.md 第 3 行写捕获“不影响主类型的内存布局”，第 41 行把 Ref 的依赖表示成包有 T 的闭包类型；而该 Ref 自身还含有 index 字段。这里可能是在展示附加上下文，也可能真想改写值的承载类型，不能直接照抄成等式。

- A. 先分别定义函数值捕获环境、依赖类型所需环境、CMTT 代码上下文，再讨论哪些表示或规则能共享。
- B. 统一为一种上下文携带类型，所有捕获、依赖与代码引用均由同一套构造解释。

建议答复：A。尤其将“不影响布局”限定为能够从外层对象或调用环境取得所需信息的情形；若一个值脱离那个环境仍可独立使用，相关信息必须仍可取得。这里不强制它存到每个元素内，但不能承诺信息在所有位置都不占任何地方。Ref 的 index 与依赖环境也不能因提到元素类型 T 而消失。

我的理由：先区分语义对象，比先发明统一包装符号更能保护这项设计。是否具有零额外布局，应该从完整的使用与传递契约得到，而不是作为所有闭包类型的口号。

### 21. 可达性与 memory effect 在类型主题中负责哪一层？

- A. 类型侧定义值依赖哪些对象/区域、哪些操作要求仍然有效；内存侧定义操作怎样改变对象、区域与关系，再据此影响可用事实。
- B. 把全部内存图、赋值、移动和销毁状态直接合进普通类型相等及推导关系。
- C. 可达性只作诊断元数据，不影响程序操作是否合法。

建议答复：A。一个类型及其可用性质需要能引用必要的依赖，但“两个类型相等”不应因此隐含“它们在每一时刻有相同的内存状态”。outcomes 和 memory view 在本轮只保留输入/输出接口，具体集合代数、路径失效和递归传播算法留内存主题。

我的理由：这能接住备忘中 Vec 重分配、不同索引和嵌套容器的场景，又不把整套内存管理强塞进基础类型推导。memory effect 与 algebraic effect 继续明确分开。

### 22. Once/Clone/Copy/Drop 的现有文字是否可直接作本主题公理？

材料：memory-management/once-clone-copy.md 写 Clone 为“完全独立”的深拷贝，并给出整个能力层次；其他草稿仍在探索拥有/非拥有指针和可达性组合。这些不是从语法或 comptime 结论就能推出的。

- A. 本轮只确认类型系统需要资源使用与销毁契约接口；具体能力层次和 Clone 等规则在资源专题逐项审阅。
- B. 将现有资源章节逐条作为已接受基线，类型主题直接据此推导复合类型规则。

建议答复：A。分清值的类型、使用次数约束、复制操作和销毁责任；不要在全貌阶段替作者再确认一套类似其他语言的所有权模型。已有明确确认仍保留，未核定的“深拷贝”“拥有者唯一”等强说法不能仅凭文档语气升格。

我的理由：类型组合确实依赖资源契约，但本轮只需规定必须问哪些问题，不需要立即决定每个容器或指针如何实现它。

### 23. 静态失败、运行时检查和安全等级如何接合？

材料差异：basics/primitives.md 的指针段写“直接解引用和算术操作属于 unsafe”；memory-management/pointers.md 又描述在 normal 中经可达性分析使用指针。需要确认前者是否在说未经证明的访问，不能私自选边。

- A. 按检查对象与阶段分类：ordinary 必检项静态解决；comptime 延迟项在实例化执行；runtime 依赖与具体指针操作按其明确的安全契约处理。
- B. 只要静态证明失败就自动插入 runtime 检查。使用简单，但改变 ordinary 承诺，也需要为全部证明命题提供可监测对象。
- C. ordinary 中所有指针解引用都要求 unsafe，即使可达性信息足够；相应收紧指针章节。

建议答复：A。倾向将指针问题按“其安全条件是否已被相应机制满足”区分，而非仅看操作符；这是待你确认的候选解释。不能把求解器 unknown 一律变成 runtime trap，更不能一律视为 UB。normal/unsafe/verified 与 ordinary/loose 的职责也要分别写清。

我的理由：不同失败归属直接决定调用接口。这里先建立分类表，避免某个 later type 章为了方便，悄悄改变基础检查何时完成的承诺。

### 24. 下一轮从哪里开始收敛？

- A. 从类型身份、关系与 Any 入手，先做第 2–7 题的最小共同定义，再进入推导与量化。
- B. 从 data family/newtype 与用户定义类型入手，先看构造目标，再反推核心关系。

## 二、我的总体判断

### 1. 现在最需要的是几套判断的边界

如果按文件名从“两级类型”一路写到“可达性”，很容易写出很多局部合理的章节，却无法判断一次调用究竟因为什么成立。

我建议先让整个类型系统回答六个具体问题：一个类型表达式是否成立；两种写法是否指同一类型；一个值能否用于给定的目标类型；当前操作有哪些可用能力；缺失的类型信息何时取得；运行时值需要携带什么信息。这里列的是文档需要回答的问题，不是发明六个新语言构造。

比如，把一个普通值交给可选类型参数，可能涉及构造包装；用一个受约束的类型参数调用方法，涉及命题证明；让延迟类型继续参与检查，涉及部分信息。若都叫“类型兼容”，就无法分别规定是否有运行时代价、是否可逆、能否传递，以及失败应该发生在哪里。

### 2. PTC 是连接操作与事实的框架，不应被写成能解决一切的求解器

comptime 主题已经确认：ordinary 可以先检查 requirement，再利用结果命题继续。类型主题接下来需要说明事实从哪里来、描述哪个对象、在哪些路径上有效，以及哪些类型关系能作为检查依据。

但不能由“所有 PTC 命题可执行”推出“所有命题在未知参数下都可证明”。可执行性保证具体输入具备后能进行相应计算；ordinary 的符号证明能力仍需要边界。也不能把一个纯函数的返回值契约自动当作该函数的完整数学定义展开。

我建议把“类型关系”“事实证明”“需要具体输入的求值”分别写清楚，然后说明它们怎样通过 query 依赖协作。无需要求实现有三套隔离的机器，更不应固定新 pass。

### 3. Any 的位置会决定其余章节的含义

备忘中的 Any 同时出现在 comptime 异构容器、延迟类型的占位与 runtime 函数的签名里。这三种位置不必有相同的运行时表示。

我目前最倾向的解释是：Any 描述当前掌握的类型信息不足；在 comptime 执行器中可以实际持有不同类型的值，在 ordinary 中按已知契约检查，在交付 runtime 实例前按该实例需要确定表示。它不自动等于“所有 runtime 值都有同一种动态盒子”。若作者另有 runtime Any，应明确它的包装与检查边界，而不是顺手从渐进类型理论带入。

这与“运行时依赖类型”也不同。一个结构的长度直到运行时才取得，仍可以有清楚的类型及受约束的布局访问方式；它不必因此成为 Any。

### 4. 类型身份必须早于类型工厂与缓存规范

同字段的两个结构是否相同、两次类型工厂调用是否得到同一类型、newtype 是否建立新身份，会直接影响 trait implementation、关联类型、coherence 和 query 缓存。

这些问题不能由编译器某次碰巧命中缓存来回答。应先定义可观察的类型身份，再让缓存遵守它。尤其不能把用户 Eq 对任意编译时值的比较，未经限制地提升成改变类型身份的权限。

### 5. 不要把所有“附加信息”都塞进一个限定类型演算

错误集合、代数效应、可达性依赖和捕获环境都可能出现在类型附近，但其含义不同：有的区分结果分支，有的描述控制转移，有的约束值在内存变化后还能否使用，有的决定一次操作从哪里取得额外输入。

可以共享语法和分析基础设施，但不能因此假定它们都按集合并集、同一种子类型规则或任意交换顺序组合。特别是“可达性只影响检查”与“依赖值必须在运行时可取得”也不能混为一谈。

### 6. data family 值得进入总图，但现在不能先给它套现成理论

TODO-data-family.md 的 C ABI、ECS、数据库与宿主语言例子，让我看到的是：作者希望通过不同的编译时构造入口定义数据类型，并用相同的声明方式接回语言。

这可能只是类型工厂的库级应用，也可能意味着不同数据表示家族具有不同的构造、布局和操作契约。两者对类型系统开放面的要求差很多。仅凭文件名，不能认定它就是某种外部语言的 type family，也不能认定每个例子都需要编译器插件或特殊关键字。

## 四、沿用的已确认基线

- comptime/runtime 是执行阶段，normalization/instantiation 是编译过程；类型是编译时计算的输入和结果。
- ordinary/loose 的边界由构造决定；未知输入不会自动使 ordinary 变成 loose。
- ordinary 检查操作 requirement，操作的结果命题可以支持后续检查；不必等待每项计算取得具体结果。
- PTC predicate 具有可执行语义；PTC assumes 在实例化直接执行。PTC 与 runtime 程序验证不能混同，也不开放任意用户逻辑公理。
- defer 的已确认用途、Any 占位与 refinement 命题提取沿用 comptime 结论；本轮讨论精确的类型关系，不重新投票是否保留这些机制。
- pure 的信任承诺不是用户定义逻辑公理的接口；参与缓存的值需要相应 comptime Eq/Hash。
- runtime 实际值不能被编译时直接读取；quoted 表示不等于已经取得未来的内存内容。
- Splice 方法是带 comptime 输入的普通 runtime 方法，两相与 proxy 沿用刚完成的文档。
- 不引入同名函数重载；trait 两相共享 coherence。这个结论不直接规定所有词法遮蔽规则。

### 2. 是否区分类型相等、子类型、一致性、转换与命题成立？

- A. 区分这些判断及其结果；可共享算法，但必须说明何时有代码转换、何时仅有证明。
- B. 对用户只有一个“可以用于目标类型”的判断；其他关系全部隐藏在实现中。界面少，但推导、代价和错误解释更难精确。

建议答复：A。类型相等关心是否同一个类型；子类型关心已有值能否按另一个类型使用；渐进一致性描述当前已知信息是否相容；转换描述如何产生或解释目标值；PTC 证明说明当前操作所需条件是否成立。它们之间如何衔接另行定义，不先把任何一项等同于另一项。

我的理由：例如，一个转换可以分配或失败，却不能由此把两边类型认定为相等。未知信息彼此相容也不能自动变成可传递的类型相等关系。这是全貌中最先要钉住的边界。

### 3. 命名声明、结构和别名怎样决定类型身份？

- A. 以声明身份为有名类型的基础，typealias 指称原类型，newtype 建立新身份；匿名/计算生成类型另按其构造契约判断。
- B. 默认按结构确定身份，只有 newtype 强制区别。匿名构造自然，但结构变化更容易影响相等和实现选择。
- C. 所有类型身份都由其所属构造器或 data family 定义，语言只规定最小一致性要求。开放面大，但普通声明也需要明确所属规则。

建议答复：A 作为普通声明的候选基线，data family 的扩展点再由第 18 题限定。相同字段、相同布局和相同可用方法都不足以单独推出两个有名类型相等。别名透明也不自动意味着 newtype 的转换、成员转发或布局已经确定。

我的理由：这能先稳定用户能观察的类型边界，避免提前要求所有类型都按结构展开比较。现有 newtype/alias 只有语法和用例，尚不能把这项建议记成已有语义。

### 4. 相同输入的类型工厂调用，是否必须得到相同类型身份？

- A. 普通可复用的编译时类型构造，按构造定义身份和语义输入稳定确定结果；不同 newtype 声明仍是不同声明。
- B. 每次执行构造都可以产生新类型身份；缓存与纯函数承诺必须显式考虑这种生成行为。
- C. 两种都存在，由构造器契约明确区分。表达力更多，需要保证调用者能识别其身份行为。

建议答复：A 作为本轮最小方案。不能让一次物理缓存命中与一次重新执行决定两个类型是否相等；实际影响身份的输入必须进入语义依赖。若要保留生成新身份的计算，再单独扩展 C，不暗中让所有工厂都具有这种行为。

我的理由：类型身份会被后续 trait、关联类型、类型模式和 ABI 使用。这里讨论的是对用户可见的同一性，不是要求编译器采用某种 interning 或哈希算法。

### 5. Any 的几个使用场景是否有同一种 runtime 表示？

材料边界：docs/type/refined-type.md 第 3 行写“鸭子类型不可做返回值”；comptime 文档则已允许延迟结果以 Any 及契约参与检查。它们可能适用于不同层，不直接判定为互斥。

- A. Any 首先表达未知类型信息；comptime 中可持有异构值，ordinary 中可作受契约约束的占位，但不自动提供统一 runtime 盒子。
- B. Any 也明确是通用 runtime 动态值类型，可以独立存储、返回并动态检查。需要定义包装、资源管理及失败行为。
- C. Any 只允许在 comptime，runtime 定义里不得以其作源语言签名；延迟类型的内部占位与它另行区分。

建议答复：A。对“不能作返回值”的原文先限定问题：拒绝的是最终无法确定表示的返回，还是连实例化后可确定的返回也禁止？我的建议是允许后者的描述能力，拒绝凭 Any 隐式创造 runtime 动态包装。这个细化待你确认，不直接删旧句。

我的理由：comptime 异构容器、ordinary 的未知信息、runtime 擦除值是三个问题。把它们一次合并会同时把运行时布局和类型失败时机带进来。

### 6. Any、草稿中的 any、推导空缺及被隐藏的类型如何区分？

- A. 区分未知类型信息、待求解变量、模式通配与明确隐藏的类型；分别给出后续操作可依赖什么。
- B. 统一成一种未知对象，按使用位置再决定约束和执行行为。实现入口少，但很难说明共享与独立未知量。

any描述任意comptime值（某些使用场景下还用来逃逸runtime dependent clause param），而Any仅描述任意类型，前者是后者的超集。而对于comptime来说，它们也都是独立的值，可以相容其它值的值

### 7. Refinement 描述的对象与失败阶段怎样划界？

- A. 同一类“类型附带条件”的表述，必须另外标明条件依赖什么、在哪个阶段验证；PTC refinement 先沿用编译时机制。
- B. 所有 refinement 都保证在 normalization 证明；未知条件直接拒绝。简单但与已有实例化检查方向冲突。
- C. 所有 refinement 都可转成 runtime 检查。需要扩展运行时语义，不能视为 comptime 结论的自然延伸。

建议答复：A。先把 PTC 中的类型性质、对具体值的条件、以及依赖内存状态的条件分清。已有 refinement 约束在 instantiation 执行的规则继续成立；关于 runtime 数据的条件不能被误写成编译器会提前读取该值。某项事实若依赖可变内容，还要说明它绑定的是哪次值或状态。

我的理由：否则后续可达性和运行时依赖类型会把“已证明过一次”错误理解为“永远成立”。这轮先要求标出接口，不制定完整失效算法。

### 8. Refinement 的两种草稿表面形式如何处理？

- B. 沿用章节草稿的后缀：`refinement_type -> expr refines { expr }`。贴近“对一个类型添加条件”的阅读顺序，但需处理嵌套。

### 9. 类型构造器参数、全称量化与 higher-rank 的范围？

材料边界：docs/type/refined-type.md 第 18 行称“放弃 higher-ranked types”；grammar/syntax 存在 `forall_type -> forall<parameter*> expr` 和 `for_type -> for<parameter*> expr`。存在这两个产生式并不自动说明任意嵌套的 higher-rank 已被支持。

- A. 先区分参数化定义/类型构造器的传递，与值级函数参数内部的全称量化；后者逐位置决定是否支持。
- B. 直接支持全称类型在任意类型位置嵌套，并承担相应检查和注解规则。
- C. 仅保留定义端参数化，所有进一步的多态值与类型构造器参数都暂不开放。边界小，但可能限制已有类型工厂方向。

forall type已跟随higher ranked type废弃，而for type只是个语法糖，它是pure comptime fn的简写，比如 Slice: for<T> Type, Slice: pure comptime fn<T> -> Type，这两者语义是一致的。comptime主题下忘记讲子句参数了，咱们后期再补充。

我的理由：这是 Type、comptime 函数与普通函数类型相接的位置，不能用一个“支持/不支持泛型”的开关概括。

### 10. 类型推导的默认职责边界？

- A. 以局部推导和期望类型检查为主；需要时依据显式签名、子句及已知 comptime 输入继续检查。
- B. 默认追求全程序推导，通过跨定义约束反推接口。注解可能减少，但与开放定义、增量检查及诊断位置有较大张力。
- C. 每个绑定都要求完整类型注解。可控但损失现有局部推导使用方式。

建议答复：A。实际上我期望采用的是local type inference/bidirectional type inference的现代推广：contextual type inference，不只是type inference，实际上很多的推导分析都可以应用它的contextual思想。

我的理由：这适合先给 C 背景读者可预测的注解边界。双向检查可作实现参考，但本轮不承诺完整算法、主类型性质或“所有省略都必能推断”。

### 11. 不同分支的结果怎样汇合？

- A. 先使用已有期望类型和已确认转换规则；没有共同依据就要求注解或报错，不自动创造匿名联合类型。
- B. 自动求一个公共上界，必要时生成联合、动态包装或新的 refinement 类型。表达力高，需要先定义上界是否唯一及运行时表示。
- C. 所有分支必须首先得到相同类型，完全不利用期望类型转换。容易解释，但可能过度限制 option/error 的自然构造。

不，我觉得汇合要么完全相同要么Any, 这样非常符合直觉，并且其实是鼓励用户不依赖分支来yield值，内部消化，并且大部分场景基本都是相同的类型，而如果确实是yield了Any的话，那么引导用户在使用时再次对其refine也是非常简单的事，其实跟处理一个泛型变量、defer了类型的参数没什么区别。

### 13. option/error/effect/reachability/closure 是否共享一套组合规则？

### 14. 复合类型的变型先怎么确定？

- A. 根据操作契约和可变性分别建立；在无法证明替换安全前，不自动把成员关系提升为整个容器关系。
- B. 所有复合类型默认随参数协变，再对写操作添加例外。使用方便，但例外可能穿透指针和开放方法。
- C. 所有参数化类型永远不变。保守，但会限制本可安全表达的只读使用。

建议答复：A。先问容器提供的是读取、写入、消耗还是其他能力，再决定哪些方向可替换。函数输入/输出、错误集合和可达性集合也不直接套同一变型规则。

我的理由：这不是向 Flurry 塞一种借用体系，而是要求类型替换保持已有操作契约。具体变型规则可以在对应类型章节中逐项闭合。

### 15. Trait 要求、结构能力与关联类型如何进入核心关系？

- A. trait 满足性是操作能力的证据；关联类型由适用 implementation 或其契约确定；结构能力与类型身份分别判断。
- B. 把“具有相同方法”作为类型相等或普遍子类型的依据，trait 主要是这一结构关系的名字。

建议答复：A。同一类型可以满足多个 trait，而这不让它变成多个相等的类型。开放类型的关联结果可以先通过契约参与检查，但具体结果需要何时确定仍依已有阶段规则。草稿里查询“是否有某方法”的形式先当结构能力提案，不据此宣布结构类型系统已存在。

### 21. 可达性与 memory effect 在类型主题中负责哪一层？

- A. 类型侧定义值依赖哪些对象/区域、哪些操作要求仍然有效；内存侧定义操作怎样改变对象、区域与关系，再据此影响可用事实。
- B. 把全部内存图、赋值、移动和销毁状态直接合进普通类型相等及推导关系。
- C. 可达性只作诊断元数据，不影响程序操作是否合法。

建议答复：A。一个类型及其可用性质需要能引用必要的依赖，但“两个类型相等”不应因此隐含“它们在每一时刻有相同的内存状态”。outcomes 和 memory view 在本轮只保留输入/输出接口，具体集合代数、路径失效和递归传播算法留内存主题。

我的理由：这能接住备忘中 Vec 重分配、不同索引和嵌套容器的场景，又不把整套内存管理强塞进基础类型推导。memory effect 与 algebraic effect 继续明确分开。

首先error qualified type、effect qualified type已经转向row polymorphism编码（注意闭包不是）：
```flurry
fn map(monad: ?T, lambda f: %C #Effs !Errs fn(T) -> O) -> #Effs !Errs ?O
where T, O, C: Type.vars.Closure, Effs: Type.vars.Effects, Errs: Type.vars.Errors {
    monad match {
        some? => f(some)#!,
        null => null,
    }
}
```
其中Type.vars中都是用于标记的内置类型，比如Effects、Errors用于声明这两种类型的行变量，而Closure指代闭包捕获的环境。
这里f前加lambda关键字是用来标识该函数可以用隐式函数，就是scala那种list.reduce(0, _0 + _1)这样的闭包语法糖，functions主题会讲。
实际上闭包的类型是另一层CMTT,注意不要与staging compilation的CMTT混淆。
闭包类型现在是%{} F这样设计是为了风格的一致性，比如effect qualified type以#为前缀，error以!为前缀，reachability type以&为前缀，refinement type以refines关键字为前缀...而且现在%{} fn() == fn()，这样延伸出的语义非常符合直觉，整个类型心智模型也更加统一，也不需要再额外设计Fn系列trait，当然现在你只能在一个函数类型限定一个Closure，因为我不知道限定多个有什么意义（像这样%{a: usize} %{b: usize} fn()）。closure的等价性遵循CMTT的等价性，因此实际上不需要在每个构造闭包的地方为闭包生成一个匿名类型。关于reachability type, 论文团队实际上有一些新成果我还没有看，咱们留到资源管理主题（内存管理已改名资源管理主题）再讲。

staging programming CMTT的一些前瞻：
quoted expr type -> < Psi |- T >，比如 '( a + b ): < a: i32, b: i32 |- i32 >
quoted pattern type -> < T -| Psi >，（是的，我不仅设计了表达式的，还设计了对偶的quoted pattern）比如 '< Student { name, ...} > : < Student -| name: String >

注意方括号内的内容是用来进行显式substitute的，比如'[c = a]( a + b ) : < c: i32, b: i32 |- i32 >，~[x = w]<some_quoted_expr>
quoting expr -> '( expr ) | '([ (id = id)* ])? ( expr )
quoting pattern -> '< pattern > | '([ (id = id)* ])? < pattern >

splicing expr -> ~<expr> | ~'([ (id = id)* ])? <expr>
splicing pattern -> ~<pattern> | ~'([ (id = id)* ])? <pattern>
