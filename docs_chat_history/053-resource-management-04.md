| 规格函数只能读常量区 | 允许观察明确的程序状态或快照，同时要求无被观察状态修改、确定性及适当的全定义条件 |

## 三、金字塔：由下向上增加保证

我建议保留六层，但让每一层都说明一个可检查的保证。实际分类的对象是“表达式在给定边界与已知条件下的行为”，不只是函数名字。

| 层级 | 名称 | 增加的保证 |
|---|---|---|
| **P5** | **总值纯** | P4，且在已满足的入口条件下保证有限完成并交付声明的结果；无 trap、挂起或其他未交付控制转移 |
| **P4** | **值纯** | P3，且结果及完成行为只由显式输入的值语义和真正不可变的常量决定；不依赖另行变化的存储版本，不产生可观察的新身份 |
| **P3** | **稳定观测** | P2，且读取对象、世代、内容版本及观察上下文，在声明的复用范围内保持有效；相同输入与这些依赖决定相同行为 |
| **P2** | **观测只读** | P1，且不修改或终结入口可观察状态、不交付新的可观察资源身份；读取足迹明确，允许结果依赖所读状态，也允许返回带真实依赖的视图 |
| **P1** | **有界状态变更** | 可以 read/write/kill、创建资源等，但对外影响有明确契约与足迹；没有未交付的外界交互或未知调用效果 |
| **P0** | **一般行为** | I/O、未消去的外界请求、时钟／随机环境、同步观测、未知调用或尚未封闭的影响等；只采用已经知道的局部保证 |

这里是保证的包含关系：P5 能用于要求 P4 的位置，P4 能用于要求 P3 的位置，依此类推。一个较弱级别也可以额外具备某项强保证，例如“P2，但已经证明终止”；不要求为了获得终止信息就伪装成值纯。

**P3 必须带范围。** 对可变对象，在两次读取之间没有 write/kill 的一个区间内可以成立稳定性；跨越未知回调或并发写入后就未必成立。它不是给指针盖一个永久稳定的章。

“快照”可以是验证中的状态版本，不要求自动复制全部内存。版本名本身也不使现实存储不可变：要使用同一快照，必须有真实保持依据，或真的持有独立快照值。

**P4 不保证终止。** 这与现行 comptime 章节对 pure 不承诺终止的区分相容；runtime 的标记是否核验，另见 Q2 审阅项。

“显式输入”不能只按参数名字判断。普通指针的位值相同，不代表目标内容相同；读取可变 pointee 仍属于 P2，取得有效的稳定区间后可升到 P3。真正不可变引用的内容若由其契约纳入值语义，可以参与 P4 判定；纯度标记本身不冻结存储。

**P5 的总性有定义域。** `requires` 必须在新执行位置仍成立；总值纯也不能把只在合法下标条件下执行的内部 load 提到边界检查之前。返回 `?T` 或 `!E T` 可以是有限完成的结果；后续 `?`／`!` 引起的控制传播与清理另按实际表达式计入。

### 分析边界怎样选

设边界 B 是某个表达式、函数调用或被完整处理的计算。下面这些都属于它应交付的行为：

- 对边界入口已经存在的可观察区域的访问、修改、终结，以及外部保留关系。
- 实际调用、回调、捕获环境访问、handler 行为和所有出口清理。
- 新资源的分配、身份交付、分配器效果，以及结果携带的依赖和责任。

本次执行中新建、没有外部别名、没有逃逸身份的私有临时存储，可以在边界摘要中隐藏。实现不需要因为使用了局部 var 就失去纯性。

但“按值传入”不自动使参数原有的堆资源成为可隐藏的 scratch。释放传入 String 的缓冲区、改变外部 allocator、输出日志，都仍需保留。地址变成整数后泄漏身份，也不算没有逃逸。

普通值及其责任从参数转交到结果，单独记录仿射流；仅移动一个描述符不会自动降成外部状态写入。真实的释放、可观察分配和清理效果则进入金字塔判定。

## 四、等级之外必须保留的信息

只给每个函数一个数字，会丢掉决定优化合法性的关键事实。建议保留下面这份紧凑摘要，默认分析只求保守近似：

~~~text
Summary(B) =
  读取／写入／终结足迹与依赖身份
  入口条件、相关状态版本、执行上下文依赖
  结果依赖、仿射责任转移、新身份与逃逸
  外界事件、同步／volatile／atomic 等顺序要求
  完成方式：正常结果、错误值、检查失败、挂起、其他控制转移、可能发散
  依据来源：本地推导、已核验契约、verified 证明、受检动态依据、可信底层边界
~~~

这不是再设计一个全能求解器。多数项来自指令、操作契约、局部数据流与清理；不清楚就保守，不强求 safe 推出最强结论。

需要特别防止四种混淆：

1. **无写入 ≠ 无事件。** 原子读取、volatile 读取、设备观察和某些同步操作有次数或次序语义。本文暂将它们放在 P0，并保留更精确摘要供专门规则使用；不在此制定 Flurry 的完整并发内存模型。
2. **无内存效果 ≠ 可随意复制调用。** 输入或结果可能携带 Once 责任。删除调用指令也不等于删除实参求值、责任转移和结果清理。
3. **相同内容 ≠ 相同身份。** 新建两份拥有资源的值，不能因内容相同就合并成一份拥有责任。
4. **确定计算 ≠ 任意代数恒等式成立。** 浮点结合顺序、整数溢出前提、错误传播都按实际运算语义处理，pure 不提供额外代数公理。

Copy 只给出合法的表示复制资格，复制指针仍指向同一目标；Clone 是一次有独立契约的调用，可能读取、分配或改变引用计数，不能按 trait 名字认定纯度。Once 约束责任交付，不能据此把交付前的多次合法观察也算成重复消耗。

## 五、用代码检验每一层

以下 pure fn 的含义按本轮候选解释；没有新增等级语法。

### 1. 局部 var 不妨碍值纯

~~~flurry
pure fn smaller(left: u32, right: u32) -> u32 {
    var result = left;
    if right < result {
        result = right;
    }
    result
}
~~~

result 的槽位属于本次调用私有存储。没有逃逸、分配器动作或隐藏清理；正常结果只依赖两个输入，且有限完成，可判到 P5。

若把“出现 write”一律视为不纯，编译器是否先把变量转换成 SSA 就会改变程序的纯度，这不是合适的用户语义。

### 2. 只读在内容更新后不能复用

~~~flurry
fn load_value(source: *i32) -> i32
where outcomes read<source>
{
    source.*
}

test {
    var value = 1i32;
    let first = load_value(value.ref);
    value = 2i32;
    let second = load_value(value.ref);
    println("{} {}", first, second);
}
~~~

结果应为 `1 2`。load_value 的一般接口是 P2；两次指针值相同，内容版本却不同，不能只用函数入口和指针位值作为复用键。

在另一个已证没有相关写入或终结的区间内，这种调用可以获得 P3 的局部复用依据。它不要求把所有读取的内容复制出来再当输入传一遍。

### 3. 无外部效果的发散仍不能随意删除

~~~flurry
pure fn spin() {
    while true {}
}

fn never_prints() {
    spin();
    println("done");
}
~~~

按候选规则，spin 可以是 P4，但不是 P5。删掉未使用的调用会使程序开始输出 done，因此禁止仅凭纯度删除。这里不暗中引入“没有可观察进展就允许删循环”的语言规则。

反过来，若同一确定计算已经在当前路径成功返回，消除后面同输入、同依赖的重复求值不一定需要证明它对所有输入都终止；具体变换可以利用已有支配关系与成功事实。

### 4. 整个函数总值纯，不代表内部指令能随意上提

~~~flurry
pure fn value_or_zero(values: Array<i32, n>, index: usize) -> i32
where n: usize
{
    if index < n {
        values[index]
    } else {
        0
    }
}
~~~

把数组视为已经合法交付的按值输入，本函数可有限完成；但内部分支中的元素读取依赖 index<n。优化不能因为整个函数是 P5，就无条件在判断之前读取 values[index]。

纯度标注施加在某个边界；内部操作的入口条件仍须逐项保留。

### 5. predicate 可以观察状态，但事实带版本

~~~flurry
predicate below_limit(source: *u32, limit: u32) {
    source.* < limit
}

fn read_bounded(source: *u32) -> u32 {
    assumes below_limit(source, 10);
    source.*
}
~~~

读取 source 的前提必须先成立；predicate 本身不提供凭空解引用的许可。该规格是对某个合法状态的确定观察，不要求被观察数据位于常量区。

成功检查发布的是这个状态版本下的事实。后来若 source 指向的内容被改成 12，原事实就不能继续使用。引用有效性、状态版本与检查结果都由程序验证层处理；predicate 不加 comptime，也不进入 PTC。

runtime checker 对条件进行判定，判定失败的报告、控制转移和清理属于检查动作的效果。不能因为判定主体只读，就把整个 assumes 当作没有可观察行为的死代码。

### 6. 纯测试也有选择次序

~~~flurry
fn classify(value: u32) -> u32 {
    if value < 10 {
        1
    } else if value < 100 {
        2
    } else {
        3
    }
}
~~~

两个比较都可为 P5；交换这两层选择会让输入 3 从结果 1 变成结果 2。

匹配优化也应保留编译期展开所确定的优先关系。可以在证据充分时改变测试树、合并测试或并行准备测试结果，再按原语义选择；不能把“测试只读”当作任意交换获胜臂的依据。依赖前项绑定、tag 或合法区间的后项测试，还必须保留这些数据与有效性依赖。

TuplePatternView 在编译期生成这些测试和控制流；以上分析只作用于它生成的 runtime 代码。

### 7. 新建拥有值需要保留资源身份

~~~flurry
fn fresh_text() -> String {
    "same".to_string()
}

test {
    let first = fresh_text();
    let second = fresh_text();
    println("{} {}", first.as_str(), second.as_str());
}
~~~

按实际 String 和分配器契约分析。若这两次构造分别交付独立缓冲区的责任，不能把第二次简单替换为 first 的按位副本。它们还可能有分配失败、allocator 状态及析构行为。

已封闭的分配契约可放在 P1；影响未知时为 P0。不能仅因为返回相同字符内容就判成 P4。若某个库提供共享不可变表示，则应按它真实的共享和清理契约另行判断。

### 8. 源码没有显式 I/O，退出也可能有

~~~flurry
struct Trace {
    id: u32,
}

impl Drop for Trace {
    fn drop(*self) {
        println("drop {}", self.id.*);
    }
}

fn apparently_quiet() {
    let local = Trace { id: 7 }
}
~~~

apparently_quiet 的清理会输出，因此整体是 P0。局部对象不逃逸，不能掩盖它的 Drop。

同理，处理掉某个 effect 标签后，实际 handler 的写入和系统动作仍属于该计算。完全确定、没有剩余可观察事件的处理区域可以得到更强摘要；依据是组合后的行为，而不是效应行变空。

### 9. 仿射交付与状态写入分别记录

~~~flurry
fn pass_text(value: String) -> String {
    value
}
~~~

若实际契约只将描述符及同一资源责任交付给结果，函数体可具有值纯的行为；它没有自动 kill 字符分配，也不创建新的资源身份。

但调用者仍消耗这份 String 的按值交付资格。优化器不能因为主体纯，就把一次交付复制成两次；它也必须保留最终由谁、在何时清理的语义。

### 10. 有写入仍可以局部重排

~~~flurry
struct Pair {
    left: i32,
    right: i32,
}

fn set_left(pair: *Pair, value: i32)
where outcomes write<pair.left>
{
    pair.left.* = value;
}

fn set_right(pair: *Pair, value: i32)
where outcomes write<pair.right>
{
    pair.right.* = value;
}

fn set_both(pair: *Pair) {
    set_left(pair, 1);
    set_right(pair, 2);
}
~~~

这些调用是 P1。若 Pair 的实际布局证明两字段不重叠、调用前提均已满足、两次赋值有限完成且没有其他事件或清理，则可以交换 set_both 中两个写入，最终值及其他可观察行为相同。

不相交的依据来自 memory view 与布局，不能仅凭两个字段名不同就推广到 union 或重叠视图。这里也不隐含允许并发观察中的任意重排；并发可观察性仍须另行兑现。

## 六、不同身份的表达式要求什么

| 使用位置 | 候选要求与解释 |
|---|---|
| 普通表达式／普通 fn | 可以位于任意层，按实际契约执行；P0 也能优化其有证据的子表达式 |
| runtime pure fn | 建议承诺 P4；不自动承诺终止，相关实现依据仍需检查 |
| 可执行 spec fn／计算真值的 predicate | 建议要求 P3 加确定性、入口条件下全定义及适合规格的结果；状态参数可以是逻辑快照 |
| 纯逻辑规格 | 描述明确状态下的命题，不因被声明就取得可执行判定器，也不强求所有逻辑命题都可判定 |
| 描述 memory effect 的 predicate | read/write 等是规格构造，不是执行这些内存动作；应区分规格含义与其可执行判定器 |
| memory_view | 元层构造区域描述；不偷偷执行 runtime 内存操作。生成的寻址、读取和检查代码按各自行为分析 |
| case／pattern view | 元层 elaboration 与生成代码分开；生成代码可以有已交付的状态效果，不因叫 view 就默认纯 |
| 模式 guard | 具备某一级纯度时可以采用对应优化；有副作用的合法 guard 按生成的实际控制流执行 |
| assumes 的判定主体 | 只观察合法输入／状态，成功才交付事实；失败报告及监控设施另计效果 |
| verified 主体 | 可以有写入和资源操作，纯度不是进入 verified 的条件；由 OSL 等方法证明其规格 |
| 回调／闭包 | 构造、调用、销毁分别求摘要；复杂关系依赖显式契约和 assumption，不要求 safe 自动推完整关系 |

可执行 spec fn／predicate 的“全定义”只针对已声明的有效输入与状态。默认可从有限直线计算、有界遍历及已核验库契约取得依据；一般递归不要求 safe 自动证明终止。超出范围时，可使用 verified 的证明或已核验的判定实现；不能把一次超时或陷入错误当成谓词为 false。

不可执行的逻辑规格与可执行 runtime checker 也要分清。某项数学规格成立，不代表已经得到可运行的检查算法；反过来，一个会修改被验证对象的算法也不能无条件作为同一规格的只读判定器。

## 七、优化按证据开门，不按数字直接放行

以下为首版可用的充分条件；不要求把所有语义等价变换都自动识别出来。

优化级别只决定搜索和应用变换的积极程度，不改变这些语义前提；最高优化级别也不能自行放宽失败、发散或清理行为的保留要求。

| 变换 | 需要检查的核心条件 |
|---|---|
| 复用重复求值（CSE） | 输入、调用身份与依赖版本相同；已有结果支配新位置；没有必须保留的事件或新身份；结果复用与仿射责任相容 |
| 删除未使用求值 | 没有必须保留的外部行为或清理；能够排除可观察失败、挂起及发散，或有等价的局部控制流证明；实参求值不能顺带丢弃 |
| 循环外提 | 数据与状态依赖在移动范围内稳定；即使循环执行零次，新位置也满足访问与完成条件；不破坏资源责任和清理次序 |
| 从分支内提前求值 | 新位置满足该表达式全部前提，额外执行不会引入失败、发散、事件或身份差异；保留必要的先行检查 |
| 交换两个计算 | 没有值依赖；write/kill 与对方 read/write/有效性要求无冲突；控制、事件、责任转移可交换 |
| 并行执行 | 交换条件之外，还需并发访问资格、线程／handler 上下文合法、取消及终结协议；两次普通 read 不是完整证明 |
| 重排模式测试 | 满足前面相应条件，保留匹配优先关系、前缀绑定依赖、失败控制流和实际清理 |

例如，令 Mut(A)=write(A)∪kill(A)，Need(B) 包含读取及继续有效所需区域。Mut(A) 与 Need(B) 分离，只是一部分重排条件；还需双向检查写冲突、资源流和外界事件。不会把这个集合公式伪装成全能的重排判定器。

将 P4 直接映射为后端 memory(none)、将 P2 直接映射为 readonly 也不够：后端属性有自己的位置范围、捕获、失败和控制流契约。只能逐项翻译已成立的保证。[LLVM 内存效果与其他函数属性](https://llvm.org/docs/LangRef.html#function-attributes)

## 八、默认分析保持轻量

### 1. safe 在 normalized IR 上做什么

1. 从操作和已交付契约取得实际足迹、完成方式及资源流，包含隐式清理。
2. 区分新建私有存储与入口可观察区域；只用已有的逃逸和布局依据隐藏私有动作。
3. 顺序合成效果；分支的可能影响取并集，保证只保留所有相关路径共有部分。保留能低成本表达的条件关系。
4. 普通调用替换实际区域和环境。未知回调若缺少满足所需纯度的契约，保守处理并提示缺口；不自动生成任意高阶证明义务网。
5. 用有预算的数据流、现成区域关系及三次以内的多元多项式算术处理常见证明。预算耗尽保留 Unknown，不当作成功，也不默认程序不合法。
6. 普通代码在不需要更强保证时可以继续执行，只少做优化；某语法位置或显式纯度声明确实要求更强保证时，要求补足相应依据。

标注 outcomes 或“至少某等级”仍须核验行为。接收者是 *self，不推定它写整个对象；出现按值 self，也不推定它释放全部可达资源。

### 2. 复杂场景怎样交给其他系统

- **assumption**：由用户明确提供本位置需要的条件，避免 safe 无休止向调用链顶层推导。
- **verified / OSL**：在 instantiated IR 上证明复杂关系、资源框架、函数行为及必要的等价性；交付能被调用者使用的契约。
- **runtime verification**：用实际 checker、元数据或维护协议建立可观察事实；相应检查本身的成本、失败与效果不能被纯度标签抹掉。

例如，运行时证实两个区间分离，可以支撑这次受保护执行的分离前提；比较前后内容相同，却不能证明中间从未写入。一次读取值未变，也不能证明未来不会被异步改写。

同样，没有一个通用的廉价 checker 能判定任意 callback 总会终止且永远没有 I/O。没有对应观察／保持设施时，就需要更强契约或 verified 证明；不能把裸 assumption 降为优化器无条件相信的断言。

若为了取得优化依据引入检查或监控，优化必须保留它实际建立依据的路径。不能先借一次检查证明可以删代码，再把提供该证明的检查一并删掉。监控的失败行为也属于整体摘要。

### 3. unsafe 如何跨边界

我建议同时保留“实现依赖 unsafe”的审计信息和“调用者可依赖什么”的行为契约。前者不强制把每个使用底层库的函数都降到 P0；后者也不能靠调用点的 skip 属性随意削弱。

即使允许阻断某种 unsafe 标记传播，println 仍有 system 效果。可信底层边界必须完整交付实际契约；需要免检承诺时，要明确它是信任责任，而不是编译器已经证明。

| **P4** | **值纯** | P3，且结果及完成行为只由显式输入的值语义和真正不可变的常量决定；不依赖另行变化的存储版本，不产生可观察的新身份 |
| **P3** | **稳定观测** | P2，且读取对象、世代、内容版本及观察上下文，在声明的复用范围内保持有效；相同输入与这些依赖决定相同行为 |
| **P2** | **观测只读** | P1，且不修改或终结入口可观察状态、不交付新的可观察资源身份；读取足迹明确，允许结果依赖所读状态，也允许返回带真实依赖的视图 |
| **P1** | **有界状态变更** | 可以 read/write/kill、创建资源等，但对外影响有明确契约与足迹；没有未交付的外界交互或未知调用效果 |
| **P0** | **一般行为** | I/O、未消去的外界请求、时钟／随机环境、同步观测、未知调用或尚未封闭的影响等；只采用已经知道的局部保证 |

这里是保证的包含关系：P5 能用于要求 P4 的位置，P4 能用于要求 P3 的位置，依此类推。一个较弱级别也可以额外具备某项强保证，例如“P2，但已经证明终止”；不要求为了获得终止信息就伪装成值纯。

**P3 必须带范围。** 对可变对象，在两次读取之间没有 write/kill 的一个区间内可以成立稳定性；跨越未知回调或并发写入后就未必成立。它不是给指针盖一个永久稳定的章。

“快照”可以是验证中的状态版本，不要求自动复制全部内存。版本名本身也不使现实存储不可变：要使用同一快照，必须有真实保持依据，或真的持有独立快照值。

**P4 不保证终止。** 这与现行 comptime 章节对 pure 不承诺终止的区分相容；runtime 的标记是否核验，另见 Q2 审阅项。

“显式输入”不能只按参数名字判断。普通指针的位值相同，不代表目标内容相同；读取可变 pointee 仍属于 P2，取得有效的稳定区间后可升到 P3。真正不可变引用的内容若由其契约纳入值语义，可以参与 P4 判定；纯度标记本身不冻结存储。

**P5 的总性有定义域。** `requires` 必须在新执行位置仍成立；总值纯也不能把只在合法下标条件下执行的内部 load 提到边界检查之前。返回 `?T` 或 `!E T` 可以是有限完成的结果；后续 `?`／`!` 引起的控制传播与清理另按实际表达式计入。

### 分析边界怎样选

设边界 B 是某个表达式、函数调用或被完整处理的计算。下面这些都属于它应交付的行为：

- 对边界入口已经存在的可观察区域的访问、修改、终结，以及外部保留关系。
- 实际调用、回调、捕获环境访问、handler 行为和所有出口清理。
- 新资源的分配、身份交付、分配器效果，以及结果携带的依赖和责任。

本次执行中新建、没有外部别名、没有逃逸身份的私有临时存储，可以在边界摘要中隐藏。实现不需要因为使用了局部 var 就失去纯性。

但“按值传入”不自动使参数原有的堆资源成为可隐藏的 scratch。释放传入 String 的缓冲区、改变外部 allocator、输出日志，都仍需保留。地址变成整数后泄漏身份，也不算没有逃逸。

普通值及其责任从参数转交到结果，单独记录仿射流；仅移动一个描述符不会自动降成外部状态写入。真实的释放、可观察分配和清理效果则进入金字塔判定。

## 四、等级之外必须保留的信息

只给每个函数一个数字，会丢掉决定优化合法性的关键事实。建议保留下面这份紧凑摘要，默认分析只求保守近似：

~~~text
Summary(B) =
  读取／写入／终结足迹与依赖身份
  入口条件、相关状态版本、执行上下文依赖
  结果依赖、仿射责任转移、新身份与逃逸
  外界事件、同步／volatile／atomic 等顺序要求
  完成方式：正常结果、错误值、检查失败、挂起、其他控制转移、可能发散
  依据来源：本地推导、已核验契约、verified 证明、受检动态依据、可信底层边界
~~~

这不是再设计一个全能求解器。多数项来自指令、操作契约、局部数据流与清理；不清楚就保守，不强求 safe 推出最强结论。

需要特别防止四种混淆：

1. **无写入 ≠ 无事件。** 原子读取、volatile 读取、设备观察和某些同步操作有次数或次序语义。本文暂将它们放在 P0，并保留更精确摘要供专门规则使用；不在此制定 Flurry 的完整并发内存模型。
2. **无内存效果 ≠ 可随意复制调用。** 输入或结果可能携带 Once 责任。删除调用指令也不等于删除实参求值、责任转移和结果清理。
3. **相同内容 ≠ 相同身份。** 新建两份拥有资源的值，不能因内容相同就合并成一份拥有责任。
4. **确定计算 ≠ 任意代数恒等式成立。** 浮点结合顺序、整数溢出前提、错误传播都按实际运算语义处理，pure 不提供额外代数公理。

Copy 只给出合法的表示复制资格，复制指针仍指向同一目标；Clone 是一次有独立契约的调用，可能读取、分配或改变引用计数，不能按 trait 名字认定纯度。Once 约束责任交付，不能据此把交付前的多次合法观察也算成重复消耗。

## 五、用代码检验每一层

以下 pure fn 的含义按本轮候选解释；没有新增等级语法。

### 1. 局部 var 不妨碍值纯

~~~flurry
pure fn smaller(left: u32, right: u32) -> u32 {
    var result = left;
    if right < result {
        result = right;
    }
    result
}
~~~

result 的槽位属于本次调用私有存储。没有逃逸、分配器动作或隐藏清理；正常结果只依赖两个输入，且有限完成，可判到 P5。

若把“出现 write”一律视为不纯，编译器是否先把变量转换成 SSA 就会改变程序的纯度，这不是合适的用户语义。

### 2. 只读在内容更新后不能复用

~~~flurry
fn load_value(source: *i32) -> i32
where outcomes read<source>
{
    source.*
}

test {
    var value = 1i32;
    let first = load_value(value.ref);
    value = 2i32;
    let second = load_value(value.ref);
    println("{} {}", first, second);
}
~~~

结果应为 `1 2`。load_value 的一般接口是 P2；两次指针值相同，内容版本却不同，不能只用函数入口和指针位值作为复用键。

在另一个已证没有相关写入或终结的区间内，这种调用可以获得 P3 的局部复用依据。它不要求把所有读取的内容复制出来再当输入传一遍。

### 3. 无外部效果的发散仍不能随意删除

~~~flurry
pure fn spin() {
    while true {}
}

fn never_prints() {
    spin();
    println("done");
}
~~~

按候选规则，spin 可以是 P4，但不是 P5。删掉未使用的调用会使程序开始输出 done，因此禁止仅凭纯度删除。这里不暗中引入“没有可观察进展就允许删循环”的语言规则。

反过来，若同一确定计算已经在当前路径成功返回，消除后面同输入、同依赖的重复求值不一定需要证明它对所有输入都终止；具体变换可以利用已有支配关系与成功事实。

### 4. 整个函数总值纯，不代表内部指令能随意上提

~~~flurry
pure fn value_or_zero(values: Array<i32, n>, index: usize) -> i32
where n: usize
{
    if index < n {
        values[index]
    } else {
        0
    }
}
~~~

把数组视为已经合法交付的按值输入，本函数可有限完成；但内部分支中的元素读取依赖 index<n。优化不能因为整个函数是 P5，就无条件在判断之前读取 values[index]。

纯度标注施加在某个边界；内部操作的入口条件仍须逐项保留。

### 5. predicate 可以观察状态，但事实带版本

~~~flurry
predicate below_limit(source: *u32, limit: u32) {
    source.* < limit
}

fn read_bounded(source: *u32) -> u32 {
    assumes below_limit(source, 10);
    source.*
}
~~~

读取 source 的前提必须先成立；predicate 本身不提供凭空解引用的许可。该规格是对某个合法状态的确定观察，不要求被观察数据位于常量区。

成功检查发布的是这个状态版本下的事实。后来若 source 指向的内容被改成 12，原事实就不能继续使用。引用有效性、状态版本与检查结果都由程序验证层处理；predicate 不加 comptime，也不进入 PTC。

runtime checker 对条件进行判定，判定失败的报告、控制转移和清理属于检查动作的效果。不能因为判定主体只读，就把整个 assumes 当作没有可观察行为的死代码。

### 6. 纯测试也有选择次序

~~~flurry
fn classify(value: u32) -> u32 {
    if value < 10 {
        1
    } else if value < 100 {
        2
    } else {
        3
    }
}
~~~

两个比较都可为 P5；交换这两层选择会让输入 3 从结果 1 变成结果 2。

匹配优化也应保留编译期展开所确定的优先关系。可以在证据充分时改变测试树、合并测试或并行准备测试结果，再按原语义选择；不能把“测试只读”当作任意交换获胜臂的依据。依赖前项绑定、tag 或合法区间的后项测试，还必须保留这些数据与有效性依赖。

TuplePatternView 在编译期生成这些测试和控制流；以上分析只作用于它生成的 runtime 代码。

### 7. 新建拥有值需要保留资源身份

~~~flurry
fn fresh_text() -> String {
    "same".to_string()
}

test {
    let first = fresh_text();
    let second = fresh_text();
    println("{} {}", first.as_str(), second.as_str());
}
~~~

按实际 String 和分配器契约分析。若这两次构造分别交付独立缓冲区的责任，不能把第二次简单替换为 first 的按位副本。它们还可能有分配失败、allocator 状态及析构行为。

已封闭的分配契约可放在 P1；影响未知时为 P0。不能仅因为返回相同字符内容就判成 P4。若某个库提供共享不可变表示，则应按它真实的共享和清理契约另行判断。

### 8. 源码没有显式 I/O，退出也可能有

~~~flurry
struct Trace {
    id: u32,
}

impl Drop for Trace {
    fn drop(*self) {
        println("drop {}", self.id.*);
    }
}

fn apparently_quiet() {
    let local = Trace { id: 7 }
}
~~~

apparently_quiet 的清理会输出，因此整体是 P0。局部对象不逃逸，不能掩盖它的 Drop。

同理，处理掉某个 effect 标签后，实际 handler 的写入和系统动作仍属于该计算。完全确定、没有剩余可观察事件的处理区域可以得到更强摘要；依据是组合后的行为，而不是效应行变空。

### 9. 仿射交付与状态写入分别记录

~~~flurry
fn pass_text(value: String) -> String {
    value
}
~~~

若实际契约只将描述符及同一资源责任交付给结果，函数体可具有值纯的行为；它没有自动 kill 字符分配，也不创建新的资源身份。

但调用者仍消耗这份 String 的按值交付资格。优化器不能因为主体纯，就把一次交付复制成两次；它也必须保留最终由谁、在何时清理的语义。

### 10. 有写入仍可以局部重排

~~~flurry
struct Pair {
    left: i32,
    right: i32,
}

fn set_left(pair: *Pair, value: i32)
where outcomes write<pair.left>
{
    pair.left.* = value;
}

fn set_right(pair: *Pair, value: i32)
where outcomes write<pair.right>
{
    pair.right.* = value;
}

fn set_both(pair: *Pair) {
    set_left(pair, 1);
    set_right(pair, 2);
}
~~~

这些调用是 P1。若 Pair 的实际布局证明两字段不重叠、调用前提均已满足、两次赋值有限完成且没有其他事件或清理，则可以交换 set_both 中两个写入，最终值及其他可观察行为相同。

不相交的依据来自 memory view 与布局，不能仅凭两个字段名不同就推广到 union 或重叠视图。这里也不隐含允许并发观察中的任意重排；并发可观察性仍须另行兑现。

## 六、不同身份的表达式要求什么

| 使用位置 | 候选要求与解释 |
|---|---|
| 普通表达式／普通 fn | 可以位于任意层，按实际契约执行；P0 也能优化其有证据的子表达式 |
| runtime pure fn | 建议承诺 P4；不自动承诺终止，相关实现依据仍需检查 |
| 可执行 spec fn／计算真值的 predicate | 建议要求 P3 加确定性、入口条件下全定义及适合规格的结果；状态参数可以是逻辑快照 |
| 纯逻辑规格 | 描述明确状态下的命题，不因被声明就取得可执行判定器，也不强求所有逻辑命题都可判定 |
| 描述 memory effect 的 predicate | read/write 等是规格构造，不是执行这些内存动作；应区分规格含义与其可执行判定器 |
| memory_view | 元层构造区域描述；不偷偷执行 runtime 内存操作。生成的寻址、读取和检查代码按各自行为分析 |
| case／pattern view | 元层 elaboration 与生成代码分开；生成代码可以有已交付的状态效果，不因叫 view 就默认纯 |
| 模式 guard | 具备某一级纯度时可以采用对应优化；有副作用的合法 guard 按生成的实际控制流执行 |
| assumes 的判定主体 | 只观察合法输入／状态，成功才交付事实；失败报告及监控设施另计效果 |
| verified 主体 | 可以有写入和资源操作，纯度不是进入 verified 的条件；由 OSL 等方法证明其规格 |
| 回调／闭包 | 构造、调用、销毁分别求摘要；复杂关系依赖显式契约和 assumption，不要求 safe 自动推完整关系 |

可执行 spec fn／predicate 的“全定义”只针对已声明的有效输入与状态。默认可从有限直线计算、有界遍历及已核验库契约取得依据；一般递归不要求 safe 自动证明终止。超出范围时，可使用 verified 的证明或已核验的判定实现；不能把一次超时或陷入错误当成谓词为 false。

不可执行的逻辑规格与可执行 runtime checker 也要分清。某项数学规格成立，不代表已经得到可运行的检查算法；反过来，一个会修改被验证对象的算法也不能无条件作为同一规格的只读判定器。

## 七、优化按证据开门，不按数字直接放行

以下为首版可用的充分条件；不要求把所有语义等价变换都自动识别出来。

优化级别只决定搜索和应用变换的积极程度，不改变这些语义前提；最高优化级别也不能自行放宽失败、发散或清理行为的保留要求。

| 变换 | 需要检查的核心条件 |
|---|---|
| 复用重复求值（CSE） | 输入、调用身份与依赖版本相同；已有结果支配新位置；没有必须保留的事件或新身份；结果复用与仿射责任相容 |
| 删除未使用求值 | 没有必须保留的外部行为或清理；能够排除可观察失败、挂起及发散，或有等价的局部控制流证明；实参求值不能顺带丢弃 |
| 循环外提 | 数据与状态依赖在移动范围内稳定；即使循环执行零次，新位置也满足访问与完成条件；不破坏资源责任和清理次序 |
| 从分支内提前求值 | 新位置满足该表达式全部前提，额外执行不会引入失败、发散、事件或身份差异；保留必要的先行检查 |
| 交换两个计算 | 没有值依赖；write/kill 与对方 read/write/有效性要求无冲突；控制、事件、责任转移可交换 |
| 并行执行 | 交换条件之外，还需并发访问资格、线程／handler 上下文合法、取消及终结协议；两次普通 read 不是完整证明 |
| 重排模式测试 | 满足前面相应条件，保留匹配优先关系、前缀绑定依赖、失败控制流和实际清理 |

例如，令 Mut(A)=write(A)∪kill(A)，Need(B) 包含读取及继续有效所需区域。Mut(A) 与 Need(B) 分离，只是一部分重排条件；还需双向检查写冲突、资源流和外界事件。不会把这个集合公式伪装成全能的重排判定器。

将 P4 直接映射为后端 memory(none)、将 P2 直接映射为 readonly 也不够：后端属性有自己的位置范围、捕获、失败和控制流契约。只能逐项翻译已成立的保证。[LLVM 内存效果与其他函数属性](https://llvm.org/docs/LangRef.html#function-attributes)

## 八、默认分析保持轻量

### 1. safe 在 normalized IR 上做什么

1. 从操作和已交付契约取得实际足迹、完成方式及资源流，包含隐式清理。
2. 区分新建私有存储与入口可观察区域；只用已有的逃逸和布局依据隐藏私有动作。
3. 顺序合成效果；分支的可能影响取并集，保证只保留所有相关路径共有部分。保留能低成本表达的条件关系。
4. 普通调用替换实际区域和环境。未知回调若缺少满足所需纯度的契约，保守处理并提示缺口；不自动生成任意高阶证明义务网。
5. 用有预算的数据流、现成区域关系及三次以内的多元多项式算术处理常见证明。预算耗尽保留 Unknown，不当作成功，也不默认程序不合法。
6. 普通代码在不需要更强保证时可以继续执行，只少做优化；某语法位置或显式纯度声明确实要求更强保证时，要求补足相应依据。

标注 outcomes 或“至少某等级”仍须核验行为。接收者是 *self，不推定它写整个对象；出现按值 self，也不推定它释放全部可达资源。

### 2. 复杂场景怎样交给其他系统

- **assumption**：由用户明确提供本位置需要的条件，避免 safe 无休止向调用链顶层推导。
- **verified / OSL**：在 instantiated IR 上证明复杂关系、资源框架、函数行为及必要的等价性；交付能被调用者使用的契约。
- **runtime verification**：用实际 checker、元数据或维护协议建立可观察事实；相应检查本身的成本、失败与效果不能被纯度标签抹掉。

例如，运行时证实两个区间分离，可以支撑这次受保护执行的分离前提；比较前后内容相同，却不能证明中间从未写入。一次读取值未变，也不能证明未来不会被异步改写。

同样，没有一个通用的廉价 checker 能判定任意 callback 总会终止且永远没有 I/O。没有对应观察／保持设施时，就需要更强契约或 verified 证明；不能把裸 assumption 降为优化器无条件相信的断言。

若为了取得优化依据引入检查或监控，优化必须保留它实际建立依据的路径。不能先借一次检查证明可以删代码，再把提供该证明的检查一并删掉。监控的失败行为也属于整体摘要。

### 3. unsafe 如何跨边界

我建议同时保留“实现依赖 unsafe”的审计信息和“调用者可依赖什么”的行为契约。前者不强制把每个使用底层库的函数都降到 P0；后者也不能靠调用点的 skip 属性随意削弱。

即使允许阻断某种 unsafe 标记传播，println 仍有 system 效果。可信底层边界必须完整交付实际契约；需要免检承诺时，要明确它是信任责任，而不是编译器已经证明。

## 九、需要你审阅的四项选择

### Q1. 是否采用这套六层主干与独立保证？

- **A. 采用 P0–P5 六层，优化再检查足迹、终止、仿射、控制与依据。** 读者有清楚的金字塔，实现保留必要精度。
- **B. 对外只分一般行为、有界变更、只读、值纯四类，把稳定性与总性全部作为附加条件。** 名称更少，阅读具体优化规则时需要组合更多条件。

**预填答复：A。** 金字塔用于组织理解和默认要求，精确摘要决定具体变换。六层都不要求独立关键字。

### Q2. runtime pure 承诺到哪一层？

- **A. P4 值纯，不默认承诺终止。** 局部可变算法与一般递归仍能表达；删除、推测执行另需完成性依据。
- **B. P5 总值纯。** 标记更强，很多优化更容易；不能证明终止的递归和循环无法取得 pure，需要额外区分部分计算。

**预填答复：A。** runtime pure 是需按本主题规则兑现的行为约束。comptime pure 已确认的可信承诺机制保持原有语义，不因本轮建议被悄悄改写；两个执行阶段的核验政策要在文档中分别说明。

### Q3. spec fn／predicate 是否允许稳定观察可变程序状态？

- **A. 允许 P3 的状态观察，加上确定性和有效输入下全定义的要求。** 能直接描述容器内容、内存视图与前后状态；事实必须携带版本和有效范围。
- **B. 继续要求 P4／只读真正不可变输入。** 状态需先显式转成快照值，规格体系较小，但常见内存规格需要更多复制或建模接口。

**预填答复：A。** 支持内存安全规格实际需要的状态读取，限制证明与判定的副作用；不要求 safe 自动解决任意规格的全定义证明。

### Q4. unsafe 与纯度证据怎样处理？

- **A. 审计来源与行为契约分离；安全封装能依靠完整的已核验或明确可信契约交付更强纯度。** 无契约时保守，普通 skip 属性不能删掉效果或检查义务。
- **B. 只要传递依赖 unsafe 就默认限制纯度，只有专门列出的内建或 verified 边界才能解除。** 实现政策更保守，但大量系统库封装需要额外登记才能参与优化。
- **C. runtime pure 本身就是与 comptime pure 类似的开发者可信承诺。** 注解可以直接交付性质，分析只作辅助诊断；同时改写 Q2 预填中的核验政策，错误承诺的责任及语义后果必须明确。

**预填答复：A。** 日常标记不变成任意信任入口，底层封装也不因实现包含 unsafe 而永远失去纯度信息。
