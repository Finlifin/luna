### R1. 用户定义的名义类型是否必须显式取得 Copy？

现行 [once-clone-copy.md](/home/fin/luna/docs/resource-management/once-clone-copy.md) 同时写了“只包含 Copy 字段的结构体”和“可以通过 derive 自动获得 Copy 和 Clone”。需要明确：字段可复制是派生条件，还是无需声明就拥有能力。

~~~flurry
struct Code {
    value: u32,
}

test {
    let first = Code { value: 7 }
    let second = first;
    println("{} {}", first.value, second.value);
}
~~~

- **A. 名义类型通过显式 impl/derive 取得 Copy；内建类型按各自定义提供。** 上例未声明 Copy，交付给 second 后不能再读取 first。字段条件用于验证派生，使用语义不会因悄悄增加一个可派生实现而变化。
- **B. 满足结构与资源条件就自动取得 Copy。** 上例可以打印 `7 7`；更改字段或责任可能改变同一种赋值的含义。
- **C. 由类型声明额外选择是否进行结构化能力推导。** 可控制自动性，但需增加一个目前尚未确定的配置入口。

**预填答复：A。** 显式取得能力。字段全为 Copy 不能掩盖独占终结责任；复制指针也不复制 pointee 的责任。本题确定取得方式，Copy 实现仍要兑现已审阅的复制契约。

### R2. let 限制哪些写入位置？

[bindings.md](/home/fin/luna/docs/resource-management/bindings.md) 只确定 var 可重新赋值，把进一步分工留给本主题。下面三处应分别判定，不能仅用“let 不可变”含混概括：

~~~flurry
struct Counter {
    value: u32,
}

test {
    let counter = Counter { value: 1 }
    counter.value = 2;                   -- ① 写字段
    counter.ref.* = Counter { value: 3 } -- ② 经指针替换整个本体
    counter = Counter { value: 4 }       -- ③ 直接给 let 名称赋值
}
~~~

这些操作逐项讨论；不能因第一个被拒绝而跳过后两项。

- **A. let 限制直接以该名称进行整值赋值；字段写入及经指针的写入按对象契约检查。** ①②可合法，③拒绝。let 不承诺本体内容不变，不能用于推导常量存储或并发只读。
- **B. let 固定整个本体身份；允许字段更新，但禁止整体替换，包括经别名的替换。** ①可合法，②③拒绝；程序验证层还需保留“完整本体不可替换”的资格。
- **C. let 使本体及内联字段只读，指针必须保留这一限制。** 三项都拒绝；间接资源另按契约处理，现有通过 let 容器修改描述符的意向用法也需复核。

**预填答复：A。** 与此前以 let 持有对象、通过 *self 更新对象的方向一致。var 提供直接整值赋值入口；合法写入仍需满足当前内存有效性及清理契约。

选择 A 意味着 `let number = 1i32` 也不能承诺其存储永不被指针修改。这是有意的语言规则，文档应直接展示，而不是让读者靠猜测别名行为发现。

### R3. 局部值何时清理，替换值是否改变清理次序？

[drop-elaboration.md](/home/fin/luna/docs/resource-management/drop-elaboration.md) 一处写离开作用域插入 drop，末尾又写“资源在不再需要时立即释放”。二十例第 13 例已经要求把析构读取计入分析；这里补足可观察的时机与次序。

以下定义供 R3–R5 共用：

~~~flurry
struct Trace {
    id: u32,
}

impl Drop for Trace {
    fn drop(*self) {
        println("drop {}", self.id.*);
    }
}

fn cleanup_order() {
    var first = Trace { id: 1 }
    let second = Trace { id: 2 }
    first = Trace { id: 3 }
    println("body");
}
~~~

- **A. 词法作用域结束时按局部绑定的声明逆序清理；赋值不改变绑定的次序。** 在覆盖赋值完成旧值清理的前提下，输出为 `drop 1`、`body`、`drop 2`、`drop 3`。最后一次普通使用不自动提前可观察清理。
- **B. 以每份当前值完成初始化的时间决定逆序清理；替换值重新取得清理次序。** 同一前提下，尾部改为 `drop 3`、`drop 2`。赋值会改变后来作用域退出时的次序。
- **C. 以包含隐式操作的最后使用决定最早清理点。** 需要把该规则落实为确定的用户语义；没有后续读取的 Trace 可能在 body 之前清理，不能再许诺上面的作用域日志次序。

**预填答复：A。** 每个作用域按绑定位置固定清理次序，当前未初始化或已移出的槽位跳过。覆盖赋值只替换该位置持有的责任，不重排清理次序。return、错误传播、break/continue 按离开的作用域逐层清理；优化只有保持可观察行为时才能提前释放。

此处不会按依赖图自动拓扑排序析构。如果固定次序使后析构对象读取了已释放存储，应诊断或调整程序；编译器不能通过暗中换序改变日志、锁或事务行为。

### R4. 用户 Drop 与字段清理如何组合？

现行 [drop-elaboration.md](/home/fin/luna/docs/resource-management/drop-elaboration.md) 只说明“不实现 Drop 的类型，其 drop 操作默认为递归 drop 各字段”，尚未确定用户 Drop 是否替代字段清理。

~~~flurry
struct Bundle {
    first: Trace,
    second: Trace,
}

impl Drop for Bundle {
    fn drop(*self) {
        println("bundle");
    }
}

fn cleanup_bundle() {
    let value = Bundle {
        first: Trace { id: 1 },
        second: Trace { id: 2 },
    }
}
~~~

- **A. 先执行用户 Drop，再按字段声明逆序自动清理仍已初始化的字段。** 输出为 `bundle`、`drop 2`、`drop 1`；字段最后一次被赋值的时间不改变这一顺序。
- **B. 有用户 Drop 时，由它承担全部字段清理。** 本例只输出 `bundle`，且这个实现遗漏了两个 Trace 的清理责任；必须补齐实现才能成立。
- **C. 先执行用户 Drop，再按字段声明顺序自动清理仍已初始化的字段。** 输出为 `bundle`、`drop 1`、`drop 2`；用户 Drop 与自动清理的分工同 A，固定顺序不同。

**预填答复：A。** 用户 Drop 处理额外动作，自动清理覆盖剩余已初始化字段。元组按元素位置的逆序，数组按下标逆序；enum 只处理当前实际变体。这里的次序是待确认的统一默认规则。

部分移出的有效性沿用二十例第 14 例：剩余清理需要哪些字段，就证明那些字段仍可访问。用户 Drop 若只读取 second，不能仅因 first 被移出就一概拒绝；若会读取 first，则该路径不满足清理前提。其入口状态与访问证明由程序验证层检查，不为这些状态增加 PTC 命题。

用户 Drop 自己合法转移出去的字段不会再被自动清理；不得重复释放，也不能因定义了一个空 Drop 就悄悄丢弃字段责任。

### R5. 覆盖赋值在哪一步结束旧值，新值构造失败后还剩什么？

“赋值前清理旧值”还不够精确：它可能指右侧求值之前，也可能指右侧已经成功交付新值之后。

~~~flurry
enum BuildErr {
    Refused,
}

fn build_trace(id: u32, fail: bool) -> !BuildErr Trace {
    println("build {}", id);
    if fail {
        error BuildErr.Refused
    } else {
        Trace { id: id }
    }
}

fn replace_trace(target: *Trace, fail: bool) -> !BuildErr void {
    target.* = build_trace(2, fail)!;
}

test {
    var value = Trace { id: 1 }
    replace_trace(value.ref, true)! {
        .Refused => println("kept {}", value.id),
    }
}
~~~

- **A. 右侧成功交付新值之后，才清理目标中仍持有的旧值并安装新值。** 本例输出 `build 2`、`kept 1`，最后清理旧值 `drop 1`。右侧失败不会由赋值机制额外销毁目标。
- **B. 先结束旧值，再计算右侧。** 本例错误出口留下未初始化目标，handler 不能读取 value；函数接口须表达这种失败后状态，调用方须恢复或交付相应状态。
- **C. 首版拒绝直接覆盖仍持有清理责任的值，要求显式拆分。** 路径容易看清，但普通容器和字段更新会产生大量手工责任操作。

**预填答复：A。** 赋值先取得可供安装的新值，再结束目标的旧责任，最后交付新责任。目标路径和右侧遵守普通求值规则且各求值一次；进入旧值清理和最终写入前都须检查该目标仍合法。

这里的失败保证只针对赋值机制。右侧如果主动修改了目标、调用外部函数或执行 I/O，这些已发生行为不会被回滚。右侧若合法移走了目标原值，旧槽位已空，不能再清理同一份责任。

同一规则应覆盖构造失败：

~~~flurry
fn build_bundle(fail: bool) -> !BuildErr Bundle {
    let first = build_trace(1, false)!;
    let second = build_trace(2, fail)!;
    Bundle { first: first, second: second }
}
~~~

本例显式分步确定求值次序。second 失败时，只清理已经构造成功的 first；没有完整 Bundle，就不调用 Bundle.drop。成功移入聚合后，两个局部源位置不再清理。若实现直接在目标存储中构造，也必须保持这些可观察行为。

如果旧值清理自身不能正常完成，新值由临时责任持有，其后续命运要满足 R6 的清理契约；A 不等于给任意析构过程自动添加事务回滚。

### R6. 隐式清理允许哪些错误与效应，handler 要活到何时？

已确认：需要环境的 Drop 在责任建立时绑定证据，move 传递这份证据。此题只决定执行清理时的控制流约束。

`fn drop(*self)` 的 void 结果没有承诺纯函数。上面的 Trace 会输出；依赖 allocator 或系统资源的清理也会有真实效果。这些行为必须进入调用者及退出路径的摘要。

- **A. 自动 Drop 不新增可恢复错误返回；可以执行其接口允许且清理位置能够兑现的效应。** 不为退出路径隐式发明错误合并规则。处理环境和全部剩余责任必须覆盖实际清理过程。
- **B. Drop 可以交付可恢复错误，由退出路径显式携带。** 还需规定正常结果与清理错误、原错误与后续清理错误如何组合，以及哪些后续清理继续执行。
- **C. 自动清理必须属于受限无效应子集，日志等动作只能显式执行。** 限制较容易描述，但 Trace 示例和现有资源释放方向都需要调整。

**预填答复：A。** 保持 void 的自动清理结果，不允许 impl 私自加强接口的错误或效应要求。内部资源在其所需 handler 环境仍有效时清理，再结束 handler 自身责任；该顺序必须进入控制边界的实际契约。

挂起清理或取消续延需要额外的、已经交付的保持与终结契约。没有这份保证时，在该清理位置拒绝。不能把“执行过 Drop 的开头”记成全部责任已兑现，也不能把 handler 的中止当成删除剩余责任的许可。

本题不凭空引入 panic、abort 或二次失败规则；具体失败若由某个库动作产生，仍按它实际交付的契约检查。

## 二、这轮要解决的事

内存有效性能够判断某条清理路径是否合法，但程序员还需要知道实际执行哪一条路径。例如，两种析构次序都可能内存安全，却产生不同日志；新值构造失败时，旧值是否已经被销毁，也不能交给验证器自行挑选。

## 三、六项预填

### R1. 用户定义的名义类型是否必须显式取得 Copy？

现行 [once-clone-copy.md](/home/fin/luna/docs/resource-management/once-clone-copy.md) 同时写了“只包含 Copy 字段的结构体”和“可以通过 derive 自动获得 Copy 和 Clone”。需要明确：字段可复制是派生条件，还是无需声明就拥有能力。

~~~flurry
struct Code {
    value: u32,
}

test {
    let first = Code { value: 7 }
    let second = first;
    println("{} {}", first.value, second.value);
}
~~~

- **A. 名义类型通过显式 impl/derive 取得 Copy；内建类型按各自定义提供。** 上例未声明 Copy，交付给 second 后不能再读取 first。字段条件用于验证派生，使用语义不会因悄悄增加一个可派生实现而变化。
- **B. 满足结构与资源条件就自动取得 Copy。** 上例可以打印 `7 7`；更改字段或责任可能改变同一种赋值的含义。
- **C. 由类型声明额外选择是否进行结构化能力推导。** 可控制自动性，但需增加一个目前尚未确定的配置入口。

**预填答复：A。** 显式取得能力。字段全为 Copy 不能掩盖独占终结责任；复制指针也不复制 pointee 的责任。本题确定取得方式，Copy 实现仍要兑现已审阅的复制契约。

### R2. let 限制哪些写入位置？

[bindings.md](/home/fin/luna/docs/resource-management/bindings.md) 只确定 var 可重新赋值，把进一步分工留给本主题。下面三处应分别判定，不能仅用“let 不可变”含混概括：

~~~flurry
struct Counter {
    value: u32,
}

test {
    let counter = Counter { value: 1 }
    counter.value = 2;                   -- ① 写字段
    counter.ref.* = Counter { value: 3 } -- ② 经指针替换整个本体
    counter = Counter { value: 4 }       -- ③ 直接给 let 名称赋值
}
~~~

这些操作逐项讨论；不能因第一个被拒绝而跳过后两项。

- **A. let 限制直接以该名称进行整值赋值；字段写入及经指针的写入按对象契约检查。** ①②可合法，③拒绝。let 不承诺本体内容不变，不能用于推导常量存储或并发只读。
- **B. let 固定整个本体身份；允许字段更新，但禁止整体替换，包括经别名的替换。** ①可合法，②③拒绝；程序验证层还需保留“完整本体不可替换”的资格。
- **C. let 使本体及内联字段只读，指针必须保留这一限制。** 三项都拒绝；间接资源另按契约处理，现有通过 let 容器修改描述符的意向用法也需复核。

**预填答复：A。** 与此前以 let 持有对象、通过 *self 更新对象的方向一致。var 提供直接整值赋值入口；合法写入仍需满足当前内存有效性及清理契约。

选择 A 意味着 `let number = 1i32` 也不能承诺其存储永不被指针修改。这是有意的语言规则，文档应直接展示，而不是让读者靠猜测别名行为发现。

### R3. 局部值何时清理，替换值是否改变清理次序？

[drop-elaboration.md](/home/fin/luna/docs/resource-management/drop-elaboration.md) 一处写离开作用域插入 drop，末尾又写“资源在不再需要时立即释放”。二十例第 13 例已经要求把析构读取计入分析；这里补足可观察的时机与次序。

以下定义供 R3–R5 共用：

~~~flurry
struct Trace {
    id: u32,
}

impl Drop for Trace {
    fn drop(*self) {
        println("drop {}", self.id.*);
    }
}

fn cleanup_order() {
    var first = Trace { id: 1 }
    let second = Trace { id: 2 }
    first = Trace { id: 3 }
    println("body");
}
~~~

- **A. 词法作用域结束时按局部绑定的声明逆序清理；赋值不改变绑定的次序。** 在覆盖赋值完成旧值清理的前提下，输出为 `drop 1`、`body`、`drop 2`、`drop 3`。最后一次普通使用不自动提前可观察清理。
- **B. 以每份当前值完成初始化的时间决定逆序清理；替换值重新取得清理次序。** 同一前提下，尾部改为 `drop 3`、`drop 2`。赋值会改变后来作用域退出时的次序。
- **C. 以包含隐式操作的最后使用决定最早清理点。** 需要把该规则落实为确定的用户语义；没有后续读取的 Trace 可能在 body 之前清理，不能再许诺上面的作用域日志次序。

**预填答复：A。** 每个作用域按绑定位置固定清理次序，当前未初始化或已移出的槽位跳过。覆盖赋值只替换该位置持有的责任，不重排清理次序。return、错误传播、break/continue 按离开的作用域逐层清理；优化只有保持可观察行为时才能提前释放。

此处不会按依赖图自动拓扑排序析构。如果固定次序使后析构对象读取了已释放存储，应诊断或调整程序；编译器不能通过暗中换序改变日志、锁或事务行为。

### R4. 用户 Drop 与字段清理如何组合？

现行 [drop-elaboration.md](/home/fin/luna/docs/resource-management/drop-elaboration.md) 只说明“不实现 Drop 的类型，其 drop 操作默认为递归 drop 各字段”，尚未确定用户 Drop 是否替代字段清理。

~~~flurry
struct Bundle {
    first: Trace,
    second: Trace,
}

impl Drop for Bundle {
    fn drop(*self) {
        println("bundle");
    }
}

fn cleanup_bundle() {
    let value = Bundle {
        first: Trace { id: 1 },
        second: Trace { id: 2 },
    }
}
~~~

- **A. 先执行用户 Drop，再按字段声明逆序自动清理仍已初始化的字段。** 输出为 `bundle`、`drop 2`、`drop 1`；字段最后一次被赋值的时间不改变这一顺序。
- **B. 有用户 Drop 时，由它承担全部字段清理。** 本例只输出 `bundle`，且这个实现遗漏了两个 Trace 的清理责任；必须补齐实现才能成立。
- **C. 先执行用户 Drop，再按字段声明顺序自动清理仍已初始化的字段。** 输出为 `bundle`、`drop 1`、`drop 2`；用户 Drop 与自动清理的分工同 A，固定顺序不同。

**预填答复：A。** 用户 Drop 处理额外动作，自动清理覆盖剩余已初始化字段。元组按元素位置的逆序，数组按下标逆序；enum 只处理当前实际变体。这里的次序是待确认的统一默认规则。

部分移出的有效性沿用二十例第 14 例：剩余清理需要哪些字段，就证明那些字段仍可访问。用户 Drop 若只读取 second，不能仅因 first 被移出就一概拒绝；若会读取 first，则该路径不满足清理前提。其入口状态与访问证明由程序验证层检查，不为这些状态增加 PTC 命题。

用户 Drop 自己合法转移出去的字段不会再被自动清理；不得重复释放，也不能因定义了一个空 Drop 就悄悄丢弃字段责任。

### R5. 覆盖赋值在哪一步结束旧值，新值构造失败后还剩什么？

“赋值前清理旧值”还不够精确：它可能指右侧求值之前，也可能指右侧已经成功交付新值之后。

~~~flurry
enum BuildErr {
    Refused,
}

fn build_trace(id: u32, fail: bool) -> !BuildErr Trace {
    println("build {}", id);
    if fail {
        error BuildErr.Refused
    } else {
        Trace { id: id }
    }
}

fn replace_trace(target: *Trace, fail: bool) -> !BuildErr void {
    target.* = build_trace(2, fail)!;
}

test {
    var value = Trace { id: 1 }
    replace_trace(value.ref, true)! {
        .Refused => println("kept {}", value.id),
    }
}
~~~

- **A. 右侧成功交付新值之后，才清理目标中仍持有的旧值并安装新值。** 本例输出 `build 2`、`kept 1`，最后清理旧值 `drop 1`。右侧失败不会由赋值机制额外销毁目标。
- **B. 先结束旧值，再计算右侧。** 本例错误出口留下未初始化目标，handler 不能读取 value；函数接口须表达这种失败后状态，调用方须恢复或交付相应状态。
- **C. 首版拒绝直接覆盖仍持有清理责任的值，要求显式拆分。** 路径容易看清，但普通容器和字段更新会产生大量手工责任操作。

**预填答复：A。** 赋值先取得可供安装的新值，再结束目标的旧责任，最后交付新责任。目标路径和右侧遵守普通求值规则且各求值一次；进入旧值清理和最终写入前都须检查该目标仍合法。

这里的失败保证只针对赋值机制。右侧如果主动修改了目标、调用外部函数或执行 I/O，这些已发生行为不会被回滚。右侧若合法移走了目标原值，旧槽位已空，不能再清理同一份责任。

同一规则应覆盖构造失败：

~~~flurry
fn build_bundle(fail: bool) -> !BuildErr Bundle {
    let first = build_trace(1, false)!;
    let second = build_trace(2, fail)!;
    Bundle { first: first, second: second }
}
~~~

本例显式分步确定求值次序。second 失败时，只清理已经构造成功的 first；没有完整 Bundle，就不调用 Bundle.drop。成功移入聚合后，两个局部源位置不再清理。若实现直接在目标存储中构造，也必须保持这些可观察行为。

如果旧值清理自身不能正常完成，新值由临时责任持有，其后续命运要满足 R6 的清理契约；A 不等于给任意析构过程自动添加事务回滚。

### R6. 隐式清理允许哪些错误与效应，handler 要活到何时？

已确认：需要环境的 Drop 在责任建立时绑定证据，move 传递这份证据。此题只决定执行清理时的控制流约束。

`fn drop(*self)` 的 void 结果没有承诺纯函数。上面的 Trace 会输出；依赖 allocator 或系统资源的清理也会有真实效果。这些行为必须进入调用者及退出路径的摘要。

- **A. 自动 Drop 不新增可恢复错误返回；可以执行其接口允许且清理位置能够兑现的效应。** 不为退出路径隐式发明错误合并规则。处理环境和全部剩余责任必须覆盖实际清理过程。
- **B. Drop 可以交付可恢复错误，由退出路径显式携带。** 还需规定正常结果与清理错误、原错误与后续清理错误如何组合，以及哪些后续清理继续执行。
- **C. 自动清理必须属于受限无效应子集，日志等动作只能显式执行。** 限制较容易描述，但 Trace 示例和现有资源释放方向都需要调整。

**预填答复：A。** 保持 void 的自动清理结果，不允许 impl 私自加强接口的错误或效应要求。内部资源在其所需 handler 环境仍有效时清理，再结束 handler 自身责任；该顺序必须进入控制边界的实际契约。

挂起清理或取消续延需要额外的、已经交付的保持与终结契约。没有这份保证时，在该清理位置拒绝。不能把“执行过 Drop 的开头”记成全部责任已兑现，也不能把 handler 的中止当成删除剩余责任的许可。

本题不凭空引入 panic、abort 或二次失败规则；具体失败若由某个库动作产生，仍按它实际交付的契约检查。
