# 编译：elaboration、依赖调度与冻结边界

日期：2026-10-07。编译主题第 1 轮，对应 history 077。

**DRAFT — NOT CANONICAL。** 以下是供你修改的分析、内容规划与预填答复。Pipeline projection 已按上一轮答复写入；这一轮不把尚未确认的 elaboration 选择写成正式语义。程序验证的高级算法留到后续，编译主题只保留已确认的规格交付边界。

## 我对这篇草稿的理解

依据：[elaboration-of-elaboration](/home/fin/vilya/examples/2026-10-7-elaboration-of-elaboration.md)。阅读覆盖全文 200 节；下面按问题引用章节，避免把长文的组织顺序直接变成文档目录。

这篇草稿的核心是：让传统的递归 elaborator 保留直接执行的快路径，同时允许少数真正缺少信息的工作暂停，让能够提供信息的其他工作继续进行。类型规则决定可以取得什么事实，solver 维护事实，scheduler 决定何时再次尝试。Continuation 可以承载暂停点，但它本身没有增加一条推断规则。

我赞同这条架构方向。它处理的是 elaboration 的组织、信息流与成本，而不是单独提出了一套新的类型推断理论。是否成立，需要检查调度替换是否保持结果、暂停边界是否留下可运行的生产者，以及局部状态能否在定义检查与实例化之间正确交付。仅凭能表达 wait/resume，还不能证明这些性质。

我认为下面四个区分应该贯穿编译主题。

### 1. 三张图承担三种责任

| 对象 | 节点代表什么 | 边代表什么 | 建议生命周期 |
|---|---|---|---|
| 语法结构 | 源程序的构造 | 语法包含关系 | 保留源码结构及来源 |
| 局部 elaboration 图 | 可以独立受阻的义务或计算 | 某个观察所等待的信息 | 一次受控的推断区域 |
| 增量 query 图 | 值得缓存的语义结果 | 实际读取的稳定输入 | 跨查询、跨编辑复用 |

这是草稿 §4–6、§51–53 的主线。第三张图里不需要为每个字段读取建立一个 query；第二张图里也不需要为每个 AST 节点创建协程。

但还需要补一个细分：局部等待队列与“允许留给实例化的残余计算”不是同一份数据。后者可以成为稳定的 query 结果，前者包含本次求解的临时状态。这个问题放在 C1 拍板。

### 2. 遇到 wait 不代表当前整个父计算都应被捕获

考虑第一个实参里的 lambda 等待第二个实参提供类型。若暂停捕获了整个调用的 elaboration，第二个实参就永远没有机会开始。草稿 §12、§15、§33–34、§188 已抓住这个关键。

需要在能够继续安排兄弟工作的边界建立子任务，然后由子任务的局部观察暂停。是否使用代数效应、显式状态机或协程，是暂停点的实现载体；这些载体都必须满足同一个边界契约。

“遇到缺失信息就自动变成任务”也不够。首先要判断信息是否有其他生产者，以及当前操作是否允许推导它。新鲜推断变量可以被合法约束赋值；定义端刚性参数则不能靠等待或强制赋值变成某个具体类型。

### 3. 信息已产生，与规则允许使用该信息，是两回事

草稿 §18 使用后续参数协助前面 lambda 的例子；§44–47、§165–167 又讨论前缀局部推断的可能限制。两者代表可选的语言政策，不能让 ready queue 的顺序暗中决定。

无论选哪一种，分支假设、实现候选的临时替换、phase 和实现环境都必须限制事实的适用范围。共享 solver 不等于所有任务共享一个没有条件的命题集合。

Runtime 实参按源码顺序求值已经确定，但这不自动规定编译器收集类型信息的次序。C2 只讨论后者。

### 4. “没有答案”至少分为等待、合法残余与检查失败

草稿 §126 的 Known / Blocked / Error 很适合作为某一次局部观察的接口，但它不应直接取代每个子系统原有的结果分类。

特别是 PTC 的 Unknown 可能来自预算耗尽、未支持片段或缺少具体见证。只有能指出尚未就绪的输入及其生产者时，才适合转成等待票据。预算耗尽不能转换成“等待这个类型有一天变具体”，更不能转换成反证。

队列暂时为空时，还要检查必需义务是否完成、是否存在失败生产者、是否形成依赖环，以及剩余工作是否属于语言已经允许的延迟。不能以“目前没有任务可跑”作为类型检查成功的判据。

## 已确认的约束，直接继承

这些规则不作为新问题重新征求意见：

1. **Normal form 不展开。** 草稿中的 normalize、require_head 等抽象操作，落实到 Flurry 时只允许观察既有语义准许的形态。Identity<T> 不因其函数体返回 T 就与 T 建立关系。pure 也不授权展开。
2. **Ordinary/loose 由构造决定。** 调度困难不能降低检查强度，合法 defer 则应被正确保留。
3. **PTC 只处理类型命题。** Memory view、runtime 可达关系和程序状态规格进入程序验证层。编译主题描述两者的交付边界，不把验证算术塞进 PTC。
4. **实现选择按结构精度和适用性。** 更精确候选未决时，不能因为较宽候选先完成就提交它；Unknown 不是“不实现”。
5. **普通实参运行时求值顺序与次数不变。** 重跑推断工作不代表重跑程序的 runtime 求值；quote fn 的普通实参仍求值一次。
6. **编译时纯性与缓存许可不同。** 缓存需要完整依赖和合法值身份；不能因为计算被包成 query，就省掉必须发生的不纯执行。
7. **投影声明的接口可先于完整代码生成。** build 默认指 host pipeline，设备配置显式读取包元数据；编译后端不能修改已经交付的类型接口。
8. **错误与效应保留不同 ABI。** 若编译器使用效应实现等待，等待 continuation 属于编译器本次 elaboration 的内部控制；它不改变源程序的 error/effect 语义。

## C1. Normalization 的残余计算，与 region finish 的冻结结果，怎样衔接？

当前正式文档 [normalization-and-instantiation](/home/fin/luna/docs/comptime/normalization-and-instantiation.md) 的“Query 图的输入与状态”和算法第 8 步要求交付已完成的检查、可用契约和剩余计算依赖。Instantiation 在输入具备后继续。

草稿 §171–175 则要求 query 边界清除 region-local ids、holes 与未完成的必需 metas。我的判断是，两者可以兼容，但必须区分“保留有定义的参数化工作”与“把一次活跃推断挂在缓存里”。

- **A. 冻结稳定的残余计算，销毁本次活跃推断状态。** Query 结果可以包含显式绑定的参数、已检查契约、合法延迟的计算及依赖；不能包含尚无语义归属的临时洞、union-find 节点、waiter 或 continuation。实例化从稳定结果创建新的局部推断状态。缓存边界清楚，但需要设计残余计算如何保存绑定与适用前提。
- **B. 缓存完整的暂停推断会话。** Instantiation 尽量继续原来的 metas 和 continuation；复用直观，但缓存必须管理编辑版本、环境有效期、分支快照和取消，跨会话复用也更困难。
- **C. 参数化定义仅保存检查摘要，残余计算不作为可复用的冻结产物。** 具体实例从源码或其他稳定 IR 重建所需计算。第一版持久格式较小，但重复工作和对两阶段关系的解释成本更高。

**预填答复：A。**

Frozen 不等于“所有值均已具体”。Frozen 的要求是所有可留待后续的未知都有稳定、显式的绑定和语义依据，而非仍依靠当前 solver 的活动内存。必检义务必须完成；合法延迟义务可以被重新表达成稳定产物。尚不能合法表达的未决选择不能为了让 region 结束而直接冻结成成功。

建议区分以下三类内容，名称只是实现说明：

| 内容 | Query 输出可否包含 |
|---|---|
| 绑定在定义上的参数、已证明且保留前提的契约 | 可以 |
| 有明确输入和合法延迟依据的残余计算 | 可以 |
| 未解决的本地推断洞、等待队列、捕获运行栈 | 不可以 |

## C2. 同一个调用内，后面的实参能否帮助前面的实参完成推断？

下面是完整的教学函数。这个例子只用于区分候选规则；示例是否在没有额外标注时被接受，取决于本题决定。

```flurry
use std.prelude.*;

fn apply_first(function: fn(T) -> U, value: T) -> U
where T, U
{
    function(value)
}

test {
    let result = apply_first(|item| item + 1, 41i32);
    println("{}", result);
}
```

处理 lambda 时，形参类型还可能未知；后面的 41i32 可以约束 T。这个例子与草稿 §18 的兄弟参数场景相同，但使用 Flurry 已有语法。

- **A. 一个调用的共同约束可以双向协作。** Callee 签名、外围期望及各实参提供的合法事实可共同约束该调用的新鲜推断变量；允许后面的参数帮助前面的 lambda。必须保留作用域、阶段、分支和候选事务的适用范围，不把它扩大为整个函数体的无限制反向推断。
- **B. 参数按前缀取得信息。** 第 i 个参数只读取 callee、外围期望和此前参数允许提供的事实。上例需要给 lambda 补足类型信息；实现须编码可见性，不能靠碰巧先跑哪个任务保证限制。
- **C. 仅显式标注及已知参数类型可反向传播。** 后面的已知类型可以帮助前面，但需要搜索实现或继续推断才能取得的结论不反向传播。推断范围较窄，却需要进一步界定“已知”的规则，不能用完成时间代替定义。

**预填答复：A。**

限制单位是该次调用及其合法上下文，而非源文件的任意已知事实。每个候选的试探信息只留在候选内部，提交后的结果才能向父调用公开。外围期望与实参不一致时报告冲突，不采取“先到者决定类型”的规则。

按 A，上例的 T 为 i32，lambda 取得 fn(i32) -> i32 的上下文并输出 42。编译器为了取得类型信息可以先检查第二个参数，但生成程序仍遵守既有实参求值次序。

## C3. 实现候选试探期间，需要执行不能安全重放的 comptime 计算时，怎样处理？

当前 [实现选择](/home/fin/luna/docs/traits/implementation-resolution.md) 要求候选拥有独立回退点。草稿 §29–30、§66–67 也要求暂存试探结果，提交后再发布。

回退替换表不能撤销已经发生的外部操作，也不能自动撤销所有已发出的诊断。更隐蔽的问题是：一个 goal 被唤醒重试时，若从头执行，其中已经完成的编译时调用会不会执行第二次。

- **A. 试探只运行可隔离、可重放的检查；不可安全重放的执行留到选择确定后。** 候选选择依靠已交付契约与允许的纯计算。若必须靠执行一个未提交候选的非重放操作才能判定其适用性，则要求显式消歧或报告缺少可用依据，不能自行尝试外部副作用。已经发生的必要执行在恢复时从进度记录之后继续。
- **B. 为可支持的 comptime 效果建立事务协议。** 候选可以暂存诊断及其他能明确提交或丢弃的效果；没有事务实现的操作禁止进入试探。表达能力较大，但每种可见效果都需要协议，不等于任意 I/O 都能回滚。
- **C. 此类调用一律先要求唯一显式候选。** 先由作者提供足够标注或显式选择，再执行相关计算；减少试探机制，但对本可借助纯计算解决的调用也更保守。

**预填答复：A。**

这里不新增“所有 comptime 函数必须 pure”的规则，也不阻止源程序已明确要求的一次普通执行为推断提供结果。限制的是：不能为了探索一个可能被放弃的候选，就提前执行不应发生的工作。

试探产生的错误先作为候选失败依据保存。最终没有可行选择时，诊断可以说明各候选的失败原因；不能在稍后成功选择其他候选后，仍把已放弃候选的试探错误作为整个程序的错误发布。

如果适用性依赖一次不可在试探中执行的操作，排队等待不是解决方案；系统必须指出缺少哪个明确选择或契约依据。这个边界应直接反映到诊断。

## 我建议直接采用的实现骨架

这一节是候选实现方案，等待你审阅；伪代码不引入 Flurry 公开 API，也不要求编译器从第一天就具备完整效应 runtime。

### 局部状态与观察

一个推断区域持有：新鲜推断变量、受适用前提约束的事实、候选事务、待完成项、ready queue 和等待登记。语法递归可以在没有阻塞时直接返回结果。只有需要保留独立进度的工作才成为 goal。

```text
observe(request, allowed_context):
    inspect committed facts visible to allowed_context
    perform locally justified progress, if any
    if result is established:
        return Known(result, evidence)
    if a required input has a real pending producer:
        return Blocked(input_identity, observed_generation)
    return the domain's unresolved or failure result
```

最后一行故意不一概叫 Error：具体领域可以交付合法残余、歧义、未支持片段或预算诊断。是否允许残余由语言检查边界决定，不由 observation 接口临时授权。

### 等待登记与唤醒

```text
run(goal):
    outcome = attempt(goal)
    if outcome is Done:
        record completed result
    if outcome is Blocked:
        register watcher against observed input generation
        if that generation has changed:
            enqueue goal once
    if outcome is Failed:
        record failure and notify dependent work

commit(candidate):
    atomically publish the accepted facts and term results
    invalidate affected observations
    enqueue affected work
    do not re-enter elaboration during the partial update
```

这里至少有六条实现不变量：

1. 检查与登记之间的状态变化不能丢失唤醒。即便第一版单线程，也要防止调用其他逻辑引起的重入。
2. 多个触发源可以唤醒同一个 goal，但不能重复恢复一次性 continuation。
3. Union-find 代表元合并后，原代表元上的观察仍能收到变化；只监听一个旧节点地址会漏掉后续结果。
4. 分支和候选回退时，同时恢复替换、适用前提、证据、term hole、暂存诊断与相应登记。失败的试探不能留下可被其他任务读到的事实。
5. 生产者失败或取消时，消费者得到相应状态，不永久等待。区域退出时不留下仍捕获本地状态的工作。
6. 唤醒只要求再次观察，不保证所需形态已经就绪；一次变化可能只是 T 从未知变成另一个仍未知的项。

### 结束与冻结

```text
finish(region):
    drain runnable work under the fixed inference rules
    classify remaining obligations and producers
    reject missing required evidence or failed dependencies
    diagnose unresolved cycles and ambiguities as required
    serialize only language-permitted residual work
    resolve local references into stable bound representations
    discard local solver state, waiters and continuations
    return checked frozen result
```

普通函数之间的递归引用，并不自动构成错误的 query 环。接口、函数体和实例代码生成应分开依赖；已经存在的函数签名可以支持合法递归。需要自身尚未产生的具体值来确定自身的循环，则要提供可读的依赖路径。两种情况不能共用一个“遇到正在处理就返回占位成功”的策略。

### 载体与成本

建议先固定上述语义接口，用局部递归加显式任务状态验证正确性。以后可以用一次性 continuation 承载深层 wait，而不改变 facts、observation、commit 和 freeze 的契约。草稿 §85–88、§135、§178、§194 已给出这种实现自由度。

这不是预先否定效应实现；我认为效应最适合解决“深层调用怎样交回控制”这一点。类型规则和缓存边界先独立成立，才能比较不同承载方式的实际成本。

不把“不阻塞时零分配”或全算法 O(V + E) 写成承诺。可测指标包括：创建 goal 数、真实挂起数、无效唤醒数、候选试探与回退次数、重复观察次数、冷构建耗时、编辑后的重用比例，以及冻结产物的体积。图遍历的成本与 PTC 求解、comptime 执行、实例数量增长分别记账。

## 我对这篇草稿的理解

依据：[elaboration-of-elaboration](/home/fin/vilya/examples/2026-10-7-elaboration-of-elaboration.md)。阅读覆盖全文 200 节；下面按问题引用章节，避免把长文的组织顺序直接变成文档目录。

这篇草稿的核心是：让传统的递归 elaborator 保留直接执行的快路径，同时允许少数真正缺少信息的工作暂停，让能够提供信息的其他工作继续进行。类型规则决定可以取得什么事实，solver 维护事实，scheduler 决定何时再次尝试。Continuation 可以承载暂停点，但它本身没有增加一条推断规则。

我赞同这条架构方向。它处理的是 elaboration 的组织、信息流与成本，而不是单独提出了一套新的类型推断理论。是否成立，需要检查调度替换是否保持结果、暂停边界是否留下可运行的生产者，以及局部状态能否在定义检查与实例化之间正确交付。仅凭能表达 wait/resume，还不能证明这些性质。

我认为下面四个区分应该贯穿编译主题。

### 1. 三张图承担三种责任

| 对象 | 节点代表什么 | 边代表什么 | 建议生命周期 |
|---|---|---|---|
| 语法结构 | 源程序的构造 | 语法包含关系 | 保留源码结构及来源 |
| 局部 elaboration 图 | 可以独立受阻的义务或计算 | 某个观察所等待的信息 | 一次受控的推断区域 |
| 增量 query 图 | 值得缓存的语义结果 | 实际读取的稳定输入 | 跨查询、跨编辑复用 |

这是草稿 §4–6、§51–53 的主线。第三张图里不需要为每个字段读取建立一个 query；第二张图里也不需要为每个 AST 节点创建协程。

但还需要补一个细分：局部等待队列与“允许留给实例化的残余计算”不是同一份数据。后者可以成为稳定的 query 结果，前者包含本次求解的临时状态。这个问题放在 C1 拍板。

### 2. 遇到 wait 不代表当前整个父计算都应被捕获

考虑第一个实参里的 lambda 等待第二个实参提供类型。若暂停捕获了整个调用的 elaboration，第二个实参就永远没有机会开始。草稿 §12、§15、§33–34、§188 已抓住这个关键。

需要在能够继续安排兄弟工作的边界建立子任务，然后由子任务的局部观察暂停。是否使用代数效应、显式状态机或协程，是暂停点的实现载体；这些载体都必须满足同一个边界契约。

“遇到缺失信息就自动变成任务”也不够。首先要判断信息是否有其他生产者，以及当前操作是否允许推导它。新鲜推断变量可以被合法约束赋值；定义端刚性参数则不能靠等待或强制赋值变成某个具体类型。

### 3. 信息已产生，与规则允许使用该信息，是两回事

草稿 §18 使用后续参数协助前面 lambda 的例子；§44–47、§165–167 又讨论前缀局部推断的可能限制。两者代表可选的语言政策，不能让 ready queue 的顺序暗中决定。

无论选哪一种，分支假设、实现候选的临时替换、phase 和实现环境都必须限制事实的适用范围。共享 solver 不等于所有任务共享一个没有条件的命题集合。

Runtime 实参按源码顺序求值已经确定，但这不自动规定编译器收集类型信息的次序。C2 只讨论后者。

### 4. “没有答案”至少分为等待、合法残余与检查失败

草稿 §126 的 Known / Blocked / Error 很适合作为某一次局部观察的接口，但它不应直接取代每个子系统原有的结果分类。

特别是 PTC 的 Unknown 可能来自预算耗尽、未支持片段或缺少具体见证。只有能指出尚未就绪的输入及其生产者时，才适合转成等待票据。预算耗尽不能转换成“等待这个类型有一天变具体”，更不能转换成反证。

队列暂时为空时，还要检查必需义务是否完成、是否存在失败生产者、是否形成依赖环，以及剩余工作是否属于语言已经允许的延迟。不能以“目前没有任务可跑”作为类型检查成功的判据。

## 已确认的约束，直接继承

这些规则不作为新问题重新征求意见：

1. **Normal form 不展开。** 草稿中的 normalize、require_head 等抽象操作，落实到 Flurry 时只允许观察既有语义准许的形态。Identity<T> 不因其函数体返回 T 就与 T 建立关系。pure 也不授权展开。
2. **Ordinary/loose 由构造决定。** 调度困难不能降低检查强度，合法 defer 则应被正确保留。
3. **PTC 只处理类型命题。** Memory view、runtime 可达关系和程序状态规格进入程序验证层。编译主题描述两者的交付边界，不把验证算术塞进 PTC。

5. **普通实参运行时求值顺序与次数不变。** 重跑推断工作不代表重跑程序的 runtime 求值；quote fn 的普通实参仍求值一次。

8. **错误与效应保留不同 ABI。** 若编译器使用效应实现等待，等待 continuation 属于编译器本次 elaboration 的内部控制；它不改变源程序的 error/effect 语义。

## C1. Normalization 的残余计算，与 region finish 的冻结结果，怎样衔接？

当前正式文档 [normalization-and-instantiation](/home/fin/luna/docs/comptime/normalization-and-instantiation.md) 的“Query 图的输入与状态”和算法第 8 步要求交付已完成的检查、可用契约和剩余计算依赖。Instantiation 在输入具备后继续。

草稿 §171–175 则要求 query 边界清除 region-local ids、holes 与未完成的必需 metas。我的判断是，两者可以兼容，但必须区分“保留有定义的参数化工作”与“把一次活跃推断挂在缓存里”。

- **A. 冻结稳定的残余计算，销毁本次活跃推断状态。** Query 结果可以包含显式绑定的参数、已检查契约、合法延迟的计算及依赖；不能包含尚无语义归属的临时洞、union-find 节点、waiter 或 continuation。实例化从稳定结果创建新的局部推断状态。缓存边界清楚，但需要设计残余计算如何保存绑定与适用前提。
- **B. 缓存完整的暂停推断会话。** Instantiation 尽量继续原来的 metas 和 continuation；复用直观，但缓存必须管理编辑版本、环境有效期、分支快照和取消，跨会话复用也更困难。
- **C. 参数化定义仅保存检查摘要，残余计算不作为可复用的冻结产物。** 具体实例从源码或其他稳定 IR 重建所需计算。第一版持久格式较小，但重复工作和对两阶段关系的解释成本更高。

Frozen 不等于“所有值均已具体”。Frozen 的要求是所有可留待后续的未知都有稳定、显式的绑定和语义依据，而非仍依靠当前 solver 的活动内存。必检义务必须完成；合法延迟义务可以被重新表达成稳定产物。尚不能合法表达的未决选择不能为了让 region 结束而直接冻结成成功。

| 绑定在定义上的参数、已证明且保留前提的契约 | 可以 |
| 有明确输入和合法延迟依据的残余计算 | 可以 |
| 未解决的本地推断洞、等待队列、捕获运行栈 | 不可以 |

## C2. 同一个调用内，后面的实参能否帮助前面的实参完成推断？

下面是完整的教学函数。这个例子只用于区分候选规则；示例是否在没有额外标注时被接受，取决于本题决定。

```flurry
use std.prelude.*;

fn apply_first(function: fn(T) -> U, value: T) -> U
where T, U
{
    function(value)
}

test {
    let result = apply_first(|item| item + 1, 41i32);
    println("{}", result);
}
```

处理 lambda 时，形参类型还可能未知；后面的 41i32 可以约束 T。这个例子与草稿 §18 的兄弟参数场景相同，但使用 Flurry 已有语法。

- **A. 一个调用的共同约束可以双向协作。** Callee 签名、外围期望及各实参提供的合法事实可共同约束该调用的新鲜推断变量；允许后面的参数帮助前面的 lambda。必须保留作用域、阶段、分支和候选事务的适用范围，不把它扩大为整个函数体的无限制反向推断。
- **B. 参数按前缀取得信息。** 第 i 个参数只读取 callee、外围期望和此前参数允许提供的事实。上例需要给 lambda 补足类型信息；实现须编码可见性，不能靠碰巧先跑哪个任务保证限制。
- **C. 仅显式标注及已知参数类型可反向传播。** 后面的已知类型可以帮助前面，但需要搜索实现或继续推断才能取得的结论不反向传播。推断范围较窄，却需要进一步界定“已知”的规则，不能用完成时间代替定义。

**预填答复：A。**

限制单位是该次调用及其合法上下文，而非源文件的任意已知事实。每个候选的试探信息只留在候选内部，提交后的结果才能向父调用公开。外围期望与实参不一致时报告冲突，不采取“先到者决定类型”的规则。

## C3. 实现候选试探期间，需要执行不能安全重放的 comptime 计算时，怎样处理？

当前 [实现选择](/home/fin/luna/docs/traits/implementation-resolution.md) 要求候选拥有独立回退点。草稿 §29–30、§66–67 也要求暂存试探结果，提交后再发布。

回退替换表不能撤销已经发生的外部操作，也不能自动撤销所有已发出的诊断。更隐蔽的问题是：一个 goal 被唤醒重试时，若从头执行，其中已经完成的编译时调用会不会执行第二次。

- **A. 试探只运行可隔离、可重放的检查；不可安全重放的执行留到选择确定后。** 候选选择依靠已交付契约与允许的纯计算。若必须靠执行一个未提交候选的非重放操作才能判定其适用性，则要求显式消歧或报告缺少可用依据，不能自行尝试外部副作用。已经发生的必要执行在恢复时从进度记录之后继续。
- **B. 为可支持的 comptime 效果建立事务协议。** 候选可以暂存诊断及其他能明确提交或丢弃的效果；没有事务实现的操作禁止进入试探。表达能力较大，但每种可见效果都需要协议，不等于任意 I/O 都能回滚。
- **C. 此类调用一律先要求唯一显式候选。** 先由作者提供足够标注或显式选择，再执行相关计算；减少试探机制，但对本可借助纯计算解决的调用也更保守。

**预填答复：A。**

这里不新增“所有 comptime 函数必须 pure”的规则，也不阻止源程序已明确要求的一次普通执行为推断提供结果。限制的是：不能为了探索一个可能被放弃的候选，就提前执行不应发生的工作。

试探产生的错误先作为候选失败依据保存。最终没有可行选择时，诊断可以说明各候选的失败原因；不能在稍后成功选择其他候选后，仍把已放弃候选的试探错误作为整个程序的错误发布。

如果适用性依赖一次不可在试探中执行的操作，排队等待不是解决方案；系统必须指出缺少哪个明确选择或契约依据。这个边界应直接反映到诊断。

## 我建议直接采用的实现骨架

这一节是候选实现方案，等待你审阅；伪代码不引入 Flurry 公开 API，也不要求编译器从第一天就具备完整效应 runtime。

### 局部状态与观察

一个推断区域持有：新鲜推断变量、受适用前提约束的事实、候选事务、待完成项、ready queue 和等待登记。语法递归可以在没有阻塞时直接返回结果。只有需要保留独立进度的工作才成为 goal。

```text
observe(request, allowed_context):
    inspect committed facts visible to allowed_context
    perform locally justified progress, if any
    if result is established:
        return Known(result, evidence)
    if a required input has a real pending producer:
        return Blocked(input_identity, observed_generation)
    return the domain's unresolved or failure result
```

最后一行故意不一概叫 Error：具体领域可以交付合法残余、歧义、未支持片段或预算诊断。是否允许残余由语言检查边界决定，不由 observation 接口临时授权。

### 等待登记与唤醒

```text
run(goal):
    outcome = attempt(goal)
    if outcome is Done:
        record completed result
    if outcome is Blocked:
        register watcher against observed input generation
        if that generation has changed:
            enqueue goal once
    if outcome is Failed:
        record failure and notify dependent work

commit(candidate):
    atomically publish the accepted facts and term results
    invalidate affected observations
    enqueue affected work
    do not re-enter elaboration during the partial update
```

这里至少有六条实现不变量：

1. 检查与登记之间的状态变化不能丢失唤醒。即便第一版单线程，也要防止调用其他逻辑引起的重入。
2. 多个触发源可以唤醒同一个 goal，但不能重复恢复一次性 continuation。
3. Union-find 代表元合并后，原代表元上的观察仍能收到变化；只监听一个旧节点地址会漏掉后续结果。
4. 分支和候选回退时，同时恢复替换、适用前提、证据、term hole、暂存诊断与相应登记。失败的试探不能留下可被其他任务读到的事实。
5. 生产者失败或取消时，消费者得到相应状态，不永久等待。区域退出时不留下仍捕获本地状态的工作。
6. 唤醒只要求再次观察，不保证所需形态已经就绪；一次变化可能只是 T 从未知变成另一个仍未知的项。

### 结束与冻结

```text
finish(region):
    drain runnable work under the fixed inference rules
    classify remaining obligations and producers
    reject missing required evidence or failed dependencies
    diagnose unresolved cycles and ambiguities as required
    serialize only language-permitted residual work
    resolve local references into stable bound representations
    discard local solver state, waiters and continuations
    return checked frozen result
```

普通函数之间的递归引用，并不自动构成错误的 query 环。接口、函数体和实例代码生成应分开依赖；已经存在的函数签名可以支持合法递归。需要自身尚未产生的具体值来确定自身的循环，则要提供可读的依赖路径。两种情况不能共用一个“遇到正在处理就返回占位成功”的策略。

### 载体与成本

建议先固定上述语义接口，用局部递归加显式任务状态验证正确性。以后可以用一次性 continuation 承载深层 wait，而不改变 facts、observation、commit 和 freeze 的契约。草稿 §85–88、§135、§178、§194 已给出这种实现自由度。

这不是预先否定效应实现；我认为效应最适合解决“深层调用怎样交回控制”这一点。类型规则和缓存边界先独立成立，才能比较不同承载方式的实际成本。

不把“不阻塞时零分配”或全算法 O(V + E) 写成承诺。可测指标包括：创建 goal 数、真实挂起数、无效唤醒数、候选试探与回退次数、重复观察次数、冷构建耗时、编辑后的重用比例，以及冻结产物的体积。图遍历的成本与 PTC 求解、comptime 执行、实例数量增长分别记账。

这里规划验收案例，不在本轮启动编译器开发：

2. 同一程序改变 ready queue 出队顺序，仍得到相同的语义结果；独立错误的展示次序可以由诊断策略统一。
3. 宽泛实现已适用，更精确实现仍未决：保留义务，不能提前提交宽泛实现。
4. 失败候选回退后，不留下类型赋值、局部假设或已经发布的试探诊断。
5. 范式 Identity<T> 保留自身身份，既不展开，也不把等待 T 的任务误认作等待头展开。
6. PTC 因预算返回 Unknown，诊断说明实际原因，不伪造一个永远不会被唤醒的输入依赖。
7. 合法残余计算经过冻结、缓存、实例化，保持绑定及控制依赖，不保存上一轮推断的本地对象。
8. Query 缓存命中恢复应有的结果与诊断；不能跳过必须执行的 comptime 工作。
9. 两个普通递归函数通过各自已知签名检查；真正需要自身结果的计算环给出依赖诊断。
10. 最终交付 runtime 实例时，必需类型、调用证据、布局和检查均已具备；临时错误占位仅可服务编辑器恢复，不进入代码生成。
