下面六题围绕这些边界，不预设公开 trait 名、产物注册 API 或某个后端的内部结构。

## P1. 投影目标在形成 IIR 实例前，还是之后确定？

草稿里的汇编 wrapper 会读取 `build.target.arch` 和 `build.target.features`。如果这些条件已经按 host 目标在 instantiation 中消去，再将所得 IIR 交给另一目标，后端不能恢复被删去的分支；`usize`、布局等目标相关计算也有同样的问题。

现行 [build 规则](../docs/code-organization/builtin-packages.md) 已规定：查询属于定义所在包的具体构建实例，不随普通调用或内联改读调用者环境。因此这里应明确投影实例的目标，不能把 build 改成一份动态全局状态。

- **A. 投影在形成目标实例之前确定其目标环境。** 同一源码可以在不同目标构建实例下形成 IIR；名称来源和包归属保留。pipeline 最终收到的是已经按其目标完成相应实例化的函数。
- **B. 投影只接收所属构建实例原本产生的 IIR。** pipeline 可以改变后端处理方式，但不能改变前端已使用的目标；要编译 CUDA，先由构建系统单独建立相应目标实例。

**预填答复：A。** pipeline 的目标是实例形成的明确输入；允许构建系统事先提供，也允许投影配置要求相应实例，但不能事后拿 host IIR 冒充 device IIR。build 仍属于定义所在包的这份构建实例。仅仅更换后端实现、没有改变任何语义输入时，不必强制重做前端。

## P2. 被投影入口调用普通 helper 时，投影到哪里为止？

例如 CUDA 入口调用了没有投影属性的普通数学函数，该数学函数又调用另外两个函数。只有根入口写属性最便于复用；另一方面，直接把整个依赖包都编译成 device 代码也没有必要。

- **A. 从入口沿实际需要的调用与数据依赖取得目标版本。** 普通 helper 不必逐个加属性；不支持的依赖在目标合规检查时报错。显式指向其他执行域的入口需要合法桥接，不能自动当成本域 helper。
- **B. 每个跨定义调用都要求显式投影声明。** 接入集合更直观，但普通工具函数及其依赖需要大量重复标记。

**预填答复：A。** 以本次已实例化程序实际需要的依赖为准；编译期已排除的分支不引入目标代码。递归调用图保持有限实例图，不要求强制内联。函数值和间接调用必须交付本 pipeline 支持的目标入口与环境；不能把宿主函数指针原样带进 device 程序。是否支持某种递归或间接调用由具体 pipeline 的合规契约决定。

## P3. 投影后的函数在原环境中，以什么身份被使用？

`^cuda.global pub unsafe fn matmul(...)` 有普通的 Flurry 签名，但 CUDA kernel 入口不自动等于可按 CPU 函数 ABI 调用的地址。内联调用、取函数值与提交一次 kernel 工作也不是同一种操作。

- **A. 投影声明形成目标入口；跨执行域使用由 pipeline／库的明确桥接协议提供。** 原签名用于检查目标主体，不自动承诺一个同签名的 host 调用。库可以另外交付启动接口、句柄或包装函数。
- **B. 投影属性同时要求生成 host 调用包装。** 源码对 matmul 的普通调用固定接到该包装，启动参数、同步方式和返回契约须由投影接口给出。
- **C. 投影默认额外生成一个目标版本，原函数始终保留普通 host 版本。** 使用者另行选择目标入口；含 device 专用操作的原主体必须有合法的 host 处理策略。

**预填答复：A。** 语言保留入口和 ABI 的边界，具体库决定怎样启动与等待。某个 pipeline 可以明确承诺生成 host 包装，但不让所有投影都隐式改变普通函数调用语义。公开名称、可取得的入口值及其调用协议必须与实际产物一致，不能得到一个指向另一执行域却伪装成本机函数的指针。

## P4. Intrinsic 参数完全开放时，结果类型从哪里来？

我接受“不由通用 IR 检查 intrinsic 的参数”，但草稿中的两种结果流仍需要区分：fma 的结果最后交付为 f32；load 的结果则先绑定到 vx，再流入下一条向量 intrinsic。后一种没有现成的外围结果类型可以反向提供。

这里不能用 runtime Any 填空；comptime Any 的通配规则也不会凭空产生机器表示。

- **A. 允许 pipeline 专属的结果节点推迟定型。** 它先在受限的 intrinsic 数据流中传递，pipeline 完成结果与表示检查；进入普通 Flurry 运算、对象存储或函数边界前必须兑现对应要求。这需要定义通用检查如何保留这些义务。
- **B. Intrinsic 入口提供最小结果接口。** 可以是已知结果类型，也可以是由操作标签及实际输入信息计算的结果形状。通用层据此建立结果；参数个数、操作数合法性和内存使用仍由 pipeline 负责，不顺带恢复一整套通用参数检查。
- **C. 仅允许使用处明确供应结果类型。** 声明、返回或合法的目标上下文必须确定每个结果，无法推得时要求注解；接口最少，但向量中间量会增加标注。

**预填答复：B。** 只要求交付供外围程序使用的结果接口，不限制 intrinsic 的开放操作数。无结果操作交付 void，多结果可以交付已声明的聚合接口。若某个后端确实需要只有自身理解的中间表示，应明确增加 A 的受限通道，不把“参数不检查”悄悄扩展成任意未知类型可以流入全部 Flurry 程序。

## P5. 通用优化器面对尚未解释的 intrinsic，可以做什么？

unsafe 说明调用方承担相应责任，但不表示该操作纯、可以重复执行、可以删除或可以跨内存访问重排。load、store、读时钟、带状态的设备提交以及改变控制流的指令，后果差别很大。

- **A. 默认保守保留，只有明确的操作契约才能缩小约束。** 通用优化先保留执行及顺序责任；目标 pipeline 识别后按操作语义优化。已有可信描述时，可以提前开放对应优化。
- **B. 每个 intrinsic 必须先给出完整的内存、控制与其他可观察行为摘要。** 通用优化可以立即利用这些信息，但定义一个扩展节点的最低要求更高，未知行为不能仅靠 unsafe 留给后端。

**预填答复：A。** “忠实翻译汇编”至少要求不凭空丢失操作及其声明的约束；它不等于所有指令都必须按源码排列成完全相同的机器文本。结果、内存行为、寄存器／标志位约束和控制出口由目标协议解释。缺少安全变换的依据就保留；目标也没有定义某项必要行为时应拒绝。普通 wrapper 想对外承诺 memory effect 或纯度，仍要承担那份契约，不能从 unsafe 自动推得。

## P6. 返回 void 的 pipeline 回调如何向编译任务交付产物？

草稿的 pure comptime 回调通过宿主库编译 kernel，并能提交诊断，但函数自身返回 void。编译结果还需要代码、符号、链接关系和依赖；缓存命中时也不能只恢复一个 void，让目标文件消失。

现行 pure comptime 已经是可信的结果依赖承诺，本题不重新要求编译器验证其纯性，也不修改 normal form 的规则。

- **A. Pipeline 有受编译任务管理的输出通道。** 回调可保持 void；注册的产物、诊断和真实依赖一起构成该次编译任务的结果。缓存复用恢复这些结果，宿主文件写入只作为声明产物的交付步骤。
- **B. 回调必须显式返回一份产物描述。** 将草稿的 void 接口改为具体结果接口；统一编译层负责接收、缓存和落地。结果更显式，但要调整当前回调形式。

**预填答复：A。** 保留草稿的胶水风格，不在这里规定公开 API 名。任务记录实际使用的目标、工具实现、输入及外部依赖；失败不能留下被当成成功的半份产物。任意宿主 I/O 仍不因回调带 pure 就自动可缓存。IR handle 是访问入口，不以它的进程内数值作为跨次构建的语义身份。
