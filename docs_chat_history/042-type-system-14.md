### 审阅 1：Any、上下文检查与转换，能否按“使用处须可交付”收束？

**仍需裁决的原文边界：** [refined-type.md](/home/fin/luna/docs/type/refined-type.md:3) 写有“鸭子类型不可做返回值”；后来你确认了 Any 的调用点单态化、异型汇合和类型值用途。后者不自动证明任意 Any 返回都合法，也不支持继续保留一个没有区分场景的绝对禁令。

**我的最小规则候选：**

| 情况 | 建议的结果 |
|---|---|
| 返回类型描述含 Any，具体实例已能确定所需类型、操作与表示 | 不因出现 Any 这个名字单独拒绝 |
| 同一实例中，runtime 分支的结果类型仍不同 | 汇合仍为 Any；后续操作必须有足够事实和已定义的表示/传递机制 |
| 只有“各分支都可满足某性质”，没有足够的操作来源与表示依据 | 不能由编译器自动假设一个通用动态盒子或隐式类型分派 |
| 使用上下文已给目标类型 | 将目标要求传给分支，应用已确认的适配；没有目标时仍用原来的同型/Any 汇合规则 |
| 已有一层 option 值进入两层 option | 先保留源值整体，再添加外层；不自动递归改写源值里面的 null |
| 只知道参数的类型是 Type | 不自动获得布局、trait 或其他额外事实；需要什么就从声明、契约或可证明结构取得什么 |

“保留源值整体”的可观察差别是：已有的内层空值被装入外层成功分支，和直接得到外层空值不同。这里只用文字区分，不引入新的构造 API。无具体源类型的 null 按目标可选类型构造外层空值。error 的成功注入与行拓宽仍分开，不由 option 的嵌套规则代替。

这不要求所有类型参数必须显式写出每项已能推导的性质，也不把每个 Type 都宣告为不可表示；它只禁止从“尚未求出结果”凭空得出正、负性质。

- **A. 采用上述规则（建议）。** 以使用与交付需求划边界，修掉旧文的无条件返回禁令；不新增通用 runtime Any 包装。
- **B. 承诺异型 runtime 结果可以直接动态传递与分派。** 需要为包装、操作来源及调用交付定义额外运行时契约；这会扩大当前基础。
- **C. 保留 Any 返回位置的语法禁令。** 即使具体实例最终已知也拒绝该标注；应把它明确写成语言限制，并说明异型汇合如何在函数内部消化。

**预填答复：A。** 返回位置本身不是禁令；实例交付必须具备需要的信息。目标上下文先约束分支，嵌套 option 优先整体包装已有源值；普通类型参数没有未经声明或证明的默认布局/trait 事实。

### 审阅 2：% 环境限定的主体，是否可以是非函数类型？

**需要补齐的范围：** [closure-type.md](/home/fin/luna/docs/type/qualified-types/closure-type.md:1) 把闭包用于动态依赖值；你后来确认了 %、函数上的单一 Closure 限定、空环境函数等式，并说明 Buffer 逃逸时可捕获长度。它们确定了环境封闭的需求，但还没有单独裁决“公开的 % 限定是否只用于函数”。

以下 %C T 是既有闭包前缀的候选适用范围，C 是环境上下文，T 是主体；不是恢复旧前缀。

为了把“遵循 CMTT 等价”写成实现者能检查的边界，我先列出四条共同候选：

1. 上下文绑定的一致改名不改变类型；按依赖有效的声明次序对应检查，初版不额外引入任意环境排列的相等规则。
2. 已引用的外部 runtime identity 不是可以随绑定改名交换的局部名字；两个对象当前内容相同不足以使依赖相等。
3. 函数体或普通捕获值不同，不单独制造不同闭包类型；若它们参与类型依赖，则按相应依赖关系比较。
4. 类型等价与具体环境布局分开；布局优化必须保留环境取得契约，捕获不会自动延长被依赖对象的生命。

- **A. 可限定一般主体类型，采用上述四条（建议）。** %C T 表示使用 T 所需的环境；函数闭包是其中一类。一个已归一的主体最多有一个 Closure 上下文，显式合成环境后再限定，不把多个 Closure 当行求并集。
- **B. 公开的 % 只限定函数类型，其环境采用上述四条。** 非函数依赖值的封闭另由其声明/承载机制表达；初版须明确它的传递契约，不能直接从函数闭包类型推演所有依赖值。
- **C. 可限定一般类型，并额外把依赖允许的环境排列视为同型。** 放宽第 1 条的次序限制；需要有可检查的绑定对应与环境适配，不能仅按捕获集合去重。

**预填答复：A。** 环境限定可以作用于一般类型；空环境的一般限定也消去，函数的既有等式是其特例。采用四条等价与交付边界；环境可在外层共享或在必要处封闭，不要求每个值本体重复存一份指针。这里不决定对象移动、赋值和销毁后的 identity 有效性，那些仍归资源主题。

### 审阅 3：Self、Itself、itself 的指称，是否采用下表？

你已要求对 C 背景读者独立讲解它们。029 的成员要求示例已经使用 itself，但 030 的完整指称表仍未确认。没有这个表，refinement 章节容易在“被检查的是类型还是值”处说不清楚。

下表是**候选语义**，不是按拼写猜出的现有事实：

| 位置 | Self | Itself | itself |
|---|---|---|---|
| 普通类型成员或 trait/impl 的词法环境 | 所属类型或该 trait 的实现主体类型 | 仅在相应局部要求引入后使用 | 仅在相应局部要求引入后使用 |
| 对类型 T 的 refinement / 类型能力要求 | 保持外层词法含义；无外层绑定时不凭空补一个 | 当前受检类型 T | 没有普通运行时受检值；成员签名中的接收者槽另按下一行解释 |
| 对已知对象 v 的成员能力要求 | 保持外层词法含义 | v 的类型 | v；可用于说明要求中的接收者关系 |
| 嵌套的受检对象 | 不因嵌套要求自动改变 | 由最内层明确的受检对象绑定 | 同左；没有值对象时不产生值绑定 |

类型能力要求中的 itself / *itself 参数形式，是接收者关系槽；当要求用于检查某对象的成员时对应那个对象或其引用接收者。它不是对任意 comptime 值应用“指针类型构造”。现行 grammar 已为这两种参数形式单列产生式。

尤其当受检对象是类型 T 时，候选 Itself 指 T，不因 T 是一个编译时值就误换成元类型 Type。只写一个 T 的能力要求，不应凭空引入某个 runtime 实例。

- **A. 采用“词法 Self + 局部受检对象”的表（建议）。** 嵌套要求的指称可局部解释，类型主体与值主体有区别。
- **B. 类型 refinement 同时重新绑定 Self。** Self 在这类局部要求中也指 T；Itself 的用途需在表中进一步区分，否则不能把两者含糊写成同义词。
- **C. 不采用统一配对表，逐类要求分别规定替换。** 可以保留不同位置的特殊语义，但需要你改写对应行；不能只留“反身代词”这个名称。

**预填答复：A。** Self 保持词法来源，Itself / itself 随明确的受检对象绑定；类型要求不凭空生成运行时对象。不存在相应绑定的位置静态拒绝。本轮只定义 PTC/类型能力中的指称，不引入程序验证层的 runtime refinement。

### 审阅 4：类型身份与反射，是否固定为“结果身份明确、交付后结构稳定”？

已确认的纯工厂缓存复用、normal form 区别、typealias 命名方向和 transactional build 不重问。这里补齐此前普通声明身份与 038 反射候选的剩余部分。

**建议基线：**

| 对象或操作 | 建议契约 |
|---|---|
| 两个独立的普通 struct / enum / union 声明 | 字段或变体相同不自动同型；声明身份不同 |
| 参数化声明 | 同一声明的已给参数按相应等式/identity 契约比较；不能只看某次布局相同 |
| newtype | 建立区别于原类型及其他 newtype 声明的身份；保留与原类型的直接表示关系，不产生字段、方法或 trait 继承 |
| typealias | 指向目标类型，不产生另一个身份；工厂结果继续遵守已确认的执行/复用模型 |
| 结构观察与布局观察 | 分别满足自身前提；能获得字段结构不意味着偏移、尺寸已经全可求出 |
| 尚未应用的参数化定义 | 可以有定义信息；不自动当作已应用类型值，供所有类型反射接口使用 |
| 已交付的类型结果 | 字段/变体结构与影响表示的属性稳定；修改结构构造另一个结果 |
| build 失败 | 不交付可被其他程序依赖的半成品类型；不扩展成任意副作用或 impl 的全局事务 |

其中 newtype 的直接表示关系，建议明确为保留原类型本体的大小、对齐和合法值编码；区别在类型身份及接口。类型外的资源操作和 trait 实现仍按各自规则，不因“表示相同”自动继承。

- **A. 采用上述基线（建议）。** 名义区别、结构观察和表示依赖分别有依据；反射及已生成程序不会因原地改结构而失去依据。
- **B. 普通数据声明采用结构身份，newtype 仍建立名义区别。** 同字段结构可能同型，需要重新约束声明命名空间、trait 和递归类型的接合。
- **C. 类型可保留身份而在交付后修改结构。** 必须规定已有值、已生成代码和已证明性质如何失效或迁移；transactional build 单独不足以提供这些规则。

**预填答复：A。** 普通声明按身份区分；alias 不增身份；newtype 保留直接表示关系并隔离接口。反射按各观察的前提取得信息，交付后的类型结构稳定。若结构构造需要变化，形成另一个结果，不原地改变已有类型。


### 审阅 5：struct 构造是否采用“每个字段得到唯一初始化”的基线？

完全指名和声明顺序已经确认；这里收束 033 留下的默认值与构造完整性，不重问那两个决定。

**建议的可执行规则：**

1. 根据标签把显式构造项对应到字段；未知字段、重复指定同一字段静态拒绝。
2. 每个字段要么有显式输入，要么有声明默认表达式；两者都没有时静态拒绝，不自动补零或调用某个默认 trait。
3. 按字段声明顺序处理：有显式输入就求该输入，否则求该字段的默认表达式，再按字段类型检查/适配。被显式输入覆盖的默认表达式不执行。
4. 默认表达式在每次实际构造需要它时求值一次；不因定义中写了一份就默认跨实例共享结果。普通纯编译时缓存仍按已有规则，不由构造顺序另设例外。
5. 不把初始化顺序解释为普通 struct 的物理字段顺序。布局的具体结果由目标、类型和明确表示配置确定；没有指定的默认布局保证不从 C 补入。
6. 这套规则只决定构造输入、求值与完整性。途中失败后的资源清理、默认表达式能否使用部分构造对象等，按资源与初始化专题补齐，不在这里推导自动回滚或提前可用的 self。

- **A. 采用上述基线（建议）。** 构造行为可逐字段解释，不隐含默认填充；示例可检验副作用顺序与被覆盖默认值不执行。
- **B. 缺失字段也可自动由某种默认机制补齐。** 需要指定调用入口及适用条件，不能只借当前存在字段默认语法来推定。
- **C. 默认表达式在类型构造/定义时先算成共享默认值。** 会改变可变值和有行为表达式的观察结果；需说明每次实例构造是复制、共享还是再构造。

**预填答复：A。** 标签决定字段对应，声明顺序决定初始化次序；没有显式输入且没有声明默认值就是错误。默认表达式按每次构造的实际需要求值，不额外设计隐式默认 trait。

### 1. 从用户的问题进入

### 3. 七段骨架怎样落实

每篇仍采用 Intro、语法、正式定义、常见示例、跨语言差异、运行时实现引导、编译器实现引导。每篇有自己的内容重点：

- **Intro：** 一两个具体观察建立心智模型，不堆“支持哪些特性”的清单。
- **语法：** 只列本篇用到的轻量产生式；采用作者已确认的现行形式，不能复制旧备忘后再让读者猜哪里过时。
- **正式定义：** 给出可检验的成功条件和拒绝条件；例如什么同型、何时发生包装、什么信息缺失会阻止操作。
- **示例：** 每例承担一项推理任务；能从正式定义独立判断结果，不依赖作者私有库或被省略的资源契约。
- **跨语言差异：** 编写时核查实际对应物，只比较本版已决定的 Flurry 行为；不把文档目录或内部实现当差异。
- **运行时引导：** 对实际需要的表示、传递、环境与分支处理给出前后条件。只在编译时存在的机制就准确说明其目标程序后果，不虚构额外运行时。
- **编译器引导：** 说明操作输入、依赖事实、残余义务、实例交付条件与错误原因；核心算法保留 worklist、回滚、终止条件和未覆盖片段，不指向现有源码函数。

PTC 的 19 类原子模式和 11 个模块应形成可追溯的完整表；ROW 按 041 暂定方案修订适用域。公开谓词可通过派生规则扩展，不能在导览写成“只有 19 个 predicate”。Split、扩展、嵌入证据与布尔原子的区别要保留。

### 审阅 2：% 环境限定的主体，是否可以是非函数类型？

**需要补齐的范围：** [closure-type.md](/home/fin/luna/docs/type/qualified-types/closure-type.md:1) 把闭包用于动态依赖值；你后来确认了 %、函数上的单一 Closure 限定、空环境函数等式，并说明 Buffer 逃逸时可捕获长度。它们确定了环境封闭的需求，但还没有单独裁决“公开的 % 限定是否只用于函数”。

以下 %C T 是既有闭包前缀的候选适用范围，C 是环境上下文，T 是主体；不是恢复旧前缀。

为了把“遵循 CMTT 等价”写成实现者能检查的边界，我先列出四条共同候选：

1. 上下文绑定的一致改名不改变类型；按依赖有效的声明次序对应检查，初版不额外引入任意环境排列的相等规则。
2. 已引用的外部 runtime identity 不是可以随绑定改名交换的局部名字；两个对象当前内容相同不足以使依赖相等。
3. 函数体或普通捕获值不同，不单独制造不同闭包类型；若它们参与类型依赖，则按相应依赖关系比较。
4. 类型等价与具体环境布局分开；布局优化必须保留环境取得契约，捕获不会自动延长被依赖对象的生命。

- **A. 可限定一般主体类型，采用上述四条（建议）。** %C T 表示使用 T 所需的环境；函数闭包是其中一类。一个已归一的主体最多有一个 Closure 上下文，显式合成环境后再限定，不把多个 Closure 当行求并集。
- **B. 公开的 % 只限定函数类型，其环境采用上述四条。** 非函数依赖值的封闭另由其声明/承载机制表达；初版须明确它的传递契约，不能直接从函数闭包类型推演所有依赖值。
- **C. 可限定一般类型，并额外把依赖允许的环境排列视为同型。** 放宽第 1 条的次序限制；需要有可检查的绑定对应与环境适配，不能仅按捕获集合去重。

**预填答复：A。** 环境限定可以作用于一般类型；空环境的一般限定也消去，函数的既有等式是其特例。采用四条等价与交付边界；环境可在外层共享或在必要处封闭，不要求每个值本体重复存一份指针。这里不决定对象移动、赋值和销毁后的 identity 有效性，那些仍归资源主题。

### 审阅 3：Self、Itself、itself 的指称，是否采用下表？

你已要求对 C 背景读者独立讲解它们。029 的成员要求示例已经使用 itself，但 030 的完整指称表仍未确认。没有这个表，refinement 章节容易在“被检查的是类型还是值”处说不清楚。

下表是**候选语义**，不是按拼写猜出的现有事实：

| 位置 | Self | Itself | itself |
|---|---|---|---|
| 普通类型成员或 trait/impl 的词法环境 | 所属类型或该 trait 的实现主体类型 | 仅在相应局部要求引入后使用 | 仅在相应局部要求引入后使用 |
| 对类型 T 的 refinement / 类型能力要求 | 保持外层词法含义；无外层绑定时不凭空补一个 | 当前受检类型 T | 没有普通运行时受检值；成员签名中的接收者槽另按下一行解释 |
| 对已知对象 v 的成员能力要求 | 保持外层词法含义 | v 的类型 | v；可用于说明要求中的接收者关系 |
| 嵌套的受检对象 | 不因嵌套要求自动改变 | 由最内层明确的受检对象绑定 | 同左；没有值对象时不产生值绑定 |

类型能力要求中的 itself / *itself 参数形式，是接收者关系槽；当要求用于检查某对象的成员时对应那个对象或其引用接收者。它不是对任意 comptime 值应用“指针类型构造”。现行 grammar 已为这两种参数形式单列产生式。

尤其当受检对象是类型 T 时，候选 Itself 指 T，不因 T 是一个编译时值就误换成元类型 Type。只写一个 T 的能力要求，不应凭空引入某个 runtime 实例。

- **A. 采用“词法 Self + 局部受检对象”的表（建议）。** 嵌套要求的指称可局部解释，类型主体与值主体有区别。
- **B. 类型 refinement 同时重新绑定 Self。** Self 在这类局部要求中也指 T；Itself 的用途需在表中进一步区分，否则不能把两者含糊写成同义词。
- **C. 不采用统一配对表，逐类要求分别规定替换。** 可以保留不同位置的特殊语义，但需要你改写对应行；不能只留“反身代词”这个名称。

**预填答复：A。** Self 保持词法来源，Itself / itself 随明确的受检对象绑定；类型要求不凭空生成运行时对象。不存在相应绑定的位置静态拒绝。本轮只定义 PTC/类型能力中的指称，不引入程序验证层的 runtime refinement。

### 审阅 4：类型身份与反射，是否固定为“结果身份明确、交付后结构稳定”？

已确认的纯工厂缓存复用、normal form 区别、typealias 命名方向和 transactional build 不重问。这里补齐此前普通声明身份与 038 反射候选的剩余部分。

**建议基线：**

| 对象或操作 | 建议契约 |
|---|---|
| 两个独立的普通 struct / enum / union 声明 | 字段或变体相同不自动同型；声明身份不同 |
| 参数化声明 | 同一声明的已给参数按相应等式/identity 契约比较；不能只看某次布局相同 |
| newtype | 建立区别于原类型及其他 newtype 声明的身份；保留与原类型的直接表示关系，不产生字段、方法或 trait 继承 |
| typealias | 指向目标类型，不产生另一个身份；工厂结果继续遵守已确认的执行/复用模型 |
| 结构观察与布局观察 | 分别满足自身前提；能获得字段结构不意味着偏移、尺寸已经全可求出 |
| 尚未应用的参数化定义 | 可以有定义信息；不自动当作已应用类型值，供所有类型反射接口使用 |
| 已交付的类型结果 | 字段/变体结构与影响表示的属性稳定；修改结构构造另一个结果 |
| build 失败 | 不交付可被其他程序依赖的半成品类型；不扩展成任意副作用或 impl 的全局事务 |

其中 newtype 的直接表示关系，建议明确为保留原类型本体的大小、对齐和合法值编码；区别在类型身份及接口。类型外的资源操作和 trait 实现仍按各自规则，不因“表示相同”自动继承。

- **A. 采用上述基线（建议）。** 名义区别、结构观察和表示依赖分别有依据；反射及已生成程序不会因原地改结构而失去依据。
- **B. 普通数据声明采用结构身份，newtype 仍建立名义区别。** 同字段结构可能同型，需要重新约束声明命名空间、trait 和递归类型的接合。
- **C. 类型可保留身份而在交付后修改结构。** 必须规定已有值、已生成代码和已证明性质如何失效或迁移；transactional build 单独不足以提供这些规则。

**预填答复：A。** 普通声明按身份区分；alias 不增身份；newtype 保留直接表示关系并隔离接口。反射按各观察的前提取得信息，交付后的类型结构稳定。若结构构造需要变化，形成另一个结果，不原地改变已有类型。

2. 每个字段要么有显式输入，要么有声明默认表达式；两者都没有时静态拒绝，不自动补零或调用某个默认 trait。
3. 按字段声明顺序处理：有显式输入就求该输入，否则求该字段的默认表达式，再按字段类型检查/适配。被显式输入覆盖的默认表达式不执行。
4. 默认表达式在每次实际构造需要它时求值一次；不因定义中写了一份就默认跨实例共享结果。普通纯编译时缓存仍按已有规则，不由构造顺序另设例外。
5. 不把初始化顺序解释为普通 struct 的物理字段顺序。布局的具体结果由目标、类型和明确表示配置确定；没有指定的默认布局保证不从 C 补入。
6. 这套规则只决定构造输入、求值与完整性。途中失败后的资源清理、默认表达式能否使用部分构造对象等，按资源与初始化专题补齐，不在这里推导自动回滚或提前可用的 self。

- **A. 采用上述基线（建议）。** 构造行为可逐字段解释，不隐含默认填充；示例可检验副作用顺序与被覆盖默认值不执行。
- **B. 缺失字段也可自动由某种默认机制补齐。** 需要指定调用入口及适用条件，不能只借当前存在字段默认语法来推定。
- **C. 默认表达式在类型构造/定义时先算成共享默认值。** 会改变可变值和有行为表达式的观察结果；需说明每次实例构造是复制、共享还是再构造。

**预填答复：A。** 标签决定字段对应，声明顺序决定初始化次序；没有显式输入且没有声明默认值就是错误。默认表达式按每次构造的实际需要求值，不额外设计隐式默认 trait。

### 1. 从用户的问题进入

读者首先应能回答：

- 一个类型名指的是什么；另一个同样字段的声明是否就是同一个类型。
- 一个值为什么能或不能交给某个参数；这种接纳是否会构造新的值。
- 泛型代码尚不知道具体类型时，凭什么能调用某个成员。
- 行、闭包环境和 runtime 依赖各自在类型中保留哪类信息。
- 某条操作在哪里检查；暂时未知时还有什么合法的继续方式。

总览用短例建立这些区别，随后再读理论和算法。不能要求 C 开发者先理解 EUF、CMTT 或整个 PTC 原子表，才知道怎么声明一个类型。

### 3. 七段骨架怎样落实

每篇仍采用 Intro、语法、正式定义、常见示例、跨语言差异、运行时实现引导、编译器实现引导。每篇有自己的内容重点：

- **Intro：** 一两个具体观察建立心智模型，不堆“支持哪些特性”的清单。
- **语法：** 只列本篇用到的轻量产生式；采用作者已确认的现行形式，不能复制旧备忘后再让读者猜哪里过时。
- **正式定义：** 给出可检验的成功条件和拒绝条件；例如什么同型、何时发生包装、什么信息缺失会阻止操作。
- **示例：** 每例承担一项推理任务；能从正式定义独立判断结果，不依赖作者私有库或被省略的资源契约。
- **跨语言差异：** 编写时核查实际对应物，只比较本版已决定的 Flurry 行为；不把文档目录或内部实现当差异。
- **运行时引导：** 对实际需要的表示、传递、环境与分支处理给出前后条件。只在编译时存在的机制就准确说明其目标程序后果，不虚构额外运行时。
- **编译器引导：** 说明操作输入、依赖事实、残余义务、实例交付条件与错误原因；核心算法保留 worklist、回滚、终止条件和未覆盖片段，不指向现有源码函数。

PTC 的 19 类原子模式和 11 个模块应形成可追溯的完整表；ROW 按 041 暂定方案修订适用域。公开谓词可通过派生规则扩展，不能在导览写成“只有 19 个 predicate”。Split、扩展、嵌入证据与布尔原子的区别要保留。
