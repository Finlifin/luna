## 一、先建立全貌

我建议这一主题用三个彼此连接、但不能混为一谈的对象组织：

1. **值的可用状态**：这个位置是否初始化，是否已经移出，能否再观察、复制或消耗？
2. **清理责任**：谁负责结束这个资源，责任在移动、分支和错误退出中怎样传递？
3. **内存与依赖有效性**：指针或视图实际依赖哪个区域、哪个世代；执行操作以后哪些访问仍成立？

这会直接影响文档写法。Once 不宜解释成“任何操作只能做一次”；move 不宜统一解释为 kill；Clone 不宜统一解释为完全独立深复制；Copy 也不能仅由 sizeof 和字段位表示决定。

你先前明确的方向继续保留：只有指针，不引入另一套借用指针语法；memory-effect predicate 是 safe 也能使用的程序规格，不标 comptime；safe 自动推理限制在三次以内多元多项式算术，能力外通过受 runtime verification 支撑的 assumes 接合。这里的“三次”是总次数，不是每个变量各允许三次。

九月 memory 草稿中的具体区域推导、Clone/Copy 条款和清理算法仍要区分作者原意与助手补充。本轮把需要落为资源契约的部分单独列出来，不因为已写在 proposal 里就全部认定为定稿。

## 三、本轮预填

### M1. Once 的“一次”限制消耗，还是限制所有使用？

现行 [once-clone-copy.md](/home/fin/luna/docs/resource-management/once-clone-copy.md) 写“至多使用一次（被消耗或销毁）”。这个表达容易让读者以为读取一次就不能再读取。

候选例，假设 Ticket 没有 Copy 实现：

~~~flurry
struct Ticket {
    code: u32,

    fn inspect(*self) -> u32 {
        self.code
    }
}

fn finish(ticket: Ticket) {
    println("finished: {}", ticket.code);
}

test {
    let ticket = Ticket { code: 7 }
    println("{}", ticket.inspect());
    println("{}", ticket.inspect());
    finish(ticket);
    -- 此后不能再次读取或移出 ticket。
}
~~~

- A. Once 约束按值消耗或终结；仍可进行满足契约的多次观察和修改（建议）。非 Copy 交付迁移可用状态及责任，源位置变成 moved-out。
- B. 除显式豁免外，任何使用都消耗一次额度。需要为所有观察操作建立额外恢复/借用协议，和现有 *self 用法不自然。
- C. Once 要求恰好消耗一次。将从仿射走向线性要求，需要明确定义不需要清理的值为何不能直接离开作用域。

**助手预填：A。** 类型默认具备仿射使用边界。自动清理兑现剩余责任，不意味着每次读取都移动整个值。Once 的标记证据不等于已经证明所有 memory-effect 操作合法。

### M2. 名义聚合的 Copy 怎样取得？

当前正文一方面把“只包含 Copy 字段的结构体”列为常见 Copy 类型，另一方面又展示显式 derive。它没有说字段条件是自动取得能力，还是只说明能够派生。

- A. 内建类型按定义提供；用户名义类型通过显式 impl/derive 取得，字段与资源条件决定能否接受（建议）。新增字段可能使原 derive 失败，而不是悄悄改变源代码的移动语义。
- B. 只要全部字段可 Copy 且没有冲突责任，就自动推导 Copy。省声明，但类型实现细节改变可能使普通赋值语义改变。
- C. 由类型属性显式选择结构化自动推导。需要一个额外控制入口；若 derive 已足够，收益有限。

**助手预填：A。** “全部字段 Copy”是结构派生的必要检查之一，不是充分的资源正确性证明。拥有唯一释放责任的包装不能靠指针字段可复制就取得 Copy。Copy 的隐式复制不调用任意用户 clone 方法；它必须满足无额外用户副作用的表示复制契约。

能力层次建议保留 `Copy :- Clone :- Once`，但不要求语言通过执行 clone 来实现 Copy。显式 clone 必须满足接口的值语义契约，不能反过来授权复制独占责任。

### M3. Clone 保证什么：完全独立，还是按实现契约产生新值？

当前正文明确写 Clone 是“深拷贝——一个完全独立的、拥有自己资源的新副本”。memory 草稿则有指针包装的 Clone、引用计数式共享，以及复制依赖字段仍然指向原存储的例子。

~~~flurry
struct NumberView {
    pointer: *i32,

    fn read(*self) -> i32 {
        self.*.pointer.*
    }
}

impl Clone for NumberView {
    fn clone(*self) -> Self {
        Self { pointer: self.pointer.* }
    }
}

test {
    var number = 3i32;
    let first = NumberView { pointer: number.ref }
    let second = first.clone();
    number = 4i32;
    println("{} {}", first.read(), second.read());
}
~~~

- A. Clone 显式产生新的合法值，其共享关系、效果和依赖由实现契约说明；不统一保证深复制（建议）。候选输出为 `4 4`。
- B. Clone 必须切断与源值的所有资源共享。上述实现非法，指针或引用计数复制需要另一接口。
- C. 区分两种语言级克隆能力，一种共享、一种深复制。表达更细，但会增加接口、派生及泛型要求的复杂度。

**助手预填：A。** 是否分配新缓冲区由具体类型契约决定。聚合派生 Clone 不只是逐字段调用：字段之间有依赖时，必须验证复制后的关系；无法证明时要求手写重建。复制 storage 后直接复制 view，不能自动宣称 view 指向新 storage。

### M4. let/var 管重新绑定，还是也决定指针写许可？

现行 [bindings.md](/home/fin/luna/docs/resource-management/bindings.md) 对 var 的可变性分工留有说明；已有多份例子则用 let 保存容器，再调用 *self 方法修改内容。

~~~flurry
struct Cell {
    value: u32,
}

test {
    let cell = Cell { value: 1 }
    let pointer = cell.ref;
    pointer.value.* = 2;
    println("{}", cell.value);
}
~~~

- A. let 禁止把该名称重新绑定到另一个值；对象或字段写入由指针、memory effect 和有效性契约检查（建议，符合已有用法）。上述修改可以合法，不能由 let 推出深层只读。
- B. let 使本体及其子位置不可修改；通过它取得的指针也必须保留只读约束。需要修改既有 let 容器写入例，并明确单一 *T 下许可怎样表达。
- C. let 固定本体，但外部间接资源可修改。需要精确定义本体边界；同一容器方法写描述符和写缓冲区可能得到不同许可。

**助手预填：A。** var 允许替换绑定值；替换已有资源仍须清理旧值。const 的编译时值契约另按 comptime 规则处理，不能把 let 等同于 const。

这不是授予任意指针随意写入的许可：对象有效性、别名相关事实、方法规格和区域状态仍需检查。

### M5. move 与 kill 是否正式分开？

你的 String 例子需要区分描述符与字符分配。移动描述符可以转交字符分配的责任，而不搬迁这块分配；另一方面，对局部槽位取址后不能默认地址会随移动修复。

- A. move 迁移值状态和责任；kill 表示相关区域或世代终结，是否发生由实际操作决定（建议）。视图沿真实目标判断，不沿变量赋值历史串依赖。
- B. 非 Copy 移动保守地使所有关联视图失效。实现容易，但会拒绝大量只转移描述符的容器用法。
- C. move 自动更新指向原值及内部资源的全部视图。需要可重定位引用或运行时重写，不适合作为普通指针默认语义。

**助手预填：A。** 普通 write 撤销受影响的内容事实，不自动终结目标槽位。扩容若可能替换缓冲区，则旧世代视图不能继续使用；只检查新容器长度足够也不能修复它。涉及内联自引用时，普通 move 不自动修复内部地址。

### M6. 可观察的清理时机与顺序是什么？

现行 [drop-elaboration.md](/home/fin/luna/docs/resource-management/drop-elaboration.md) 一处按离开作用域插入 drop，末尾又说“资源在不再需要时立即释放”。两者对有日志、锁、事务或 allocator 效果的 Drop 不是同一种语义。

- A. 以确定的作用域/责任结束点为基线，局部值按完成初始化的逆序清理；提前清理只有在保持可观察行为时作为优化（建议）。最后一次普通读取不自动定义析构点。
- B. 以最后一次使用定义清理点。需要把未来清理自身的依赖也纳入使用分析，且编辑一处后续使用会改变可观察析构时机。
- C. 每类资源声明自己的清理策略。表达空间更大，但要为未标记值和组合聚合再定义默认规则。

**助手预填：A。** 正常块退出、return、错误传播、break/continue 和被终止的计算都沿实际退出边清理。移动之后源位置不再清理；重新赋值前结束旧值责任。临时值另按完整表达式及实际延长规则收束，不能由优化器任意决定。

候选验收：创建日志资源 A，再创建 B，正常退出应观察 B、A；中途把 A 移到调用方后，本地只清理 B。若 B 的 Drop 读取 A，则 A 的有效性必须覆盖该实际清理调用。

### M7. 用户 Drop、字段清理与部分移出怎样组合？

当前正文只说明“没有 Drop 时递归 drop 字段”，没有确定用户 Drop 存在时是否仍自动清理字段。这决定手写 Drop 到底负责整个聚合，还是只负责额外行为。

- A. 用户 Drop 先执行，随后自动清理仍已初始化的字段；没有用户 Drop 时直接清理字段（建议）。用户 Drop 若显式移走字段，状态更新必须阻止再次清理。
- B. 提供 Drop 后由用户负责全部字段清理。契约直接，但每个资源聚合都容易遗漏字段，派生也需不同路径。
- C. Drop 只描述资源效果，字段清理由另一显式接口决定。机制更分散，暂未看到必须如此拆分的收益。

**助手预填：A。** 字段清理按实际成功初始化的逆序进行，失败初始化只清理已完成部分。未初始化与已移出都不能调用该字段的 Drop。

对外部代码部分移出具有用户 Drop 的聚合，我建议首版拒绝，除非操作本身提供可验证的重建/责任转移契约；否则析构主体可能读取已经不存在的字段。没有用户 Drop 的结构可以按字段维护初始化位并只清理剩余字段。此处不引入新的源码状态标记。

### M8. Drop 的错误、效应与依赖如何进入退出路径？

上一主题已经确定：需要环境的 Drop 在清理责任建立时绑定证据，移动时传递，不在销毁现场搜索 space/allocator。本题只补其执行结果与作用域。

- A. 保持 `fn drop(*self)` 的 void 结果，清理不能新增未声明的可恢复错误；允许接口与清理位置能够兑现的效应和 memory effects（建议）。所有隐式清理都进入函数摘要和 handler 路由检查。
- B. Drop 可以返回错误，由退出路径自动合并。需要定义正常结果与析构错误、原错误与二次错误的优先级，不能仅写成错误行并集。
- C. Drop 必须无效应，只允许受限释放原语。简化控制流，但难以表达现有依赖 allocator 或系统资源的实现。

**助手预填：A。** void 不代表纯函数；释放、日志及外部资源动作仍有实际效果。但允许效应的前提是 Drop 的接口契约确实表达了可交付需求，不能通过 impl 私自强化调用要求。不能在尚未定义的异常二次失败策略上承诺任意 Drop 永不失败。

handler 离开前还是离开后执行内部资源清理，应按该控制边界的退出次序固定；我建议内部资源清理仍处于其有效的处理环境，最后再结束 handler 自身责任。续延若被放弃，必须兑现它持有的剩余清理责任；multi-shot 不能仅复制这些责任的位表示。

## 四、默认推导怎样减轻 notation

我的建议是先让下面的过程成为统一候选，而不是要求用户手写每个位置的资源注解：

~~~text
检查普通操作的实际状态转移
  -> 补入每条退出边的清理动作
  -> 合成内存效果、结果依赖及责任转移摘要
  -> 若有显式规格，检查实际摘要被它允许
  -> 在函数、闭包和动态接口边界交付所需摘要与证据
~~~

有显式 outcomes 仍应检查真实行为；它不使推导停止。高阶函数必须组合回调的实际状态转移，不能因为同一种 effect 标签在集合中只出现一次，就把调用两次消耗资源误算成一次。

safe 的三次多项式上限限制静态自动推理片段，不限制用户程序只能计算三次多项式。assumes 也不产生所有权、不复活 moved-out 值；动态检查应在非法读取或溢出之前执行，其事实只在成功边和相关状态仍有效时可用。

## 一、先建立全貌

我建议这一主题用三个彼此连接、但不能混为一谈的对象组织：

1. **值的可用状态**：这个位置是否初始化，是否已经移出，能否再观察、复制或消耗？
2. **清理责任**：谁负责结束这个资源，责任在移动、分支和错误退出中怎样传递？
3. **内存与依赖有效性**：指针或视图实际依赖哪个区域、哪个世代；执行操作以后哪些访问仍成立？

这会直接影响文档写法。Once 不宜解释成“任何操作只能做一次”；move 不宜统一解释为 kill；Clone 不宜统一解释为完全独立深复制；Copy 也不能仅由 sizeof 和字段位表示决定。

你先前明确的方向继续保留：只有指针，不引入另一套借用指针语法；memory-effect predicate 是 safe 也能使用的程序规格，不标 comptime；safe 自动推理限制在三次以内多元多项式算术，能力外通过受 runtime verification 支撑的 assumes 接合。这里的“三次”是总次数，不是每个变量各允许三次。

九月 memory 草稿中的具体区域推导、Clone/Copy 条款和清理算法仍要区分作者原意与助手补充。本轮把需要落为资源契约的部分单独列出来，不因为已写在 proposal 里就全部认定为定稿。

## 三、本轮预填

### M1. Once 的“一次”限制消耗，还是限制所有使用？

现行 [once-clone-copy.md](/home/fin/luna/docs/resource-management/once-clone-copy.md) 写“至多使用一次（被消耗或销毁）”。这个表达容易让读者以为读取一次就不能再读取。

候选例，假设 Ticket 没有 Copy 实现：

~~~flurry
struct Ticket {
    code: u32,

    fn inspect(*self) -> u32 {
        self.code
    }
}

fn finish(ticket: Ticket) {
    println("finished: {}", ticket.code);
}

test {
    let ticket = Ticket { code: 7 }
    println("{}", ticket.inspect());
    println("{}", ticket.inspect());
    finish(ticket);
    -- 此后不能再次读取或移出 ticket。
}
~~~

- A. Once 约束按值消耗或终结；仍可进行满足契约的多次观察和修改（建议）。非 Copy 交付迁移可用状态及责任，源位置变成 moved-out。
- B. 除显式豁免外，任何使用都消耗一次额度。需要为所有观察操作建立额外恢复/借用协议，和现有 *self 用法不自然。
- C. Once 要求恰好消耗一次。将从仿射走向线性要求，需要明确定义不需要清理的值为何不能直接离开作用域。

**助手预填：A。** 类型默认具备仿射使用边界。自动清理兑现剩余责任，不意味着每次读取都移动整个值。Once 的标记证据不等于已经证明所有 memory-effect 操作合法。

消耗就是消耗，然后在我们希望多次使用数据时，引出Clone、Copy和引用系统，进一步引出引用的有效性系统。

### M2. 名义聚合的 Copy 怎样取得？

当前正文一方面把“只包含 Copy 字段的结构体”列为常见 Copy 类型，另一方面又展示显式 derive。它没有说字段条件是自动取得能力，还是只说明能够派生。

- A. 内建类型按定义提供；用户名义类型通过显式 impl/derive 取得，字段与资源条件决定能否接受（建议）。新增字段可能使原 derive 失败，而不是悄悄改变源代码的移动语义。
- B. 只要全部字段可 Copy 且没有冲突责任，就自动推导 Copy。省声明，但类型实现细节改变可能使普通赋值语义改变。
- C. 由类型属性显式选择结构化自动推导。需要一个额外控制入口；若 derive 已足够，收益有限。

**助手预填：A。** “全部字段 Copy”是结构派生的必要检查之一，不是充分的资源正确性证明。拥有唯一释放责任的包装不能靠指针字段可复制就取得 Copy。Copy 的隐式复制不调用任意用户 clone 方法；它必须满足无额外用户副作用的表示复制契约。

能力层次建议保留 `Copy :- Clone :- Once`，但不要求语言通过执行 clone 来实现 Copy。显式 clone 必须满足接口的值语义契约，不能反过来授权复制独占责任。

### M3. Clone 保证什么：完全独立，还是按实现契约产生新值？

当前正文明确写 Clone 是“深拷贝——一个完全独立的、拥有自己资源的新副本”。memory 草稿则有指针包装的 Clone、引用计数式共享，以及复制依赖字段仍然指向原存储的例子。

~~~flurry
struct NumberView {
    pointer: *i32,

    fn read(*self) -> i32 {
        self.*.pointer.*
    }
}

impl Clone for NumberView {
    fn clone(*self) -> Self {
        Self { pointer: self.pointer.* }
    }
}

test {
    var number = 3i32;
    let first = NumberView { pointer: number.ref }
    let second = first.clone();
    number = 4i32;
    println("{} {}", first.read(), second.read());
}
~~~

- A. Clone 显式产生新的合法值，其共享关系、效果和依赖由实现契约说明；不统一保证深复制（建议）。候选输出为 `4 4`。
- B. Clone 必须切断与源值的所有资源共享。上述实现非法，指针或引用计数复制需要另一接口。
- C. 区分两种语言级克隆能力，一种共享、一种深复制。表达更细，但会增加接口、派生及泛型要求的复杂度。

**助手预填：A。** 是否分配新缓冲区由具体类型契约决定。聚合派生 Clone 不只是逐字段调用：字段之间有依赖时，必须验证复制后的关系；无法证明时要求手写重建。复制 storage 后直接复制 view，不能自动宣称 view 指向新 storage。

### M4. let/var 管重新绑定，还是也决定指针写许可？

现行 [bindings.md](/home/fin/luna/docs/resource-management/bindings.md) 对 var 的可变性分工留有说明；已有多份例子则用 let 保存容器，再调用 *self 方法修改内容。

~~~flurry
struct Cell {
    value: u32,
}

test {
    let cell = Cell { value: 1 }
    let pointer = cell.ref;
    pointer.value.* = 2;
    println("{}", cell.value);
}
~~~

- A. let 禁止把该名称重新绑定到另一个值；对象或字段写入由指针、memory effect 和有效性契约检查（建议，符合已有用法）。上述修改可以合法，不能由 let 推出深层只读。
- B. let 使本体及其子位置不可修改；通过它取得的指针也必须保留只读约束。需要修改既有 let 容器写入例，并明确单一 *T 下许可怎样表达。
- C. let 固定本体，但外部间接资源可修改。需要精确定义本体边界；同一容器方法写描述符和写缓冲区可能得到不同许可。

**助手预填：A。** var 允许替换绑定值；替换已有资源仍须清理旧值。const 的编译时值契约另按 comptime 规则处理，不能把 let 等同于 const。

这不是授予任意指针随意写入的许可：对象有效性、别名相关事实、方法规格和区域状态仍需检查。

### M5. move 与 kill 是否正式分开？

你的 String 例子需要区分描述符与字符分配。移动描述符可以转交字符分配的责任，而不搬迁这块分配；另一方面，对局部槽位取址后不能默认地址会随移动修复。

- A. move 迁移值状态和责任；kill 表示相关区域或世代终结，是否发生由实际操作决定（建议）。视图沿真实目标判断，不沿变量赋值历史串依赖。
- B. 非 Copy 移动保守地使所有关联视图失效。实现容易，但会拒绝大量只转移描述符的容器用法。
- C. move 自动更新指向原值及内部资源的全部视图。需要可重定位引用或运行时重写，不适合作为普通指针默认语义。

**助手预填：A。** 普通 write 撤销受影响的内容事实，不自动终结目标槽位。扩容若可能替换缓冲区，则旧世代视图不能继续使用；只检查新容器长度足够也不能修复它。涉及内联自引用时，普通 move 不自动修复内部地址。

### M6. 可观察的清理时机与顺序是什么？

现行 [drop-elaboration.md](/home/fin/luna/docs/resource-management/drop-elaboration.md) 一处按离开作用域插入 drop，末尾又说“资源在不再需要时立即释放”。两者对有日志、锁、事务或 allocator 效果的 Drop 不是同一种语义。

- A. 以确定的作用域/责任结束点为基线，局部值按完成初始化的逆序清理；提前清理只有在保持可观察行为时作为优化（建议）。最后一次普通读取不自动定义析构点。
- B. 以最后一次使用定义清理点。需要把未来清理自身的依赖也纳入使用分析，且编辑一处后续使用会改变可观察析构时机。
- C. 每类资源声明自己的清理策略。表达空间更大，但要为未标记值和组合聚合再定义默认规则。

**助手预填：A。** 正常块退出、return、错误传播、break/continue 和被终止的计算都沿实际退出边清理。移动之后源位置不再清理；重新赋值前结束旧值责任。临时值另按完整表达式及实际延长规则收束，不能由优化器任意决定。

候选验收：创建日志资源 A，再创建 B，正常退出应观察 B、A；中途把 A 移到调用方后，本地只清理 B。若 B 的 Drop 读取 A，则 A 的有效性必须覆盖该实际清理调用。

### M7. 用户 Drop、字段清理与部分移出怎样组合？

当前正文只说明“没有 Drop 时递归 drop 字段”，没有确定用户 Drop 存在时是否仍自动清理字段。这决定手写 Drop 到底负责整个聚合，还是只负责额外行为。

- A. 用户 Drop 先执行，随后自动清理仍已初始化的字段；没有用户 Drop 时直接清理字段（建议）。用户 Drop 若显式移走字段，状态更新必须阻止再次清理。
- B. 提供 Drop 后由用户负责全部字段清理。契约直接，但每个资源聚合都容易遗漏字段，派生也需不同路径。
- C. Drop 只描述资源效果，字段清理由另一显式接口决定。机制更分散，暂未看到必须如此拆分的收益。

**助手预填：A。** 字段清理按实际成功初始化的逆序进行，失败初始化只清理已完成部分。未初始化与已移出都不能调用该字段的 Drop。

对外部代码部分移出具有用户 Drop 的聚合，我建议首版拒绝，除非操作本身提供可验证的重建/责任转移契约；否则析构主体可能读取已经不存在的字段。没有用户 Drop 的结构可以按字段维护初始化位并只清理剩余字段。此处不引入新的源码状态标记。

### M8. Drop 的错误、效应与依赖如何进入退出路径？

上一主题已经确定：需要环境的 Drop 在清理责任建立时绑定证据，移动时传递，不在销毁现场搜索 space/allocator。本题只补其执行结果与作用域。

- A. 保持 `fn drop(*self)` 的 void 结果，清理不能新增未声明的可恢复错误；允许接口与清理位置能够兑现的效应和 memory effects（建议）。所有隐式清理都进入函数摘要和 handler 路由检查。
- B. Drop 可以返回错误，由退出路径自动合并。需要定义正常结果与析构错误、原错误与二次错误的优先级，不能仅写成错误行并集。
- C. Drop 必须无效应，只允许受限释放原语。简化控制流，但难以表达现有依赖 allocator 或系统资源的实现。

**助手预填：A。** void 不代表纯函数；释放、日志及外部资源动作仍有实际效果。但允许效应的前提是 Drop 的接口契约确实表达了可交付需求，不能通过 impl 私自强化调用要求。不能在尚未定义的异常二次失败策略上承诺任意 Drop 永不失败。

handler 离开前还是离开后执行内部资源清理，应按该控制边界的退出次序固定；我建议内部资源清理仍处于其有效的处理环境，最后再结束 handler 自身责任。续延若被放弃，必须兑现它持有的剩余清理责任；multi-shot 不能仅复制这些责任的位表示。

## 四、默认推导怎样减轻 notation

我的建议是先让下面的过程成为统一候选，而不是要求用户手写每个位置的资源注解：

~~~text
检查普通操作的实际状态转移
  -> 补入每条退出边的清理动作
  -> 合成内存效果、结果依赖及责任转移摘要
  -> 若有显式规格，检查实际摘要被它允许
  -> 在函数、闭包和动态接口边界交付所需摘要与证据
~~~

有显式 outcomes 仍应检查真实行为；它不使推导停止。高阶函数必须组合回调的实际状态转移，不能因为同一种 effect 标签在集合中只出现一次，就把调用两次消耗资源误算成一次。

safe 的三次多项式上限限制静态自动推理片段，不限制用户程序只能计算三次多项式。assumes 也不产生所有权、不复活 moved-out 值；动态检查应在非法读取或溢出之前执行，其事实只在成功边和相关状态仍有效时可用。

这部分先作为后续章的推导方向，不在本轮直接决定所有 memory view 表面 API。你可以先改 M1–M8；采用后，我再围绕覆盖赋值、部分初始化、高阶回调和清理环境给出下一轮更具体的代码。
